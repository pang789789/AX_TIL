# 📚 오늘의 학습 기록: NLP 텍스트 분류 개선 & DB 트랜잭션 정합성

오늘은 파이썬을 활용한 텍스트 분류 모델의 전처리 과정과, 데이터베이스의 신뢰성을 지키는 트랜잭션(Transaction) 개념을 함께 파고들었다. 눈으로만 보는 코드가 아니라, 실제로 '실행'해보고 '검증'하는 과정의 중요성을 뼈저리게 느낀 세션이었다.

---

## 💡 Part 1. 머신러닝 모델 전처리와 검증 (Chapter 07)

텍스트 분류 모델을 개선하기 위해 데이터를 뜯어보고, 형태소 분석기를 도입해 기준점(Baseline)과 성능을 비교해보았다.

**🤔 나의 질문:** 
"단순히 띄어쓰기 기준으로 단어를 쪼개서 학습시키면 안 되나요? 왜 굳이 형태소 분석기를 써서 전처리를 해야 하죠?"

**🤖 AI의 답변:**
"띄어쓰기만 기준으로 삼으면 '파이썬은', '파이썬이', '파이썬을'이 모두 다른 단어로 인식되어서 노이즈가 심해집니다. `Kiwi` 같은 형태소 분석기를 사용해 NNG(일반 명사), NNP(고유 명사), SL(영문) 등 뼈대가 되는 핵심 토큰만 추출하면, 모델(TF-IDF)이 훨씬 더 정확하게 문서의 특징을 파악할 수 있어요."

**🤔 나의 질문:**
"불용어(Stopwords) 처리를 많이 할수록 성능이 무조건 좋아지는 건가요?"

**🤖 AI의 답변:**
"그렇지 않습니다! 오늘 실습에서도 '에디션' 같은 단어를 제거했을 때 극적인 성능 향상은 없었죠. 데이터 보강, 텍스트 표현 방식, 모델 로직 등 여러 요소가 얽혀 있기 때문에, 전처리를 한 번에 왕창 하기보다는 **작은 변경을 적용한 뒤 반드시 성능(Accuracy, F1 Score 등)을 다시 측정**하며 비교하는 것이 중요합니다."

### 📝 알아낸 내용 (Takeaways)
*   **Baseline의 중요성:** 개선 전 기준점(Baseline Accuracy: 48.74%)이 있어야, 나의 전처리가 실제로 유효했는지(Improved Accuracy: 51.26%) 객관적으로 증명할 수 있다.
*   **추천 시스템의 맹점:** 코사인 유사도가 0임에도 무조건 상위 5개를 뱉어내는 기존 로직의 허점을 발견했다. 코드가 에러 없이 돌아간다고 해서 올바른 비즈니스 로직을 수행하는 것은 아니다.

## 💡 Part 2. 데이터 정합성과 트랜잭션 (Chapter 09)

수강신청 시스템을 예시로, 다중 테이블(좌석, 신청, 결제)의 데이터 상태를 완벽하게 일치시키는 트랜잭션 설계 방법을 학습했다.

**🤔 나의 질문:**
"수강신청 과정에서 1. 좌석 차감, 2. 신청 정보 생성, 3. 결제 정보 생성... 이 세 가지를 따로따로 DB에 저장하면 어떤 문제가 생기나요?"

**🤖 AI의 답변:**
"만약 1번(좌석 차감)은 성공했는데, 네트워크 오류로 2번과 3번이 실패했다고 가정해 보세요. 실제 수강생은 없는데 좌석만 줄어드는 심각한 데이터 불일치(정합성 파괴)가 발생합니다. 트랜잭션은 이 세 가지 과정을 하나의 묶음으로 처리해서, **모두 성공하면 확정(`COMMIT`)하고, 하나라도 실패하면 전부 원래대로 되돌리는(`ROLLBACK`) 역할**을 합니다."

**🤔 나의 질문:**
"두 명이 동시에 남은 좌석 1개를 차지하려고 누르면 어떻게 되나요? 데드락(Deadlock)이라는 단어가 있던데."

**🤖 AI의 답변:**
"동시성 제어를 위해 `SELECT ... FOR UPDATE`를 사용해 대상 행을 잠금(Lock) 처리합니다. 한 사람이 좌석을 확보해 트랜잭션을 진행 중이면, 다른 사람은 그 트랜잭션이 끝날 때까지 대기하게 되죠. 데드락은 서로가 서로의 잠금이 풀리기만을 무한정 기다리는 '순환 대기' 상태를 말합니다. 이를 막기 위해서는 항상 같은 순서로 자원에 접근하고 트랜잭션을 최대한 짧게 유지해야 합니다."

### 📝 알아낸 내용 (Takeaways)
*   **ACID 특성:** 트랜잭션의 4대 요소. 모두 반영/취소되거나(Atomicity), 규칙에 맞거나(Consistency), 서로 간섭하지 않거나(Isolation), 영구히 저장되어야(Durability) 한다.
*   **영향 행 수 검증:** 단순히 `UPDATE` 문을 실행했다고 끝이 아니라, `RETURNING` 등을 통해 실제로 업데이트된 행(Row)의 수가 의도한 바와 일치하는지 확인하고 `COMMIT` 해야 완벽한 정합성을 지킬 수 있다.
