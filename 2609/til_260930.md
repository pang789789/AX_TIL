## Chapter 10 확장 실습 — 실행 계획으로 인덱스 효과 검증하기

### 📌 학습 개요
- **목표**: PostgreSQL 실행 계획(`EXPLAIN ANALYZE`)을 활용하여 인덱스 생성 전후의 성능(비용, 행 수, Buffers, 실행 시간)을 측정·비교하고, 인덱스의 유지/보류/제거 여부를 판단.
- **주요 실습 환경**: PostgreSQL (기준 버전: PostgreSQL 16), DBeaver, GitHub
- **실습 스키마**: `performance_lab` (대량 성능 실험용 데이터)

---

### 🛠️ 전체 진행 순서 & Key Points

1. **STEP 1. PostgreSQL 버전 및 시작 상태 확인**
   - DB 버전, database, user, schema, search_path 확인 및 기록.
   - *참고*: PostgreSQL 16과 18+(B-tree Skip Scan 도입)은 실행 계획이 다를 수 있으므로 버전을 반드시 기록.

2. **STEP 2. 성능 실험 전용 `performance_lab` 준비**
   - 소규모 데이터셋에서는 `Seq Scan`이 효율적일 수 있으므로, 대량 테스트 데이터 구축.
   - **데이터 규모**: `students` (10,003행), `instructors` (2행), `courses` (2,003행), `enrollments` (100,005행)
   - **데이터 분포 예시**: `status = '수강중'` 조건은 전체 데이터의 약 30%(30,001행) 차지.

3. **STEP 3. 인덱스 생성 전 기준 실행 계획 기록**
   - 후보 인덱스를 생성하기 전 `EXPLAIN (ANALYZE, BUFFERS)`를 사용하여 베이스라인 측정.
   - 측정 지표: `Seq Scan`, `cost`, `actual rows`, `Buffers hit/read`, `Execution Time` 등.

4. **STEP 4~6. 후보 인덱스 생성 및 사후 재측정**
   - **후보 인덱스**:
     - `idx_performance_courses_title`
     - `idx_performance_enrollments_student_id`
     - `idx_performance_enrollments_course_status`
   - 동일 조건(데이터, SQL, 통계)에서 인덱스 생성 후 재측정하여 Before / After 비교표 작성.

5. **STEP 7~9. 실행 계획 해석 및 관찰**
   - **Seq Scan 선택 이유**: 전체 데이터의 약 30%처럼 많은 행을 읽어야 하는 경우 인덱스보다 Table Scan이 더 빠르다고 판단될 수 있음 (인덱스 미사용 != 실패).
   - **`ORDER BY` + `LIMIT`**: 인덱스 정렬 순서 활용 시 별도의 전체 `Sort` 노드 없이 빠른 응답 가능.
   - **`rows` vs `actual rows`**: 옵티마이저의 추정치와 실제 행 수 차이 확인.

6. **STEP 10~11. 인덱스 정의/비용 검토 및 유지 여부 결정**
   - 인덱스는 **CUD(INSERT, UPDATE, DELETE)** 작업 및 디스크 용량 비용을 수반함.
   - `idx_scan = 0`이라고 바로 삭제하기보다는 업무 패턴 및 제약조건 여부를 판단하여 유지 / 보류 / 제거 결정.

7. **STEP 12~13. 자동 완료 게이트 & 인덱스 만능론 반박**
   - 무조건적인 인덱스 추가, 선택도/규모를 고려하지 않은 `Index Scan` 신봉 등 잘못된 통념을 실행 계획 근거로 반박.

8. **STEP 14~15. 개인 프로젝트 적용 & AI 리뷰**
   - 본인 프로젝트의 주요 조회 패턴 2가지 도출 및 후보 인덱스 근거 작성.
   - AI를 인덱스 단순 추천기가 아닌 **실행 계획 리뷰어**로 활용하여 검토 후 최종 반영.
