# PostgreSQL과 DBeaver 환경 설정 및 기본 사용법

## 1. 학습목표

* PostgreSQL과 DBeaver의 역할을 구분한다.
* 자신의 환경에 맞는 설치 경로를 선택한다.
* PostgreSQL 서버의 실행 상태를 확인한다.
* DBeaver에서 PostgreSQL 연결을 만든다.
* Host, Port, Database, Username의 의미를 설명한다.
* `ai_database_book` 데이터베이스를 확인하고 필요한 경우 생성한다.
* 새 데이터베이스로 연결을 전환한다.
* 현재 데이터베이스, 사용자, 스키마와 검색 경로를 확인한다.
* SQL 한 문장, 선택 영역, 전체 스크립트 실행을 구분한다.
* 환경 확인 SQL과 자동 확인 SQL을 실행한다.
* 연결 오류를 유형별로 분류하고 다시 확인한다.
* 비밀번호와 전체 접속 URL을 공개 자료에서 분리한다.

# 2. PostgreSQL과 DBeaver의 역할

PostgreSQL과 DBeaver는 서로 대체하는 프로그램이 아니다.

둘은 **데이터베이스를 사용하는 서로 다른 역할**을 담당한다.

## 2.1 PostgreSQL

PostgreSQL은 **데이터베이스 관리 시스템(DBMS)**이다.

쉽게 말하면 실제로 데이터를 저장하고 SQL을 처리하는 **데이터베이스 서버**이다.

주요 역할:

* 데이터베이스 생성 및 관리
* 테이블 생성 및 관리
* 데이터 저장 및 조회
* SQL 실행
* 사용자 및 권한 관리
* 트랜잭션 처리
* 데이터의 일관성 유지

즉,

> PostgreSQL = 실제 데이터베이스를 관리하고 SQL을 실행하는 서버

---

## 2.2 DBeaver

DBeaver는 **데이터베이스 클라이언트/GUI 도구**이다.

PostgreSQL 자체가 아니라 PostgreSQL 서버에 접속하여 데이터베이스를 편리하게 관리할 수 있도록 해주는 프로그램이다.

주요 역할:

* 데이터베이스 서버 연결
* SQL 작성 및 실행
* 테이블과 스키마 탐색
* 데이터 조회 및 편집
* SQL 결과 확인
* 데이터베이스 구조 확인

즉,

> DBeaver = PostgreSQL 서버에 접속하여 사용하기 위한 화면과 도구

---

## 2.3 둘의 관계

```text
[사용자]
   ↓
[DBeaver]
   ↓
PostgreSQL 연결
   ↓
[PostgreSQL 서버]
   ↓
[Database]
   ↓
[Table / Data]
```

DBeaver가 데이터를 직접 저장하는 것이 아니다.

DBeaver에서 SQL을 실행하면 PostgreSQL 서버로 SQL이 전달되고, PostgreSQL이 SQL을 처리한 결과를 DBeaver가 보여준다.

### 핵심 정리

| 구분     | PostgreSQL       | DBeaver                |
| ------ | ---------------- | ---------------------- |
| 종류     | DBMS / 데이터베이스 서버 | 데이터베이스 클라이언트           |
| 역할     | 데이터 저장 및 SQL 처리  | 서버 접속 및 관리             |
| 데이터 저장 | O                | X                      |
| SQL 실행 | O                | SQL을 서버에 전달            |
| GUI    | 기본적인 관리 도구 제공    | 강력한 GUI 제공             |
| 관계     | 실제 작업을 수행        | PostgreSQL을 사용하기 위한 도구 |

# 3. 설치 경로 선택

PostgreSQL을 설치할 때 중요한 것은 **자신의 운영체제와 실행 환경에 맞는 설치 방법을 선택하는 것**이다.

일반적으로 확인해야 할 환경:

* Windows
* macOS
* Linux
* Docker 등의 컨테이너 환경

## 3.1 설치 전에 확인할 것

```text
운영체제 확인
    ↓
CPU 아키텍처 확인
    ↓
PostgreSQL 설치 방법 선택
    ↓
설치
    ↓
서버 실행 여부 확인
```

특히 macOS에서는 Intel 기반인지 Apple Silicon 기반인지에 따라 설치 방식이 달라질 수 있다.

Linux에서는 배포판과 패키지 관리 방식에 따라 설치 방법이 달라질 수 있다.

# 4. PostgreSQL 서버와 데이터베이스의 차이

초보자가 가장 많이 혼동하는 부분 중 하나이다.

## PostgreSQL 서버

PostgreSQL 프로그램이 실행되고 있는 **데이터베이스 서버**이다.

서버가 실행되고 있어야 클라이언트인 DBeaver에서 접속할 수 있다.

## Database

PostgreSQL 서버 안에 존재하는 **하나의 데이터베이스 공간**이다.

예:

```text
PostgreSQL Server
│
├── postgres
├── ai_database_book
├── test_db
└── ...
```

따라서

> PostgreSQL 서버와 Database는 같은 개념이 아니다.

서버 안에 여러 Database가 존재할 수 있다.

---

# 5. PostgreSQL 서버 실행 상태 확인

DBeaver에서 연결하기 전에 PostgreSQL 서버가 실행 중인지 확인해야 한다.

## 5.1 서버가 실행 중이어야 하는 이유

DBeaver는 PostgreSQL 서버와 네트워크 연결을 만들어 SQL을 전달한다.

따라서 서버가 실행되지 않았다면 연결할 수 없다.

```text
DBeaver
   ↓
연결 요청
   ↓
PostgreSQL Server
   ↓
실행 중 → 연결 성공
정지 상태 → 연결 실패
```

## 5.2 서버 상태 확인의 핵심

운영체제에 따라 확인 방법은 다르지만 기본적으로 다음을 확인한다.

* PostgreSQL 서비스가 실행 중인가?
* PostgreSQL 프로세스가 실행 중인가?
* PostgreSQL이 사용하는 Port가 열려 있는가?
* 올바른 PostgreSQL 인스턴스를 확인하고 있는가?

# 6. DBeaver에서 PostgreSQL 연결 만들기

DBeaver에서 PostgreSQL 연결을 생성할 때는 PostgreSQL 서버의 접속 정보를 입력한다.

일반적인 연결 정보:

```text
Host
Port
Database
Username
Password
```

이 정보가 정확해야 PostgreSQL 서버에 연결할 수 있다.

---

# 7. Host, Port, Database, Username

PostgreSQL 연결에서 가장 중요한 기본 개념이다.

## 7.1 Host

**어떤 컴퓨터의 PostgreSQL 서버에 접속할 것인지**를 나타낸다.

로컬 컴퓨터에서 PostgreSQL을 실행하고 있다면 일반적으로 다음과 같은 값을 사용한다.

```text
localhost
```

또는

```text
127.0.0.1
```

### 의미

```text
Host = PostgreSQL 서버가 위치한 컴퓨터
```

예를 들어:

```text
Host = localhost
```

라면 현재 자신의 컴퓨터에서 실행되고 있는 PostgreSQL 서버를 의미한다.

---

## 7.2 Port

Port는 서버 프로그램과 통신하기 위한 **네트워크 통신 번호**이다.

PostgreSQL의 기본 Port는 일반적으로:

```text
5432
```

이다.

### 의미

```text
Host = 어느 컴퓨터?
Port = 그 컴퓨터의 어느 네트워크 서비스?
```

예:

```text
Host: localhost
Port: 5432
```

→ 현재 컴퓨터의 PostgreSQL 서비스에 접속

단, 설치 과정에서 Port를 변경했다면 실제 설정된 Port를 사용해야 한다.

---

## 7.3 Database

접속할 PostgreSQL 내부의 **데이터베이스 이름**이다.

예:

```text
Database = ai_database_book
```

이는 PostgreSQL 서버에 있는 `ai_database_book` 데이터베이스로 접속하겠다는 의미이다.

---

## 7.4 Username

PostgreSQL에 접속할 **사용자 계정**이다.

예:

```text
Username = postgres
```

PostgreSQL에는 데이터베이스 사용자와 권한 개념이 존재한다.

따라서 Username은 단순히 운영체제의 사용자 이름을 의미하는 것이 아니다.

> PostgreSQL 서버에서 인증받기 위한 데이터베이스 사용자이다.

---

# 8. 연결 정보를 하나의 관점으로 이해하기

다음과 같이 생각하면 이해하기 쉽다.

```text
Host
↓
어느 컴퓨터의 PostgreSQL인가?

Port
↓
그 컴퓨터의 어느 PostgreSQL 서비스인가?

Database
↓
어느 데이터베이스에 들어갈 것인가?

Username
↓
어떤 PostgreSQL 사용자로 접속할 것인가?

Password
↓
그 사용자가 본인임을 어떻게 인증할 것인가?
```

예:

```text
Host     = localhost
Port     = 5432
Database = ai_database_book
Username = postgres
Password = ********
```

# 9. ai_database_book 데이터베이스 확인

학습 환경에서 사용할 데이터베이스가 다음과 같다고 가정한다.

```text
ai_database_book
```

먼저 해당 데이터베이스가 이미 존재하는지 확인한다.

PostgreSQL에서는 `psql` 또는 DBeaver의 데이터베이스 탐색기를 통해 확인할 수 있다.

SQL을 이용하면 다음과 같이 데이터베이스 목록을 확인할 수 있다.

```sql
SELECT datname
FROM pg_database
ORDER BY datname;
```

결과에서 다음 이름이 존재하는지 확인한다.

```text
ai_database_book
```

---

# 10. 데이터베이스 생성

`ai_database_book`이 존재하지 않는 경우 필요한 권한이 있다면 생성할 수 있다.

```sql
CREATE DATABASE ai_database_book;
```

생성 후 데이터베이스 목록을 다시 확인한다.

```sql
SELECT datname
FROM pg_database
ORDER BY datname;
```

### 주의

이미 존재하는 데이터베이스를 다시 생성하면 오류가 발생한다.

따라서 일반적인 순서는 다음과 같다.

```text
존재 여부 확인
      ↓
존재함 → 그대로 사용
      ↓
존재하지 않음
      ↓
CREATE DATABASE
```

---

# 11. 새 데이터베이스로 연결 전환

`ai_database_book`을 생성했다고 해서 **현재 DBeaver 연결이 자동으로 해당 데이터베이스로 변경되는 것은 아니다.**

현재 연결이 다른 Database를 사용하고 있다면 새 데이터베이스를 대상으로 연결을 변경해야 한다.

예:

```text
기존 연결
Database = postgres

        ↓ 연결 설정 변경

새 연결
Database = ai_database_book
```

DBeaver에서는 연결 설정에서 Database 항목을 변경하거나 새로운 연결을 생성할 수 있다.

# 12. 현재 연결 상태 확인

연결한 뒤에는 실제로 원하는 데이터베이스에 접속했는지 확인하는 것이 중요하다.

다음 SQL을 사용할 수 있다.

```sql
SELECT
    current_database(),
    current_user;
```

결과를 통해 다음을 확인할 수 있다.

```text
현재 Database
현재 User
```

예상 결과:

```text
current_database
----------------
ai_database_book

current_user
------------
postgres
```

# 13. 현재 스키마 확인

PostgreSQL에는 **Schema**라는 개념이 있다.

Schema는 하나의 Database 안에서 데이터베이스 객체를 논리적으로 구분하는 공간이다.

예:

```text
Database
└── Schema
    ├── Table
    ├── View
    └── Function
```

현재 기본 스키마를 확인하려면:

```sql
SELECT current_schema();
```

---

# 14. 검색 경로(Search Path)

PostgreSQL은 SQL에서 테이블 이름을 지정할 때 어떤 Schema를 먼저 검색할지 결정하기 위해 **search_path**를 사용한다.

확인:

```sql
SHOW search_path;
```

또는:

```sql
SELECT current_setting('search_path');
```

예:

```text
"$user", public
```

이는 테이블을 스키마 이름 없이 참조할 경우 설정된 검색 경로를 기준으로 검색한다는 의미이다.

예를 들어:

```sql
SELECT *
FROM books;
```

라고 작성했을 때 PostgreSQL은 `search_path`에 설정된 Schema를 기준으로 `books` 테이블을 찾는다.

명시적으로 Schema를 지정할 수도 있다.

```sql
SELECT *
FROM public.books;
```

# 15. 현재 환경 확인 SQL

학습 환경이 올바르게 설정되었는지 확인하기 위해 다음 SQL을 실행할 수 있다.

```sql
SELECT
    current_database() AS database_name,
    current_user AS user_name,
    current_schema() AS schema_name;

SHOW search_path;
```

이를 통해 다음 네 가지를 확인할 수 있다.

```text
현재 Database
현재 User
현재 Schema
Search Path
```

# 16. SQL 실행 방법의 차이

DBeaver에서는 SQL을 작성하는 것뿐만 아니라 **어떤 범위를 실행하는지**도 중요하다.

대표적으로 세 가지 방식이 있다.

1. SQL 한 문장 실행
2. 선택 영역 실행
3. 전체 스크립트 실행

---

# 17. SQL 한 문장 실행

커서가 위치한 SQL 문장 하나를 실행하는 방식이다.

예:

```sql
SELECT current_database();
```

여러 SQL이 작성되어 있어도 현재 SQL 문장만 실행할 수 있다.

```sql
SELECT current_database();

SELECT current_user;

SHOW search_path;
```

이 경우 한 문장 실행을 사용하면 하나의 SQL만 실행된다.

---

# 18. 선택 영역 실행

SQL의 특정 부분을 마우스로 선택한 뒤 선택된 영역만 실행할 수 있다.

예:

```sql
SELECT current_database();

SELECT current_user;

SHOW search_path;
```

여기에서:

```sql
SELECT current_database();
```

만 선택하여 실행하면 선택한 SQL만 실행된다.

### 장점

* 필요한 SQL만 실행 가능
* 긴 스크립트에서 특정 부분만 테스트 가능
* 위험한 SQL의 실수 실행을 줄일 수 있음

---

# 19. 전체 스크립트 실행

작성된 SQL 스크립트 전체를 실행하는 방식이다.

예:

```sql
SELECT current_database();

SELECT current_user;

SHOW search_path;
```

전체 스크립트 실행을 하면 작성된 여러 SQL을 순서대로 실행할 수 있다.

### 주의

전체 스크립트 실행은 여러 SQL이 한꺼번에 실행될 수 있으므로 **실행 내용을 확인한 후 사용해야 한다.**

특히 다음과 같은 명령이 포함되어 있다면 주의한다.

```sql
DROP
DELETE
UPDATE
ALTER
CREATE
```

---

# 20. SQL 실행 범위 정리

| 실행 방식      | 실행 범위     | 사용 상황          |
| ---------- | --------- | -------------- |
| 한 문장 실행    | 현재 SQL 문장 | 하나의 SQL 테스트    |
| 선택 영역 실행   | 선택한 SQL   | 특정 부분만 테스트     |
| 전체 스크립트 실행 | 전체 SQL    | 여러 명령을 순서대로 실행 |

핵심은:

> **무엇을 실행할 것인지 확인하고 실행한다.**

# 21. 환경 확인 SQL

PostgreSQL 연결이 정상인지 확인할 때는 간단한 SQL부터 실행하는 것이 좋다.

## 현재 Database

```sql
SELECT current_database();
```

## 현재 User

```sql
SELECT current_user;
```

## 현재 Schema

```sql
SELECT current_schema();
```

## Search Path

```sql
SHOW search_path;
```

## PostgreSQL 버전

```sql
SELECT version();
```

# 22. 자동 확인 SQL

여러 항목을 한 번에 확인하려면 다음과 같이 작성할 수 있다.

```sql
SELECT
    current_database() AS database_name,
    current_user AS user_name,
    current_schema() AS schema_name,
    version() AS postgres_version;

SHOW search_path;
```

이를 통해 현재 접속 환경을 빠르게 확인할 수 있다.

---

# 23. 연결 오류를 유형별로 분류하기

PostgreSQL 연결 오류가 발생했을 때 무작정 설정을 변경하기보다 **오류 유형을 먼저 분류하는 것**이 중요하다.

대표적인 원인은 다음과 같다.

```text
1. 서버 문제
2. Host 문제
3. Port 문제
4. Database 문제
5. Username 문제
6. Password / 인증 문제
7. 권한 문제
8. SSL 또는 기타 연결 설정 문제
```

---

# 24. 서버 실행 문제

### 증상

PostgreSQL 서버 자체가 실행되고 있지 않을 수 있다.

### 확인

```text
PostgreSQL 서비스 상태 확인
```

서버가 정지되어 있다면 DBeaver의 연결 설정을 수정하는 것으로 해결되지 않는다.

먼저 PostgreSQL 서버를 실행해야 한다.

---

# 25. Host 문제

Host가 잘못되어 있으면 DBeaver가 올바른 서버를 찾지 못한다.

예:

```text
Host = localhost
```

로컬에서 PostgreSQL을 실행하는 환경이라면 일반적으로 사용할 수 있다.

그러나 원격 서버에 접속하는 경우에는 실제 서버의 Host를 사용해야 한다.

---

# 26. Port 문제

PostgreSQL 기본 Port는 일반적으로:

```text
5432
```

이다.

그러나 실제 서버 설정에서 다른 Port를 사용하고 있을 수 있다.

따라서 연결이 되지 않는다면:

```text
DBeaver Port
        ↕
PostgreSQL 실제 Port
```

가 일치하는지 확인한다.

---

# 27. Database 문제

Database 이름이 틀렸다면 원하는 데이터베이스에 접속할 수 없다.

예:

```text
ai_database_book
```

을 사용해야 하는데:

```text
ai_database
```

처럼 입력하면 연결에 실패하거나 원하는 데이터베이스에 접근하지 못할 수 있다.

따라서 Database 이름을 정확하게 확인한다.

---

# 28. Username / Password 문제

Username과 Password는 PostgreSQL 인증에 사용된다.

다음 항목을 확인한다.

```text
Username이 정확한가?
Password가 정확한가?
해당 사용자가 존재하는가?
해당 사용자의 인증 방식이 적절한가?
```

비밀번호가 틀린 경우 서버 자체는 정상적으로 실행되고 있어도 인증에 실패한다.

---

# 29. 권한 문제

연결에 성공했지만 특정 작업이 실패하는 경우 **권한 문제**일 수 있다.

예:

```sql
CREATE DATABASE ...
```

또는 특정 테이블에 대한 작업을 수행할 때 권한이 부족할 수 있다.

따라서

> 연결 성공 ≠ 모든 작업에 대한 권한 보유

라는 점을 기억해야 한다.

---

# 30. 오류 발생 시 확인 순서

연결 오류가 발생했다면 다음 순서로 확인하면 효율적이다.

```text
① PostgreSQL 서버가 실행 중인가?
          ↓
② Host가 올바른가?
          ↓
③ Port가 올바른가?
          ↓
④ Database가 올바른가?
          ↓
⑤ Username이 올바른가?
          ↓
⑥ Password가 올바른가?
          ↓
⑦ 사용자에게 필요한 권한이 있는가?
          ↓
⑧ SSL 및 기타 연결 설정이 필요한가?
```

핵심은 **오류 메시지를 먼저 읽고 해당 범위를 좁혀가는 것**이다.

# 31. 연결 오류와 SQL 오류를 구분하기

중요한 구분이다.

## 연결 오류

PostgreSQL 서버와 통신 자체가 되지 않는 문제이다.

예:

```text
서버가 실행되지 않음
Host 오류
Port 오류
인증 실패
```

## SQL 오류

서버에 연결은 성공했지만 실행한 SQL이 잘못된 경우이다.

예:

```sql
SELECT *
FROM nonexistent_table;
```

테이블이 존재하지 않으면 SQL 실행 오류가 발생한다.

따라서:

```text
연결 실패
    ≠
SQL 실행 실패
```

이다.

# 32. 연결 오류 발생 후 다시 확인

오류를 수정한 뒤에는 단순히 "고쳤다"고 생각하지 말고 실제로 연결이 정상화되었는지 확인해야 한다.

가장 간단한 확인 방법:

```sql
SELECT 1;
```

```sql

    current_database(),
    current_user,
    current_schema();
```

즉,

```text
오류 발생
 ↓
원인 분류
 ↓
설정 수정
 ↓
재연결
 ↓
확인 SQL 실행
 ↓
정상 환경 확인
```

예:

```text

Username
```

특히:

# 34. 전체 접속 URL의 위험성

PostgreSQL 연결 정보를 URL 형태로 표현할 수도 있다.

형식 예시:

```text
postgresql://USERNAME:PASSWORD@HOST:PORT/DATABASE
```

여기에는 다음 정보가 한 번에 들어간다.

```text
Username
Password
Host
Port
Database
```

따라서 이 URL을 그대로 공개하면 **비밀번호까지 노출될 수 있다.**

예를 들어 다음과 같은 형태의 문자열은 공개 자료에 그대로 포함하지 않는다.

```text
postgresql://user:password@example.com:5432/database
```

실제 비밀번호가 포함되어 있기 때문이다.

```text

```

## PostgreSQL 구조

```text

        ↓
    Database
        ↓
      Schema
        ↓
      Table
        ↓

```

# 39. 복습 문제

### Q1. PostgreSQL과 DBeaver의 차이는 무엇인가?

**답:** PostgreSQL은 실제 데이터를 저장하고 SQL을 처리하는 데이터베이스 서버/DBMS이고, DBeaver는 PostgreSQL과 같은 데이터베이스에 접속하여 관리할 수 있도록 해주는 클라이언트 도구이다.

### Q2. PostgreSQL의 기본 Port는 무엇인가?

**답:** 일반적으로 `5432`이다. 단, 실제 설치 환경에서 변경되었을 수 있으므로 실제 설정을 확인해야 한다.

### Q3. Host와 Port의 차이는 무엇인가?

**답:** Host는 접속할 서버가 위치한 컴퓨터를 나타내고, Port는 해당 컴퓨터에서 PostgreSQL 서비스와 통신하기 위한 네트워크 포트를 나타낸다.

### Q4. Database와 Schema는 같은 것인가?

**답:** 아니다. Database는 PostgreSQL 서버 안의 데이터 저장 및 관리 단위이고, Schema는 Database 내부에서 테이블 등의 객체를 논리적으로 구분하는 공간이다.

### Q5. 현재 접속한 Database를 어떻게 확인하는가?

### Q6. 현재 사용자를 어떻게 확인하는가?

```sql
SELECT current_user;
```

### Q7. 현재 Schema를 어떻게 확인하는가?

```sql
SELECT current_schema();
```

### Q8. Search Path를 어떻게 확인하는가?

```sql
SHOW search_path;
```

### Q9. 연결 오류와 SQL 오류의 차이는 무엇인가?

**답:** 연결 오류는 PostgreSQL 서버와 연결하거나 인증하는 과정에서 발생하는 문제이고, SQL 오류는 서버 연결에는 성공했지만 실행한 SQL 자체에서 발생하는 문제이다.

### Q10. PostgreSQL 접속 URL을 공개할 때 가장 주의해야 할 것은 무엇인가?

**답:** URL에 비밀번호가 포함될 수 있으므로 실제 접속 URL을 공개 자료에 그대로 게시해서는 안 된다.

# 2. CSV 파일과 pandas DataFrame의 차이

## 2.1 CSV란?

CSV는 **Comma-Separated Values**의 약자로, 데이터를 행과 열 형태로 저장하는 텍스트 파일 형식이다.

예:

```csv
customer_id,name,age
C001,Kim,25
C002,Lee,31
C003,Park,28
```

CSV는 파일에 데이터를 저장하기 위한 **파일 형식**이다.

즉,

> CSV = 디스크에 저장된 데이터 파일

---

## 2.2 pandas DataFrame이란?

pandas의 `DataFrame`은 Python 프로그램에서 데이터를 **행과 열 형태로 다루기 위한 자료구조**이다.

예:

```python
import pandas as pd

df = pd.read_csv("customers.csv")
```

이 코드를 실행하면 CSV 파일의 데이터가 pandas `DataFrame`으로 읽힌다.

```text
customers.csv
      ↓
pd.read_csv()
      ↓
pandas DataFrame
      ↓
Python에서 데이터 분석
```

즉,

> DataFrame = Python 메모리에서 데이터를 분석하고 조작하기 위한 구조

---

## 2.3 CSV와 DataFrame 비교

| 구분     | CSV             | DataFrame     |
| ------ | --------------- | ------------- |
| 형태     | 파일              | Python 자료구조   |
| 저장 위치  | 디스크             | 주로 메모리        |
| 목적     | 데이터 저장/교환       | 데이터 분석/처리     |
| 사용 환경  | 다양한 프로그램        | Python/pandas |
| 예      | `customers.csv` | `df`          |
| 데이터 분석 | 제한적             | 다양한 분석 기능 제공  |

핵심:

> **CSV는 저장 형식이고, DataFrame은 분석을 위한 자료구조이다.**

# 3. DataFrame의 기본 구조

DataFrame은 기본적으로 다음 구조를 가진다.

```text
             열(Column)
          name      age
        ┌────────┬─────┐
행 0    │ Kim    │ 25  │
행 1    │ Lee    │ 31  │
행 2    │ Park   │ 28  │
        └────────┴─────┘
             ↑
           값(Value)
```

데이터를 이해하기 위해 다음 개념을 구분해야 한다.

```text
행(Row)
열(Column)
값(Value)
인덱스(Index)
업무용 ID(Business ID)
```

---

# 4. 행(Row)

행은 데이터의 **한 건의 레코드**를 나타내는 경우가 많다.

예:

```text
customer_id | name | age
------------|------|----
C001        | Kim  | 25
C002        | Lee  | 31
```

각 행은 하나의 고객 정보를 나타낸다.

```text
행 1 → C001 고객
행 2 → C002 고객
```

다만 모든 데이터에서 행 하나가 반드시 하나의 "사람"을 의미하는 것은 아니다.

예를 들어 주문상세 데이터에서는:

```text
행 하나 = 주문의 상품 한 줄
```

일 수 있다.

따라서

> 행의 의미는 데이터셋의 업무적 정의에 따라 결정된다.

---

# 5. 열(Column)

열은 데이터의 **속성 또는 변수**를 나타낸다.

예:

```text
customer_id
name
age
```

각각 고객 데이터의 속성이다.

```text
customer_id → 고객 식별자
name        → 고객 이름
age         → 고객 나이
```

---

# 6. 값(Value)

값은 특정 행과 열이 만나는 **실제 데이터**이다.

예:

```text
customer_id | name | age
------------|------|----
C001        | Kim  | 25
```

여기서:

```text
C001
Kim
25
```

등이 각각 값이다.

---

# 7. 인덱스(Index)

pandas DataFrame에는 각 행을 구분하기 위한 **인덱스(Index)**가 있다.

예:

```text
index | customer_id | name
------|-------------|-----
0     | C001        | Kim
1     | C002        | Lee
2     | C003        | Park
```

기본적으로 pandas가 자동으로:

```text
0
1
2
...
```

형태의 인덱스를 생성할 수 있다.

---

# 8. 업무용 ID(Business ID)

업무용 ID는 실제 업무에서 특정 대상을 식별하기 위해 사용하는 값이다.

예:

```text
customer_id
product_id
order_id
```

예를 들어:

```text
customer_id = C001
```

은 업무적으로 특정 고객을 식별한다.

---

# 9. 인덱스와 업무용 ID의 차이

둘은 비슷해 보이지만 완전히 다른 개념이다.

```text
Index
→ DataFrame에서 행을 구분하기 위한 값

Business ID
→ 실제 업무에서 고객/상품/주문 등을 식별하기 위한 값
```

예:

```text
index | customer_id | name
------|-------------|-----
0     | C001        | Kim
1     | C002        | Lee
2     | C003        | Park
```

여기서:

```text
0, 1, 2 → pandas index
C001...  → 업무용 customer_id
```

이다.

### 중요한 점

행 순서가 바뀌거나 행이 삭제되어도 업무용 ID는 업무적으로 동일한 대상을 계속 식별할 수 있다.

따라서:

> **인덱스 ≠ 업무용 ID**

# 10. 고객·상품·주문·주문상세 데이터

실제 업무 데이터는 하나의 거대한 파일에 모든 정보를 넣기보다 여러 데이터셋으로 분리되어 있는 경우가 많다.

대표적인 구조:

```text
고객(Customer)
       │
       └──── 주문(Order)
                 │
                 └──── 주문상세(Order Detail)
                              │
                              └──── 상품(Product)
```

# 13. 주문 데이터

# 14. 주문상세 데이터

주문상세 데이터는 하나의 주문에 **어떤 상품이 몇 개 포함되었는지**를 나타낸다.

예:

```text

product_id
quantity
unit_price
```

하나의 주문에 여러 상품이 들어갈 수 있기 때문에 주문 하나에 여러 행이 존재할 수 있다.

예:

```text
order_id | product_id | quantity
---------|------------|---------
O001     | P001       | 2
O001     | P003       | 1
O002     | P002       | 3
```

여기서 `O001` 주문에는 상품 두 종류가 포함되어 있다.

# 15. 네 데이터의 역할 비교

| 데이터  | 무엇을 나타내는가?        | 대표 ID                    |
| ---- | ----------------- | ------------------------ |
| 고객   | 누가                | `customer_id`            |
| 상품   | 무엇을               | `product_id`             |
| 주문   | 어떤 거래인가           | `order_id`               |
| 주문상세 | 거래에 무엇이 얼마나 포함됐는가 | `order_id`, `product_id` |

쉽게 기억하면:

```text
고객 = Who
상품 = What
주문 = When / 거래
주문상세 = What + How many
```

# 28. 자료형 변환

CSV로 데이터를 읽으면 원래 의미와 다른 자료형으로 읽히는 경우가 있다.

예를 들어:

```text
"100"
"200"
"300"
```

이 숫자처럼 보이지만 문자형으로 저장되어 있을 수 있다.

이 경우 숫자형으로 변환할 수 있다.

```python
df["price"] = pd.to_numeric(df["price"])
```

날짜도 마찬가지이다.

```python
df["order_date"] = pd.to_datetime(df["order_date"])
```

---

# 29. 변환 성공과 실패를 반드시 확인하기

자료형 변환을 했다고 해서 **무조건 성공했다고 가정하면 안 된다.**

예를 들어:

```text
100
200
unknown
300
```

을 숫자로 변환하면 `unknown`은 숫자로 변환할 수 없다.

실패값을 결측값으로 처리하도록 할 수도 있다.

```python
df["price"] = pd.to_numeric(
    df["price"],
    errors="coerce"
)
```

이 경우 변환할 수 없는 값은:

```text
NaN
```

이 된다.

---

# 30. 변환 후 실패값 확인

변환 후에는 반드시 결과를 점검해야 한다.

```python
df["price"].isna().sum()
```

변환 전에 결측치가 없었다면 새롭게 생긴 `NaN`이 변환 실패 때문에 발생했을 가능성이 있다.

변환 실패값을 원래 데이터와 비교하기 위해 변환 전 데이터를 별도로 보관하는 방법도 있다.

예:

```python
original = df["price"].copy()

converted = pd.to_numeric(
    original,
    errors="coerce"
)

failed = original[converted.isna() & original.notna()]

failed
```

핵심:

> **변환 명령을 실행하는 것보다 변환 결과를 확인하는 것이 중요하다.**

# 31. 결측치(Missing Value)

결측치는 데이터가 비어 있거나 값이 존재하지 않는 상태이다.

pandas에서는 대표적으로:

```text
NaN
NaT
None
```

등으로 나타날 수 있다.

---

# 32. 결측치가 항상 오류는 아니다

중요한 개념이다.

예를 들어:

```text
customer_id | phone_number
------------|-------------
C001        | 010-1111-1111
C002        | NaN
```

C002의 전화번호가 없다고 해서 반드시 데이터 오류라고 할 수는 없다.

실제로:

* 고객이 전화번호를 제공하지 않았을 수 있음
* 해당 정보가 업무상 필요하지 않을 수 있음
* 아직 수집되지 않았을 수 있음

따라서:

> **결측치의 존재 자체가 오류를 의미하지 않는다.**

결측치가 **업무적으로 허용되는지** 판단해야 한다.

---

# 33. 결측치 확인

전체 데이터에서 결측치를 확인하려면:

```python
df.isna().sum()
```

예:

```text
customer_id     0
name            0
phone_number   25
```

이면 `phone_number`에 25개의 결측치가 있다는 뜻이다.

# 34. 전체 행 중복

완전히 동일한 행이 여러 번 존재하는 경우를 **전체 행 중복**이라고 할 수 있다.

확인:

```python
df.duplicated().sum()
```

중복 행을 확인:

```python
df[df.duplicated()]
```

예:

```text
customer_id | name | age
------------|------|----
C001        | Kim  | 25
C001        | Kim  | 25
```

두 행의 모든 컬럼이 동일하다면 전체 행 중복이다.

---

# 35. 업무용 ID 중복

업무용 ID가 중복되는 것은 별도의 문제이다.

예:

```text
customer_id | name | age
------------|------|----
C001        | Kim  | 25
C001        | Kim  | 26
```

전체 행은 서로 다르지만:

```text
customer_id = C001
```

이 중복된다.

따라서:

```text
전체 행 중복
≠
업무용 ID 중복
```

이다.

---

# 36. 업무용 ID 중복 확인

예를 들어 고객 ID가 고유해야 한다면:

```python
df["customer_id"].duplicated().sum()
```

중복된 ID를 확인:

```python
df[df["customer_id"].duplicated(keep=False)]
```

### 중요한 질문

중복 ID가 발견되었다고 무조건 오류라고 판단해서는 안 된다.

데이터의 역할에 따라:

```text
고객 테이블
→ customer_id가 일반적으로 한 고객을 나타내므로 고유해야 할 가능성이 높음

주문 테이블
→ customer_id가 여러 번 등장할 수 있음
```

즉,

> **ID의 고유성은 데이터셋의 업무 규칙에 따라 판단한다.**

# 37. 범주형 값의 표기 불일치

범주형 데이터는 같은 의미의 값이 여러 가지 형태로 기록되는 문제가 발생할 수 있다.

예:

```text
남성
남
M
male
Male
```

사람 입장에서는 비슷한 의미라고 판단할 수 있지만 컴퓨터에서는 서로 다른 문자열이다.

또 다른 예:

```text
서울
서울시
Seoul
SEOUL
```

# 38. 범주형 값 확인

특정 컬럼의 고유값을 확인할 수 있다.

```python
df["category"].value_counts(dropna=False)
```

또는:

```python
df["category"].unique()
```

이렇게 하면 예상하지 못한 표기가 있는지 확인할 수 있다.

예:

```text
Electronics
electronics
Electronic
전자제품
```

처럼 동일하거나 유사한 범주의 표기가 섞여 있는지 확인한다.

# 39. 날짜 범위 확인

날짜 데이터를 분석하기 전에 **최소 날짜와 최대 날짜**를 확인하는 것이 좋다.

먼저 날짜형으로 변환한다.

```python
df["order_date"] = pd.to_datetime(
    df["order_date"],
    errors="coerce"
)
```

그다음:

```python
df["order_date"].min()
df["order_date"].max()
```

을 확인한다.

이를 통해 데이터가:

```text
언제부터
언제까지
```

존재하는지 알 수 있다.

---

# 40. 날짜 변환 실패값 확인

잘못된 날짜가 존재할 수도 있다.

예:

```text
2026-01-01
2026-02-10
2026-99-99
unknown
```

`errors="coerce"`를 사용하면 변환할 수 없는 값이 `NaT`가 된다.

```python
df["order_date"] = pd.to_datetime(
    df["order_date"],
    errors="coerce"
)
```

변환 실패 확인:

```python
df["order_date"].isna().sum()
```

하지만 원래 결측치와 변환 실패를 구분하려면 **변환 전 데이터를 보존하는 것이 중요하다.**

# 41. 부모 데이터와 자식 데이터

고객·상품·주문·주문상세 데이터처럼 여러 테이블이 연결된 데이터에서는 **관계(Relationship)**를 이해해야 한다.

예:

```text
Customer
    │
    │ customer_id
    ↓
Order
    │
    │ order_id
    ↓
Order Detail
    │
    │ product_id
    ↓
Product
```

여기서 참조되는 쪽을 부모 데이터, 참조하는 쪽을 자식 데이터로 생각할 수 있다.

---

# 42. 부모 데이터의 고유성

부모 데이터의 ID는 일반적으로 고유해야 한다.

예:

```text
Customer

customer_id | name
------------|-----
C001        | Kim
C002        | Lee
C003        | Park
```

`customer_id`가 고객을 유일하게 식별한다면:

```text
C001 → 하나의 고객
C002 → 하나의 고객
C003 → 하나의 고객
```

이어야 한다.

따라서 부모 테이블의 ID 중복은 중요한 데이터 품질 문제일 수 있다.

---

# 43. 자식 데이터의 참조 무결성

자식 데이터에서는 부모 데이터에 존재하는 ID를 참조해야 한다.

예:

```text
Customer

customer_id
-----------
C001
C002
C003
```

Order:

```text
order_id | customer_id
---------|------------
O001     | C001
O002     | C002
O003     | C999
```

여기서 `C999`가 Customer에 존재하지 않는다면:

```text
존재하지 않는 고객을 주문이 참조
```

하는 문제가 발생한다.

이를 **참조 무결성(Referential Integrity)** 문제라고 볼 수 있다.

---

# 44. 참조 무결성 점검

개념적으로는 다음을 확인한다.

```text
자식 테이블의 ID
        ↓
부모 테이블에 존재하는가?
        ↓
YES → 정상 참조
NO  → 참조 무결성 문제 가능
```

예를 들어:

```text
Order.customer_id
```

가

```text
Customer.customer_id
```

에 존재하는지 확인한다.

---

# 45. 부모 고유성 vs 자식 참조 무결성

| 점검 대상 | 확인 내용               |
| ----- | ------------------- |
| 부모 ID | 중복 없이 고유한가?         |
| 자식 ID | 부모에 존재하는 ID를 참조하는가? |

예:

```text
Customer.customer_id
→ 고유해야 함

Order.customer_id
→ Customer에 존재해야 함
```

이 차이를 기억해야 한다.

# 46. 데이터 문제 발견과 처리의 차이

데이터 품질 작업에서는 **문제를 발견하는 것**과 **문제를 처리하는 것**을 구분해야 한다.

## 발견

현재 데이터에 어떤 문제가 있는지 확인한다.

예:

```python
df.isna().sum()
df.duplicated().sum()
df["customer_id"].duplicated().sum()
df["category"].value_counts(dropna=False)
```

이 단계에서는 데이터를 함부로 변경하지 않는다.

---

## 처리

문제를 발견한 뒤 업무 규칙에 따라 수정한다.

예:

```text
결측치 → 제거 / 대체 / 유지
중복 → 제거 / 통합
표기 불일치 → 표준화
잘못된 날짜 → 수정 / 제외
잘못된 ID → 원인 확인
```

---

# 47. 발견과 처리의 기본 흐름

```text
데이터 탐색
    ↓
문제 발견
    ↓
문제의 원인 파악
    ↓
업무 규칙 확인
    ↓
처리 방법 결정
    ↓
데이터 수정
    ↓
수정 결과 검증
```

중요한 원칙:

> **문제를 발견했다고 바로 삭제하거나 수정하지 않는다.**

먼저 그 값이 실제로 잘못된 것인지 업무적 의미를 확인해야 한다.

---

# 48. 데이터 품질 점검의 대표 항목

전체적인 데이터 점검은 다음과 같이 정리할 수 있다.

```text
구조
├── 행 수 / 열 수
├── 컬럼 이름
└── 자료형

값
├── 결측치
├── 중복
├── 범주형 표기 불일치
└── 이상값

날짜
├── 최소 날짜
├── 최대 날짜
└── 변환 실패

관계
├── 부모 ID 고유성
└── 자식 → 부모 참조 무결성
```

# 49. LLM에 원본 데이터를 그대로 제공하지 않기

LLM을 활용해 데이터 분석을 도움받을 수 있지만, 원본 데이터를 그대로 제공하는 것은 주의해야 한다.

특히 데이터에 다음 정보가 포함될 수 있다.

```text
이름
전화번호
이메일
주소
고객 ID
주문 정보
기타 민감한 정보
```

따라서 LLM에 데이터를 전달할 때는 **필요 이상의 원본 데이터를 제공하지 않는 것**이 좋다.

# 50. 안전한 구조 요약 제공

원본 데이터 대신 데이터의 구조와 통계적 요약을 제공할 수 있다.

예:

```text
파일명: customers.csv

열 수: 6

컬럼:
- customer_id: object
- age: int64
- gender: object
- signup_date: datetime64[ns]
- region: object
- email: object

- age: 12
```

# 52. LLM의 설명을 그대로 믿으면 안 되는 이유

LLM은 코드나 데이터 분석 방법을 설명하는 데 도움을 줄 수 있지만, 실제 데이터의 실행 결과를 직접 보지 않았다면 잘못된 설명을 할 수도 있다.

따라서:

```text
LLM 설명
    ↓
실제 Python 코드 실행
    ↓
실행 결과 확인
    ↓
둘을 비교
```

하는 과정이 필요하다.

# 57. 최종 핵심 정리

## CSV vs DataFrame

```text
CSV
→ 데이터를 저장하는 파일 형식

DataFrame
→ Python/pandas에서 데이터를 분석하기 위한 자료구조
```

## 데이터 구조

```text
행      → 레코드
열      → 속성/변수
값      → 실제 데이터
인덱스  → DataFrame의 행 구분자
업무용 ID → 업무상 대상을 식별하는 값
```

## 기본 탐색

```text
shape   → 행/열 개수
head()  → 앞부분
tail()  → 뒷부분
columns → 컬럼 이름
info()  → 구조 + 결측치 + 자료형
dtypes  → 자료형
```

## 자료형

```text
숫자형 → 계산
문자형 → 문자열/범주
날짜형 → 날짜 및 시간 분석
```

## 데이터 품질

```text
결측치
→ 항상 오류는 아님

전체 행 중복
→ 행 전체가 중복

업무용 ID 중복
→ 특정 식별자가 중복

범주형 불일치
→ 같은 의미가 서로 다른 표기로 저장

날짜 오류
→ 변환 실패 및 비정상 범위 확인
```

## 관계 무결성

```text
부모 ID
→ 고유해야 함

자식의 참조 ID
→ 부모에 존재해야 함
```

## 문제 처리

```text
발견 → 원인 파악 → 업무 규칙 확인 → 처리 → 검증
```

## LLM

```text
원본 데이터
→ 가능하면 제공하지 않음

구조 요약
→ 필요한 정보만 제공

LLM 설명
→ 실제 실행 결과와 비교하여 검증
```

# 58. 시험 전 1분 암기

> **CSV는 파일이고 DataFrame은 Python에서 데이터를 다루는 구조이다.**

> **행은 레코드, 열은 속성, 값은 실제 데이터, 인덱스는 DataFrame의 행 구분자, 업무용 ID는 실제 업무 대상을 식별하는 값이다.**

> **고객 = 누가, 상품 = 무엇을, 주문 = 거래, 주문상세 = 거래에 어떤 상품이 얼마나 포함됐는가.**

> **`shape`는 크기, `head()`는 앞, `tail()`은 뒤, `columns`는 컬럼 이름, `info()`는 구조, `dtypes`는 자료형을 확인한다.**

> **숫자형·문자형·날짜형은 의미와 처리 방법이 다르므로 적절한 자료형인지 확인한다.**

> **자료형 변환은 성공했다고 가정하지 말고 변환 실패값을 반드시 확인한다.**

> **결측치는 항상 오류가 아니며 업무 규칙에 따라 판단한다.**

> **전체 행 중복과 업무용 ID 중복은 서로 다른 문제이다.**

> **부모 데이터의 ID는 고유해야 하고, 자식 데이터의 참조 ID는 부모 데이터에 존재해야 한다.**

> **데이터 문제는 발견과 처리를 구분하고, 처리 후 반드시 결과를 다시 검증한다.**

> **LLM에는 원본 데이터보다 안전한 구조 요약을 제공하고, LLM의 설명은 실제 실행 결과와 비교하여 검증한다.**

# 59. 복습 문제

### Q1. CSV와 DataFrame의 차이는?

**답:** CSV는 데이터를 저장하는 파일 형식이고, DataFrame은 Python/pandas에서 데이터를 분석하고 처리하기 위한 자료구조이다.

### Q2. `df.shape`는 무엇을 알려주는가?

**답:** DataFrame의 행 수와 열 수를 알려준다.

### Q3. `head()`와 `tail()`의 차이는?

**답:** `head()`는 데이터 앞부분을, `tail()`은 데이터 뒷부분을 보여준다.

### Q4. pandas의 인덱스와 업무용 ID는 같은가?

**답:** 아니다. 인덱스는 DataFrame의 행을 구분하기 위한 것이고, 업무용 ID는 실제 업무에서 고객·상품·주문 등을 식별하기 위한 값이다.

### Q5. 고객, 상품, 주문, 주문상세의 역할은?

**답:**

```text
고객 → 누가
상품 → 무엇을
주문 → 거래
주문상세 → 어떤 상품이 얼마나 포함되었는가
```

### Q6. `info()`와 `dtypes`의 차이는?

**답:** `dtypes`는 각 컬럼의 자료형을 확인하고, `info()`는 자료형뿐 아니라 컬럼, 행 수, Non-Null Count 등 DataFrame의 구조를 종합적으로 확인한다.

### Q7. 결측치가 발견되면 무조건 삭제해야 하는가?

**답:** 아니다. 결측치는 업무적으로 허용되는 값일 수도 있으므로 원인과 업무 규칙을 확인한 후 처리해야 한다.

### Q8. 전체 행 중복과 ID 중복의 차이는?

**답:** 전체 행 중복은 모든 컬럼의 값이 같은 행이 중복되는 것이고, ID 중복은 전체 행의 내용이 달라도 특정 업무용 ID가 중복되는 것이다.

### Q9. 날짜 변환에서 `errors="coerce"`를 사용하면 어떻게 되는가?

**답:** 변환할 수 없는 값이 `NaT`로 처리된다. 이후 `isna()` 등을 통해 변환 실패 여부를 확인할 수 있다.

### Q10. 부모 데이터와 자식 데이터에서 각각 무엇을 확인해야 하는가?

**답:** 부모 데이터에서는 식별자의 고유성을 확인하고, 자식 데이터에서는 참조하는 ID가 부모 데이터에 실제로 존재하는지 확인한다.

### Q11. 데이터 문제를 발견하자마자 수정하면 안 되는 이유는?

**답:** 해당 값이 실제 오류인지 업무적으로 허용되는 값인지 판단해야 하기 때문이다. 먼저 원인과 업무 규칙을 확인한 후 처리해야 한다.

### Q12. LLM에 원본 CSV를 그대로 제공하지 않는 이유는?

**답:** 고객 이름, 이메일, 전화번호 등의 개인정보나 업무상 민감한 정보가 포함될 수 있기 때문이다. 필요한 경우 구조와 통계적 요약만 제공하는 것이 안전하다.

### Q13. LLM이 제시한 분석 결과를 그대로 사용해도 되는가?

**답:** 아니다. 실제 Python 코드나 분석 도구를 실행한 결과와 비교하여 검증해야 한다.
