## 1. Chapter 18: 클래스(Class)와 객체(Object) 기초

### 1) 객체(Object) vs 인스턴스(Instance)
* **객체 (Object):** 소프트웨어 세상에 존재하여 독립적인 데이터와 기능을 가진 모든 실체 (넓은 개념).
* **인스턴스 (Instance):** 특정 클래스(설계도)와의 관계를 강조할 때 쓰는 표현 (~의 인스턴스).
* **결론:** 실무나 개발 대화에서는 두 단어를 구별 없이 동일한 의미로 혼용해서 사용함.

### 2) `self`의 개념과 역할
* **개념:** "지금 실행 중인 바로 그 객체(자기 자신)"를 가리키는 주소표 역할.
* **사용 이유:**
  1. 하나의 클래스로 만들어진 여러 객체(`student1`, `student2`)를 구분하기 위함.
  2. 객체마다 고유한 데이터(`self.name`, `self.score`)를 메모리에 독립적으로 저장하고 접근하기 위함.
* **메서드 호출 시 동작:** `student1.show_result()` 실행 시 파이썬 내부에서는 `Student.show_result(student1)`처럼 객체 자신을 첫 번째 인자로 자동 전달.
* **`self` 누락 시 오류:** 메서드 정의 시 `self`를 빼먹으면 `TypeError: show_result() takes 0 positional arguments but 1 was given` 오류 발생.

### 3) 코드 실행 순서 및 `__init__()` 규칙
* **실행 흐름:** `def __init__(...)` 영역은 정의할 때 실행되지 않고, `Student("민수", 85)`로 객체를 생성하는 순간 위쪽 `__init__`으로 이동하여 자동 호출됨.
* **위치 및 순서:**
  * 클래스 내 `__init__()` 메서드의 작성 위치(위/아래)는 영향이 없음.
  * 전달하는 인자의 순서는 매개변수 순서와 엄격히 일치해야 함 (단, `name="민수"`와 같은 키워드 인자 사용 시 순서 변경 가능).

### 4) 데이터 타입 확인 및 디버깅 (`dict` vs `class`)
* **`dict` (딕셔너리):** Key-Value 쌍으로 단순 데이터만 저장할 때 사용.
* **`class` (클래스):** 데이터와 동작/기능(메서드)을 함께 묶어서 다룰 때 사용.
* **유의 사항:** 대화형 환경에 이전 변수(`student = {}`)가 남아있는 상태에서 `type(student)`를 호출하면 `<class 'dict'>`가 나올 수 있으므로 정확한 변수명(`type(student1)`) 확인 필요.

## 2. Chapter 19: AI와 함께 프로그램 설계하고 작성하기

### 1) 프로그램 범위 및 요구사항 정의
* 코드를 작성하기 전에 프로그램의 목적, 범위(4~6문장) 및 **"하지 않을 것"**(DB, GUI, 웹 등)을 짧은 문장으로 명확히 정의함.

### 2) IPO (입력 · 처리 · 출력) 데이터 설계
* **INPUT (입력):** 날짜, 카테고리, 금액을 담은 딕셔너리 리스트.
* **PROCESS (처리):** 전체 합계, 카테고리별 합계 계산.
* **OUTPUT (출력):** 총 지출액, 카테고리별 지출액 콘솔 출력.
* 데이터 모양(리스트, 딕셔너리)을 코딩 전에 먼저 설계해야 전체 구현이 쉬워짐.

### 3) 함수 분해 및 작게 시작하기
* 한 함수가 한 가지 역할만 담당하도록 분해 (`calculate_total`, `calculate_by_category`, `show_report`).
* 가장 작은 기능부터 직접 구현하고, **실행 전 예상 결과를 먼저 계산하여 실제 출력값과 비교**하는 검증 과정을 습관화함.

### 4) 올바른 AI 파트너 활용법
* 완성된 전체 코드를 요구하지 않고, 막힌 지점에서 **자료구조 힌트나 다음 1단계 설명**만 요청함.
* AI가 제안한 코드에 배우지 않은 문법이 있다면 **배운 기본 문법(리스트, 딕셔너리, for, if)으로 변경해 달라고 재요청**함.
* 작성한 코드가 오류 없이 실행되더라도 요구사항을 충족했는지 검증하고, AI에게 **현재 작성된 코드의 리뷰 및 경계 조건(예: 빈 리스트) 테스트를 요청**하여 직접 수정함.

## 3. Chapter Check 10문답 점검

1. **AI에게 코드를 요청하기 전에 프로그램의 목적과 범위를 정해야 하는 이유:**
   * AI가 의도를 멋대로 추정해 불필요하게 복잡하거나 원하지 않는 기능(GUI, DB 등)을 포함하는 것을 방지하기 위함.
2. **요구사항에 "하지 않을 것"을 함께 적는 장점:**
   * 구현 범위를 명확히 제한하여 오버엔지니어링을 막고 핵심 기능 구현에만 집중할 수 있음.
3. **입력·처리·출력(IPO)의 의미:**
   * **입력(Input):** 프로그램에 들어오는 데이터.
   * **처리(Process):** 데이터를 가공 및 계산하는 로직.
   * **출력(Output):** 처리 결과를 사용자에게 보여주는 화면/콘솔.
4. **코드를 작성하기 전에 데이터 모양을 정할 때의 장점:**
   * 어떤 자료구조(리스트, 딕셔너리)를 쓸지 알면 반복문과 조건문 처리가 명확해지고 함수 설계가 쉬워짐.
5. **큰 기능을 작은 함수로 나누는 이유:**
   * 디버깅과 테스트가 쉬워지고, 코드의 재사용성과 가독성이 높아짐.
6. **전체 코드 대신 한 단계 힌트를 요청할 때의 장점:**
   * 스스로 고민하고 코드를 작성하면서 실제 문제 해결 능력과 문법 적용 능력이 향상됨.
7. **AI가 배우지 않은 문법을 제안했을 때 해결법:**
   * "배운 문법(리스트, 딕셔너리, for, if)만 사용해서 다시 작성해 줘"라고 재요청함.
8. **오류 없이 실행되어도 예상 결과와 비교해야 하는 이유:**
   * 문법 오류가 없어도 잘못된 계산 로직(논리 오류)이 존재할 수 있기 때문 (`실행 성공 ≠ 요구사항 충족`).
9. **새 코드 생성 대신 현재 코드 리뷰를 요청하는 장점:**
   * 자신이 작성한 코드의 문제점과 개선 방향을 직접 파악하고 수정하는 학습 효과를 얻음.
10. **요구사항 → 설계 → 구현 → 실행 다음 과정:**
    * **예상 결과 검증 → AI 리뷰 요청 → 직접 수정 → 재실행**의 반복 개선 과정.
