# 2026-10-13 프로젝트 4일차 최종 발표 및 회고

## 오늘의 상황

오늘은 KANT·MOA 프로젝트의 최종 발표를 위해 최신 배포 화면과 Git 기록을 다시 확인하고, 프로젝트의 기획 의도부터 기술 선택, 핵심 기능, 한계와 개선 방향까지 발표 자료와 대본으로 정리했다. 단순히 개발 과정을 나열하기보다 “왜 이 서비스를 만들었는가”, “어떤 문제를 해결하려 했는가”, “기술을 왜 이렇게 선택했는가”가 자연스럽게 연결되도록 발표 흐름을 다듬었다.

최종 발표에서는 여러 아티스트의 굿즈와 콘텐츠가 흩어져 있어 탐색이 불편하다는 문제에서 출발해, 아티스트 발견부터 상품 구매와 주문 확인까지 하나의 서비스에서 이어지는 경험을 구현했다는 점을 중심으로 설명했다.

## 오늘 한 일

### 1. 최신 프로젝트 상태 점검

- 최신 Git 변경 사항과 배포 사이트를 다시 확인했다.
- 과거 화면이 발표 자료에 들어가지 않도록 현재 로고와 실제 배포 화면을 기준으로 자료를 교체했다.
- 발표 평가에서 모바일 화면을 중요하게 볼 수 있어 데스크톱과 모바일 화면을 함께 준비했다.
- 초기 3팀 중심의 구성에서 기존 아티스트를 포함한 11팀 구성으로 확장된 과정을 발표 내용에 반영했다.
- 메인 브랜치에 병합하기 전 팀원 전체가 변경 사항과 화면을 확인하고 승인했다는 실제 협업 방식을 정리했다.

### 2. 최종 발표 자료 구성

- 프로젝트 시작 배경과 목표를 짧고 명확하게 정리했다.
- GitHub를 통한 코드 관리와 Redmine을 이용한 일정 관리 방식을 설명했다.
- 한 명은 DB·인증·주문 로직을 맡고, 나머지 팀원은 프론트 페이지를 나누어 맡은 이유를 정리했다.
- Next.js와 Supabase를 선택한 이유를 기능 나열이 아닌 프로젝트 상황과 연결해 설명했다.
- 주문·결제·취소 과정의 가격 재검증, 재고 차감, RLS 적용과 정적 데이터 대비책을 핵심 기술 강점으로 정리했다.
- 발표 자료의 팀 회고가 좁아 보이지 않도록 팀원 네 명의 내용을 2×2 구조로 재배치했다.
- 공개 발표에 맞게 지나치게 유치한 색상을 피하고 회색·흰색 기반에 절제된 포인트 색상을 사용했다.

### 3. 발표 대본 다듬기

- 개발 과정을 모두 설명하기보다 서비스 제작 이유, 장점, 핵심 기술과 시연 흐름을 중심으로 대본을 구성했다.
- 프로젝트 목표를 다음과 같이 정리했다.

> 여러 아티스트의 굿즈를 한곳에서 발견하고, 탐색부터 구매까지 끊김 없이 경험할 수 있는 K-POP 굿즈 플랫폼을 만드는 것.

- 긴 기술 설명은 발표에서 이해하기 쉬운 표현으로 줄였다.
- UI 구성의 어려움은 “디자인 경험 부족으로 UI 구성과 이미지 품질을 통일하는 일이 어려웠다”는 문장으로 정리했다.
- 보안 설명은 “DB에서 가격과 재고를 검증하고 RLS로 사용자 데이터를 보호했으며, DB 장애에 대비해 정적 상품 데이터도 준비했다”는 내용으로 압축했다.

### 4. 예상 질문과 답변 준비

다음 주제를 중심으로 발표 후 질문에 대비했다.

- RLS를 통한 사용자 데이터 보호
- Supabase 장애 시 정적 상품 데이터를 사용하는 이유
- Next.js를 선택한 이유
- 이미지 로딩이 느린 원인과 개선 계획
- 3팀에서 11팀으로 확장한 이유
- 기존 굿즈 쇼핑몰과의 차별점
- 팀원 역할과 협업 방식
- 현재 결과물의 한계와 향후 개선 방향

### 5. 최종 발표 진행

- 프로젝트를 시작한 이유와 서비스의 장점을 먼저 설명했다.
- 실제 배포 화면을 통해 아티스트 탐색, 상품 확인, 장바구니, 주문 흐름을 시연했다.
- 프론트엔드 과제였지만 실제 서비스에 가까운 구매 흐름을 만들기 위해 서버 측 DB가 필요했던 이유를 설명했다.
- 기능 구현뿐 아니라 사용자 데이터와 재고를 안전하게 처리하기 위한 설계를 소개했다.
- 팀원별 회고와 프로젝트의 한계, 시간이 더 있다면 개선하고 싶은 부분까지 발표했다.

## 주요 기술 선택과 배운 점

### Next.js를 선택한 이유

상품과 이미지가 많은 쇼핑몰에서 첫 화면을 빠르게 제공하고, 페이지 단위로 역할을 나누어 협업하기에 적합하다고 판단했다. 동적 경로를 사용해 아티스트나 상품이 늘어나도 같은 페이지 구조를 재사용할 수 있었고, 서버와 브라우저의 역할도 화면 성격에 맞게 나눌 수 있었다.

### Supabase를 선택한 이유

재고, 구매 제한, 주문 내역처럼 여러 사용자가 함께 사용하는 데이터는 브라우저 저장소만으로 일관성을 보장하기 어렵다. 프로젝트 일정이 짧고 백엔드 담당이 한 명이었기 때문에 별도의 서버를 처음부터 구축하기보다 인증·DB·Storage를 한곳에서 제공하는 Supabase를 활용했다.

주문과 결제에서는 화면이 전달한 가격을 그대로 사용하지 않고 DB에서 다시 계산했다. 재고가 충분할 때만 차감되도록 DB 함수로 처리했으며, RLS를 적용해 사용자가 본인의 장바구니·주문·배송지만 조회하거나 수정할 수 있도록 제한했다.

## 이미지 로딩 문제 분석

이미지와 영상 파일이 크고 수가 많아 처음 접속할 때 로딩이 느려질 수 있었다. `next/image`를 사용하고 있어도 원본 파일의 크기와 외부 저장소에서 처음 가져오는 비용까지 모두 해결되지는 않는다.

발표에서는 이를 복잡한 용어보다 다음과 같이 설명했다.

> 이미지와 영상 파일이 크고 많아 처음 접속할 때 로딩이 느립니다. 이미지 규격과 불러오는 순서를 조정해 초기 로딩 속도를 개선할 계획입니다.

추후에는 이미지 업로드 규격을 통일하고, 첫 화면에서 꼭 필요한 요청을 구분하며, 모바일용 영상과 대표 이미지를 별도로 최적화해야 한다. 또한 실제 기기에서 LCP와 네트워크 요청을 측정해 체감 속도가 느린 정확한 지점을 확인할 필요가 있다.

## 프로젝트 진행 과정에서 어려웠던 점

가장 어려웠던 부분은 UI 구성이었다. 팀원들의 디자인 경험이 많지 않아 화면의 정보 배치와 분위기를 정하는 데 시간이 많이 들었다. 아티스트와 상품 이미지를 만들고 서로 다른 이미지의 품질과 스타일을 통일하는 작업도 예상보다 큰 비중을 차지했다.

Redmine 사용이 익숙하지 않았고 일정이 짧아, 기능 개발과 디자인 수정, 이미지 제작, 문서 정리를 동시에 진행해야 했다. 초반 설계 기준이 충분하지 않으면 구현 도중 같은 결정을 반복하게 되고 AI 사용량과 작업 시간도 함께 늘어난다는 점을 체감했다.

## 팀 회고

### 성호

작업을 빠르게 시작하는 것보다 충분한 사전 준비와 기준 합의가 중요하다는 점을 배웠다. 레퍼런스를 미리 조사하고 팀이 같은 결과를 떠올릴 수 있도록 기준을 정하면 협업 속도와 결과물의 완성도를 함께 높일 수 있다고 느꼈다.

### 충만

개발자의 입장에서 기능이 동작하는지만 확인하는 것과 실제 사용자의 입장에서 사이트를 이용하는 것은 다르다는 점을 배웠다. 사용 흐름을 따라가며 확인했을 때 예상하지 못했던 불편과 문제를 발견할 수 있었다.

### 지나

예쁜 화면을 만드는 것과 사용하기 편한 서비스를 만드는 것은 다르다는 점을 배웠다. 로고, 버튼, 호버 효과처럼 작은 요소도 페이지마다 구조와 동작이 다르면 서비스 전체의 일관성이 깨질 수 있어 공용 기준과 반복 검수가 중요하다고 느꼈다.

### 진

많은 이미지 파일을 저장소에 올리고 서비스에서 불러오는 과정에서 용량과 트래픽도 중요한 설계 요소라는 점을 배웠다. 기능뿐 아니라 시연에서 보이는 화면의 밀도와 디자인 완성도도 사용자의 첫인상과 서비스 평가에 큰 영향을 준다는 인사이트를 얻었다.

## 개인 회고

이번 프로젝트를 통해 프론트엔드는 단순히 화면을 예쁘게 만드는 작업이 아니라는 점을 다시 느꼈다. 하나의 버튼이나 로고를 바꾸는 작업도 로그인 상태, 페이지 구조, 모바일 화면에 따라 결과가 달라질 수 있었다. 따라서 구현 전에 공통 규칙을 세우고 실제 사용자 흐름으로 반복 확인하는 과정이 중요했다.

AI가 발전했더라도 내가 충분한 지식과 기준을 갖고 있지 않으면 원하는 결과를 정확히 얻기 어렵다는 점도 배웠다. 특히 디자인처럼 정답이 하나가 아닌 작업에서는 좋은 레퍼런스를 찾고, 원하는 결과를 구체적인 언어로 설명하고, 결과를 직접 판단할 수 있는 능력이 필요했다.

발표를 준비하면서는 많은 내용을 넣는 것보다 프로젝트의 시작 배경, 선택의 이유, 구현 결과와 배운 점이 하나의 이야기로 이어지는 것이 중요하다는 점을 알게 되었다. 기술적인 내용을 단순히 나열하지 않고 사용자의 문제와 연결해 설명해야 듣는 사람도 선택의 이유를 이해할 수 있었다.

## 현재 한계와 다음 단계

- 기존 K-POP 굿즈 플랫폼이 이미 강하게 자리 잡고 있어 실제 사용자를 모으려면 더 분명한 차별성이 필요하다.
- 아티스트 콘텐츠, 팬 참여 기능, 독점 상품처럼 KANT·MOA만의 이용 이유를 강화해야 한다.
- 이미지와 영상의 용량, 초기 로딩 요청, 모바일 반응형을 추가로 개선해야 한다.
- 다국어와 다양한 통화를 지원해 해외 사용자도 편리하게 이용할 수 있도록 확장하고 싶다.
- 장기적으로는 Supabase에 의존하지 않고 자체 백엔드를 구축해 서버 구조와 운영 경험까지 넓혀 보고 싶다.
