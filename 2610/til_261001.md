### 📝 [학습 기록] AI 바이브코딩을 활용한 DB 웹 관리 시스템 구축

#### 1. 무엇을 배웠는가? (What I Learned)
- **웹과 DB의 전체 연결 구조 이해**: 브라우저(HTTP 요청) ➔ 웹 서버(PHP) ➔ DB(MySQL) ➔ 웹 서버 ➔ 브라우저(HTML 응답)로 이어지는 데이터 흐름을 실습했습니다.
- **WAMP 로컬 개발 환경 구축**: Apache, PHP, MySQL, DBeaver를 연동하여 실제 운영 가능한 풀스택 구조의 최소 버전을 구현해 보았습니다.
- **대용량 Seed 데이터 구축**: 재귀 CTE(Recursive CTE)를 활용해 학생 1,000명, 수강신청 10,000건 등의 실무형 덤이 데이터를 직접 생성해 보았습니다.
- **JOIN 및 PDO/Prepared Statement**: 단순 단일 테이블 조회를 넘어 여러 테이블을 결합(JOIN)해 의미 있는 화면을 구성하고, SQL Injection을 방지하는 PDO 보안 방식을 적용했습니다.

---

#### 2. 어떤 생각을 했는가? (My Thoughts)
- **AI 바이브코딩의 역할과 한계**: AI를 활용하면 보일러플레이트 코드를 매우 빠르게 생성할 수 있지만, 프롬프트를 명확하게 정의(엔터티, 테이블 관계, 보안 규칙 지정 등)하지 않으면 원하는 결과를 얻기 어렵다는 것을 느꼈습니다.
- **코드 이해의 중요성**: AI가 코드를 다 짜주더라도 HTML/CSS/JavaScript/SQL을 직접 수정하고 제어할 줄 알아야 오류를 잡고 커스텀할 수 있음을 깨달았습니다. 결국 개발자의 핵심 역량은 '기초 흐름을 다루는 제어권'에 있다는 생각이 들었습니다.
- **동적 웹의 핵심**: 정적 웹과 달리 데이터베이스의 변화가 실시간으로 화면에 반영되는 과정을 직접 확인하면서, 데이터베이스가 웹 서비스에서 갖는 무게감을 실감했습니다.

---

#### 3. 무엇을 알게 되었는가? (Key Takeaways)
- **구조화된 데이터 표시**: `enrollments` 테이블처럼 ID 값만 갖고 있는 외래키 데이터를 사용자 친화적인 '학생명', '강좌명', '강사명'으로 변환하려면 **JOIN 문**이 필수적이라는 점을 확실히 알게 되었습니다.
- **직접 수정을 통한 역할 분담 체득**:
  - `HTML`: 웹 사이트의 구조와 내용 지정
  - `CSS`: 디자인 및 사용자 경험(UX) 개선
  - `JavaScript`: 클라이언트 측 이벤트를 통한 동적 반응
  - `SQL`: DB로부터 필요한 데이터 조건 추출 (`ORDER BY`, `LIMIT`, `WHERE`)
- **보안 및 실무 고려사항**: 교육용 설정(`root/1234`)과 달리 실제 환경에서는 보안 인증 및 Prepared Statement를 사용한 파라미터 바인딩이 필수적임을 이해했습니다.

### 📝 [학습 기록] LLM 기반 데이터 분석 실무 및 검증 프로세스 (Chapter 11 상세)

---

#### 1. 무엇을 배웠는가? (What I Learned)

* **STEP 0. Processed 데이터 고정 및 Raw Fallback 금지 원칙**:
  - 분석 환경 구축 시 `data/processed` 내 전처리 완료된 데이터셋만 입력으로 활용하도록 고정하는 법을 배웠습니다.
  - 데이터가 비어 있을 때 임의로 `raw` 데이터로 돌아가는 fallback을 철저히 금지함으로써, 정제되지 않은 데이터나 불필요한 개인정보가 분석에 혼입되는 위험을 근본적으로 차단하는 체계를 익혔습니다.

* **STEP 1. 분석 질문과 사람-AI 역할의 명확한 정의**:
  - LLM에게 무작정 질문하기 전에 분석 단위, 측정 지표(Metric), 데이터 내 계산 가능 여부를 사람이 먼저 확정해야 함을 배웠습니다.
  - LLM은 집계 코드 작성 및 검증 체크리스트 제안 등의 '초안 작성' 역할을 맡고, 사람은 실제 컬럼 병합 관계, 총합 산출, 해석 범위 판단 등 '최종 검증' 역할을 맡는 구조적 분업을 실습했습니다.

* **STEP 2~3. Safe Context 생성 및 자동 Validation의 한계 이해**:
  - 원본 행 데이터나 개인식별자를 배제하고, 데이터셋의 구조적 요약 및 민감 컬럼 리뷰 결과만을 포함한 `Safe Context` 생성 기법을 익혔습니다.
  - 자동화 스크립트를 통한 Validation 결과가 `PASS`로 나오더라도, 이는 기술적 최소 조건일 뿐 외부 LLM 전송 승인을 의미하는 것은 아니며 반드시 사람의 조직 정책 기반 검토가 동반되어야 함을 확인했습니다.

* **STEP 4~7. Prompt Contract 및 보안적 격리(Untrusted Data) 적용**:
  - 역할, 목적, 승인된 Context, 제약 조건, 계산 기준, 검증 조건을 명시하는 프롬프트 계약 구조를 실습했습니다.
  - 머신러닝 연계 시 타겟 누수 방지, Frozen Final Test 등의 엄격한 제약 조건을 적용하고, 외부 문서에 포함된 지시문("이전 지시 무시" 등)은 실행 명령이 아닌 단순 분석 대상 문자열(Untrusted Data)로 처리하여 프롬프트 인젝션을 방지하는 법을 배웠습니다.

* **STEP 8~12. Evidence Matrix 기반 검증 및 객관적 Usage Log 관리**:
  - LLM이 출력한 코드와 주장을 `df.columns`, `df.isna().sum()`, 행 수 확인, 수치 합계 비교 등 실제 코드를 통해 수치적 근거(Evidence)로 검증하고 '사용 / 수정 후 사용 / 보류'로 분류하는 프레임워크를 적용했습니다.
  - 자동 생성된 로그의 초기 상태(`not_executed`, `not_used`)를 유지하되, 실제 LLM을 호출하고 사람이 수정한 내역만 객관적으로 기록하여 분석의 재현성과 신뢰성을 확보했습니다.

---

#### 2. 어떤 생각을 했는가? (My Thoughts)

* **질문의 정교함이 AI 분석의 품질을 결정한다**:
  - 데이터를 그냥 넘겨주며 "분석해 줘"라고 할 때보다, 사람이 먼저 계산 가능 여부와 지표 기준을 명확히 설정했을 때 LLM이 비로소 정확한 코드 초안과 검증 항목을 제시할 수 있음을 깨달았습니다.
  - 결국 좋은 질문을 던지고 결과의 적절성을 판별하는 능력은 데이터 분석가 고유의 핵심 역량이라는 생각이 들었습니다.

* **기술적 자동 검증과 인간 판단의 상호보완성**:
  - 자동 Validation에서 `PASS`가 뜨는 것은 최악의 보안 사고를 막아주는 1차 방어선일 뿐이며, 생성된 Context를 실제로 외부에 공유해도 되는지 최종 판단하는 것은 사람의 책임이라는 점을 명심하게 되었습니다.
  - 편의성을 위해 보안이나 검증 절차를 생략하고 싶은 유혹이 들 때마다 체계적인 승인 프로세스가 왜 필요한지 체감했습니다.

* **환각(Hallucination) 방지와 Evidence 중심 사고방식**:
  - 그럴듯한 문장이나 깔끔한 코드 형태에 속지 않고, 직접 실행 결과를 수치적으로 대조(Evidence Matrix)해보는 과정이 데이터 분석의 신뢰도를 결정짓는 필수 관문임을 느꼈습니다.
  - 확실한 데이터 근거 없이 주장하는 비즈니스 원인 추론은 주장이 아닌 단순 '가설'로 남겨두어야 타당한 분석이 된다는 것을 알게 되었습니다.

---

#### 3. 무엇을 알게 됐는가? (Key Takeaways)

* **Safe Context 구축 메커니즘**:
  - `share_raw_values = no` 정책을 바탕으로 원본 행 예시를 절대 전달하지 않고, 메타데이터 구조 요약만으로 LLM에 안전하게 맥락을 제공하는 구체적 구현 방법을 파악했습니다.

* **프롬프트 보안 및 예외 처리 구별법**:
  - 외부 텍스트/문서 데이터 내에 명령어 형태의 텍스트가 섞여 들어오더라도 이를 실행 코드로 인식하지 않도록 격리하여 다루는 데이터 보안적 취약점 방어법을 알게 되었습니다.

* **실무형 데이터 분석 워크플로우의 완성**:
  - [입력 고정 ➔ 구조 요약 ➔ Safe Context 생성 ➔ 프롬프트 계약 작성 ➔ Evidence 검증 ➔ 사람 승인 ➔ Usage Log 기록]으로 이어지는 일련의 재현 가능한(Reproducible) LLM 활용 분석 표준 체계를 확립하게 되었습니다.
