# TIL | Make와 Supabase로 관광 데이터 수집·정제 자동화 실습

- 학습일: 2026-10-19
- 참고 자료: 「Chapter 14-2. 관광 데이터를 수집·저장하고 지도 기반 AI Dashboard로 서비스하기」
- 키워드: Make, HTTP API, Supabase, PostgreSQL Function, Database Trigger, Gemini, Next.js

## 오늘 학습한 내용

오늘은 NAVER와 한국관광공사 API에서 관광 관련 데이터를 가져오고, Make와 Supabase를 연결해 원본 데이터 저장부터 정제까지 자동화하는 실습을 진행했다. 수업 진도가 빠르고 여러 서비스의 화면을 동시에 오가다 보니 중간에 현재 단계를 놓치기도 했다. 그래도 마지막에는 각 도구가 맡는 역할과 데이터가 이동하는 순서를 조금 더 구체적으로 이해할 수 있었다.

오늘 완성한 핵심 흐름은 다음과 같다.

```text
HTTP 1: NAVER 검색 트렌드
    ↓
HTTP 2: 관광 체류 강도
    ↓
HTTP 3: 관광 소비 강도
    ↓
HTTP 4: NAVER Local 대표 장소
    ↓
Supabase raw_api_data에 원본 1행 저장
    ↓
PostgreSQL AFTER INSERT Trigger 실행
    ↓
naver_trend / tourism_demand / local_places로 자동 정제
```

이후 Dashboard 개발을 준비하기 위해 Next.js 프로젝트도 만들고 Supabase와 차트 패키지까지 설치했다.

## 1. Supabase 프로젝트와 데이터 모델 만들기

먼저 Supabase 프로젝트를 만들고 SQL Editor에서 관광 데이터용 테이블을 생성했다.

주요 테이블은 다음과 같다.

| 테이블 | 역할 |
|---|---|
| `raw_api_data` | 네 개 API의 원본 응답과 처리 상태 저장 |
| `regions` | 지역 코드, 지역명, 중심 좌표 저장 |
| `naver_trend` | 날짜·키워드별 NAVER 검색 관심도 저장 |
| `tourism_demand` | 날짜·지역별 체류 강도와 소비 강도 저장 |
| `local_places` | 대표 장소의 이름, 주소, 좌표 저장 |
| `ai_region_analysis` | AI가 작성한 지역 분석 결과 저장 |
| `collection_runs` | 수집 실행 상태와 오류 기록 |

처음에는 여러 테이블을 왜 나눠야 하는지 복잡하게 느껴졌다. 하지만 `raw_api_data`에는 API가 돌려준 원본을 보존하고, Dashboard에서 사용할 값은 정제 테이블로 분리한다는 구조를 이해하니 이유가 명확해졌다.

원본을 남겨 두면 정제 결과가 이상할 때 API 응답까지 거슬러 올라가 확인할 수 있다. 정제된 값만 저장하면 오류가 원본 데이터 때문인지 변환 로직 때문인지 찾기 어려울 수 있다.

## 2. Seed 데이터를 만들어 초기 화면용 데이터 확보

Dashboard를 처음 만들 때 API 수집 데이터가 충분하지 않을 수 있으므로 Seed 데이터를 준비했다. Python과 pandas를 이용하는 전용 작업 폴더를 만들고 CSV 데이터를 생성·정리했다.

```text
chapter14-2-seed/
├─ raw/
├─ processed/
└─ prepare_seed.py
```

처음에는 API가 여러 개인데 CSV 파일 하나만 만들어도 되는지 궁금했다. 중요한 것은 API 개수와 CSV 파일 개수가 일치하는지가 아니라, 최종 테이블 구조에 맞는 데이터가 충분히 들어 있는지였다. 체류 강도와 소비 강도처럼 최종적으로 같은 `tourism_demand` 테이블에 들어가는 값은 한 CSV 안에 정리할 수 있었다.

Seed 데이터는 Supabase CSV Import로 넣은 뒤 SQL로 행 수와 결측치를 확인했다. 데이터를 생성하는 것에서 끝나는 것이 아니라 실제 테이블에 들어갔는지, 숫자 컬럼이 숫자로 저장됐는지를 확인해야 했다.

## 3. Make에서 네 개 HTTP 요청 연결하기

Make Scenario에 HTTP 모듈 네 개를 순서대로 만들었다.

### HTTP 1 — NAVER Search Trend

NAVER Search Trend는 `POST` 요청을 사용했다.

- URL: NAVER Search Trend Endpoint
- 인증: 별도 인증 방식 대신 Header에 Client ID와 Client Secret 전달
- `Content-Type`: `application/json`
- Body: 시작일, 종료일, 월 단위 조회, 키워드 그룹

키워드는 여행, 축제, 캠핑, 맛집으로 구성했다. 응답의 `ratio`는 실제 검색 횟수가 아니라 상대 관심도라는 점을 다시 확인했다.

### HTTP 2 — 관광 체류 강도

한국관광공사 API는 `GET` 요청과 Query Parameter를 사용했다.

- `serviceKey`
- `MobileOS`
- `MobileApp`
- `baseYm`
- `areaCd`
- `tarSjrnDsIxCd`
- `pageNo`
- `numOfRows`
- `_type`

여기서 `numOfRows`를 충분히 크게 설정하지 않으면 기본 건수만 받아올 수 있다는 점을 배웠다.

### HTTP 3 — 관광 소비 강도

HTTP 2 모듈을 복제한 뒤 Endpoint와 지수 코드를 소비 강도용으로 변경했다. 비슷한 API라고 URL과 파라미터가 완전히 같은 것은 아니었다. 체류 강도의 `tarSjrnDsIxCd`와 소비 강도의 `tarExpDsIxCd`를 구분해야 했다.

### HTTP 4 — NAVER Local

NAVER Local Search는 대표 관광 장소를 검색하기 위해 사용했다.

- Method: `GET`
- Header: NAVER Client ID와 Client Secret
- Query: 검색어, 표시 개수, 시작 위치, 정렬 방식

여기서 `display = 5`는 지역의 모든 관광지를 수집한다는 뜻이 아니라 대표 장소 다섯 개를 지도 Marker 후보로 가져오는 설정이다.

## 4. 가장 어려웠던 부분: HTTP 모듈 설정과 API 인증

오늘 가장 많이 막힌 부분은 HTTP 요청 설정이었다. URL, Method, Header, Query Parameter, Body가 한 화면에 나오는데 각각의 역할이 익숙하지 않아 무엇을 어디에 입력해야 하는지 헷갈렸다.

특히 다음 오류를 경험했다.

### Authentication type과 Body structure 오류

HTTP 설정 화면에서 다음과 같은 오류가 표시됐다.

```text
Authentication type: Value must not be empty.
Body structure: Value must not be empty.
```

처음에는 API Key가 잘못돼서 생긴 오류라고 생각했지만, 실제로는 Make가 요구하는 필수 설정을 선택하지 않은 문제였다. 인증을 Header로 직접 전달하는 API는 `No authentication`을 선택하고, POST 요청에서는 Body 형식을 JSON으로 정확히 지정해야 했다.

### Header 이름과 값의 역할 혼동

NAVER API에서는 Header의 `Name`에 아래 항목명을 넣고, `Value`에 실제 발급값을 넣어야 한다.

```text
X-NCP-APIGW-API-KEY-ID
X-NCP-APIGW-API-KEY
```

처음에는 환경변수 형식인 `NAVER_CLIENT_ID=...` 전체를 넣어야 하는지 혼동했다. Make에서는 환경변수 선언문이 아니라 Header 이름과 값만 각각 넣는다는 점을 알게 됐다.

### 공공데이터 Service Key 위치 찾기

공공데이터포털에서 활용신청까지 했지만 실제 인증키가 어디 있는지 찾기 어려웠다. 개발계정 상세 화면에서 일반 인증키를 확인하고, 이를 URL 전체에 붙이는 대신 Make의 `serviceKey` Query Parameter 값으로 전달했다.

### JSON이 아니라 XML로 반환된 문제

관광공사 API가 HTTP 200을 반환했지만 출력이 XML인 경우가 있었다. 성공 표시만 보고 끝낼 것이 아니라 Output Bundle의 `Content-Type`과 실제 `Data` 내용을 확인해야 했다. `_type=json` 파라미터가 정확히 들어갔는지 확인하면서 응답 형식을 점검했다.

이 과정을 통해 초록색 체크와 HTTP 200만으로는 데이터 수집 성공을 판단할 수 없다는 것을 느꼈다. 필요한 필드와 행이 실제 응답에 포함됐는지까지 봐야 한다.

## 5. Make는 원본을 한 번만 저장하고 Supabase가 정제하도록 변경

처음에는 Make에서 API 응답을 하나씩 분리하고 반복 처리한 뒤 각 테이블에 저장하는 구조를 생각했다. 하지만 최종 구조에서는 Make가 네 API 응답을 `raw_api_data`의 한 행에 저장하고, Supabase가 Function과 Trigger로 정제하도록 역할을 나눴다.

Make의 Supabase `Create a Row` 모듈은 다음처럼 매핑했다.

```text
source                  = BATCH_RAW
naver_trend_raw         = HTTP 1 Data
tourism_demand_raw      = HTTP 2 Data
tourism_consumption_raw = HTTP 3 Data
naver_local_raw         = HTTP 4 Data
process_status          = PENDING
```

`run_id`와 `fetched_at`은 비워 두어 DB 기본값인 UUID 생성 함수와 `now()`가 적용되도록 했다.

이 구조는 Make Scenario를 단순하게 유지하고 데이터 처리 로직을 SQL로 관리할 수 있다는 장점이 있었다. Make 화면에서 Iterator, Router와 수많은 매핑을 모두 관리하는 것보다 문제가 생겼을 때 Function을 따로 테스트하기 쉬웠다.

## 6. PostgreSQL Function과 Trigger 만들기

Supabase SQL Editor에서 다음 처리 함수를 만들었다.

- `process_naver_trend_raw`
- `process_tourism_demand_raw`
- `process_naver_local_raw`

그리고 `raw_api_data`에 새 행이 들어온 직후 세 함수를 실행하는 `AFTER INSERT Trigger`를 연결했다.

```text
Make가 Raw INSERT
    ↓
trg_process_batch_raw 실행
    ↓
NAVER Trend 정제
관광 체류·소비 결합
NAVER Local 장소 정제
    ↓
성공: PROCESSED
실패: ERROR + error_message 기록
```

### Trigger 설치 전 데이터가 PENDING으로 남은 문제

처음 Make를 실행했을 때 `raw_api_data`의 첫 번째 행은 `PENDING` 상태였다. 데이터가 잘못 저장된 줄 알았지만, 그 행은 Trigger를 설치하기 전에 생성된 데이터였다. `AFTER INSERT Trigger`는 이미 존재하는 행을 자동으로 다시 처리하지 않고, 설치 이후 새로 INSERT되는 행부터 동작한다.

해결을 위해 Trigger 생성 후 Make를 다시 `Run once`로 실행했다. 새로 생성된 두 번째 행은 자동으로 `PROCESSED`로 바뀌었고 오류 메시지는 `NULL`이었다.

정제 결과는 다음과 같았다.

| 정제 테이블 | 생성된 행 수 |
|---|---:|
| `naver_trend` | 40 |
| `tourism_demand` | 26 |
| `local_places` | 5 |

이 결과를 통해 Make의 HTTP 네 개부터 Raw 저장, Trigger, 정제 테이블까지 실제로 연결됐음을 확인했다.

## 7. AI 요약 단계에서 혼동한 부분

교안에서는 AI가 Raw JSON을 직접 정리하지 않고, Trigger 처리가 끝난 검증 데이터만 설명하도록 역할을 제한한다.

```text
검증된 naver_trend / tourism_demand / local_places
    ↓
AI 요약
    ↓
ai_region_analysis 저장
```

하지만 수업 화면에서는 기존 수집 Scenario 뒤에 OpenAI 모듈을 바로 연결하는 모습도 나와 교안의 권장 구조와 차이가 있었다. 나는 비용이 발생하지 않도록 Gemini 사용을 선택했다. Make에 Google Gemini AI 모듈을 추가했지만, Connection에 개인 Gemini API Key를 연결해야 하는 단계에서 멈췄다.

AI 응답의 `summary`와 `limitations`를 분리하는 설명도 처음에는 이해하기 어려웠다. AI가 아래처럼 JSON 한 덩어리를 반환하면 정석은 JSON parsing을 통해 각 값을 꺼내 별도 컬럼에 저장하는 것이다.

```json
{
  "summary": "관광 데이터 요약",
  "limitations": "현재 데이터만으로 인과관계를 판단할 수 없음"
}
```

수업에서는 시간을 줄이기 위해 파싱 없이 AI 응답 전체를 저장하는 방식을 사용했다. 같은 `Result`를 `summary`와 `limitations` 양쪽에 넣으면 내용이 중복되므로, 파싱하지 않는다면 `summary`에 전체 응답을 넣고 `limitations`는 비워 두는 편이 더 자연스럽다고 생각했다.

현재 `ai_region_analysis`에는 저장된 행이 없으며, Gemini Connection과 결과 저장 모듈은 다음 실습에서 마무리해야 한다.

## 9. Next.js Dashboard 개발 준비

수집·정제 자동화를 그대로 둔 상태에서 별도의 Dashboard 프로젝트를 만들었다. Make와 Supabase를 지우거나 바꾸는 것이 아니라, Next.js가 Supabase의 정제 데이터를 읽어 화면으로 보여주는 구조다.

먼저 설치 상태를 확인했다.

```powershell
node --version
npm --version
npx --version
```

내 환경에는 다음 버전이 이미 설치돼 있어 npx를 별도로 설치할 필요가 없었다.

```text
Node.js v24.21.0
npm 11.19.0
npx 11.19.0
```

Next.js 프로젝트를 생성했다.

```powershell
npx create-next-app@latest tourism-dashboard `
  --typescript --tailwind --eslint --app --src-dir `
  --import-alias "@/*" --use-npm --yes
```

그리고 Supabase 연결과 차트에 필요한 패키지를 설치했다.

```powershell
npm install @supabase/supabase-js recharts
```

설치 결과는 다음과 같았다.

```text
@supabase/supabase-js 2.118.0
recharts 3.10.1
```

### Next.js 빌드에서 발생한 문제와 해결

처음 `npm run build`를 실행했을 때 Google Fonts에 접근하지 못해 Geist 폰트를 내려받는 과정에서 실패했다. 인터넷 접근을 허용해 다시 실행했지만 이번에는 Turbopack 내부 오류가 발생했다.

```text
TurbopackInternalError: Failed to write app endpoint /page
```

프로젝트 코드의 TypeScript 오류라기보다 Turbopack 처리 과정의 문제로 보였기 때문에 Webpack 방식으로 빌드를 다시 확인했다.

```powershell
npx next build --webpack
```

Webpack 빌드는 정상적으로 완료됐고 `/`와 `/_not-found` 정적 페이지 생성까지 확인했다. 오류가 발생했을 때 같은 명령만 반복하기보다 로그에서 어느 도구가 실패했는지 확인하고 다른 빌드 방식을 시험하는 것이 도움이 됐다.

## 오늘 어려웠던 점과 해결 방법 정리

| 어려웠던 점 | 원인 | 해결 방법 |
|---|---|---|
| Make에서 현재 단계와 모듈 순서를 놓침 | 수업 진도가 빠르고 화면을 여러 개 동시에 사용함 | 각 STEP의 최종 출력이 무엇인지 먼저 확인하고 하나씩 `Run once` 실행 |
| HTTP 필수값 오류 | Authentication Type과 Body 형식이 비어 있었음 | Header 인증 API는 `No authentication`, POST Body는 JSON으로 지정 |
| API Key 입력 위치 혼동 | 환경변수 문법과 HTTP Header 구조를 혼동함 | Header 이름과 실제 값을 Name/Value로 분리 |
| 관광 API가 XML로 반환됨 | `_type=json` 또는 파라미터 설정 문제 | Output Bundle과 Content-Type을 보고 Query Parameter 재확인 |
| 첫 Raw 행이 PENDING에 머묾 | Trigger 설치 전에 INSERT된 행이었음 | Trigger 설치 후 Make를 다시 실행해 새 행으로 검증 |
| AI 결과 컬럼 분리 이해가 어려움 | AI 결과가 JSON 문자열 한 덩어리로 반환됨 | JSON parsing의 역할을 이해하고, 미사용 시 전체 응답만 보관 |
| Gemini 모듈 실행 불가 | API Connection이 아직 생성되지 않음 | Gemini Key를 Make Connection에 연결한 뒤 Run once 필요 |
| Next.js 기본 빌드 실패 | Google Fonts 접근과 Turbopack 내부 오류 | 네트워크 확인 후 Webpack 빌드로 우회하여 프로젝트 정상 여부 검증 |

## 해보고 느낀 점

오늘 실습에서 가장 크게 느낀 점은 자동화 도구를 연결하는 것보다 **각 단계에서 무엇이 입력되고 무엇이 출력되는지 확인하는 습관**이 더 중요하다는 것이다. Make의 모듈에 초록색 체크가 표시돼도 원하는 데이터가 들어 있는지는 별개의 문제였다. HTTP Status, 응답 형식, 필드와 행 수를 직접 확인해야 했다.

처음에는 교수님의 화면과 똑같이 만드는 데만 집중해서 현재 어떤 데이터를 다루고 있는지 놓쳤다. 그러다 보니 HTTP 2와 HTTP 3의 차이, Header와 Query Parameter의 차이도 바로 이해하지 못했다. 이후에는 모듈 하나를 볼 때마다 “어디에서 받아서 어디로 보내는가”를 먼저 생각하니 흐름이 조금씩 보이기 시작했다.

Supabase Trigger가 특히 인상적이었다. 이전에는 데이터가 들어오면 Make가 모든 변환을 끝내야 한다고 생각했는데, Make는 원본을 안전하게 저장하고 DB가 정제하도록 나누니 Scenario가 훨씬 단순해졌다. 또한 원본과 정제 데이터를 연결하는 `raw_id` 덕분에 Dashboard의 숫자가 어떤 API 실행에서 만들어졌는지 추적할 수 있다는 점도 이해했다.

오류가 발생했을 때 처음에는 설정을 지우고 처음부터 다시 해야 한다고 생각했다. 하지만 실제로는 오류 메시지와 실행 결과를 보고 범위를 좁히는 편이 더 빨랐다. Trigger 이전에 생성된 `PENDING` 행처럼 실패가 아니라 실행 시점 차이 때문에 생긴 결과도 있었다. 오류처럼 보이는 결과를 바로 삭제하기보다 발생 순서와 조건을 확인해야겠다.

AI 단계에서는 수업 화면과 교안의 권장 구조가 달라 혼란스러웠다. 앞으로는 단순히 화면을 복제하기보다 비용, 데이터 검증, 유지보수 측면에서 왜 구조를 나누는지 생각하면서 선택해야겠다. 특히 AI는 데이터를 계산하거나 정답을 만드는 도구가 아니라, 검증된 결과를 설명하고 한계를 적는 역할로 제한하는 것이 안전하다고 느꼈다.

## 아직 잘 안 된 부분

오늘 모든 과정이 완전히 끝난 것은 아니다.

- Gemini Connection이 만들어지지 않아 AI 요약을 실제 실행하지 못했다.
- `ai_region_analysis`에 AI 결과가 아직 저장되지 않았다.
- Next.js의 `.env.local`과 Supabase Client 연결은 다음 단계에서 진행해야 한다.
- NAVER 지도, KPI 카드, Trend 차트와 AI 요약 화면은 아직 만들지 않았다.
- Make Schedule은 전체 검증 후 켜야 하므로 현재 비활성 상태로 두었다.
- npm 감사 결과에서 높은 심각도의 의존성 경고가 5건 표시됐으며, 프로젝트를 깨뜨릴 수 있는 `npm audit fix --force`는 실행하지 않았다.
