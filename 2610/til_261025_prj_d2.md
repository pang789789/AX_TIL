## 오늘 정리한 내용

오늘은 새로운 기능을 추가하지 않고, 프로젝트에서 내가 맡은 역할과 구현된 코드를 다시 정리했다. 처음 작업할 때는 여러 파일과 설정을 한꺼번에 다루느라 각 코드가 왜 필요한지 충분히 이해하지 못한 부분이 있었다. 그래서 오늘은 “무엇을 만들었는가”보다 “왜 이런 방식으로 처리했는가”를 중심으로 복습했다.

내 담당 범위는 다음 네 가지였다.

```text
회원
인증
마이페이지
기본 배송지
```

이를 실제 기능으로 나누면 로그인, JWT 발급·검증, 비밀번호 해싱, 로그아웃 토큰 차단, 내 정보 조회·수정, 기본 배송지 조회·수정·삭제였다.

## 1. 로그인은 단순한 이메일 확인이 아니었다

로그인 요청이 들어오면 먼저 이메일에 해당하는 사용자를 찾는다. 사용자가 존재한다고 바로 로그인시키는 것이 아니라 다음 조건을 순서대로 확인한다.

```text
사용자가 존재하는가?
→ 활성화된 사용자인가?
→ 입력 비밀번호가 저장된 해시와 일치하는가?
→ 모두 통과하면 JWT 발급
```

비밀번호는 DB에 원문으로 저장하지 않고 Argon2 해시로 저장했다. 로그인할 때 입력값을 복호화하는 것이 아니라, 입력한 비밀번호와 저장된 해시가 일치하는지 검증한다.

### 느낀 점

이전에는 로그인 기능을 아이디와 비밀번호를 비교하는 작업으로만 생각했다. 실제로는 비밀번호를 안전하게 저장하는 방법, 비활성 사용자를 막는 방법, 로그인 후 사용자를 식별하는 방법까지 포함된 기능이었다.

## 2. JWT는 로그인 결과이자 이후 요청의 신분증이다

로그인에 성공하면 FastAPI가 JWT를 발급한다. JWT에는 다음 정보가 들어간다.

- `sub`: 사용자 ID
- `jti`: 해당 토큰의 고유 ID
- `exp`: 토큰 만료 시간

사용자는 마이페이지처럼 인증이 필요한 API를 호출할 때 JWT를 함께 보낸다. 서버는 토큰을 단순히 해석하는 것이 아니라 다음 항목을 검사한다.

1. 서버 비밀키로 만든 정상적인 서명인지 확인한다.
2. 허용한 알고리즘인지 확인한다.
3. 만료된 토큰인지 확인한다.
4. 토큰 속 사용자가 실제로 존재하는지 확인한다.
5. 사용자가 활성 상태인지 확인한다.
6. 로그아웃으로 차단된 토큰인지 확인한다.

이 검사를 통과한 사용자만 보호된 API를 사용할 수 있다.

## 3. 다른 사용자의 정보를 수정하지 못하게 한 방법

마이페이지에서는 사용자 ID를 요청 데이터로 받아 처리하지 않았다. 클라이언트가 `user_id`를 보내도록 만들면 개발자 도구나 직접 만든 요청으로 다른 사람의 ID를 넣을 수 있기 때문이다.

대신 서버가 검증한 JWT의 `sub`에서 현재 사용자 ID를 얻고, 그 ID로만 프로필과 배송지를 조회하거나 수정했다.

```text
잘못된 방식
클라이언트가 user_id 전달 → 서버가 그대로 신뢰

적용한 방식
JWT 검증 → 서버가 현재 사용자 ID 확정 → 본인 데이터만 처리
```

### 배운 점

화면에서 다른 사람의 ID를 선택할 수 없다고 해서 안전한 것은 아니었다. 권한 검사는 항상 서버가 가진 신뢰할 수 있는 인증 정보로 처리해야 한다.

## 4. JWT 로그아웃에 블랙리스트가 필요한 이유

JWT는 발급된 후 서버 메모리에서 바로 삭제할 수 있는 세션이 아니다. 브라우저에서 JWT를 지우기만 하면 그 브라우저에서는 로그아웃된 것처럼 보이지만, 이미 복사된 토큰은 만료 전까지 다시 사용할 수 있다.

이를 막기 위해 각 JWT에 `jti`를 넣고 로그아웃 시 해당 값을 차단 토큰 테이블에 저장했다.

```text
로그아웃 요청
→ JWT의 jti와 만료 시간 확인
→ RevokedToken 테이블에 저장
→ 브라우저의 JWT 쿠키 삭제
→ 이후 같은 jti로 요청하면 401 반환
```

차단 토큰과 함께 만료 시간을 저장한 이유는 JWT가 만료된 후에는 해당 블랙리스트 데이터도 더 이상 필요하지 않기 때문이다.

### 어려웠던 점

처음에는 브라우저에서 토큰을 삭제하면 로그아웃 구현이 끝난다고 생각했다. 그러나 사용자의 화면에서 사라지는 것과 서버에서 다시 사용할 수 없는 것은 다른 문제였다. 로그아웃 요구사항에 “같은 토큰으로 다시 요청하면 401”이 있었기 때문에 서버 측 차단 기록이 필요했다.

## 5. 프론트엔드에서는 HTTP-only 쿠키를 사용했다

FastAPI에서 받은 JWT를 `localStorage`에 넣으면 JavaScript 코드에서 쉽게 읽을 수 있다. 하지만 XSS 문제가 발생하면 공격자가 토큰을 가져갈 수 있다.

그래서 Next.js 서버 액션이 FastAPI 로그인 API를 호출하고, 발급받은 JWT를 HTTP-only 쿠키에 저장하도록 연결했다.

```text
HttpOnly  → 브라우저 JavaScript에서 토큰을 읽지 못함
SameSite=Lax → 외부 사이트에서 발생하는 일부 요청 제한
Secure → 운영 환경에서는 HTTPS에서만 전송
Max-Age → JWT 만료 시간과 쿠키 수명을 맞춤
```

프론트 화면은 JWT 원문을 직접 다루지 않는다. 서버 컴포넌트와 서버 액션이 쿠키를 읽고 FastAPI 요청의 Authorization 헤더에 넣는다.

## 6. 가장 잘 안 됐던 부분: 로그인 후 마이페이지 접근 실패

로그인 API는 정상적으로 200을 반환했고 JWT 쿠키도 저장됐다. 그런데 `/mypage`로 이동하면 다시 로그인 화면으로 돌아가는 문제가 있었다.

처음에는 JWT 발급이나 쿠키 저장이 잘못됐다고 생각했다. 그러나 요청 흐름과 개발 서버 로그를 확인해보니 원인은 기존 Supabase 인증 미들웨어였다.

```text
FastAPI 로그인 성공
→ JWT 쿠키 저장
→ /mypage 요청
→ 기존 미들웨어가 Supabase 세션 검사
→ Supabase 세션이 없으므로 비로그인으로 판단
→ /login으로 리디렉션
```

로그인 화면과 마이페이지 API는 FastAPI로 바꿨지만, 보호 페이지에 들어가기 전에 실행되는 미들웨어는 기존 방식을 그대로 사용하고 있었다.

### 해결 방법

미들웨어도 FastAPI 인증 기준을 사용하도록 변경했다. 단순히 JWT 쿠키가 있는지만 확인하지 않고 FastAPI의 `/api/v1/users/me`를 호출해 실제 유효성을 검사했다.

```text
JWT 쿠키 확인
→ /users/me 호출
→ 서명·만료·사용자·블랙리스트 검증
→ 성공하면 보호 페이지 허용
→ 실패하면 쿠키 삭제 후 로그인 화면으로 이동
```

인증 서버에 연결할 수 없는 경우에도 보호 페이지를 열어주지 않는 `fail-closed` 방식으로 처리했다.

### 이 문제로 배운 점

인증 방식을 변경할 때 로그인 API만 바꾸면 되는 것이 아니었다. 프로젝트 안에서 로그인 여부를 확인하는 모든 지점을 찾아야 했다. 특히 미들웨어는 페이지 코드보다 먼저 실행되므로, 페이지 코드가 정상이어도 이전 인증 방식이 남아 있으면 접근할 수 없다.

## 7. 마이페이지와 기본 배송지 처리

내 정보와 기본 배송지는 다음 API로 처리했다.

| 기능 | Method | API |
|---|---|---|
| 로그인 | `POST` | `/api/v1/auth/login` |
| 로그아웃 | `POST` | `/api/v1/auth/logout` |
| 내 정보 조회 | `GET` | `/api/v1/users/me` |
| 프로필 수정 | `PATCH` | `/api/v1/users/me/profile` |
| 배송지 조회 | `GET` | `/api/v1/users/me/address` |
| 배송지 저장·수정 | `PUT` | `/api/v1/users/me/address` |
| 배송지 삭제 | `DELETE` | `/api/v1/users/me/address` |

배송지는 한 사용자에게 기본 배송지 하나가 존재하도록 구성했다. 처음 저장할 때는 생성하고 이미 있으면 같은 API에서 수정한다. 받는 사람, 연락처, 우편번호, 주소의 필수값과 형식도 서버에서 검증했다.

## 8. 기능을 확인한 방법

Swagger에서 다음 정상 흐름을 확인했다.

```text
로그인 200
→ 내 정보 조회 200
→ 배송지 저장 200
→ 배송지 재조회 200
→ 로그아웃 204
→ 로그아웃한 JWT 재사용 401
```

실제 브라우저에서도 다음 흐름을 검증했다.

```text
이메일 로그인
→ 메인 화면 이동
→ 마이페이지에서 이메일·닉네임·배송지 표시
→ 로그아웃
→ 마이페이지 재접근 시 로그인 화면으로 이동
```

테스트 결과는 다음과 같았다.

- FastAPI 테스트 4개 통과
- 프론트엔드 전체 테스트 68개 통과
- TypeScript 타입 검사 통과
- ESLint 통과
- 프로덕션 빌드 통과

## 오늘 다시 정리하며 느낀 점

처음 구현할 때는 파일이 많고 인증 용어도 익숙하지 않아 “일단 동작하도록 연결했다”는 느낌이 컸다. 오늘 요청이 들어오는 순서대로 다시 정리해보니 각 코드의 역할이 조금 더 명확해졌다.

특히 로그인, 인증, 권한은 서로 다른 단계라는 것을 알게 됐다.

```text
로그인: 이메일과 비밀번호로 사용자를 확인하는 단계
인증: 현재 요청을 보낸 사용자가 누구인지 확인하는 단계
권한: 확인된 사용자가 해당 데이터나 기능을 사용할 수 있는지 판단하는 단계
```

로그인 성공만 확인해서는 부족했다. 발급된 토큰이 다음 요청에서 제대로 전달되는지, 로그아웃 후 다시 사용할 수 없는지, 본인 데이터만 수정할 수 있는지까지 확인해야 인증 기능이 완성된다.

또한 오류가 발생했을 때 처음 예상한 부분만 반복해서 수정하기보다 전체 요청 경로를 단계별로 나눠 확인하는 것이 중요했다. 이번 문제도 JWT 자체가 아니라 JWT보다 먼저 실행되는 기존 미들웨어가 원인이었다. 다음부터는 다음 순서로 문제를 확인해야겠다.

1. 사용자가 어떤 요청을 보냈는지 확인한다.
2. 미들웨어와 서버 액션 중 무엇이 먼저 실행되는지 확인한다.
3. 각 단계의 응답 상태와 리디렉션을 확인한다.
4. 인증 정보가 어느 저장소와 기준을 사용하는지 확인한다.
5. 수정 후 정상 시나리오뿐 아니라 실패 시나리오도 다시 검증한다.

## 아직 공부가 필요한 부분

- Access Token과 Refresh Token을 함께 사용할 때의 재발급 구조
- JWT 블랙리스트 데이터의 만료 및 자동 정리 방법
- CSRF 공격과 SameSite 쿠키 설정의 관계
- 운영 환경에서 HTTPS와 `Secure` 쿠키 적용 방법
- 비밀번호 변경 및 재설정 시 기존 토큰을 무효화하는 방법
- 공통 인증 의존성을 다른 팀원의 주문·예약 API에서 사용하는 방법
- 관리자 권한을 역할 기반으로 확장하는 방법
