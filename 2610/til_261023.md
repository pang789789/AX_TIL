## 오늘 학습한 내용

오늘은 Upstage의 Solar 모델과 문서 처리 API를 이용해 서울시 조례에 질문할 수 있는 RAG 시스템을 실습했다. 단순히 LLM에게 질문하는 것이 아니라, 조례 원문에서 관련 근거를 먼저 검색하고 그 근거 안에서만 답하도록 만드는 전체 과정을 따라갔다.

처음에는 RAG가 LLM 앞에 검색 기능 하나를 붙이는 정도라고 생각했다. 직접 실습해 보니 문서를 읽고, 검색 가능한 크기로 나누고, 인용 정보를 붙이고, 검색 결과를 검증하는 여러 단계가 모두 정확해야 최종 답변의 품질이 좋아졌다.

오늘 진행한 흐름은 다음과 같다.

```text
서울시 조례 원문 수집
        ↓
HWP 별표를 Document Parse로 구조화
        ↓
조례를 조·항 단위 Chunk로 분할
        ↓
Solar Embedding으로 벡터 생성
        ↓
Keyword Search와 Embedding Search 결합
        ↓
질문과 관련된 근거 Top-K 검색
        ↓
Solar가 근거를 사용해 답변 생성
        ↓
코드가 Citation·URL·시행일을 조립
        ↓
근거가 부족하면 '확인 불가' 반환
```

## 1. 오늘 만든 RAG의 목표

오늘 만든 시스템의 목적은 서울시 조례에 대한 질문에 답하면서 실제 근거 조항을 함께 반환하는 것이다.

예를 들면 다음과 같은 질문을 처리한다.

```text
서울시 공영주차장 1급지 노상주차장 요금은 5분에 얼마인가요?
경차를 서울시 공영주차장에 세우면 할인을 받을 수 있나요?
유기견을 입양해 동물등록을 하면 수수료를 내야 하나요?
```

출력에는 단순 답변만 들어가는 것이 아니라 다음 정보가 함께 포함된다.

- 질문에 대한 짧은 답변
- 근거가 된 조례와 조항
- 원문 URL
- 조례 시행일
- 근거를 찾지 못했을 때의 `확인 불가`

### 해보고 느낀 점

법령처럼 정확성이 중요한 데이터에서는 자연스러운 문장보다 근거가 더 중요했다. 답변이 그럴듯해도 조항 번호나 금액이 틀리면 사용할 수 없기 때문에, 생성 능력만 보는 것이 아니라 검색과 검증을 함께 설계해야 했다.

## 2. 실습 환경과 파일 구조 준비

실습 폴더는 다음 파일로 구성돼 있었다.

```text
starter-kit/
├─ app.py
├─ build_index.py

├─ demo.py
```

각 파일의 역할을 먼저 확인했다.

| 파일 | 역할 |
|---|---|
| `fetch_ordinances.py` | 법제처 API에서 조례 수집 |
| `parse_annex.py` | HWP 별표를 Document Parse로 변환 |
| `build_index.py` | Chunk 생성과 Embedding 저장 |
| `rag.py` | 검색, 답변 생성, 검증 흐름 |
| `upstage.py` | Chat·Embedding·Document Parse API 호출 |
| `check.py` | 검색 및 답변 결과 셀프 채점 |
| `app.py` | FastAPI `/ask` 엔드포인트 |
| `config.py` | 모델명과 검색 설정 관리 |

Python 가상환경을 따로 만든 뒤 필요한 패키지를 설치했다.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

프로젝트별 가상환경을 사용하면 다른 프로젝트의 라이브러리 버전과 섞이지 않고, `requirements.txt`를 통해 같은 환경을 다시 만들 수 있다.

## 3. API Key와 `.env` 관리

Upstage API를 호출하기 위해 `.env` 파일에 본인의 API Key를 저장했다.

```text
UPSTAGE_API_KEY=...
LAW_OC=...
```

API Key를 Python 코드에 직접 적지 않고 환경변수로 분리했다. `.env`는 `.gitignore`에 포함해 GitHub에 올라가지 않도록 했다.

### 처음에 주의해야 했던 부분

친구에게 받은 ZIP에는 친구의 `.env`와 `.venv`도 함께 들어 있었다. 기존 키는 폐기됐지만, 다른 사람의 환경 파일을 그대로 사용하는 습관은 위험하다. 따라서 다음 항목은 제외하고 코드와 데이터만 사용했다.

- `.env`: 개인 API Key가 포함될 수 있음
- `.venv`: 컴퓨터와 Python 경로가 달라 재사용 시 충돌 가능
- `__pycache__`, `.pyc`: 다시 생성되는 캐시 파일

본인의 API Key를 별도의 `.env`에 연결하고 가상환경도 새로 만드는 것이 안전했다.

## 4. Upstage Studio에서 문서 처리 흐름 확인

코드를 실행하기 전에 Upstage Studio에서 문서를 직접 넣어 Parse와 Extract 흐름을 확인했다.

```text
문서 업로드
→ Document Parse
→ 문서 구조와 표 인식
→ Extract 스키마 적용
→ 필요한 필드 추출
```

Parse는 문서 전체를 읽어 제목, 문단, 표 같은 구조를 복원하는 역할이고, Extract는 복원된 문서에서 필요한 값을 정해진 JSON 형태로 뽑는 역할이라고 이해했다.

단순 OCR은 글자를 읽는 데 집중하지만 Document Parse는 표의 행과 열, 문서의 구조까지 최대한 보존한다는 차이가 있었다.

## 6. HWP 별표를 따로 처리한 이유

조례 본문은 비교적 일정한 문장 구조를 가지고 있지만, 요금표와 감면표는 별표 HWP 파일에 들어 있었다. 원본의 괘선 표를 일반 텍스트로 읽으면 행과 열의 관계가 무너질 수 있었다.

예를 들어 주차장 요금표에서 다음 정보는 같은 행으로 연결돼야 한다.

```text
주차장 종류 / 급지 / 주차 시간 / 요금
```

표 구조가 깨지면 1급지 요금과 다른 급지 요금을 잘못 연결할 수 있다. `parse_annex.py`에서 Document Parse API를 사용해 별표를 Markdown 표로 변환했다.

```powershell
python -X utf8 parse_annex.py
```

### 직접 비교하며 느낀 점

원본 텍스트에도 숫자는 존재했지만 어떤 열의 값인지 알아보기 어려웠다. Markdown 표에서는 행과 열이 유지되어 요금과 감면 조건을 정확하게 찾기 쉬웠다. 문서를 읽었다는 것과 문서의 구조를 이해했다는 것은 다르다는 점을 느꼈다.

## 7. Chunk의 의미

긴 조례 문서 전체를 한 번에 검색하거나 LLM에게 전달하지 않고 작은 단위로 나눈 것을 Chunk라고 한다.

```text
긴 조례 원문
→ 검색하기 좋은 작은 단위
→ 각 Chunk에 조례명·조항·URL·시행일 저장
```

Chunk가 너무 크면 질문과 관련 없는 내용이 함께 들어가 검색 정확도가 떨어질 수 있다. 반대로 너무 작으면 답변에 필요한 조건과 예외가 서로 떨어질 수 있다.

오늘은 조 단위인 `article`과 항 단위인 `paragraph`를 비교했다.

```python
CHUNK_UNIT = "paragraph"
```

항 단위 Chunk는 근거 위치를 더 정확하게 찾을 수 있었고, citation도 `제7조 제1항`처럼 구체적으로 만들 수 있었다.

## 8. Chunk마다 Citation 정보를 미리 저장하기

Chunk를 만들 때 텍스트만 저장하지 않고 인용에 필요한 정보를 함께 저장했다.

```json
{
  "id": 10,
  "law": "서울특별시 주차장 설치 및 관리 조례",
  "label": "서울특별시 주차장 설치 및 관리 조례 제7조 제1항",
  "text": "...",
  "effective_date": "...",
  "source_url": "..."
}
```

LLM에게 조항 번호를 직접 작성하게 하면 실제로 없는 조항을 만들거나 표기를 틀릴 수 있다. 그래서 LLM은 검색 결과에서 `evidence_id`만 고르고, citation 문자열은 코드가 해당 Chunk의 `label`을 이용해 만든다.

### 느낀 점

LLM이 모든 값을 자유롭게 만들도록 하는 것보다, 판단이 필요한 부분만 맡기고 정확해야 하는 값은 코드로 채우는 편이 안전했다.

## 9. Solar Embedding 이해하기

Embedding은 문장을 의미를 나타내는 숫자 벡터로 바꾸는 과정이다. 질문과 조례 문장을 같은 벡터 공간에서 비교하면 표현이 완전히 같지 않아도 의미가 비슷한 문서를 찾을 수 있다.

이 실습에서는 문서와 질문에 서로 다른 모델을 사용했다.

```python
EMBED_PASSAGE = "solar-embedding-2-passage"
EMBED_QUERY = "solar-embedding-2-query"
```

- Passage 모델: 저장할 조례 Chunk를 벡터로 변환
- Query 모델: 사용자의 질문을 검색용 벡터로 변환

`build_index.py`를 실행해 paragraph Chunk와 벡터 파일을 만들었다.

```powershell
python -X utf8 build_index.py
```

벡터는 `vectors_paragraph.npy`에 저장되어 매 질문마다 모든 문서를 다시 Embedding하지 않도록 했다.

## 10. Keyword Search를 함께 사용한 이유

Embedding 검색은 의미가 비슷한 문장을 찾는 데 유리하지만 법령명, 조항명, 정확한 숫자나 고유 용어를 놓칠 수 있다. 그래서 글자 단위 키워드 검색인 BM25 결과를 함께 사용했다.

```text
최종 검색 점수
= Embedding 유사도 × 0.7
+ Keyword 점수 × 0.3
```

```python
score = 0.7 * cosine_similarity + 0.3 * keyword_score
```

Embedding과 Keyword Search를 결합한 방식을 Hybrid Search라고 한다.

### 해보고 느낀 점

사람이 보기에는 같은 의미여도 문서와 질문에서 사용하는 표현이 다를 수 있다. Embedding은 이런 차이를 보완하고, 키워드 검색은 법령의 정확한 용어를 지켜주는 역할을 했다. 둘 중 하나만 사용하는 것보다 장점을 결합하는 것이 안정적이었다.

## 11. 검색 결과 점검

답변을 생성하기 전에 `check.py --retrieval`로 정답 근거가 Top-K 안에 들어오는지 확인했다.

```powershell
python -X utf8 check.py --retrieval
```

현재 설정은 다음과 같았다.

```text
CHUNK_UNIT = paragraph
TOP_K = 6
정답 근거가 Top-6 안에 들어온 비율 = 81%
```

주차장 요금, 금연구역 과태료, 경차 할인, 동물등록 수수료 같은 질문은 정답 근거가 검색됐다. 하지만 다음 유형은 일부 근거를 놓치거나 관련도가 낮은 조항이 섞였다.

- 청년의 나이 범위
- 장애인 할인과 다둥이 카드의 중복 적용
- 어린이공원 음주 관련 규정
- 자전거주차장 요금

### 가장 어려웠던 부분

검색 결과가 틀렸을 때 처음에는 LLM의 답변 능력 문제라고 생각했다. 하지만 LLM이 정답 근거를 전달받지 못하면 올바른 답을 만들기 어렵다. 생성 결과를 고치기 전에 검색 순위부터 확인해야 한다는 것을 배웠다.

## 12. RAG의 전체 구조

RAG는 Retrieval-Augmented Generation의 약자로, 검색한 근거를 LLM에게 함께 제공해 답하도록 만드는 방식이다.

```text
사용자 질문
→ 질문 Embedding
→ 관련 Chunk 검색
→ Top-K 근거 구성
→ 질문과 근거를 Solar에 전달
→ 답변과 evidence_id 반환
→ 코드가 citation·URL·시행일 조립
```

`rag.py`의 프롬프트는 제공된 근거 밖의 내용은 사용하지 않고, 찾을 수 없으면 `found=false`를 반환하도록 제한했다.

## 13. LLM 단독 답변과 RAG 답변 비교

`demo.py llm-only`를 사용해 검색 없이 Solar에게 바로 질문한 결과와 RAG 결과를 비교했다.

```powershell
python -X utf8 demo.py llm-only
```

검색 없이 질문하면 모델은 자연스러운 답변을 만들지만 조항 번호, 원문 링크, 시행일을 정확하게 보장할 수 없었다. 실제로 존재하지 않는 조항을 그럴듯하게 제시할 가능성도 있었다.

RAG에서는 검색한 조례 원문을 근거로 제공하고 코드가 citation을 채우기 때문에 답변의 출처를 확인할 수 있었다.

### 느낀 점

LLM의 말투가 자신 있어 보여도 사실이라는 보장은 없다. 특히 법령, 의료, 금융처럼 근거가 중요한 분야에서는 답변 내용뿐 아니라 어디에서 나온 정보인지 확인해야 한다.

## 14. URL과 시행일을 코드가 채우는 이유

원문 URL과 시행일도 LLM이 직접 작성하지 않는다. 검색된 Chunk에 저장된 값을 코드에서 가져온다.

```text
LLM의 역할: 근거 ID 선택과 답변 생성
코드의 역할: citation, source_url, effective_date 확정
```

이 방식은 링크를 지어내거나 서로 다른 시행 버전의 조례를 섞는 문제를 줄인다. 기준 시점에 시행 중인 문서인지 확인하는 것도 법령 RAG에서 중요했다.

## 15. 괘선 표와 Document Parse 결과 비교

`demo.py annex` 실습에서는 법제처 원문의 괘선 표와 Document Parse로 변환한 Markdown 표를 비교했다.

```powershell
python -X utf8 demo.py annex
```

질문은 공영주차장 1급지 노상주차장의 5분당 요금이었다. 정답은 500원이지만, 표 구조가 무너지면 다른 주차장 종류나 급지의 금액을 선택할 수 있었다.

Document Parse 결과에서는 표의 열과 행이 유지되어 해당 조건과 금액을 정확하게 연결할 수 있었다.

## 16. 조 단위와 항 단위 Chunk 비교

`demo.py chunk`를 실행해 article과 paragraph 단위의 검색 결과를 비교했다.

```powershell
python -X utf8 demo.py chunk
```

조 단위 Chunk는 앞뒤 문맥을 넓게 유지하지만 관련 없는 항까지 함께 포함될 수 있다. 항 단위 Chunk는 근거가 구체적이고 citation이 정확하지만, 원칙과 예외가 여러 항에 나뉜 경우 여러 Chunk를 함께 찾아야 한다.

실제 paragraph 설정의 검색 점검에서는 Top-K가 6일 때 정답 근거 포함률이 81%로 확인됐다.

## 17. 근거가 없으면 `확인 불가`로 답하기

STEP 30에서 가장 중요했던 내용은 답변을 하지 않는 것도 올바른 결과가 될 수 있다는 점이었다.

예를 들어 서울시 조례 데이터에 없는 질문이나 자치구 규칙을 묻는 질문에 모델이 알고 있는 일반 지식으로 답하면 안 된다.

```json
{
  "answer": "확인 불가",
  "citation": []
}
```

오늘 사용한 함정 질문에서는 관련도가 낮은 조항이 Top-1에 나타나기도 했다. 검색 결과가 하나 존재한다는 이유만으로 답변하면 틀린 근거를 인용하게 된다.

### 해보고 느낀 점

처음에는 모든 질문에 답하는 모델이 더 좋은 모델이라고 생각했다. 하지만 RAG에서는 근거가 없을 때 멈추는 능력이 신뢰도에 더 중요했다. 모르는 것을 모른다고 말하도록 만드는 것도 서비스 설계의 일부였다.

## 19. Groundedness 오류에서 배운 점

RAG 답변을 생성하는 과정에서 기존 `groundedness-check` 모델 호출이 400 오류를 반환했다. 검색과 답변 생성까지 모두 실패한 것처럼 보였지만, 실행 흐름을 나눠 보니 검색과 Solar 답변은 동작하고 마지막 근거 검증 호출에서만 실패했다.

이때 전체 코드를 한꺼번에 수정하지 않고 다음처럼 범위를 줄여 확인했다.

1. 검색 결과가 정상인지 확인한다.
2. Solar Chat 답변이 생성되는지 확인한다.
3. Groundedness 호출 직전과 직후를 구분한다.
4. API에서 현재 지원하는 모델 이름을 확인한다.
5. 검증을 임시로 끄더라도 원본 코드는 보존한다.

아직 STEP 30 범위에서는 모델을 임의로 바꾸지 않았고, 다음 단계에서 검증 구조와 현재 사용 가능한 모델을 확인하기로 했다. 오류가 났다고 검증 기능을 바로 삭제하면 잘못된 답변을 걸러낼 수 없기 때문이다.

## 해보고 느낀 점

오늘 실습에서 가장 크게 느낀 것은 RAG의 성능이 LLM 하나의 성능으로 결정되지 않는다는 점이다. 원본 문서를 잘 읽고, 적절한 크기로 나누고, 정확한 메타데이터를 붙이고, 검색 결과를 검증하는 전체 파이프라인이 중요했다.

특히 검색 정확도가 81%라는 숫자를 직접 확인하니 “검색이 잘 되는 것 같다”라는 느낌과 측정 결과가 다를 수 있다는 점을 알게 됐다. 틀린 질문을 따로 확인해야 다음 개선 방향도 정할 수 있었다.

또한 citation, URL, 시행일처럼 정확해야 하는 값은 LLM에게 자유롭게 만들게 하지 않고 코드와 원본 데이터에서 가져오는 방식이 인상적이었다. AI가 잘하는 일과 코드가 책임져야 하는 일을 나누는 것이 실제 서비스에서는 중요했다.

## 오늘 배운 내용을 내 말로 정리

RAG는 질문을 바로 LLM에게 보내는 방식이 아니다. 먼저 원본 문서를 검색 가능한 Chunk로 만들고, 질문과 관련 있는 근거를 찾은 뒤, 그 근거만 LLM에게 전달해 답변을 생성한다.

문서의 표 구조가 중요하면 Document Parse를 사용하고, 검색에서는 Embedding과 Keyword Search를 함께 사용할 수 있다. 조항 번호와 URL처럼 정확해야 하는 정보는 LLM이 만들지 않고 Chunk의 메타데이터에서 가져온다.

검색된 문서가 있다는 이유만으로 답변해서는 안 된다. 검색 점수가 낮거나 질문과 실제로 관련이 없다면 `확인 불가`라고 답해야 한다. 좋은 RAG는 많은 질문에 답하는 시스템이 아니라, 근거가 있는 질문에만 정확하게 답하는 시스템이다.

## 오늘의 한 줄 정리

> RAG의 핵심은 답변을 잘 만드는 것보다, 올바른 근거를 찾고 근거가 없을 때 멈추는 것이다.
