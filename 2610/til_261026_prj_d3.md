## 오늘 한 일

오늘은 내가 만든 인증 API만 따로 확인하는 수준을 넘어, 실제 브라우저에서 회원이 서비스를 이용하는 순서대로 기능을 점검했다. 로그인부터 상품 탐색, 장바구니, 주문, 찜, 체험 예약, 마이페이지, 로그아웃까지 직접 눌러 보면서 화면과 FastAPI, 실제 DB가 함께 정상적으로 동작하는지 확인했다.

또한 기존 화면에 남아 있던 Google 로그인 코드를 현재 FastAPI JWT 구조와 연결했다. Google 인증을 통과한 사용자도 일반 이메일 회원과 동일한 사용자 UUID를 사용하고, 이후 장바구니·주문·찜·예약에서 같은 사용자로 식별되도록 구성했다.

## 1. 실제 사용자 흐름으로 검증한 이유

자동 테스트가 통과하더라도 실제 화면에서는 다른 문제가 생길 수 있다. 예를 들어 로그인 API가 정상이어도 쿠키가 저장되지 않거나, 페이지 이동 과정에서 예전 인증 방식이 사용되거나, 화면 안내 문구와 실제 기능이 서로 다를 수 있다.

따라서 다음 순서대로 직접 검증했다.

```text
테스트 회원 생성
→ 실제 로그인 화면에서 로그인
→ 마이페이지 정보와 배송지 저장
→ 새로고침 후 저장값 재조회
→ 상품 검색·필터·찜
→ 장바구니 담기와 수량 변경
→ 모의 주문 생성
→ 주문 상세와 DB 저장 결과 확인
→ 체험 예약·취소
→ 로그아웃
→ 보호 페이지 재접근 차단 확인
```

### 확인한 정상 동작

- 아이디 또는 이메일과 비밀번호로 로그인했다.
- 프로필과 기본 배송지를 저장한 뒤 다시 조회해도 값이 유지됐다.
- 상품 검색과 필터가 URL과 목록에 반영됐다.
- 찜한 상품이 찜 목록에 표시됐다.
- 비회원도 장바구니를 사용하고 수량과 합계를 변경할 수 있었다.
- 로그인 후 비회원 장바구니가 회원 장바구니로 연결됐다.
- 주문 당시 상품 가격·배송지·배송비가 주문 상세에 저장됐다.
- 일반 사용자가 관리자 페이지에 접근하면 권한 오류로 차단됐다.
- 체험 예약 후 잔여석이 줄고, 취소 후 다시 복구됐다.
- 로그아웃 후 마이페이지와 찜 목록에 접근하면 로그인 화면으로 이동했다.

## 2. 테스트하면서 발견한 화면 문제

기능 자체는 동작했지만 사용자가 오해할 수 있는 문구와 배치가 있었다.

### 로그인 화면 정리

로그인 화면 하단의 회원가입 안내와 로그인 없이 둘러보기 링크가 서로 어긋나 있었다. 두 항목을 가운데 정렬해 한 화면 안에서 자연스럽게 보이도록 수정했다.

Google 로그인 버튼 아래에는 “Google 로그인을 준비하고 있어요”라는 문구가 항상 표시되고 있었다. 버튼 상태만으로도 준비 여부를 알 수 있고 화면이 중복되어 보여 해당 문구를 제거했다.

### 배송지 안내 문구 수정

기본 배송지가 없는 사용자에게도 “저장한 기본 배송지를 불러왔어요”라고 표시되는 문제가 있었다. 초기 배송지 존재 여부를 따로 판단해 다음처럼 나누었다.

```text
저장된 배송지가 있음
→ 저장한 기본 배송지를 불러왔어요.

저장된 배송지가 없음
→ 저장한 기본 배송지가 없어요. 이번 주문에 사용할 배송 정보를 입력해 주세요.
```

### 비밀번호 변경 설명 수정

마이페이지에는 실제 비밀번호 변경 폼이 있는데도 설명에는 비밀번호 변경이 지원되지 않는 것처럼 적혀 있었다. 비밀번호가 해시로 저장되며 현재 비밀번호를 확인한 뒤 변경할 수 있다는 내용으로 수정했다.

### 배운 점

백엔드 응답 코드만 확인하면 이런 문제를 발견하기 어렵다. 실제 사용자는 API가 아니라 화면의 문구와 이동 흐름을 보고 기능을 이해한다. 따라서 기능 테스트와 사용자 경험 검증을 함께 해야 한다.

## 3. Google 로그인과 일반 회원가입의 차이

일반 회원가입은 사용자가 아이디·이메일·비밀번호·닉네임을 직접 입력한다. FastAPI는 비밀번호를 해시한 뒤 계정을 생성하고 JWT를 발급한다.

Google 로그인은 앱이 Google 비밀번호를 받아서는 안 된다. Google과 Supabase가 사용자를 인증하고, 앱은 검증된 사용자 ID와 이메일만 전달받아 내부 계정과 연결해야 한다.

```text
일반 회원가입
사용자 입력 → FastAPI 검증 → 비밀번호 해시 → 계정 생성

Google 회원가입
Google 인증 → Supabase 세션 발급 → FastAPI가 세션 재검증
→ 같은 UUID의 앱 계정·프로필 생성 → FastAPI JWT 발급
```

## 4. Google 사용자를 FastAPI와 연결한 방법

기존 코드에는 Supabase의 `signInWithOAuth()`와 callback 경로가 있었지만, 인증 성공 후 FastAPI의 `app_users`와 연결하는 과정이 없었다. 이 상태에서는 Google 로그인 사용자가 화면에는 로그인된 것처럼 보여도 FastAPI 장바구니·주문 API에서는 다른 인증 체계의 사용자로 처리될 수 있었다.

이를 다음 흐름으로 변경했다.

1. 사용자가 `Google로 계속하기`를 누른다.
2. Supabase가 Google OAuth와 PKCE 인증을 처리한다.
3. `/auth/callback`에서 인증 코드를 Supabase 세션으로 교환한다.
4. Next.js 서버가 Supabase access token을 FastAPI에 전달한다.
5. FastAPI가 Supabase `/auth/v1/user`에 토큰을 보내 실제 사용자임을 다시 확인한다.
6. 최초 로그인이라면 `auth.users.id`와 같은 UUID로 `app_users`와 `profiles`를 만든다.
7. 기존 사용자라면 중복 생성하지 않고 같은 계정을 사용한다.
8. FastAPI JWT를 발급해 HttpOnly 쿠키에 저장한다.

### 보안상 중요했던 부분

- 브라우저가 전달한 사용자 ID와 이메일을 그대로 신뢰하지 않았다.
- FastAPI가 Supabase 서버에 토큰을 다시 확인한 뒤 계정을 만들었다.
- Google 비밀번호와 Client Secret을 앱 DB나 Git에 저장하지 않았다.
- Google 사용자도 `JWT sub = auth.users.id = app_users.id` 규칙을 유지했다.
- 동일 이메일이 다른 UUID 계정에서 이미 사용 중이면 자동으로 합치지 않고 충돌로 처리했다.

## 5. 어려웠던 부분과 해결 방법

### 두 개의 인증 체계를 하나로 연결하기

Supabase OAuth 세션과 FastAPI JWT가 동시에 존재하면 어느 쪽을 기준으로 사용자를 식별할지 모호해질 수 있었다. Google 인증은 Supabase가 담당하되, 서비스의 보호 API와 소유권 검사는 FastAPI JWT를 사용하도록 역할을 나누었다.

```text
Supabase: Google이 실제 사용자인지 인증
FastAPI: 내부 계정 생성, JWT 발급, 권한·소유권 검사
```

### 사용자 UUID 유지하기

장바구니·주문·프로필·찜·예약은 모두 `auth.users.id`를 참조한다. Google 사용자를 별도의 UUID로 만들면 외래키와 소유권 검사가 어긋난다. 따라서 Supabase가 생성한 UUID를 그대로 `app_users.id`와 JWT `sub`에 사용했다.

### 전체 테스트에서 발생한 DB 연결 오류

프런트엔드 테스트와 인증 관련 백엔드 테스트는 통과했지만, 백엔드 전체 테스트 중 실제 DB에 동시에 접속하는 테스트 일부가 실패했다. 오류 원인은 코드 로직이 아니라 팀 Supabase의 session mode 최대 연결 수 15개를 초과한 것이었다.

```text
오류: EMAXCONNSESSION
원인: 여러 테스트와 실행 중인 서버가 DB 연결을 동시에 사용
대응: 변경한 인증 단위 테스트를 별도로 실행해 정상 통과 확인
추후: 연결 풀 크기 축소 또는 transaction pooler 검토
```

이 경험을 통해 테스트 실패를 바로 코드 오류로 단정하지 않고, 실패한 계층과 외부 환경을 구분해서 확인해야 한다는 것을 배웠다.

## 7. 아직 실제 연동에 필요한 설정

코드 연결은 완료했지만 실제 Google 계정 선택 화면을 사용하려면 외부 설정이 필요하다.

- Google Cloud에서 OAuth Client ID와 Secret 생성
- Supabase에서 Google Provider 활성화
- Supabase URL Configuration에 callback 주소 등록
- 프런트 환경변수에 Supabase URL·공개 키 설정
- 백엔드 환경변수에 같은 `SUPABASE_URL`·`SUPABASE_ANON_KEY` 설정
- 로컬과 배포 환경에서 각각 실제 로그인 검증

Client Secret은 Supabase 대시보드에만 저장하고 `.env`, 문서, 채팅, Git에는 남기지 않아야 한다.

## 오늘 느낀 점

처음에는 “사이트를 전부 눌러 본다”는 것이 단순 확인 작업이라고 생각했다. 하지만 실제로 해보니 자동 테스트가 확인하는 로직과 사람이 화면에서 느끼는 문제는 서로 달랐다. 배송지 안내처럼 기능은 성공하지만 설명이 틀린 경우도 있었고, 로그인처럼 한 화면의 성공만으로는 전체 인증 흐름이 완성됐다고 할 수 없는 경우도 있었다.

Google 로그인도 버튼 하나를 활성화하는 작업이 아니었다. 외부 인증 결과를 내부 회원 데이터와 연결하고, 기존 주문·찜·예약이 사용하는 UUID 규칙을 유지하며, 최종적으로 FastAPI JWT까지 발급해야 했다.

앞으로는 인증 기능을 구현할 때 다음 세 가지를 함께 확인해야겠다.

1. 외부 인증 제공자가 사용자를 어떻게 증명하는가?
2. 내부 서비스는 그 사용자를 어떤 ID로 저장하는가?
3. 이후 모든 API는 어떤 토큰과 ID로 권한을 검사하는가?
