# 🎤 아이돌 굿즈 쇼핑몰 프로젝트

## 1. 프로젝트 시작 배경

이번 프로젝트는 **React와 Next.js를 활용하여 쇼핑몰 웹사이트를 제작하는 팀 프로젝트**이다.

주어진 과제는 하나의 쇼핑몰 주제를 선정하고, 가상의 상품 데이터를 활용하여 실제 쇼핑몰처럼 작동하는 웹페이지를 구현하는 것이다.

기본적으로 다음 세 가지 페이지를 제작해야 한다.

- 메인 페이지
- 상품 목록 페이지
- 상품 상세 페이지

단순히 화면을 만드는 것뿐만 아니라 컴포넌트를 분리하고, 페이지 간 이동을 연결하며, 하나의 웹사이트를 완성하는 과정을 경험하는 것이 목표이다.

**사용 기술**
- Next.js (App Router)
- React
- TypeScript
- Tailwind CSS
- Git / GitHub

---

## 2. 초기 아이디어 — KANT 굿즈 쇼핑몰

프로젝트를 처음 시작했을 때는 우리 소속인 **KANT의 굿즈를 판매하는 쇼핑몰**을 만들기로 했다.

KANT라는 공통된 주제가 있기 때문에 팀원들이 같은 콘셉트 안에서 상품을 구상하고, 하나의 쇼핑몰을 만드는 방향이었다.

하지만 아이디어를 구체화하면서 굿즈의 종류나 디자인을 조금 더 자유롭게 만들어 보면 좋겠다는 생각이 들었다.

하나의 소속 굿즈에만 집중하기보다 각자 다른 콘셉트를 가지고 상품을 기획한다면, 더 다양하고 개성 있는 결과물이 나올 수 있을 것 같았다.

---

## 3. 기획 방향 변경 — 각자의 아이돌 그룹 만들기

기존의 KANT 굿즈 쇼핑몰에서 아이디어를 확장하여, **팀원들이 각자 가상의 연예인 또는 아이돌 그룹을 만들고 해당 아티스트의 굿즈를 담당하는 방식**으로 방향을 변경했다.

단순히 상품만 다르게 제작하는 것이 아니라 각자가 담당하는 아티스트의 콘셉트와 분위기까지 직접 설정하는 것이다.

예를 들어 다음과 같은 요소를 각자 기획할 수 있다.

- 아이돌 그룹 이름 및 콘셉트
- 멤버 구성과 캐릭터
- 그룹의 대표 색상과 분위기
- 앨범 및 굿즈 디자인
- 아티스트 소개 페이지
- 아티스트별 상품 목록과 상세 페이지

이렇게 하면 하나의 주제에 맞추는 방식보다 팀원 개개인의 아이디어를 자유롭게 표현할 수 있다.

또한 같은 쇼핑몰이라는 틀 안에서도 서로 다른 스타일의 페이지와 굿즈를 보여 줄 수 있다는 장점이 있다.

### 기획 변화 요약

| 구분 | 초기 기획 | 변경된 기획 |
|---|---|---|
| 주제 | KANT 굿즈 | 가상 아이돌 그룹 굿즈 |
| 상품 콘셉트 | 공통 브랜드 중심 | 각 아티스트의 개성 중심 |
| 기획 방식 | 하나의 주제 공유 | 각자 아티스트 담당 |
| 디자인 | 통일된 브랜드 콘셉트 | 아티스트별 다양한 콘셉트 |
| 확장 방향 | 일반 굿즈 쇼핑몰 | 아티스트 소개와 굿즈 쇼핑몰 결합 |

## 4. 현재 프로젝트 방향

현재는 **가상의 아이돌 그룹을 직접 기획하고, 해당 그룹의 공식 굿즈를 판매하는 쇼핑몰을 구현하는 방향**으로 진행하고 있다.

실제 아이돌 굿즈 판매 플랫폼인 **위버스샵(Weverse Shop)**을 참고하여 쇼핑몰의 구성과 상품 표현 방식을 구상하고 있다.

쇼핑몰에서 상품을 보여 주는 것뿐 아니라, 방문자가 아티스트에 대해서도 알아볼 수 있도록 다양한 페이지를 구성하고자 한다.

### 주요 페이지 구성

**① 메인 페이지**

쇼핑몰에 처음 접속했을 때 보이는 화면으로 아티스트와 대표 상품을 소개한다.

**② 아티스트 소개 페이지**

담당 아이돌 그룹의 콘셉트, 멤버, 프로필 등을 보여 주는 페이지이다.

**③ 굿즈 목록 페이지**

앨범, 응원용품, 인형 등 다양한 상품을 카테고리별로 보여 준다.

**④ 굿즈 상세 페이지**

각 상품의 이미지, 가격, 설명 등을 확인할 수 있는 페이지이다.

## 5. 내가 담당하는 기획 방향

나는 나만의 가상 아이돌 그룹을 만들고, 그 그룹을 중심으로 다양한 굿즈와 웹페이지를 제작하는 방향으로 구상하고 있다.

특히 단순한 상품 나열보다는 **실제 아이돌 공식 쇼핑몰에 접속한 것 같은 느낌**을 주고 싶다.

### 굿즈 카테고리

현재 내가 구성한 굿즈 카테고리는 총 7개이다.

1. 앨범
2. 응원용품
3. 인형
4. 액세서리
5. 의류
6. 생활용품
7. 멤버십 카드

각 카테고리에 맞는 상품을 기획하고, 아이돌 그룹의 콘셉트가 상품 디자인에서도 드러나도록 구성할 예정이다.

### 디자인 방향

- 아티스트의 콘셉트와 어울리는 시각적 디자인
- 실제 공식 굿즈 쇼핑몰을 참고한 상품 이미지 구성
- 멤버별 개성을 살린 소개 페이지
- 페이지를 스크롤하면서 아티스트 정보를 자연스럽게 살펴볼 수 있는 구성
- 상품 탐색부터 상세 정보 확인까지 이어지는 사용자 경험

## 6. 프로젝트를 통해 구현하고 싶은 것

이번 프로젝트에서는 단순히 주어진 세 가지 화면을 만드는 데 그치지 않고, 하나의 브랜드가 운영하는 쇼핑몰처럼 완성도 있는 웹사이트를 만들어 보고 싶다.

이를 위해 다음과 같은 부분을 중요하게 생각하고 있다.

- **콘셉트의 일관성:** 아이돌 그룹, 굿즈, 웹페이지가 같은 분위기를 유지하도록 구성
- **디자인의 완성도:** 실제 쇼핑몰처럼 자연스럽고 정돈된 UI 제작
- **다양한 페이지 경험:** 상품뿐만 아니라 아티스트 자체를 소개할 수 있는 페이지 구성
- **사용자 흐름:** 방문자가 상품을 찾아보고 상세 페이지까지 자연스럽게 이동하도록 구현
- **개인별 개성:** 팀원들이 각자 담당한 아이돌과 굿즈를 통해 서로 다른 아이디어를 표현

## 1. 로컬 개발 환경 설정

### 어떤 작업을 하였는가

GitHub 저장소를 내려받고 `dev/jina` 브랜치에서 작업을 시작했다. Node.js와 npm을 설치한 뒤 `npm run dev`로 개발 서버 실행을 시도했다.

### 어떤 문제가 있었는가

VS Code 터미널에서 `node`와 `npm`이 실행 프로그램으로 인식되지 않았다. Node.js는 설치되어 있었지만 `C:\Program Files\nodejs`가 현재 PowerShell 세션의 `PATH`에 반영되지 않은 상태였다.

### 어떠한 방법으로 재시도하였는가

다음 명령어로 설치 여부를 확인했다.

    Test-Path "C:\Program Files\nodejs\node.exe"

현재 PowerShell 세션에 Node.js 경로를 추가한 뒤 버전을 다시 확인했다.

    $env:Path = "C:\Program Files\nodejs;$env:Path"
    node -v
    npm -v

이후 사용자 환경변수 `PATH`에도 Node.js 경로를 등록하고 VS Code를 완전히 종료한 뒤 다시 실행했다.

### 앞으로 어떻게 할 것인가

새 개발 환경에서는 `node -v`, `npm -v`, Node.js 설치 경로, `PATH` 등록 여부를 먼저 확인한다.

## 2. 브랜치 및 최신 develop 반영

### 어떤 작업을 하였는가

개인 작업은 `dev/jina`에서 진행하고 작업 전마다 원격 `develop`을 반영했다.

    git switch dev/jina
    git status
    git fetch origin
    git merge origin/develop

### 어떤 문제가 있었는가

병합 도중 Git이 Vim 편집기를 열어 병합 커밋 메시지를 요구했다. 일반 터미널과 다른 화면이 나타나 병합이 멈춘 것으로 오해했다. `git pull`을 반복하면서 개인 로컬 저장소에 불필요한 병합 커밋이 생기기도 했다.

### 어떠한 방법으로 재시도하였는가

Vim에서는 `Esc`를 누르고 `:wq`를 입력한 뒤 Enter를 눌러 기본 병합 메시지를 저장했다. 로컬 변경 없이 단순 최신화가 가능한 경우에는 다음 명령어로 fast-forward만 허용했다.

    git merge --ff-only origin/develop

### 앞으로 어떻게 할 것인가

병합 전 반드시 `git status`를 확인한다. 개인 브랜치 변경은 `dev/jina → develop PR → 리뷰 승인 → Squash merge` 흐름으로 공유하고 `main`에는 직접 병합하지 않는다.

## 3. 공통 레이아웃 및 공용 UI 구현

### 어떤 작업을 하였는가

다음 공통 요소를 구현했다.

- Header와 Footer
- KANT MOA 로고 컴포넌트
- 공용 Button, Input, Modal
- 콘텐츠 너비와 반응형 레이아웃
- 전역 색상·그림자·라운드 디자인 토큰
- 키보드 포커스 스타일
- 본문 바로가기 링크

### 어떤 문제가 있었는가

초기 헤더에는 홈, 아티스트, 상품, 검색, 장바구니, 로그인 메뉴가 모두 있어 로고와 함께 보았을 때 복잡했다. 로그인 후 닉네임은 길이에 따라 헤더 너비가 달라졌다.

### 어떠한 방법으로 재시도하였는가

로고 옆의 홈·아티스트·상품 메뉴를 제거하고 참고 이미지에 맞춰 검색 아이콘도 제거했다. 닉네임 대신 고정 텍스트 `MY`를 표시하고 클릭 시 `/mypage`로 이동하도록 했다.

최종 헤더 구성은 다음과 같다.

- KANT MOA 로고
- 장바구니
- 로그인 전: 로그인
- 로그인 후: MY, 로그아웃

### 앞으로 어떻게 할 것인가

공통 컴포넌트 변경 후 메인, 아티스트, 상품, 장바구니, 주문, 마이페이지, 로그인·회원가입 화면을 함께 확인한다.

## 4. KANT MOA 브랜드 로고 제작

### 어떤 작업을 하였는가

풍선처럼 부풀어 오른 비눗방울 글자와 민트·라일락·핑크 굴절광을 사용한 KANT MOA 로고를 제작했다.

### 어떤 문제가 있었는가

초기 로고는 색상이 너무 진했고 작은 헤더 크기에서 가독성이 떨어졌다. 참고 이미지보다 입체감이 부족했고 사이트 배경과 함께 보았을 때 지나치게 화려했다.

### 어떠한 방법으로 재시도하였는가

글자 두께와 내부 명도를 높이고 채도와 외곽선을 줄였다. 헤더 크기에서도 읽을 수 있도록 글자 간격을 조정하고 투명 PNG로 적용했다.

### 앞으로 어떻게 할 것인가

로고는 큰 원본뿐 아니라 헤더, 푸터, 모바일, 흰색 배경 등 실제 사용 크기에서도 확인한다.

## 5. 로그인·회원가입 및 인증 Provider 구현

### 어떤 작업을 하였는가

실제 Supabase 서비스를 사용하는 로그인·회원가입 화면을 구현했다.

- `/login`, `/signup`
- 입력값 검증과 서비스 오류 표시

- `onAuthChange` 1회 구독
- 로그인 시 비회원 장바구니 자동 병합 준비

### 어떤 문제가 있었는가

작업용 저장소에 Supabase 환경변수가 없어 `supabaseUrl is required` 오류가 발생했다. Supabase 서비스를 정적으로 import하면 모듈 평가 시점에 클라이언트 생성이 실행되어 화면 전체가 중단됐다. `.env.local`이 없을 때 `next.config.ts`에서도 `undefined/storage/...` URL 오류가 발생했다.

### 어떠한 방법으로 재시도하였는가

인증 서비스는 사용자 동작 시점에 동적으로 불러왔다.

    const { signIn } = await import("@/services/auth");

`AuthProvider`에서도 인증 서비스를 동적으로 불러오고 환경설정 오류가 발생해도 화면이 계속 로딩 상태로 남지 않도록 예외 처리를 추가했다. 팀에서 전달받은 값을 `.env.local`에 입력한 뒤 서버를 완전히 종료하고 다시 실행했다.

    Ctrl+C
    npm run dev

테스트 계정 정보는 소스에 하드코딩하지 않았다.

### 앞으로 어떻게 할 것인가

비회원 장바구니 추가, 로그인, 장바구니 병합, 새로고침 후 세션 유지, 로그아웃, 회원가입 후 자동 로그인 순서로 테스트한다. `.env.local`은 절대 커밋하지 않는다.

## 6. 헤더 호버 스타일 적용 및 반복 수정

### 어떤 작업을 하였는가

장바구니, 로그인, MY, 로그아웃, 인증 전환 링크, 주요 공용 버튼에 KANT MOA 로고 색상의 호버 스타일을 적용했다.

### 어떤 문제가 있었는가

첫 시도에서는 민트 단색 때문에 로고의 다양한 색감과 어울리지 않았다. 그라데이션을 적용한 뒤에는 기존의 마우스 반응이 약해졌다. 아이콘과 계정 메뉴가 서로 다른 팔레트를 사용해 명도가 달랐고, 회색을 섞어 맞추자 색감이 탁해졌다. 로그인 전과 로그인 후 계정 메뉴의 스타일도 일치하지 않았다.

### 어떠한 방법으로 재시도하였는가

다음 순서로 반복 수정했다.

1. 민트 단색을 민트·라일락·핑크 그라데이션으로 변경
2. 기존의 살짝 어두워지는 반응 복원
3. 아이콘과 계정 메뉴를 공통 CSS 클래스로 통합
4. 로그인 후 MY와 로그아웃에도 동일한 효과 적용
5. 회색기를 제거하고 밝은 파스텔 색으로 조정
6. 그림자와 테두리 강도 축소
7. 모든 헤더 액션의 배경 명도 통일

### 앞으로 어떻게 할 것인가

일반·호버·포커스 상태와 로그인 전·후, 데스크톱·모바일을 모두 비교한다. 디자인이 확정되기 전에는 커밋하지 않고, “커밋하자”는 확인 후에만 커밋·푸시한다.

---

## 7. 공통 스타일이 다른 팀원 화면에서 보이지 않았던 문제

### 어떤 작업을 하였는가

공통 헤더 호버 스타일을 `dev/jina`에 커밋하고 PR을 통해 `develop`에 공유했다.

### 어떤 문제가 있었는가

JINA 화면에서는 호버가 보였지만 다른 팀원 화면에서는 보이지 않았다. 각 팀원은 개인 브랜치에서 작업 중이므로 `develop` 변경사항을 자신의 브랜치에 병합해야 했다. 또한 공통 헤더의 호버가 다른 담당자의 개별 상품 카드나 주문 버튼에 자동으로 적용되는 것은 아니었다.

### 어떠한 방법으로 재시도하였는가

각 팀원이 자신의 브랜치에서 다음 명령어를 실행하도록 안내했다.

    git fetch origin
    git merge origin/develop

커밋 포함 여부는 다음 명령어로 확인했다.

    git branch --contains <커밋 해시>

이후 개발 서버를 재실행하고 브라우저에서 `Ctrl+Shift+R`로 강력 새로고침했다.

### 앞으로 어떻게 할 것인가

공통 헤더, 공용 UI, 개별 페이지 요소의 적용 범위를 구분한다. “최신화했다”는 말뿐 아니라 개인 브랜치에 실제 커밋이 포함되었는지 확인한다.

## 8. 아티스트 페이지 배경 이미지 구조 검토

### 어떤 작업을 하였는가

아티스트별 분위기에 맞는 hero 이미지를 사용할 수 있도록 구조를 검토했다. 1920×720 hero 이미지, 이미지가 없을 때 `themeColor` 기반 fallback, 모바일 포커스 위치, 불투명 콘텐츠 영역을 제안했다.

### 어떤 문제가 있었는가

초기 `Artist` 타입에는 `logoUrl`과 `themeColor`만 있었고 배경 이미지 필드가 없었다. 아티스트 페이지는 CHUNGMAN 담당이어서 JINA가 직접 수정하면 담당 영역 충돌이 발생할 수 있었다.

### 어떠한 방법으로 재시도하였는가

직접 페이지를 수정하지 않고 DB hero 경로, `heroImageUrl` 타입, Storage 경로, fallback 동작을 백엔드와 담당자에게 제안했다. 이후 백엔드 변경과 CHUNGMAN의 아티스트 배너 캐러셀 구현을 최신 `develop`에서 반영했다.

### 앞으로 어떻게 할 것인가

다른 담당자 파일의 수정이 필요하면 데이터 필드, 타입, 경로, UI 구현안, fallback을 먼저 공유한다.

## 9. DAYLOG 상품 이미지 제작

### 어떤 작업을 하였는가

DAYLOG 카테고리별 대표 상품 이미지 7종을 제작했다.

1. 앨범
2. 응원봉
3. 인형
4. 키링
5. 후드집업
6. 텀블러
7. 멤버십 카드

모든 이미지는 하늘색·라일락·연한 핑크·흰색을 사용한 밝고 몽환적인 상품 사진으로 제작했다.

### 어떤 문제가 있었는가

“이미지를 업로드해달라”는 요청을 Supabase Storage에 직접 업로드하라는 의미로 오해했다. 실제 요청은 공지의 폴더·파일명 규칙에 맞는 전달용 ZIP 제작이었다. 생성한 상품 7종 중 현재 DB에는 4종만 등록되어 있었다.

### 어떠한 방법으로 재시도하였는가

모든 이미지를 1440×1440 WebP로 변환했다. 기존 DB 상품 4종은 다음 구조로 정리했다.

    kantmoa-images/
    └─ products/
       └─ daylog/
          ├─ 2nd-single-diary/main.webp
          ├─ member-doll/main.webp
          ├─ daily-tumbler/main.webp
          └─ membership-card/main.webp

DB에 없는 응원봉·키링·후드집업은 잘못된 경로로 업로드되지 않도록 별도 ZIP으로 분리했다.

### 앞으로 어떻게 할 것인가

이미지 제작 전에 상품 DB 등록 여부와 slug를 확인한다. 신규 상품은 DB 등록과 slug 확정 후 이미지를 제작하고 Storage 폴더를 만든다. 상품 이미지는 Git이 아니라 Supabase Storage에서 관리한다.

## 10. Supabase Storage 업로드 방식 확인

### 어떤 작업을 하였는가

`products`, `artists` 버킷과 Storage 정책을 확인했다.

### 어떤 문제가 있었는가

공개 읽기만 설정되어 있고 쓰기 정책은 없었다. 따라서 앱의 공개 키로 업로드할 수 없고 Supabase 대시보드에서만 업로드할 수 있었다.

### 어떠한 방법으로 재시도하였는가

대시보드 업로드 가능 여부를 확인했지만, 실제 요청이 Storage 직접 업로드가 아니라 전달용 ZIP 생성임을 확인한 뒤 업로드를 중단했다.

### 앞으로 어떻게 할 것인가

요청을 업로드용 ZIP 제작, 실제 대시보드 업로드, Storage 경로 설계, DB 상품 등록 중 하나로 먼저 구분한다.

## 11. 빌드 및 캐시 문제

### 어떤 작업을 하였는가

주요 작업 후 ESLint, TypeScript, 프로덕션 빌드를 확인했다.

    npm run lint
    npx tsc --noEmit
    npm run build

### 어떤 문제가 있었는가

최신 `develop`에서 라우트가 이동된 뒤 `.next/types`에 삭제된 과거 경로가 남아 `Cannot find module '../../src/app/page.js'` 오류가 발생했다.

### 어떠한 방법으로 재시도하였는가

개발 서버를 종료하고 생성 캐시인 `.next`만 삭제한 뒤 TypeScript 검사를 다시 실행했다. 검사 통과 후 개발 서버를 다시 실행했다.

### 앞으로 어떻게 할 것인가

라우트 이동 후 원인을 알 수 없는 타입 오류가 발생하면 개발 서버 종료, `.next` 삭제, 타입 검사, 서버 재실행, 강력 새로고침 순서로 확인한다.
