# TIL | 관광 데이터를 모아서 AI Dashboard로 만들기

- 학습일: 2026-10-16
- 참고 자료: 「Chapter 14-2. 관광 데이터를 수집·저장하고 지도 기반 AI Dashboard로 서비스하기」
- 키워드: Make, Supabase, Python/pandas, NAVER API, AI 요약, Next.js, Vercel

## 오늘 공부한 내용

이번 자료는 단순히 차트를 만드는 내용이 아니라, 관광 데이터를 가져와서 정리하고 DB에 쌓은 다음 웹 화면으로 보여주는 전체 과정을 다룬다. 처음에는 도구 이름이 많이 나와서 각각을 따로 외워야 하나 싶었는데, 전체 흐름을 먼저 잡으니 역할이 조금씩 구분됐다.

내가 이해한 흐름은 이렇다.

```text
외부 API → Make에서 수집 → 데이터 정리/검증 → Supabase 저장
                                                ↓
                                           AI 요약 저장
                                                ↓
                                  Next.js Dashboard에서 조회
                                                ↓
                                    GitHub 관리 → Vercel 배포
```

중요한 건 각 도구가 모든 일을 다 하는 게 아니라는 점이다. Make는 수집 자동화, Supabase는 저장, SQL은 집계, AI는 설명, Next.js는 화면, Vercel은 배포를 맡는다. 일단 이 역할을 구분해 놓고 세부 설정을 보는 게 이해하기 쉬웠다.

## 1. 어떤 데이터를 모으는 건지 정리

이번 프로젝트에서 확인하려는 건 크게 세 가지다.

- 사람들이 여행과 관련해 어떤 주제를 검색하는지
- 지역별 관광 체류·소비 강도가 어떤지
- 각 지역에 관광지, 맛집, 카페, 숙박 장소가 어디 있는지

여기서 데이터 소스가 각각 다르다.

| 데이터 | 내가 이해한 역할 | 기억할 점 |
|---|---|---|
| NAVER Search Trend | 여행·축제·캠핑·맛집 같은 키워드의 관심도 추이 | `ratio`는 실제 검색 건수가 아니라 상대적인 관심도 |
| 한국관광공사 지역별 관광 수요 강도 API | 지역별 체류 강도와 소비 강도 확인 | 실제 응답 필드와 기준일을 문서에서 확인해야 함 |
| NAVER Local Search API | 지역별 장소 검색 결과 가져오기 | 장소 정보와 좌표를 받는 API |
| NAVER Maps JavaScript API | 웹 지도에 장소 표시하기 | Local Search와는 역할이 다름 |

처음에 특히 구분해야겠다고 생각한 건 NAVER Local Search와 NAVER Maps다. 하나는 장소 데이터를 찾는 용도고, 다른 하나는 그 데이터를 지도 위에 보여주는 용도다. 이름이 비슷해서 같은 기능처럼 생각하기 쉬운데 실제로는 다르다.

또 NAVER Trend의 `ratio`를 검색 건수처럼 표현하면 안 된다. 지역별 검색량을 보여주는 데이터도 아니므로, 관광 수요 데이터와 나란히 보여주더라도 두 데이터가 직접적인 원인과 결과 관계라고 단정하면 안 된다. 숫자를 보여주는 것만큼 그 숫자가 무슨 뜻인지 정확히 적는 것도 중요하다고 느꼈다.

참고 링크:
- [NAVER Search Trend API](https://api.ncloud-docs.com/docs/naver-api-hub-search-trend)
- [한국관광공사 지역별 관광 수요 강도](https://www.data.go.kr/data/15151868/openapi.do)
- [NAVER Local Search API](https://api.ncloud-docs.com/docs/naver-api-hub-search-local)
- [NAVER Maps JavaScript API](https://navermaps.github.io/maps.js.ncp/docs/)

## 2. Seed 데이터와 매일 수집하는 데이터는 따로 생각하기

이 부분은 전체 흐름을 이해하는 데 도움이 됐다. Dashboard를 처음 개발할 때는 화면에 보여줄 데이터가 필요하니까, 먼저 Seed 데이터를 준비해서 DB에 넣는다. 그 다음부터는 Make가 정해진 시간에 API를 호출해서 새 데이터를 추가하거나 갱신한다.

```text
처음 준비할 때
CSV/JSON → Python + pandas로 정리 → Supabase에 Import

운영할 때
Make Scheduler → API 호출 → 간단한 전처리/검증 → Supabase Upsert
```

처음부터 매일 수집 자동화까지 한 번에 만들기보다, Seed 데이터를 먼저 넣고 DB와 화면이 제대로 연결되는지 확인하는 편이 문제를 찾기 쉬울 것 같다. 원본 파일은 덮어쓰지 말고 `raw`에 두고, 처리한 결과는 `processed`에 따로 저장하는 식으로 나눠 두면 전처리 전후를 비교하기도 편하다.

### pandas를 쓰는 이유

처음 데이터를 한꺼번에 정리할 때는 Python과 pandas를 쓰고, 매일 반복되는 작업은 Make 안에서 가볍게 처리하는 방식이다. 자료에서는 날짜 형식 변환, 숫자형 변환, 필수값 확인, 중복 제거 같은 작업을 다룬다.

예를 들어 관광 수요 데이터라면 아래 컬럼이 있는지 먼저 확인해야 한다.

- `reference_date`
- `region_code`
- `stay_strength`
- `consumption_strength`

원본 CSV의 컬럼 이름이 다르면 코드가 그대로 실행되지 않을 수 있으니, 코드를 먼저 복사하기보다 실제 파일의 컬럼을 확인하는 게 먼저다. 이 부분은 AI에게 코드를 요청하더라도 원본 데이터 구조를 알려줘야 정확한 답을 받을 수 있겠다고 정리했다.

## 3. Supabase 데이터베이스 구성

Supabase는 이번 프로젝트의 중심 저장소다. 자료에서는 용도에 따라 테이블을 나눈다.

| 테이블 | 저장하는 내용 |
|---|---|
| `regions` | 지역 코드, 지역명, 중심 좌표 |
| `naver_trend` | 날짜별 키워드 관심도 |
| `tourism_demand` | 날짜·지역별 체류 강도와 소비 강도 |
| `local_places` | 장소명, 주소, 카테고리, 좌표 등 |
| `ai_region_analysis` | 지역별 AI 요약과 한계 |
| `collection_runs` | 수집 실행 시간, 상태, 처리 행 수, 오류 기록 |

테이블을 하나로 몰아넣기보다 데이터 성격에 따라 나누는 이유를 생각해 봤다. 검색 관심도와 장소 정보는 형태도 다르고 갱신 주기도 다르다. 나중에 조회하거나 문제가 생겼을 때 어느 단계에서 문제가 발생했는지 구분하기도 쉬워진다.

### 중복 저장을 막는 Unique Key와 Upsert

예를 들어 `naver_trend`는 같은 날짜와 키워드 조합이 중복으로 들어가지 않도록 `(reference_date, keyword)`를 기준으로 둔다. 관광 수요는 `(reference_date, region_code)`처럼 날짜와 지역 조합을 기준으로 한다.

매일 같은 데이터를 다시 수집할 수도 있으므로 매번 무조건 INSERT를 하면 중복이 쌓일 수 있다. 그래서 기존 데이터가 있으면 갱신하고, 없으면 새로 넣는 Upsert가 필요하다. 다만 Upsert가 제대로 동작하려면 DB 쪽에 중복을 판별할 기준이 먼저 있어야 한다는 점을 같이 기억해야겠다.

### Key와 RLS는 조심해서 설정하기

이번 내용 중 실수하면 안 되는 부분이다.

- 웹 브라우저에서 사용하는 값은 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`다.
- Supabase Secret Key는 브라우저 코드에 넣으면 안 된다.
- Secret Key를 GitHub 저장소에 올리지 않는다.
- Dashboard는 읽기만 하고, 데이터 쓰기는 Make 같은 서버 측 자동화에서 처리하는 구조로 잡는다.
- RLS 정책에서 공개 읽기를 허용하는 것은 해당 데이터가 공개되어도 괜찮을 때만 적용한다.

RLS를 켰다고 무조건 안전한 것도 아니고, 반대로 화면에 데이터가 안 나온다고 무작정 정책을 풀어버리는 것도 답이 아니다. 어떤 역할이 어떤 작업을 해야 하는지 먼저 정하고 정책을 확인해야 한다.

## 4. Make 자동화 흐름

Make에서는 API별로 Scenario를 나눠 수집하도록 구성한다.

1. NAVER Search Trend 수집
2. 관광공사 관광 수요 데이터 수집
3. NAVER Local 장소 정보 수집
4. 지역별 AI 요약 생성 및 저장

각 Scenario는 API를 호출하는 데서 끝나지 않는다. 응답 데이터에서 필요한 필드를 뽑고, 날짜나 숫자 형식을 맞추고, 값이 빠지거나 이상하지 않은지 확인한 뒤 Supabase에 저장해야 한다.

자료에서 Make Code 안의 pandas 사용 가능 여부를 확인하고, 환경에 따라 기본 모듈이나 다른 처리 방식으로 대체하는 내용도 다룬다. 그래서 pandas를 쓸 수 있다고 미리 가정하지 말고, 실제 Make 환경에서 가능한 방식을 확인해야 한다.

API 응답의 필드명도 추측하지 않는 게 중요하다. 특히 관광공사 API는 최신 Swagger나 활용 가이드에서 Endpoint, 필수 파라미터, 기준일, 지역 코드, 응답 JSON 구조를 먼저 확인해야 한다. API 이름만 보고 `region_code` 같은 필드가 무조건 있을 거라고 생각하면 안 된다.

### 수집 로그도 남기기

`collection_runs` 테이블은 단순한 부가 기능이 아니다. 언제 시작했는지, 성공했는지, 몇 건을 처리했는지, 오류가 났다면 무슨 오류였는지 남긴다. 자동화는 한 번 성공했다고 끝나는 게 아니어서, 나중에 데이터가 갱신되지 않았을 때 원인을 확인할 수 있어야 한다.

## 5. AI는 데이터를 대신 검증하는 역할이 아니다

AI 지역 요약 부분에서 기억할 건, AI에게 원본 데이터를 전부 맡겨서 분석하게 하는 게 아니라는 점이다. 먼저 SQL이나 애플리케이션 쪽에서 집계한 데이터를 준비하고, AI는 그 결과를 읽기 쉽게 설명하는 역할을 맡는다.

내가 정리한 흐름은 다음과 같다.

```text
Supabase에 저장된 검증된 데이터
        ↓
지역별 집계/비교 값 만들기
        ↓
AI에 요약 요청
        ↓
요약 결과와 한계 저장
        ↓
Dashboard에서 표시
```

프롬프트에는 확인된 데이터만 근거로 쓰고, 자료에 없는 사실을 지어내지 않도록 요청해야 한다. 데이터가 부족하면 부족하다고 말하게 하고, 상관관계만 보이는 상황에서 원인이라고 단정하지 않게 하는 것도 필요하다.

그리고 AI 결과도 `ai_region_analysis` 테이블에 저장한다. 화면을 열 때마다 AI를 다시 호출하는 대신, 저장된 결과를 조회하면 비용과 응답 시간을 관리하기 쉽고 어떤 결과를 보여줬는지도 추적할 수 있다.

## 6. Next.js Dashboard 만들기

Dashboard는 외부 API를 직접 부르지 않고 Supabase에 저장된 데이터를 조회한다. 이 구조가 중요한 이유는 화면과 데이터 수집을 분리할 수 있기 때문이다. 외부 API에 일시적인 문제가 생겨도 이미 저장된 데이터는 화면에 표시할 수 있다.

화면에는 대략 다음 요소가 들어간다.

- 주요 지표를 보여주는 KPI 카드
- NAVER 검색 관심도 추이 차트
- 지역과 장소를 표시하는 지도 및 Marker
- AI 지역 요약

프로젝트를 만들고 필요한 패키지를 설치한 다음 `.env.local`에 Supabase URL과 Publishable Key를 설정한다. 연결부터 먼저 테스트하고, 그 다음 지도, KPI 카드, 차트, AI 요약 순서로 기능을 붙이는 게 좋겠다. 처음부터 화면 전체를 만들면 연결 문제인지 지도 문제인지 UI 문제인지 한꺼번에 확인해야 해서 디버깅이 어려워질 수 있다.

### 지도 좌표에서 주의할 점

NAVER Local Search 응답의 `mapx`는 경도(longitude), `mapy`는 위도(latitude)로 사용한다. 위도와 경도를 반대로 넣으면 Marker가 잘못된 곳에 나타날 수 있다. 지도는 뜨는데 Marker 위치가 이상하면 좌표 매핑부터 확인해 봐야겠다.

또한 장소 검색 결과는 검색 API가 돌려준 일부 결과이지, 해당 지역의 모든 관광 장소를 빠짐없이 담은 완전한 목록은 아니다. Dashboard의 장소 데이터가 전체 현황을 대표한다고 과장하지 않는 편이 맞다.

## 7. GitHub와 Vercel 배포

로컬에서 동작하는 것과 배포 환경에서 동작하는 것은 다를 수 있다. 특히 환경변수는 로컬 `.env.local`에만 넣었다고 Vercel에서도 자동으로 설정되는 게 아니다. Vercel 프로젝트 설정에도 필요한 값을 등록해야 한다.

배포 흐름은 아래처럼 정리했다.

```text
로컬에서 기능 확인
    ↓
Git 초기화 및 Commit
    ↓
GitHub Repository 연결
    ↓
Vercel 환경변수 설정
    ↓
Preview 배포에서 확인
    ↓
문제 없으면 Production 배포
```

자료에서는 GitHub 연동 방식과 Vercel CLI 방식도 비교한다. 어느 방식을 쓰든 배포 전에 로컬에서 Supabase 연결, 지도, 차트, AI 요약이 동작하는지 확인하고, Preview 환경에서도 한 번 더 확인하는 게 좋다. API Secret이 코드나 저장소에 포함되지 않았는지도 배포 전에 확인해야 한다.

## 공부하면서 정리한 것

이번 자료는 도구가 많아서 각각의 사용법을 따로 외우기보다 데이터가 어떻게 이동하는지 연결해서 보는 게 더 중요해 보였다. 내가 기억할 내용은 다음과 같다.

1. **NAVER Trend의 `ratio`는 실제 검색 건수가 아니다.** 상대적인 검색 관심도로 표시해야 한다.
2. **Seed 데이터와 운영 데이터 수집은 목적이 다르다.** Seed는 처음 화면을 개발하기 위한 준비이고, Make는 이후 주기적으로 데이터를 갱신한다.
3. **초기 대량 정리는 pandas, 반복 수집은 Make로 처리한다.** 다만 Make에서 pandas를 사용할 수 있는지는 실제 환경을 확인해야 한다.
4. **Supabase가 기준 저장소다.** 수집 데이터와 AI 결과를 저장하고, Dashboard는 이 데이터를 읽는다.
5. **Upsert와 실행 로그가 있어야 운영하기 편하다.** 중복을 줄이고 수집 실패를 추적할 수 있다.
6. **AI는 확인된 데이터의 설명을 돕는 역할이다.** 없는 사실을 만들어내거나 데이터의 한계를 숨기면 안 된다.
7. **API Key와 RLS 설정은 기능 구현만큼 중요하다.** Secret Key를 브라우저나 GitHub에 노출하지 않는다.
8. **배포 전에는 Preview에서 먼저 확인한다.** 로컬에서 되는 것만으로 끝났다고 생각하지 않는다.

## AI 도움을 받은 부분과 다음에 직접 확인할 부분

이번 자료를 정리할 때 AI는 복잡한 흐름을 단계별로 풀어 보고, API·DB·화면의 역할을 구분하는 데 참고하는 보조 도구로 생각했다. 다만 AI가 제시한 코드나 필드명이 실제 API 응답과 항상 일치한다고 믿으면 안 된다. 특히 API 파라미터, DB 컬럼, 환경변수는 공식 문서와 실제 응답으로 확인해야 한다.

다음에 직접 진행할 때는 우선 Supabase 테이블을 만들고 Seed 데이터를 넣어 조회가 되는지 확인한 뒤, Make에서 API 하나씩 연결해 보려고 한다. 한 번에 모든 Scenario와 화면을 만들기보다 각 단계에서 결과를 확인하고 다음으로 넘어가는 방식이 나한테 더 맞을 것 같다.

아직 실제 API 키와 계정 설정, 배포 환경에 따라 달라지는 부분은 직접 실행해서 확인해야 한다. 이 문서는 학습 자료를 읽으며 정리한 기록이고, 모든 단계가 실제 환경에서 성공적으로 실행되었다는 의미는 아니다.
