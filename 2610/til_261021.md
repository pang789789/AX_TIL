# 오전 학습 — Fullstack Web Chapter 09~11

## 1. 함수의 매개변수와 반환값

Chapter 09에서는 Chapter 08에서 배운 변수, 조건문, 반복문을 함수로 묶는 방법을 배웠다. 함수는 자주 사용하는 동작에 이름을 붙여 필요할 때 다시 호출할 수 있게 해 준다.

```js
function greet(name) {
    return `안녕하세요, ${name}님! 환영합니다.`;
}

const message = greet('김코딩');
console.log(message);
```

처음에는 `parameter`와 `return`이 비슷하게 느껴졌다. 직접 코드를 실행해 보니 둘의 방향이 반대라는 것을 알게 됐다.

```text
parameter: 함수 바깥에서 함수 안으로 들어가는 입력값
return: 함수 안에서 만든 결과를 함수 바깥으로 돌려주는 값
```

`console.log()`는 값을 화면에 확인하는 동작이고, `return`은 결과를 다른 변수에 저장하거나 다음 연산에 사용할 수 있게 한다. 함수 안에서 출력만 하고 `return`하지 않으면 호출 결과가 `undefined`가 될 수 있다는 점도 알게 됐다.

### 해보고 느낀 점

함수는 단순히 코드를 짧게 만드는 문법이 아니었다. 입력과 출력이 분명하게 나뉘기 때문에 같은 로직을 여러 데이터에 적용하고 테스트하기 쉬워졌다.

## 2. 객체와 배열로 회원 데이터 표현하기

회원 한 명은 여러 속성을 가진 객체로 만들고, 여러 회원 객체는 배열 안에 넣었다.

```js
const users = [
    { id: 1, name: '김철수', age: 25, isActive: true },
    { id: 2, name: '이영희', age: 30, isActive: false },
    { id: 3, name: '박민수', age: 28, isActive: true },
    { id: 4, name: '최지우', age: 24, isActive: false }
];
```

Chapter 08에서는 이름만 배열에 저장했지만, 객체를 사용하니 이름, 나이, 활성 상태처럼 한 사람과 관련된 값을 함께 관리할 수 있었다. `user.name`, `user.age`, `user.isActive`처럼 속성 이름으로 값을 읽으니 배열 위치로 의미를 추측하는 것보다 코드가 이해하기 쉬웠다.

## 3. `map()`, `filter()`, `find()`의 차이

배열 메서드 세 개는 이름보다 **결과의 형태**를 기준으로 구분하니 이해하기 쉬웠다.

| 메서드 | 목적 | 결과 |
|---|---|---|
| `map()` | 모든 요소를 다른 형태로 변환 | 원본과 길이가 같은 새 배열 |
| `filter()` | 조건에 맞는 여러 요소 선택 | 새 배열 |
| `find()` | 조건에 맞는 첫 요소 하나 선택 | 객체 하나 또는 `undefined` |

모든 회원 이름만 뽑을 때는 `map()`을 사용했다.

```js
const memberNames = users.map(user => user.name);
```

활성 회원만 찾을 때는 `filter()`를 사용했다.

```js
const activeUsers = users.filter(user => user.isActive);
```

특정 이름의 회원 한 명을 찾을 때는 `find()`가 맞았다.

```js
const foundUser = users.find(user => user.name === '박민수');
```

### 어려웠던 부분

처음에는 `filter()`와 `find()`가 모두 조건에 맞는 데이터를 찾기 때문에 같은 기능처럼 보였다. 하지만 `filter()`는 조건에 맞는 사람이 한 명이어도 배열을 반환하고, `find()`는 첫 번째 객체 하나만 반환한다는 차이가 있었다. 없는 회원을 `find()`로 찾으면 오류가 아니라 `undefined`가 나오므로 사용 전에 결과가 존재하는지 확인해야 했다.

## 4. HTML·CSS·JavaScript를 세 파일로 분리한 이유

회원 실습 폴더를 다음처럼 구성했다.

```text
chapter09/greet/
├─ index.html
├─ style.css
└─ script.js
```

- `index.html`: 제목, 입력창, 버튼, 목록처럼 화면의 구조
- `style.css`: 색상, 여백, 크기, 정렬처럼 화면의 표현
- `script.js`: 데이터 가공, 화면 변경, 클릭 동작

처음에는 파일이 세 개로 늘어나 오히려 복잡해 보였다. 하지만 HTML에서 구조를 찾고, CSS에서 디자인을 수정하고, JavaScript에서 동작만 확인할 수 있어 문제의 위치를 구분하기 쉬웠다.

HTML에는 다음과 같이 외부 파일을 연결했다.

```html
<link rel="stylesheet" href="style.css">
<script src="script.js"></script>
```

JavaScript가 HTML 요소보다 먼저 실행되지 않도록 `<script>`는 `</body>` 바로 앞에 배치했다.

## 5. DOM으로 JavaScript 데이터를 화면에 출력하기

Chapter 10에서는 Console에서만 확인하던 회원 데이터를 실제 HTML 화면에 출력했다.

```html
<div id="greeting-box"></div>
<ul id="user-list"></ul>
<ul id="active-user-list"></ul>
```

JavaScript에서는 `document.getElementById()`로 HTML 요소를 가져왔다.

```js
const greetingBox = document.getElementById('greeting-box');
greetingBox.innerHTML = `<p><strong>${message}</strong></p>`;
```

`map()`으로 회원별 `<li>` 문자열 배열을 만든 뒤 `join('')`으로 하나의 문자열로 합쳐 목록에 넣었다.

```js
const userListEl = document.getElementById('user-list');
const userHtmls = users.map(user => {
    return `<li>이름: ${user.name} / 나이: ${user.age}세</li>`;
});

userListEl.innerHTML = userHtmls.join('');
```

활성 회원 목록은 `filter()`와 `map()`을 연결해 만들었다.

```js
const activeUsers = users.filter(user => user.isActive);
const activeUserHtmls = activeUsers.map(user => {
    return `<li>활성 회원 이름: ${user.name}</li>`;
});
```

### 직접 해보며 이해한 흐름

```text
JavaScript 배열
    ↓ filter로 필요한 데이터 선택
    ↓ map으로 HTML 문자열 변환
    ↓ join으로 문자열 결합
    ↓ innerHTML로 화면에 반영
```

`map()`이 단순히 숫자를 계산하는 메서드가 아니라, 객체를 화면에 필요한 HTML 형태로 변환할 때도 사용할 수 있다는 점이 가장 와닿았다.

## 6. 입력창과 확인 버튼 만들기

Chapter 11에서는 이름 왼쪽에 나이를 입력하는 textbox를 추가하고 확인 버튼을 눌렀을 때 두 값을 함께 출력했다.

```html
<div class="input-group">
    <input id="name" type="text" placeholder="이름을 입력하세요">
    <input id="age" type="text" placeholder="나이를 입력하세요">
    <input id="btn" type="button" value="확인">
</div>
```

`id`는 JavaScript에서 각 요소를 정확히 찾기 위해 사용했다.

```js
const nameInput = document.getElementById('name');
const ageInput = document.getElementById('age');
const btn = document.getElementById('btn');
```

처음에는 `<input ... />`의 마지막 `/`가 VS Code에서 빨간색으로 보여 오류라고 생각했다. HTML5에서는 `input`이 닫는 태그가 없는 void element라서 `<input ...>`만 사용해도 되고, `/>`도 브라우저가 처리한다. 실제 문법 오류라기보다 에디터의 강조 방식에 가까웠다.

## 7. 버튼 클릭 이벤트와 입력값 읽기

확인 버튼에 `onclick` 이벤트를 연결했다.

```js
btn.onclick = function () {
    alert(`이름: ${nameInput.value}, 나이: ${ageInput.value}세`);
    console.log(`이름: ${nameInput.value}, 나이: ${ageInput.value}세`);
};
```

`nameInput` 자체는 HTML 요소이고 실제 사용자가 입력한 문자열은 `nameInput.value`에 들어 있다. 처음에는 요소 변수만 출력해서 원하는 값이 나오지 않을 수 있다는 점이 헷갈렸다.

`alert()`는 사용자가 바로 결과를 확인하기 좋고, `console.log()`는 개발자가 값과 실행 흐름을 확인하기 좋았다. 같은 값을 두 곳에 출력해 보니 사용자 화면과 개발자 도구의 역할 차이도 이해됐다.

## 8. 이벤트 코드를 추가하다가 기존 코드가 안 보인 문제

클릭 이벤트를 추가하는 과정에서 중괄호 위치가 잘못되어 기존의 `greet()` 호출과 회원 목록 렌더링 코드가 `onclick` 함수 안으로 들어간 적이 있었다. 이렇게 되면 페이지를 열었을 때 바로 보여야 할 회원 목록이 버튼을 누르기 전까지 실행되지 않는다.

### 해결 방법

페이지 로딩 시 한 번 실행될 코드와 버튼을 누를 때만 실행될 코드를 분리했다.

```js
// 페이지가 열리면 바로 실행
const message = greet('김코딩');
greetingBox.innerHTML = `<p><strong>${message}</strong></p>`;

// 버튼을 눌렀을 때만 실행
btn.onclick = function () {
    console.log(nameInput.value, ageInput.value);
};
```

중괄호 한 개의 위치가 실행 시점을 바꿀 수 있으므로, 함수를 추가한 뒤에는 들여쓰기와 닫는 괄호의 위치를 다시 확인해야 한다.

## 9. 오전 학습에서 잘 안 됐던 것과 해결 방법

| 문제 | 실제 원인 | 해결 방법 |
|---|---|---|
| `map()`과 `filter()`가 헷갈림 | 변환과 선택의 목적을 구분하지 못함 | 결과 배열의 길이와 용도를 비교 |
| `filter()`와 `find()`가 비슷해 보임 | 둘 다 조건식을 사용함 | 여러 개는 배열, 첫 한 개는 객체라는 결과 형태 확인 |
| 화면에 `[object Object]` 또는 이상한 값이 표시됨 | 객체나 배열을 바로 문자열로 넣음 | `map()`으로 HTML 문자열을 만들고 `join('')` 사용 |
| JavaScript가 HTML 요소를 찾지 못함 | `id` 불일치 또는 script 실행 순서 문제 | HTML과 JS의 `id` 비교, script를 body 마지막에 배치 |
| 버튼 클릭 전 회원 목록이 안 보임 | 기존 렌더링 코드가 onclick 안에 들어감 | 초기 렌더링 코드와 이벤트 코드를 함수 밖/안으로 분리 |
| 이름 대신 요소 정보가 출력됨 | `.value`를 사용하지 않음 | `nameInput.value`, `ageInput.value`로 읽기 |

# 오후 학습 — Database Chapter 14

## 1. 분석 전에 질문과 기준부터 정하기

오늘 가장 먼저 배운 것은 SQL을 바로 작성하지 않고 분석 질문의 기준부터 정하는 것이었다. 같은 데이터라도 기간이나 포함 상태가 다르면 결과가 달라지기 때문이다.

이번 실습의 분석 기간은 다음과 같았다.

```text
[2026-01-01, 2026-07-01)
```

시작일은 포함하고 종료일은 포함하지 않는 반개방 구간이다. 이 방식을 사용하면 다음 분석 기간을 `[2026-07-01, 2027-01-01)`처럼 이어 붙여도 7월 1일 데이터가 중복되지 않는다.

분석용 VIEW에서 한 행은 수강신청 한 건이며, `enrollment_id` 하나를 의미했다. 주요 분석 질문은 다음과 같았다.

- 상태별 수강신청 건수
- 월별 신청 건수와 신청 시점 기록 금액
- 강의별 신청 건수
- 지역별 학생 수와 신청 건수
- 완료된 신청의 완료 기간

`recorded_amount`는 실제 결제 매출이 아니라 **수강신청 시점에 기록된 금액**이다. 취소 상태가 되더라도 이 값을 0으로 바꾸지 않았다. 결제와 환불 데이터가 별도로 없기 때문에 이 합계를 실제 매출이라고 표현하면 안 된다는 점도 중요했다.

### 해보고 느낀 점

이전에는 결과 표의 열 이름만 보고 의미를 추측하는 경우가 많았다. 오늘은 분석 전에 기간, 한 행의 의미, 포함 상태, 지표의 업무 의미를 먼저 써 보니 SQL과 Python 중 어느 쪽이 틀렸는지 판단할 기준이 생겼다.

## 2. 기존 스키마와 분석 스키마를 분리한 이유

## 3. 집계보다 먼저 데이터 품질 검사하기

집계 전에 다음 항목을 검사했다.

- PK 또는 분석 VIEW 중복
- 존재하지 않는 학생·강의·강사를 참조하는 고아 FK
- 완료 상태인데 완료일이 없는 데이터
- 미완료 상태인데 완료일이 있는 데이터
- 완료일이 신청일보다 빠른 데이터
- 신청일이 회원 가입일이나 강의 개설일보다 빠른 데이터
- 음수 기록 금액
- 취소 후 금액을 0으로 덮은 데이터
- 분석 기간 밖 데이터
- 동일 학생과 강의의 활성 신청 중복

모든 품질 검사 결과는 0건이었다.

### 왜 이 과정이 필요했는가

SQL이 오류 없이 실행됐다고 해서 데이터가 올바른 것은 아니었다. 예를 들어 같은 신청이 JOIN 때문에 두 번 나타나도 `SUM()`과 `COUNT()`는 정상 실행된다. 다만 결과가 실제보다 두 배로 부풀려질 뿐이다.

이번 실습을 통해 다음 두 문장을 구분해야 한다는 것을 배웠다.

```text
쿼리가 실행됐다.       → 문법과 실행에는 문제가 없다.
분석 결과가 정확하다.  → 원본 품질과 분석 기준까지 검증됐다.
```

## 5. 데이터가 없는 월도 남기는 date spine

월별 데이터를 단순히 `GROUP BY`하면 신청이 0건인 월은 결과에서 사라진다. 이를 막기 위해 `generate_series`로 월 목록을 먼저 만들고 실제 집계 결과를 `LEFT JOIN`했다.

```sql
SELECT generate_series(
    DATE '2026-01-01',
    DATE '2026-06-01',
    INTERVAL '1 month'
);
```

date spine을 사용하면 데이터가 없는 월도 0건으로 표시할 수 있다. 중간 월이 빠진 채 `LAG()`를 사용하면 두 달 전 값이 바로 전 달 값처럼 비교될 수 있으므로 시계열 분석에서는 특히 중요했다.

## 8. 가장 먼저 잘 안 됐던 부분: CSV 경로 오류

`03_pandas_analysis.py`를 처음 실행했을 때 다음 오류가 발생했다.

```text
FileNotFoundError: CSV 파일을 찾을 수 없습니다:
C:\dev\data\enrollment_analysis_dataset.csv
```

처음에는 pandas 코드에 문제가 있다고 생각했다. 하지만 Traceback을 위에서부터 읽어 보니 실제 원인은 분석 코드가 기대하는 기본 경로와 CSV가 저장된 위치가 다른 것이었다.

### 해결 방법

1. DBeaver에서 `analysis_lab.enrollment_analysis_dataset` 결과를 CSV로 내보냈다.
2. 파일을 코드가 기대하는 `C:\dev\data` 경로에 저장했다.
3. CSV만 복사하지 않고 manifest도 함께 생성했다.
4. 실행할 때 `--csv`와 `--manifest` 옵션으로 정확한 경로를 전달했다.

단순히 파일을 아무 폴더에 복사하는 것으로 끝내지 않고, 프로그램이 어떤 경로를 기준으로 파일을 찾는지 확인하는 것이 중요했다.

## 9. 두 번째로 잘 안 됐던 부분: 그래프 저장 권한 오류

pandas의 상태별·월별 집계는 정상적으로 출력됐지만 마지막 그래프 저장 단계에서 다음 오류가 발생했다.

```text
PermissionError: [WinError 5] 액세스가 거부되었습니다: 'C:\dev\output'
```

분석 결과가 화면에 출력됐기 때문에 처음에는 모든 과정이 끝난 줄 알았다. 하지만 Traceback의 마지막 줄을 확인하니 기본 출력 경로에 폴더를 만들 권한이 없는 상태였다.

### 해결 방법

기본 경로를 그대로 사용하지 않고 현재 실습 폴더 안의 쓰기 가능한 경로로 지정했다.

```text
C:\dev\analysis_lab\output\monthly_enrollment.png
```

이후 그래프가 정상적으로 저장됐고, 파일이 실제로 존재하는지도 확인했다.

### 느낀 점

코드의 앞부분이 실행됐다고 프로그램 전체가 성공한 것은 아니었다. 터미널의 마지막 줄과 종료 상태까지 봐야 한다. 특히 파일을 생성하는 프로그램은 계산 결과뿐 아니라 출력 경로와 권한도 함께 확인해야 한다.

## 10. pandas 자료형을 엄격하게 검증한 이유

CSV에서 읽은 문자열을 날짜와 숫자로 바꿀 때 오류를 조용히 숨기지 않고 strict 변환을 사용했다.

확인한 기준은 다음과 같았다.

- 정확한 17개 컬럼
- 24행
- `enrollment_id` 고유
- 날짜 컬럼의 엄격한 datetime 변환
- `recorded_amount`와 `completion_days`의 숫자 변환
- `is_completed`의 boolean 변환
- `status`와 `is_completed` 값의 일치
- 완료 상태와 완료일·완료 기간의 일치
- 분석 기간 `[2026-01-01, 2026-07-01)` 준수

처음에는 변환 오류가 생기면 `errors='coerce'`를 사용하고 `dropna()`로 지우면 편할 것 같았다. 하지만 이 방식은 문제가 있는 행을 조용히 삭제해 전체 행 수와 합계를 바꿀 수 있다. `drop_duplicates()`도 중복의 원인을 확인하지 않고 사용하면 JOIN 오류를 숨길 수 있다.

따라서 오류 행을 삭제하기 전에 다음을 먼저 확인해야 한다.

1. 원본 데이터가 잘못됐는가?
2. 컬럼 형식이 예상과 다른가?
3. 변환 규칙이 잘못됐는가?
4. JOIN 때문에 중복이 생겼는가?
5. 분석 질문에 정말 제외해야 하는 행인가?

## 12. 일부러 불일치를 만들어 원인 확인하기

원본 DB와 기준 코드는 수정하지 않고 임시 계산에서 취소 상태만 제외해 봤다.

```text
기준 결과: 24건 / 3,210,000원

차이: 3건 / 440,000원
```

오류가 난 것이 아니라 분석 범위가 달라졌기 때문에 생긴 차이였다. SQL은 전체 상태를 포함했지만 임시 pandas 계산은 취소를 제외했다.

이 실험을 통해 결과가 다를 때 기준값을 현재 결과에 맞게 수정하면 안 된다는 점을 확실히 이해했다. 기대값을 바꾸기 전에 질문, 기간, 상태 필터부터 비교해야 한다.

## 13. 시각화를 하며 느낀 점

검증된 월별 데이터를 이용해 월별 신청 건수 그래프를 만들었다. 그래프에서는 다음을 확인했다.

- 월 순서가 1월부터 6월까지 올바른가?
- 누락된 월이 없는가?
- Y축이 0에서 시작하는가?
- 표의 건수와 막대 높이가 일치하는가?
- `recorded_amount`를 매출처럼 오해할 표현이 없는가?

그래프는 흐름을 빠르게 파악하는 데는 좋지만 숫자 검증의 증거가 되지는 못했다. 필터가 잘못돼도 그래프 모양은 자연스러울 수 있기 때문이다. 따라서 **숫자를 먼저 검증하고, 그다음 그래프를 해석해야 한다.**

## 오늘 가장 어려웠던 부분

1. DBeaver에서 현재 DB와 스키마를 구분하고 올바른 SQL 파일을 순서대로 실행하는 것
2. `recorded_amount`를 실제 매출이 아니라 신청 시점 기록 금액으로 해석하는 것
3. VIEW의 행 수만 보지 않고 `enrollment_id` 고유성까지 확인하는 것
4. CSV의 실제 위치와 Python 기본 경로가 달라 발생한 오류를 찾는 것
5. pandas 출력이 나온 뒤 발생한 그래프 저장 권한 오류를 놓치지 않는 것
6. SQL과 pandas 결과가 같다는 것을 느낌이 아니라 자동 검증 결과로 확인하는 것

## 오늘 잘 안 됐던 것과 해결 방법

## 해보고 느낀 점

SQL과 pandas는 서로 대체하는 도구가 아니라 역할이 달랐다. SQL은 데이터베이스 가까이에서 품질을 검사하고 기준 집계를 만들기에 좋았다. pandas는 같은 데이터를 다시 계산하고 피벗이나 그래프로 확장하기 편했다.

가장 인상적이었던 것은 두 도구가 같은 숫자를 출력했다고 바로 믿지 않고, 원본 VIEW의 행 단위와 CSV 해시까지 확인한 점이다. 이전에는 결과가 비슷해 보이면 맞다고 생각했지만, 오늘은 데이터의 출처와 분석 조건이 같아야 비교 자체가 의미 있다는 것을 알게 됐다.

또한 오류가 생겼을 때 코드를 전부 다시 복사하기보다 Traceback의 마지막 줄, 파일 경로, 현재 작업 폴더를 먼저 확인하는 것이 훨씬 빠르게 문제를 해결하는 방법이었다.

## 아직 잘 안 된 부분

- DBeaver에서 여러 SQL 결과 탭을 빠르게 비교하는 것이 아직 익숙하지 않다.
- PostgreSQL에 읽기 전용으로 직접 연결하는 방식은 비밀번호를 안전하게 분리한 뒤 추가로 연습해야 한다.
- manifest를 직접 작성하지 않고 추출 과정에서 자동으로 생성하는 흐름을 더 익히고 싶다.
- pandas 피벗 결과를 보고 어떤 시각화가 적절한지 선택하는 것은 아직 어렵다.
- SQL의 `generate_series`, `LAG`, CTE를 혼자서 처음부터 작성하려면 더 연습이 필요하다.

## 오늘 배운 내용을 내 말로 정리

데이터 분석은 SQL을 실행하거나 그래프를 만드는 것으로 끝나지 않는다. 먼저 질문과 기간, 한 행의 의미, 지표 정의를 정해야 한다. 그다음 원본 데이터의 중복과 관계 오류를 검사하고 SQL 기준값을 만든다.

Python에서는 SQL과 같은 데이터와 같은 조건을 사용해 다시 계산해야 한다. CSV를 사용한다면 원본 DB, VIEW, 분석 기간, 행 수와 해시를 manifest에 남겨야 한다. 결과가 다를 때는 기대값을 바꾸지 말고 원본, 기간, 행 단위, 필터, 자료형, 집계식 순서로 원인을 찾아야 한다.

마지막 그래프는 검증을 통과한 숫자를 이해하기 쉽게 보여 주는 도구이지, 정확성을 증명하는 도구는 아니다.
