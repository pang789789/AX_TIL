## 1. SQLD 시험 범위를 처음 확인하며 느낀 점

SQLD는 크게 데이터 모델링과 SQL 활용 능력을 확인하는 시험이다. SQL 문법 문제에서도 단순히 결과만 계산하는 것이 아니라 다음 내용을 함께 판단해야 했다.

- 테이블에서 한 행이 무엇을 의미하는가?
- 기본키는 어떤 컬럼인가?
- 테이블끼리 어떤 관계인가?
- JOIN을 하면 행이 몇 개가 되는가?
- NULL이 조건식에 들어가면 결과가 어떻게 되는가?
- 집계 전후에 조건을 어디에 적용해야 하는가?

예전에는 쿼리가 실행되기만 하면 된다고 생각했다. 시험 문제에서는 실행 가능한 SQL이 여러 개여도 문제에서 요구하는 정확한 결과를 만드는 SQL을 골라야 했다. 그래서 문법 암기와 함께 데이터의 구조를 읽는 연습이 필요하다고 느꼈다.

## 2. 엔터티, 인스턴스, 속성 구분하기

처음에는 엔터티와 테이블을 완전히 같은 말로 생각했다. 실습에서는 비슷하게 대응되지만, 모델링 단계에서는 업무에서 관리해야 하는 대상을 엔터티라고 이해했다.

회원관리 예시로 정리하면 다음과 같다.

| 구분 | 예시 | 의미 |
|---|---|---|
| 엔터티 | 회원 | 관리하려는 대상의 집합 |
| 인스턴스 | 회원번호 101인 김민지 | 엔터티에 속한 한 건의 데이터 |
| 속성 | 회원번호, 이름, 이메일 | 대상을 설명하는 항목 |
| 속성값 | 101, 김민지, `minji@example.com` | 한 인스턴스가 가진 실제 값 |

엔터티가 성립하려면 업무에서 실제로 필요하고, 식별 가능하며, 두 개 이상의 인스턴스와 속성을 가져야 한다는 기준을 함께 확인했다.

### 해보고 느낀 점

용어의 정의만 읽을 때는 모두 비슷하게 느껴졌다. 하지만 “회원은 엔터티, 김민지는 인스턴스, 이메일은 속성”처럼 하나의 사례에 대입하니 구분이 쉬워졌다. 앞으로 새로운 용어를 공부할 때도 정의를 외우기 전에 실제 테이블 예시를 먼저 만들어봐야겠다.

## 3. 관계와 카디널리티 이해하기

회원과 주문의 관계를 생각해 봤다.

```text
회원 1명은 주문을 여러 건 할 수 있다.
주문 1건은 반드시 회원 1명에게 속한다.
```

따라서 회원과 주문은 `1:N` 관계가 된다.

```text
MEMBER (1) ──────< ORDER (N)
```

주문과 상품은 한 주문에 여러 상품이 포함되고, 한 상품도 여러 주문에 포함될 수 있으므로 `N:M` 관계다. 관계형 데이터베이스에서는 중간에 주문상품 엔터티를 만들어 두 개의 `1:N` 관계로 분리한다.

```text
ORDER (1) ──< ORDER_ITEM >── (1) PRODUCT
```

### 어려웠던 부분

처음에는 선의 모양과 기호를 외우는 데 집중했다. 그러다 보니 방향이 바뀐 그림을 보면 다시 헷갈렸다. 다음 두 문장을 각각 읽는 방식으로 해결했다.

1. 회원 한 명에게 주문은 몇 건까지 존재할 수 있는가?
2. 주문 한 건은 몇 명의 회원에게 속하는가?

기호부터 보지 않고 업무 문장을 먼저 읽으니 최소·최대 참여 수를 판단하기 쉬웠다.

## 4. 기본키, 후보키, 대체키, 외래키

식별자는 인스턴스를 구분하는 값이다. 키의 종류를 다음처럼 정리했다.

| 키 | 의미 |
|---|---|
| 슈퍼키 | 행을 유일하게 구분할 수 있는 속성의 집합 |
| 후보키 | 최소성을 만족하는 슈퍼키 |
| 기본키 | 후보키 중 대표로 선택한 키 |
| 대체키 | 기본키로 선택되지 않은 후보키 |
| 외래키 | 다른 테이블의 기본키를 참조하는 키 |

회원 테이블에서 `member_id`와 이메일이 모두 회원을 유일하게 구분한다면 둘 다 후보키가 될 수 있다. 이 중 `member_id`를 기본키로 선택하면 이메일은 대체키가 된다.

```sql
CREATE TABLE members (
    member_id BIGINT PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    member_name VARCHAR(100) NOT NULL
);
```

주문 테이블의 `member_id`는 회원 테이블을 참조하는 외래키가 된다.

```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    member_id BIGINT NOT NULL,
    order_date DATE NOT NULL,
    FOREIGN KEY (member_id) REFERENCES members(member_id)
);
```

### 잘 안 됐던 부분과 해결

`UNIQUE`가 있으면 무조건 기본키라고 생각한 것이 문제였다. 기본키는 테이블의 대표 식별자로 하나만 선택하지만 `UNIQUE` 제약조건은 여러 컬럼에 만들 수 있다. 또한 기본키는 NULL을 허용하지 않지만, UNIQUE의 NULL 처리 방식은 DBMS에 따라 차이가 있을 수 있다는 점을 구분했다.

## 5. 정규화와 함수적 종속

정규화는 테이블을 무조건 잘게 나누는 작업이 아니라, 데이터 중복과 삽입·수정·삭제 이상을 줄이는 과정이다.

다음과 같은 테이블을 예로 들었다.

| 주문번호 | 회원번호 | 회원이름 | 상품번호 | 상품명 | 수량 |
|---|---|---|---|---|---:|
| 1001 | M01 | 김민지 | P01 | 키보드 | 1 |
| 1001 | M01 | 김민지 | P02 | 마우스 | 2 |

이 구조에서는 회원 이름과 상품명이 여러 주문 행에 반복된다. 회원 이름이 바뀌면 관련 주문 행을 모두 수정해야 하므로 수정 이상이 발생할 수 있다.

### 제1정규형

하나의 컬럼에는 원자값 하나만 저장한다. 상품 목록을 `P01,P02`처럼 한 칸에 저장하지 않고 주문상품 행으로 분리한다.

### 제2정규형

복합키의 일부에만 종속된 속성을 분리한다. 주문상품의 기본키가 `(주문번호, 상품번호)`일 때 상품명은 상품번호에만 종속되므로 상품 테이블로 분리한다.

### 제3정규형

기본키가 아닌 속성에 종속된 속성을 분리한다. 주문번호로 회원번호를 알 수 있고 회원번호로 회원이름을 알 수 있다면, 회원이름은 주문번호에 이행적으로 종속되어 있으므로 회원 테이블에 둔다.

최종 구조는 다음처럼 나눌 수 있었다.

```text
MEMBER(member_id, member_name)
ORDER(order_id, member_id, order_date)
PRODUCT(product_id, product_name)
ORDER_ITEM(order_id, product_id, quantity)
```

### 가장 어려웠던 부분

제2정규형과 제3정규형을 구분하는 것이 가장 어려웠다. 다음 질문으로 판단 기준을 정리했다.

```text
제2정규형: 복합키의 일부분만으로 결정되는 컬럼이 있는가?
제3정규형: 일반 컬럼이 다른 일반 컬럼을 결정하는가?
```

문제를 풀 때 먼저 기본키를 표시하고 화살표로 함수적 종속 관계를 그리니 구분하기 쉬워졌다.

## 6. SQL의 논리적 실행 순서

SQL은 작성 순서와 실제 논리적 처리 순서가 다르다.

작성 순서는 다음과 같다.

```sql
SELECT department_id, COUNT(*) AS employee_count
FROM employees
WHERE status = 'ACTIVE'
GROUP BY department_id
HAVING COUNT(*) >= 3
ORDER BY employee_count DESC;
```

논리적 실행 순서는 다음과 같이 이해했다.

```text
FROM
→ WHERE
→ GROUP BY
→ HAVING
→ SELECT
→ ORDER BY
```

### 별칭을 WHERE에서 사용할 수 없는 이유

`SELECT`에서 만든 별칭은 논리적으로 `WHERE`보다 나중에 만들어진다. 그래서 같은 SELECT 문의 WHERE 절에서 별칭을 바로 사용할 수 없다. 반면 `ORDER BY`는 SELECT 이후에 처리되므로 별칭을 사용할 수 있다.

처음에는 DBMS가 위에서부터 한 줄씩 실행한다고 생각했다. 실행 순서를 알고 나니 왜 집계 함수는 WHERE에 쓸 수 없고 HAVING에 써야 하는지도 함께 이해됐다.

## 7. WHERE와 HAVING 구분하기

`WHERE`는 그룹을 만들기 전 개별 행을 필터링하고, `HAVING`은 그룹 집계 후 결과를 필터링한다.

```sql
SELECT department_id, COUNT(*) AS employee_count
FROM employees
WHERE status = 'ACTIVE'
GROUP BY department_id
HAVING COUNT(*) >= 3;
```

- `WHERE status = 'ACTIVE'`: 활성 직원 행만 남김
- `HAVING COUNT(*) >= 3`: 활성 직원이 3명 이상인 부서만 남김

### 잘 안 됐던 문제

“평균 급여가 4,000 이상인 부서”를 찾는 문제에서 다음처럼 작성하려고 했다.

```sql
WHERE AVG(salary) >= 4000
```

하지만 `AVG()`는 그룹을 만든 뒤 계산되므로 WHERE가 아니라 HAVING에 작성해야 했다.

```sql
SELECT department_id, AVG(salary)
FROM employees
GROUP BY department_id
HAVING AVG(salary) >= 4000;
```

## 8. NULL과 3값 논리

SQL에서 NULL은 0이나 빈 문자열이 아니라 값이 알려지지 않았다는 의미다. 따라서 NULL은 `=`로 비교하지 않고 `IS NULL` 또는 `IS NOT NULL`을 사용해야 한다.

```sql
-- 잘못된 조건
WHERE commission = NULL

-- 올바른 조건
WHERE commission IS NULL
```

`NULL = NULL`도 TRUE가 아니라 UNKNOWN이다. WHERE 절에는 TRUE인 행만 남기 때문에 UNKNOWN 결과는 제외된다.

### 직접 계산하며 헷갈렸던 부분

```sql
SELECT 100 + NULL;
```

결과는 100이 아니라 NULL이다. 알려지지 않은 값을 더한 결과도 알 수 없기 때문이다.

NULL을 다른 값으로 대체할 때는 `COALESCE`를 사용할 수 있다.

```sql
SELECT salary + COALESCE(commission, 0)
FROM employees;
```

### COUNT에서 NULL 처리

```text
COUNT(*)       → 행 전체를 계산하며 NULL 행도 포함
COUNT(column)  → 해당 컬럼이 NULL인 행은 제외
```

이 차이는 결과 건수를 묻는 문제에서 자주 실수할 수 있는 부분이라 별도로 기록했다.

## 9. INNER JOIN과 OUTER JOIN

회원과 주문을 예로 JOIN의 차이를 확인했다.

### INNER JOIN

양쪽 테이블에서 조건이 일치하는 행만 반환한다.

```sql
SELECT m.member_name, o.order_id
FROM members m
JOIN orders o
  ON o.member_id = m.member_id;
```

주문이 없는 회원은 결과에서 사라진다.

### LEFT OUTER JOIN

왼쪽 테이블의 모든 행을 유지한다.

```sql
SELECT m.member_name, o.order_id
FROM members m
LEFT JOIN orders o
  ON o.member_id = m.member_id;
```

주문이 없는 회원도 표시되고 주문 컬럼은 NULL이 된다.

### ON과 WHERE의 위치 때문에 결과가 달라진 문제

활성 주문만 연결하면서 주문이 없는 회원도 남기고 싶었다. 처음에는 다음처럼 조건을 WHERE에 작성했다.

```sql
SELECT m.member_name, o.order_id
FROM members m
LEFT JOIN orders o
  ON o.member_id = m.member_id
WHERE o.status = 'ACTIVE';
```

이렇게 하면 주문이 없는 행의 `o.status`가 NULL이므로 WHERE에서 제외되어 INNER JOIN처럼 동작할 수 있다.

조건을 ON 절로 옮기면 회원은 유지하면서 활성 주문만 연결할 수 있다.

```sql
SELECT m.member_name, o.order_id
FROM members m
LEFT JOIN orders o
  ON o.member_id = m.member_id
 AND o.status = 'ACTIVE';
```

### 해결 기준

```text
오른쪽 테이블을 연결할 조건인가? → ON
JOIN이 끝난 최종 결과를 걸러낼 조건인가? → WHERE
```

## 10. JOIN 후 행 수가 늘어나는 이유

회원 1명에게 주문이 3건 있으면 회원과 주문을 JOIN했을 때 회원 행도 3번 나타난다. JOIN은 테이블을 단순히 옆으로 붙이는 동작이 아니라 조건에 맞는 행의 조합을 만드는 작업이었다.

다음 질문을 먼저 확인하면 JOIN 결과의 행 수를 예측하기 쉬웠다.

1. 두 테이블의 관계가 1:1, 1:N, N:M 중 무엇인가?
2. JOIN 컬럼은 양쪽에서 고유한가?
3. 조건 하나에 몇 개의 행이 매칭되는가?
4. OUTER JOIN에서 유지되는 기준 테이블은 어느 쪽인가?

처음에는 JOIN 결과가 항상 원본 테이블 행 수보다 작거나 같다고 생각했다. 1:N 관계에서는 한 행이 여러 행과 연결되므로 결과가 더 많아질 수 있다는 것을 간단한 데이터를 손으로 그려 확인했다.

## 11. GROUP BY 문제 풀이 방법

집계 문제는 SELECT 절부터 읽지 않고 다음 순서로 분석했다.

1. FROM과 JOIN으로 어떤 행 집합을 만드는가?
2. WHERE에서 어떤 행을 제거하는가?
3. GROUP BY로 어떤 단위의 그룹을 만드는가?
4. 집계 함수가 NULL을 어떻게 처리하는가?
5. HAVING에서 어떤 그룹을 제거하는가?
6. ORDER BY로 최종 결과를 어떻게 정렬하는가?

예를 들어 부서별 직원 수를 구할 때 한 결과 행은 직원이 아니라 부서 한 개를 의미한다.

```sql
SELECT department_id, COUNT(*) AS employee_count
FROM employees
GROUP BY department_id;
```

SELECT 절에 일반 컬럼을 추가하려면 GROUP BY에도 포함하거나 집계 함수로 감싸야 한다.

### 실수했던 부분

부서명까지 출력하고 싶어서 SELECT에만 `department_name`을 추가했다. 하지만 그룹 기준에 포함되지 않은 일반 컬럼이라 오류가 발생할 수 있었다.

```sql
SELECT department_id, department_name, COUNT(*)
FROM employees
GROUP BY department_id, department_name;
```

그룹을 만든 후 결과의 한 행이 무엇을 나타내는지 먼저 생각하면 SELECT에 올 수 있는 컬럼을 판단하기 쉬웠다.

## 12. 오늘 풀면서 틀린 유형 정리

| 문제 유형 | 내가 선택한 잘못된 답 | 틀린 이유 | 다시 푸는 기준 |
|---|---|---|---|
| 후보키와 기본키 | UNIQUE 컬럼은 모두 기본키 | 기본키는 후보키 중 대표로 하나 선택 | 유일성과 최소성을 먼저 확인 |
| 제2·제3정규형 | 모든 종속을 제2정규형 문제로 판단 | 부분 종속과 이행 종속을 구분하지 못함 | 복합키 여부와 일반 속성 간 종속 확인 |
| 별칭 사용 | WHERE에서 SELECT 별칭 사용 | WHERE가 SELECT보다 먼저 처리 | 논리적 실행 순서 작성 |
| 집계 조건 | `WHERE AVG(salary)` 사용 | 집계 전에는 AVG 값이 없음 | 그룹 조건은 HAVING |
| NULL 비교 | `column = NULL` 사용 | NULL 비교 결과는 UNKNOWN | `IS NULL` 사용 |
| COUNT | `COUNT(column)`이 전체 행 수라고 판단 | NULL 값은 제외됨 | 전체 행은 `COUNT(*)` |
| LEFT JOIN | 오른쪽 조건을 WHERE에 작성 | NULL 확장 행이 제거됨 | 보존 목적이면 조건을 ON에 작성 |
| JOIN 행 수 | JOIN하면 행 수가 줄어든다고 판단 | 1:N 매칭으로 행이 증가 가능 | 관계와 키의 고유성 확인 |

## 오늘 가장 어려웠던 부분

1. 엔터티, 인스턴스, 속성과 같은 모델링 용어를 실제 테이블과 연결하는 것
2. 후보키·기본키·대체키의 포함 관계를 구분하는 것
3. 제2정규형의 부분 함수 종속과 제3정규형의 이행 함수 종속을 구분하는 것
4. SQL을 작성된 순서가 아니라 논리적 실행 순서로 해석하는 것
5. NULL이 포함된 비교식의 결과를 TRUE/FALSE만으로 판단하지 않는 것
6. LEFT JOIN에서 ON과 WHERE 조건의 위치에 따라 결과가 달라지는 이유를 이해하는 것

## 해보고 느낀 점

SQLD 공부를 시작하기 전에는 SQL 문법을 많이 외우는 것이 가장 중요하다고 생각했다. 오늘 문제를 직접 풀어 보니 문법보다 먼저 데이터 구조와 결과 행의 의미를 정확하게 읽어야 했다.

특히 정규화 문제는 정규형의 정의만 외우면 보기 문장이 조금만 달라져도 헷갈렸다. 기본키를 먼저 찾고 `결정자 → 종속자` 형태로 화살표를 그리니 어떤 속성을 분리해야 하는지 훨씬 잘 보였다.

SQL 문제도 실제로 쿼리를 실행하지 못하는 시험 상황에서는 머릿속으로 행의 흐름을 따라가야 했다. FROM부터 ORDER BY까지 작은 표를 손으로 만들어 계산해 보니, 별칭·집계·NULL·JOIN 문제를 한꺼번에 정리할 수 있었다.

## 아직 잘 안 되는 부분

- 식별 관계와 비식별 관계를 ERD만 보고 빠르게 판단하는 것
- 여러 후보키 중 어떤 키를 기본키로 선택해야 하는지 설명하는 것
- 복합키가 세 컬럼 이상일 때 부분 함수 종속을 찾는 것
- NULL이 포함된 `IN`, `NOT IN`, 논리 연산 결과를 빠르게 계산하는 것
- 세 개 이상의 테이블을 JOIN했을 때 최종 행 수를 예측하는 것
- DBMS별 NULL, 문자열, 날짜 함수 차이를 구분하는 것

## 해결을 위해 정한 공부 방법

1. 개념마다 회원·주문·상품 예시를 직접 만든다.
2. 정규화 문제는 기본키와 함수적 종속 화살표부터 표시한다.
3. SQL 문제는 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` 순서로 메모한다.
4. JOIN 문제는 각 테이블의 키와 관계를 먼저 표시한다.
5. NULL 문제는 TRUE, FALSE, UNKNOWN 세 결과를 모두 고려한다.
6. 틀린 문제는 정답만 표시하지 않고 내가 잘못 적용한 기준을 한 줄로 기록한다.
7. 다음 날 같은 문제를 보기 없이 다시 풀어 장기 기억으로 남긴다.

## 오늘 배운 내용을 내 말로 정리

데이터 모델링은 업무에서 관리해야 할 대상을 엔터티로 정의하고, 속성과 관계 및 식별자를 정하는 과정이다. 정규화는 중복을 줄이고 데이터 이상을 방지하기 위해 함수적 종속을 기준으로 테이블을 분리하는 작업이다.

SQL은 작성된 위쪽 줄부터 실행되는 것이 아니다. FROM에서 행 집합을 만들고 WHERE로 행을 거른 뒤 GROUP BY와 HAVING으로 그룹을 처리한다. SELECT에서 최종 컬럼을 만들고 ORDER BY로 정렬한다.

NULL은 값이 없거나 알려지지 않은 상태이므로 일반 비교 연산자로 판단하면 안 된다. JOIN은 행의 조합을 만드는 동작이라 관계에 따라 행 수가 늘어날 수 있다. OUTER JOIN에서는 오른쪽 테이블 조건을 ON에 둘지 WHERE에 둘지에 따라 보존되는 행이 달라진다.
