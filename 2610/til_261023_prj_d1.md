## 오늘 한 일

오늘은 기존에 Supabase를 사용하던 못난이마켓 프로젝트에 FastAPI 백엔드를 새로 연결하는 작업을 시작했다. 팀에서 내가 맡은 기능은 회원 인증과 마이페이지였다.

처음에는 로그인 API 몇 개만 만들면 될 것이라고 생각했다. 하지만 실제로 구현해보니 로그인 기능 하나에도 사용자 테이블, 비밀번호 저장 방식, JWT 발급과 검증, 로그아웃 처리, 프론트엔드의 토큰 보관 방법, 보호 페이지 접근 제어까지 모두 연결돼 있었다.

오늘 구현한 흐름은 다음과 같다.

```text
이메일과 비밀번호로 로그인
        ↓
Argon2 해시와 입력 비밀번호 비교
        ↓
사용자 식별자와 jti가 포함된 JWT 발급
        ↓
프론트엔드가 HTTP-only 쿠키에 JWT 저장
        ↓
JWT로 내 정보와 기본 배송지 조회·수정
        ↓
로그아웃 시 jti를 블랙리스트에 저장
        ↓
같은 JWT를 다시 사용하면 401 반환
```

## 1. 기존 프로젝트를 먼저 분석했다

새 코드를 바로 작성하지 않고 기존 로그인 페이지와 마이페이지가 어떻게 동작하는지 먼저 확인했다. 기존 코드는 Supabase Auth의 세션을 사용하고 있었고, 프로필과 배송지 데이터도 Supabase에서 직접 조회하고 있었다.

반면 새로 만드는 백엔드는 FastAPI가 로그인과 JWT 검증을 담당해야 했다. 따라서 단순히 API 주소만 바꾸는 것으로는 해결되지 않았다. 다음 부분을 함께 변경해야 했다.

- Supabase 로그인 호출을 FastAPI 로그인 API로 변경
- Supabase 세션 대신 FastAPI JWT로 현재 사용자 확인
- 프로필과 배송지 조회·수정을 FastAPI API로 변경
- 로그아웃할 때 브라우저 쿠키뿐 아니라 서버의 토큰도 무효화
- 보호 페이지에 들어갈 때 FastAPI 기준으로 인증 여부 확인

### 해보고 느낀 점

기존 프로젝트를 이어받아 작업할 때는 새 기능을 만드는 것보다 기존 인증 흐름을 정확히 읽는 것이 먼저라는 것을 느꼈다. 화면에서는 로그인 버튼 하나만 보이지만, 내부에서는 미들웨어, 서버 액션, 쿠키, 사용자 조회가 모두 연결되어 있었다.

## 2. FastAPI 회원·인증 구조 구성

FastAPI 백엔드에는 회원, 프로필, 기본 배송지, 로그아웃 토큰을 저장할 모델을 구성했다.

```text
User
├─ email
├─ password_hash
├─ is_active
└─ is_admin

Profile
├─ name
├─ phone
└─ nickname

Address
├─ recipient_name
├─ recipient_phone
├─ postal_code
├─ address
└─ address_detail

RevokedToken
├─ jti
├─ user_id
└─ expires_at
```

사용자와 프로필·배송지는 같은 사용자 ID를 기준으로 연결했다. 다른 사용자의 ID를 요청 값으로 받아 수정하지 않고, JWT에서 확인한 현재 사용자만 조회하거나 변경하도록 했다.

### 배운 점

권한이 필요한 API에서는 클라이언트가 보내는 사용자 ID를 신뢰하면 안 된다. 화면에서 값을 숨겨도 요청은 직접 바꿀 수 있기 때문이다. 서버가 검증한 JWT의 사용자 ID를 기준으로 데이터를 조회해야 다른 사용자의 정보 수정 문제를 막을 수 있다.

## 3. 비밀번호는 Argon2로 해싱했다

비밀번호 원문은 데이터베이스에 저장하지 않고 Argon2로 해싱했다. 로그인할 때도 입력한 비밀번호를 다시 저장하거나 문자열로 직접 비교하지 않고, 저장된 해시와 검증했다.

```text
회원 생성: 비밀번호 → Argon2 해시 → DB 저장
로그인: 입력 비밀번호 + 저장된 해시 → verify → 성공/실패
```

처음에는 해싱과 암호화를 비슷하게 생각했다. 암호화는 키를 사용해 원문으로 되돌릴 수 있지만, 비밀번호 해싱은 원문을 복원하지 않고 입력값이 맞는지만 확인한다는 차이를 다시 이해했다.

## 4. JWT 발급과 검증

로그인에 성공하면 사용자 ID와 토큰 고유 ID인 `jti`, 만료 시간이 포함된 JWT를 발급하도록 했다.

```text
sub: 사용자 ID
jti: 토큰마다 생성되는 고유 ID
exp: 만료 시간
```

보호된 API에서는 다음 순서로 토큰을 검증했다.

1. Authorization 헤더에 Bearer 토큰이 있는지 확인한다.
2. JWT 서명과 알고리즘을 검증한다.
3. 만료 시간을 확인한다.
4. `sub`의 사용자가 실제 존재하며 활성 상태인지 확인한다.
5. `jti`가 로그아웃 블랙리스트에 있는지 확인한다.

토큰이 없거나 변조됐거나 만료된 경우, 로그아웃으로 폐기된 경우에는 모두 보호 API 접근을 거부했다.

## 5. 로그아웃에서 가장 많이 고민한 부분

JWT는 서버 세션처럼 서버에서 바로 삭제되는 값이 아니다. 처음에는 브라우저가 토큰을 지우면 로그아웃이 끝난다고 생각했다. 하지만 탈취되거나 복사된 JWT는 만료 전까지 계속 사용할 수 있다는 문제가 있었다.

이를 해결하기 위해 JWT마다 `jti`를 넣고, 로그아웃하면 해당 `jti`와 만료 시간을 `RevokedToken` 테이블에 저장했다. 이후 인증 요청이 들어오면 블랙리스트를 확인해 이미 로그아웃한 토큰을 거부했다.

```text
로그아웃 요청
→ 현재 JWT의 jti 추출
→ RevokedToken에 저장
→ 프론트엔드 쿠키 삭제
→ 같은 JWT 재사용
→ 블랙리스트 확인
→ 401 Unauthorized
```

### 해보고 느낀 점

기능의 겉모습만 보면 로그아웃은 토큰을 지우는 단순한 작업이었다. 하지만 서버가 토큰을 즉시 무효화해야 하는 요구사항까지 생각하면 별도의 상태 저장이 필요했다. JWT를 사용한다고 해서 서버가 항상 완전한 무상태 구조가 되는 것은 아니라는 점을 배웠다.

## 6. 내 정보와 기본 배송지 API 구현

마이페이지에 필요한 API는 다음과 같이 만들었다.

| 기능 | Method | Path |
|---|---|---|
| 로그인 및 JWT 발급 | `POST` | `/api/v1/auth/login` |
| 로그아웃 및 토큰 차단 | `POST` | `/api/v1/auth/logout` |
| 내 정보 조회 | `GET` | `/api/v1/users/me` |
| 내 프로필 수정 | `PATCH` | `/api/v1/users/me/profile` |
| 기본 배송지 조회 | `GET` | `/api/v1/users/me/address` |
| 기본 배송지 저장 | `PUT` | `/api/v1/users/me/address` |
| 기본 배송지 삭제 | `DELETE` | `/api/v1/users/me/address` |

프로필과 배송지는 필수값과 길이, 전화번호, 우편번호 형식을 검증했다. 기본 배송지는 한 사용자에게 한 개만 존재하도록 구성하고, `PUT` 요청으로 처음에는 생성하고 이후에는 수정하도록 했다.

## 7. 프론트엔드에서 JWT를 어떻게 보관할지 고민했다

JWT를 브라우저의 `localStorage`에 저장하면 프론트 코드에서 사용하기 편하다. 하지만 JavaScript에서 읽을 수 있기 때문에 XSS가 발생했을 때 토큰이 노출될 위험이 있다.

그래서 Next.js 서버 액션이 FastAPI 로그인을 호출하고, 발급받은 토큰을 다음 속성의 쿠키로 저장했다.

```text
HttpOnly: JavaScript에서 읽을 수 없음
SameSite=Lax: 일반적인 CSRF 위험 완화
Secure: 운영 환경에서는 HTTPS에서만 전송
Path=/: 전체 서비스 경로에서 사용
Max-Age: JWT 만료 시간과 동일
```

브라우저 화면은 JWT 원문을 직접 다루지 않고, 서버 컴포넌트와 서버 액션이 쿠키를 읽어 FastAPI에 전달하도록 했다.

### 배운 점

API가 안전하게 구현돼도 프론트에서 토큰을 위험하게 보관하면 전체 인증이 안전하지 않을 수 있다. 백엔드와 프론트의 경계를 따로 보는 것이 아니라 로그인부터 보호 API 호출까지 한 흐름으로 설계해야 했다.

## 8. 가장 잘 안 됐던 부분: 로그인 성공 후 다시 로그인 화면으로 돌아감

실제 브라우저에서 로그인했을 때 FastAPI의 로그인 API는 200을 반환했고 메인 화면으로 이동했다. 그런데 마이페이지로 들어가면 다시 로그인 화면으로 리디렉션되는 문제가 발생했다.

처음에는 다음 가능성을 의심했다.

- JWT 쿠키가 브라우저에 저장되지 않았는지
- FastAPI가 JWT를 잘못 검증하는지
- 로그인 서버 액션의 redirect가 먼저 실행되는지
- 토큰이 이미 블랙리스트에 등록됐는지

프론트 개발 서버 로그와 요청 흐름을 확인해보니 실제 원인은 기존 Supabase 미들웨어였다. 로그인과 현재 사용자 조회는 FastAPI 방식으로 바꿨지만, 보호 페이지 접근 여부를 판단하는 미들웨어는 여전히 Supabase 세션만 확인하고 있었다.

```text
FastAPI 로그인 성공
→ JWT 쿠키 정상 저장
→ /mypage 접근
→ 기존 Supabase 미들웨어 실행
→ Supabase 세션 없음
→ /login으로 리디렉션
```

### 해결 방법

처음에는 미들웨어에서 FastAPI 쿠키의 존재 여부만 확인하려고 했다. 그러나 쿠키 이름만 맞춘 위조 값이나 만료된 토큰도 보호 경로를 통과할 수 있어 안전하지 않았다.

최종적으로 보호 경로에 접근할 때 미들웨어가 FastAPI의 `/api/v1/users/me`를 호출해 토큰을 검증하도록 변경했다.

```text
보호 경로 요청
→ HTTP-only 쿠키에서 JWT 확인
→ FastAPI /users/me 호출
→ 서명·만료·사용자·블랙리스트 검증 성공
→ 페이지 접근 허용

검증 실패 또는 인증 서버 오류
→ fail-closed
→ JWT 쿠키 제거
→ 로그인 화면으로 이동
```

### 이 문제에서 배운 점

인증 방식을 교체할 때 로그인 버튼과 API만 바꾸면 끝나는 것이 아니었다. 프로젝트 전체에서 “로그인 여부를 누가 판단하는지”를 모두 찾아야 했다. 특히 미들웨어는 페이지 코드보다 먼저 실행되므로 페이지의 인증 로직이 맞더라도 미들웨어가 이전 방식을 사용하면 접근할 수 없었다.

## 9. API와 화면을 직접 검증했다

테스트용 사용자를 생성한 뒤 Swagger에서 다음 흐름을 확인했다.

```text
로그인 200
→ 내 정보 조회 200
→ 기본 배송지 저장 200
→ 기본 배송지 재조회 200
→ 로그아웃 204
→ 동일 JWT로 내 정보 조회 401
```

Swagger 테스트만으로 끝내지 않고 실제 Next.js 화면에서도 확인했다.

```text
이메일 로그인
→ 메인 화면 이동
→ 마이페이지 접근
→ 회원 이메일·닉네임·배송지 표시
→ 로그아웃
→ /mypage 재접근
→ /login?next=/mypage로 이동
```

자동 검사 결과는 다음과 같았다.

- TypeScript 타입 검사 통과
- ESLint 통과
- 전체 테스트 68개 통과
- Next.js 프로덕션 빌드 통과
- FastAPI 테스트 4개 통과
- Ruff 검사 통과

## 10. 오늘 어려웠던 부분과 해결 방법

| 어려웠던 부분 | 실제 원인 | 해결 방법 |
|---|---|---|
| 기존 DB와 FastAPI 사용자를 어떻게 연결할지 혼란 | 기존 인증은 Supabase 세션, 신규 인증은 FastAPI JWT 사용 | FastAPI 사용자 ID를 인증 기준으로 정하고 프로필·배송지를 같은 ID로 연결 |
| 로그아웃 후 JWT가 계속 사용될 수 있음 | JWT는 발급 후 서버가 단순 삭제할 수 없음 | 토큰에 `jti`를 넣고 로그아웃 시 블랙리스트에 저장 |
| 로그인은 성공하지만 마이페이지가 열리지 않음 | 기존 Supabase 미들웨어가 보호 페이지를 먼저 차단 | 미들웨어도 FastAPI `/users/me` 검증 방식으로 교체 |
| 토큰을 어디에 저장해야 할지 고민 | `localStorage`는 JavaScript에서 읽을 수 있음 | HTTP-only·SameSite 쿠키에 저장하고 서버에서만 사용 |
| 배송지 수정 시 다른 사용자 데이터 접근 가능성 | 요청에 사용자 ID를 받으면 조작할 수 있음 | JWT에서 검증된 현재 사용자 ID만 사용 |
| 기존 테스트가 실패함 | 테스트가 Supabase 구현 구조를 전제로 작성됨 | 새 FastAPI 동작과 권한 기준에 맞게 테스트 갱신 |
| 빌드는 되지만 보안 경고가 표시됨 | 사용 중인 Next.js 버전에 알려진 취약점이 존재 | 현재 기능 검증은 완료하고 별도 보안 업그레이드 작업이 필요하다고 기록 |

## 오늘 해보고 느낀 점

오늘 가장 크게 느낀 점은 인증 기능이 하나의 API가 아니라 서비스 전체를 관통하는 공통 기능이라는 것이다. 로그인 API만 정상이어도 미들웨어, 쿠키, 사용자 조회, 로그아웃 무효화 중 하나라도 이전 방식으로 남아 있으면 전체 흐름이 깨졌다.

또한 처음에는 오류가 보이면 코드를 바로 고치려고 했지만, 실제 브라우저의 이동 경로와 서버 로그를 함께 보니 어느 단계에서 실패했는지를 더 빨리 찾을 수 있었다. 로그인 응답이 성공했다는 사실과 보호 페이지 인증이 성공했다는 사실은 서로 다른 검증 항목이었다.

보안과 편의성 사이의 선택도 직접 고민해볼 수 있었다. 쿠키 존재 여부만 확인하면 구현은 간단하지만 위조 토큰을 통과시킬 수 있었다. 조금 더 복잡하더라도 FastAPI에 실제 검증을 요청하고 실패 시 페이지를 열지 않는 방식이 안전했다. 인증 기능에서는 “정상 사용자에게 편한가”뿐 아니라 “잘못된 요청을 어떤 단계에서 차단할 것인가”를 함께 생각해야 한다.

마지막으로 Swagger 테스트, 단위 테스트, 타입 검사, 빌드, 실제 브라우저 테스트는 각각 확인하는 범위가 달랐다. API 테스트가 성공해도 프론트 미들웨어 문제는 발견하지 못했고, 타입 검사가 성공해도 실제 로그인 리디렉션은 확인할 수 없었다. 여러 단계의 검증을 함께 해야 기능이 실제 사용자 흐름에서도 동작한다고 말할 수 있었다.

## 아직 남은 점

- 팀원 기능에서 공통 인증 의존성과 사용자 ID 형식을 실제로 적용하는 작업
- 상품·장바구니·주문·예약 API와 통합했을 때 권한 검증 확인
- 운영 환경의 HTTPS와 쿠키 `Secure` 설정 검증
- 만료된 블랙리스트 토큰을 정리하는 정책 마련
- 비밀번호 변경과 재설정 기능 설계
- Next.js 보안 취약 버전 업그레이드 및 회귀 테스트
- 개인 브랜치 커밋·푸시와 develop PR은 팀 일정에 맞춰 진행

## 다음 작업에서 할 일

1. 팀원에게 인증된 사용자 정보를 가져오는 공통 의존성 사용법을 공유한다.
2. 배송지 응답 형식을 주문 담당자와 확인한다.
3. 관리자 권한이 필요한 API에서 `is_admin` 검증 방식을 통일한다.
4. 개인 브랜치 변경사항을 다시 검토하고 팀원과 함께 PR을 생성한다.
5. 통합 환경에서 로그인부터 주문·예약까지 사용자 ID가 동일하게 전달되는지 확인한다.

## 오늘의 한 줄 정리

> 인증은 로그인 API 하나를 만드는 일이 아니라, 비밀번호 저장부터 JWT 검증·쿠키·미들웨어·로그아웃 무효화까지 전체 요청 흐름을 안전하게 연결하는 작업이다.
