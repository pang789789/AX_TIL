## 오늘 학습한 내용

오늘은 Python 코드 안에 미리 작성한 회원 배열을 반환하던 방식에서 벗어나, PostgreSQL에 저장된 실제 회원 데이터를 FastAPI가 조회해 JSON으로 반환하도록 구현했다. 먼저 DBeaver에서 PostgreSQL 연결과 테이블 데이터를 확인했고, Python에서는 `psycopg`와 `python-dotenv`를 이용해 연결 코드를 분리했다. 이후 `GET /members` Endpoint와 Pydantic Response Model을 작성하고 Swagger에서 `200 OK`와 실제 응답을 확인했다.

전체 처리 흐름은 다음과 같다.

```text
Swagger에서 GET /members 요청
        ↓
FastAPI Endpoint 실행
        ↓
database.py의 get_connection() 호출
        ↓
PostgreSQL에서 SELECT 실행
        ↓
Tuple 형태의 DB Row 조회
        ↓
Python Dictionary로 변환
        ↓
MemberResponse로 출력 계약 검증
        ↓
JSON 배열과 200 OK 반환
```

이번 실습을 하면서 DB 조회에 성공하는 것과 API가 정상 응답을 만드는 것은 서로 다른 단계라는 점을 알게 됐다. SQL이 성공하더라도 Response Model의 필드와 반환 Dictionary가 다르면 API는 `500 Internal Server Error`를 반환할 수 있었다.

## 2. DBeaver에서 DB 연결과 데이터 확인

DBeaver를 업데이트한 뒤 로컬 `postgres` 연결을 열고 SQL Editor에서 `members` 테이블을 확인했다. 테이블에는 다음 컬럼이 있었다.

```text
id
name
email
age
```

조회에 사용한 SQL은 다음과 같다.

```sql
SELECT id, name, email, age
FROM members
ORDER BY id;
```

조회 결과로 `Kim`, `Lee` 두 회원을 확인했다. 이 결과를 이후 Swagger 응답과 비교할 기준 Evidence로 사용했다.

### 어려웠던 점

교안 예시에는 `member_id`와 `practice` 스키마가 나오기도 했지만, 실제 수업 화면과 현재 DB에는 `id`와 `public` 스키마가 사용되고 있었다. 교안의 이름만 그대로 복사하면 현재 테이블 구조와 맞지 않을 수 있었다.

### 해결 방법

- DBeaver에서 실제 테이블의 Schema와 Column을 직접 펼쳐 확인했다.
- `current_database()`와 `current_schema()`를 조회해 현재 연결이 `postgres / public`인지 확인했다.
- 교안의 예시보다 현재 DB의 실제 컬럼을 기준으로 SQL과 Python 코드를 맞췄다.
- API에서는 DB의 `id`를 그대로 반환하거나, 계약이 `member_id`일 때는 Dictionary 변환 과정에서 이름을 명시적으로 바꿨다.

이 과정을 통해 문서에 적힌 이름과 실제 DB 구조가 다를 때는 추측하지 말고 DB를 직접 확인해야 한다는 것을 배웠다.

## 3. database.py로 DB 연결 코드 분리

DB 연결은 `main.py`에 직접 작성하지 않고 `database.py`로 분리했다.

```python
import os

import psycopg
from dotenv import load_dotenv

load_dotenv()

DB_HOST = os.getenv("DB_HOST")
DB_PORT = os.getenv("DB_PORT")
DB_NAME = os.getenv("DB_NAME")
DB_USER = os.getenv("DB_USER")
DB_PASSWORD = os.getenv("DB_PASSWORD")


def get_connection():
    return psycopg.connect(
        host=DB_HOST,
        port=DB_PORT,
        dbname=DB_NAME,
        user=DB_USER,
        password=DB_PASSWORD,
    )
```

연결 자체를 확인하기 위한 함수도 작성했다.

```python
def check_connection():
    with get_connection() as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT current_database(), current_schema()")
            return cur.fetchone()
```

실행 결과는 다음과 같았다.

```text
('postgres', 'public')
```

### 해보고 느낀 점

API 코드와 DB 연결 코드를 분리하니 오류가 발생했을 때 확인할 범위가 줄어들었다. Endpoint가 없어도 `check_connection()`만 실행해 연결 상태를 확인할 수 있었고, 연결이 정상이라면 다음 단계인 SQL과 Response Model에 집중할 수 있었다. 기능을 나눈다는 것이 단순히 파일을 여러 개 만드는 것이 아니라 실패 지점을 구분하는 방법이라는 생각이 들었다.

## 4. fetch_members()로 실제 DB Row 조회

회원 데이터를 조회하는 함수는 다음과 같이 작성했다.

```python
def fetch_members():
    with get_connection() as conn:
        with conn.cursor() as cur:
            cur.execute(
                "SELECT id, name, email, age FROM members ORDER BY id"
            )
            return cur.fetchall()
```

`fetchall()`의 결과는 각 행이 Tuple인 List였다.

```text
[(1, 'Kim', 'kim@example.com', 25),
 (2, 'Lee', 'lee@example.com', 31)]
```

따라서 `row[0]`, `row[1]`, `row[2]`, `row[3]`이 각각 `id`, `name`, `email`, `age`에 해당한다. SQL의 SELECT 컬럼 순서가 바뀌면 Tuple의 위치도 바뀌므로 SQL과 변환 코드를 함께 확인해야 했다.

## 5. Response Model과 GET /members 구현

클라이언트에게 반환할 출력 계약은 Pydantic Model로 정의했다.

```python
class MemberResponse(BaseModel):
    id: int
    name: str
    email: str
    age: int
```

Endpoint에서는 DB Tuple을 Dictionary로 변환했다.

```python
@app.get("/members", response_model=list[MemberResponse])
def get_members():
    rows = fetch_members()
    members = []

    for row in rows:
        members.append({
            "id": row[0],
            "name": row[1],
            "email": row[2],
            "age": row[3]
        })

    return members
```

여기서 `response_model=list[MemberResponse]`는 응답이 회원 객체 여러 개로 이루어진 배열이어야 한다는 의미다. DB에 더 많은 컬럼이 있더라도 API 계약에 선언한 필드만 안정적으로 반환할 수 있다.

### 해보고 느낀 점

DB Column, Tuple 위치, Dictionary Key, Pydantic Field, 최종 JSON Key가 하나의 흐름으로 이어진다는 점이 중요했다. 각 부분을 따로 보면 간단하지만 이름이나 순서가 한 곳만 달라도 전체 API가 실패할 수 있었다.

```text
DB Column
→ Tuple 위치
→ Dictionary Key
→ Pydantic Field
→ JSON Key
```

## 6. SQL 컬럼명 오타로 발생한 500 오류

실습 중 SQL을 다음처럼 잘못 작성했다.

```sql
SELECT id, names, email
FROM member
ORDER BY id;
```

여기에는 두 가지 문제가 있었다.

- 실제 컬럼은 `names`가 아니라 `name`이었다.
- 실제 테이블은 `member`가 아니라 `members`였다.

DBeaver와 FastAPI Terminal에는 `UndefinedColumn` 오류가 표시됐고, Swagger에서는 세부 DB 오류 대신 `500 Internal Server Error`가 보였다.

### 처음 생각한 원인

처음에는 FastAPI 함수나 Swagger가 잘못됐다고 생각했다. 브라우저에는 `Internal Server Error`만 보여서 API 전체가 고장 난 것처럼 느껴졌다.

### 실제 원인과 해결 방법

Terminal의 PostgreSQL 오류 메시지를 확인하니 존재하지 않는 `names` 컬럼을 조회하고 있었다. DBeaver의 `members → Columns`를 펼쳐 실제 컬럼명을 확인하고 다음처럼 수정했다.

```sql
SELECT id, name, email, age
FROM members
ORDER BY id;
```

수정 후 Uvicorn의 자동 Reload가 완료된 것을 확인하고 Swagger에서 Execute를 다시 눌렀다. 이전에 표시된 500 응답은 자동으로 사라지는 것이 아니므로 반드시 다시 요청해야 했다.

이 오류를 통해 Swagger의 500만 보고 전체 코드를 다시 작성하기보다 Terminal의 마지막 오류와 SQL을 먼저 확인하는 것이 훨씬 빠르다는 것을 배웠다.

## 7. Response Model 불일치로 발생한 500 오류

다음 단계에서는 Response Model에 `id`와 `age`가 추가됐지만 반환 Dictionary는 이전 형식인 `member_id`, `name`, `email`을 유지하고 있었다.

```python
class MemberResponse(BaseModel):
    id: int
    name: str
    email: str
    age: int
```

하지만 반환 데이터에는 `id`와 `age`가 없어서 `ResponseValidationError`가 발생했다.

### 오류를 통해 알게 된 점

SQL 조회가 성공했고 실제 회원 데이터도 존재했지만 API는 실패했다. 즉 다음 두 문장은 같은 뜻이 아니었다.

```text
SQL 성공 = Database 조회 성공

API 성공 = Database 조회 성공
          + Python 데이터 변환 성공
          + Response Model 검증 성공
          + JSON 생성 성공
```

### 해결 방법

1. SQL에 `age`를 추가했다.
2. 반환 Key를 `member_id`에서 `id`로 변경했다.
3. `"age": row[3]`을 추가했다.
4. Response Model과 Dictionary Key를 한 줄씩 비교했다.
5. Swagger에서 요청을 다시 실행했다.

수정 후 응답은 다음과 같았다.

```json
[
  {
    "id": 1,
    "name": "Kim",
    "email": "kim@example.com",
    "age": 25
  },
  {
    "id": 2,
    "name": "Lee",
    "email": "lee@example.com",
    "age": 31
  }
]
```

## 오늘 느낀 점

오늘은 FastAPI 코드 몇 줄을 작성하는 것보다 Database부터 JSON Response까지 데이터가 이동하는 전체 경로를 읽는 것이 더 중요하다고 느꼈다. 처음에는 Swagger에 500이 나오면 API 코드 전체를 다시 작성해야 할 것처럼 보였지만, 오류를 단계별로 나누어 확인하니 대부분 한 단어 또는 한 필드의 불일치였다.

특히 `names`와 `name`, `member`와 `members`처럼 작은 오타가 SQL 전체를 실패하게 만들었다. 반대로 SQL이 성공해도 Response Model과 반환 Key가 다르면 API는 다시 실패했다. 이를 통해 Backend에서는 각 단계가 독립적으로 성공해야 최종 응답이 만들어진다는 것을 이해했다.

앞으로 오류가 발생하면 다음 순서로 확인하려고 한다.

```text
1. Swagger의 Status와 Response Body
2. Uvicorn Terminal의 실제 예외
3. 현재 DB 연결과 Schema
4. SQL의 Table과 Column
5. 실제 DB Row
6. 반환 Dictionary Key
7. Response Model Field
```

이 순서를 따르면 막연히 “안 된다”고 생각하기보다 실패 지점을 구체적으로 좁힐 수 있을 것 같다.

## 오늘 배운 내용을 내 말로 정리

FastAPI가 PostgreSQL 데이터를 반환하려면 Endpoint가 DB 연결 함수를 호출하고, SQL로 Row를 조회한 뒤 Python 데이터로 변환해야 한다. 변환된 데이터는 Response Model의 필드와 타입 검증을 통과해야 최종 JSON이 된다.

따라서 SQL이 정상 실행되는 것만으로 API가 완성된 것은 아니다. DBeaver에서 확인한 DB 결과와 Swagger의 JSON을 직접 비교하고, 행 개수와 각 필드의 값, 정렬 순서까지 일치하는지 확인해야 한다. 오류가 발생하면 Swagger만 보지 말고 Uvicorn Log, DB 연결, SQL, 실제 데이터, Response Model 순서로 실패 지점을 좁혀야 한다.

## 오늘의 한 줄 정리

> DB 기반 API의 완성은 SELECT 성공이 아니라, 실제 DB Row가 Python 변환과 Response Model 검증을 거쳐 동일한 JSON으로 반환되는지까지 확인하는 것이다.
