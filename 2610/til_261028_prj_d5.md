## 오늘 한 일

오늘은 새로운 기능을 더 붙이기보다, 우리가 제출할 코드와 설명이 같은 상태를 가리키는지 확인했다. Git 기록을 기준으로 기능 통합과 인증 보완의 병합 순서를 정리하고, 최종 README·ERD와 노션의 팀 페이지·개인 일지를 다시 확인했다.

```text
PR #5: 기존 기능을 main에 통합
PR #40: Google 계정 연결 보완과 최종 README·ERD를 develop에 반영
PR #42: develop의 최종 내용을 main에 반영
```

예전에는 기능이 동작하면 제출 준비도 끝났다고 생각했다. 막상 자료를 점검해 보니 코드가 병합된 뒤에도 문서에 `검토 중` 같은 이전 상태가 남을 수 있었다. 제출 자료에서는 구현 여부뿐 아니라 **어느 브랜치에 반영됐는지, 어떤 검증 결과를 근거로 쓰는지**도 정확해야 한다는 것을 배웠다.

## 1. 최종 README와 ERD를 현재 구조에 맞췄다

오늘의 문서 커밋 `5590389`에서 `README.md`, `docs/ERD-current.md`, 기존 ERD 설명 등을 정리했다. README에는 4조의 역할과 구현 범위, 고객 화면과 FastAPI의 실행 순서, 포트, 환경변수 준비 방법, 검사 명령을 앞쪽에 배치했다. 관리자 화면의 `3001`은 별도 서비스가 아니라 같은 Next.js 앱을 다른 포트에서 확인하는 방식이라는 점도 구분했다.

ERD에서는 마이그레이션을 기준으로 테이블 관계를 다시 확인했다. 인증과 주문을 함께 설명할 때 가장 중요한 연결 규칙은 다음과 같다.

```text
auth.users.id = app_users.id = app_users.supabase_user_id = profiles.id
FastAPI JWT의 sub = 같은 사용자 UUID
```

`app_users`는 FastAPI 계정 정보와 권한을 관리하고, 기존 장바구니·주문·찜 등은 `auth.users`의 UUID를 참조한다. 두 영역을 서로 다른 사용자 번호로 설명하면 로그인은 성공해도 장바구니나 주문의 소유자를 잘못 찾을 수 있다. 관계도에는 테이블 이름뿐 아니라 외래키와 소유권 기준까지 읽히도록 적어야 한다는 점을 다시 느꼈다.

## 2. PR과 검증 결과를 혼동하지 않도록 확인했다

팀 페이지에는 PR #40을 아직 검토 중인 것처럼 적은 부분이 있었다. 실제 병합 상태와 대조한 뒤 PR #40이 develop에, PR #42가 main에 반영된 순서로 수정했다. 자동 검사 수치도 **PR #40 브랜치에서 기록된 로컬 검증 결과**라고 출처를 한정했다.

- 백엔드: 552건 통과, 3건 건너뜀
- 프런트: 180건 통과
- 타입 검사와 린트 통과
- 프로덕션 빌드: 134페이지 생성

이 수치를 적으면서 자동 테스트 통과, 브라우저에서 직접 확인한 흐름, 실제 배포 환경 검증은 서로 다른 증거라는 점을 구분했다. 특히 튜터님이 물으신 “어떤 틀로 테스트했는가?”에는 테스트 건수만 답하기보다 정상·실패·권한 시나리오와 사용자 화면의 수동 확인을 함께 설명하는 편이 명확하다.

## 3. 노션 팀 페이지를 제출 상태에 맞춰 정리했다

팀 페이지의 프로젝트 소개와 구현 흐름을 최종 main 기준으로 고쳤다. 이전 PR 상태를 뜻하는 표현을 정리하고, 튜터 피드백의 핵심 질문과 개선 방향을 함께 남겼다. 특히 데이터 다이어그램은 표준적인 관계 표기와 선의 의미를 일관되게 쓰고, 발표 화면에서는 핵심 사용자 ID와 도메인 관계가 바로 보이도록 단순화하는 방향을 적었다.

WBS를 화면에서 보니 담당자가 비어 있는 네 개의 작업 행과 제목 없는 초안 행이 있었다. 빈 행은 휴지통으로 옮기고, 네 작업에 회원·인증/상품·찜·리뷰/장바구니·주문/체험 예약 분류와 지나·서현·영우·형준 담당자를 각각 연결했다. API 명세 표에서도 주문과 체험 항목의 기능 분류·담당자를 채웠다. 수정 뒤 새로고침하여 값이 저장됐는지 다시 확인했다.

## 4. 내 개인 작업 일지의 날짜와 근거를 맞췄다

기존의 10월 23·25·26·27일 기록을 확인한 뒤, 빠져 있던 10월 28일 기록을 추가했다. 제목은 **「지나 — 최종 README·ERD 및 Google 인증 보완」**으로 적고 날짜, 담당자, 막힌 점, 작업 내용, 해결 방법, PR #40 링크, 완료 상태와 역할 영역을 채웠다. 작성 후 페이지를 새로고침해 각 속성이 유지되는지 확인했다.

오늘 기록에는 Google OAuth에서 겪은 문제도 결과만 적지 않고 원인과 해결 순서로 정리했다.

```text
기존 auth.users·profiles는 있고 app_users만 없는 계정
→ profiles를 다시 INSERT하면 기본키 충돌
→ 기존 프로필을 재사용하고 같은 UUID의 app_users 연결

OAuth 콜백 실패 뒤 Supabase 세션만 남은 상태
→ 화면에는 로그인처럼 보이지만 FastAPI JWT가 없음
→ 실패 세션을 정리하고 서비스 JWT를 로그인 판단 기준으로 사용
```

## 어려웠던 점과 해결 방법

### “완료”라는 말의 기준을 정하기

코드의 병합 상태, 로컬 테스트 결과, 노션의 진행 상태가 서로 다른 시점의 정보를 담고 있었다. 처음에는 문장만 자연스럽게 고치면 될 것 같았지만, 그러면 실제 Git 상태와 어긋날 수 있었다. PR 병합 순서를 먼저 확인하고, 제출 요약에 남은 `검토 중` 표현과 검사 수치를 그 근거에 맞춰 수정했다.

### 템플릿 안의 작은 빈칸까지 찾기

본문을 읽을 때는 WBS의 빈 행과 담당자 칸이 잘 보이지 않았다. 제출 화면을 실제로 스크롤하며 표를 확인하니 초안 행이 남아 있었다. 문서 검토는 글만 읽는 것이 아니라 **제출자가 보게 될 화면으로 직접 보는 작업**이라는 점을 알게 됐다.

### 발표용 설명을 짧고 정확하게 만들기

튜터님은 최종 발표의 데이터 다이어그램이 더 직관적이면 좋겠다고 피드백하셨다. ERD 전체를 한 장에 빽빽하게 보여 주기보다, 발표에서는 `auth.users → app_users·profiles → 각 기능의 소유 데이터`와 같은 핵심 연결을 먼저 보여 주고 상세 제약은 문서에서 확인하도록 나누는 방법을 생각했다.

## 오늘 느낀 점

최종 제출은 코드를 올리는 한 번의 동작이 아니었다. README의 실행 방법, ERD의 관계, PR의 병합 상태, 테스트 결과의 출처, 노션의 역할 분담과 날짜별 일지가 서로 맞아야 팀 밖의 사람도 프로젝트를 따라갈 수 있다.

특히 “다 완료됐다”라는 표현보다 **무엇이 어느 PR로 반영됐고 어떤 검사로 확인됐는지**를 짧게 설명하는 것이 더 신뢰를 준다. 다음 프로젝트에서는 마지막 날에 문서를 몰아서 맞추지 않도록, 기능 PR이 병합될 때 WBS와 API 명세도 함께 갱신해야겠다.

## 오늘의 한 줄 정리

> 제출 자료의 완성도는 글의 양이 아니라 코드·테스트·ERD·진행 기록이 같은 사실을 말하는지에 달려 있다.
