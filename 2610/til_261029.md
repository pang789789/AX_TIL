## 오늘 학습한 내용

오늘은 FastAPI를 이용해 백엔드 API 서버를 처음부터 단계별로 만들어 보았다. 처음에는 브라우저에 JSON 한 줄을 보여 주는 간단한 API로 시작했고, 이후 회원 데이터를 조회하는 API에 Path Parameter와 Query Parameter를 적용했다. 마지막에는 Pydantic Model로 Request Body의 구조를 정의하고 `POST /members`의 정상 요청과 실패 요청까지 검증했다.

오늘 진행한 전체 흐름은 다음과 같다.

```text
FastAPI 애플리케이션 생성
        ↓
GET Endpoint 작성 및 서버 실행
        ↓
Path Parameter로 특정 회원 조회
        ↓
Query Parameter로 이름 검색·나이 필터링
        ↓
Pydantic Model로 Request Body 정의
        ↓
POST /members 구현
        ↓
정상 Body는 201, 잘못된 Body는 422 확인
```

단순히 코드를 입력하는 것보다 폴더와 가상환경, 실행 중인 서버, 브라우저의 Swagger 화면이 모두 같은 Chapter를 가리키도록 맞추는 것이 중요했다.

## 1. Backend와 API Server의 역할 이해하기

Frontend는 사용자가 보는 화면과 입력을 담당하고, Backend는 요청을 받아 데이터를 처리한 뒤 응답을 반환한다. 오늘은 FastAPI로 다음과 같은 가장 기본적인 Endpoint를 만들었다.

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def read_root():
    return {"message": "Hello FastAPI"}
```

`@app.get("/")`에서 `GET`은 HTTP Method이고 `/`는 요청 경로이다. 브라우저에서 해당 경로에 접속하면 FastAPI가 함수의 반환값을 JSON Response로 변환한다.

### 해보고 느낀 점

처음에는 Python 함수를 하나 만든 것처럼 보였지만, 데코레이터를 붙이는 순간 URL과 함수가 연결된다는 점이 신기했다. 함수의 `dict` 반환값이 자동으로 JSON이 되고 Swagger 문서까지 생성되는 것을 보니 FastAPI가 초보자가 API 흐름을 확인하기에 편리한 도구라는 생각이 들었다.

## 3. Path Parameter로 특정 회원 조회하기

Chapter 02에서는 먼저 회원 목록을 만들고 전체 조회와 개별 조회 API를 작성했다.

```python
members = [
    {"id": 1, "name": "Kim", "email": "kim@example.com", "age": 25},
    {"id": 2, "name": "Lee", "email": "lee@example.com", "age": 19},
    {"id": 3, "name": "Park", "email": "park@example.com", "age": 31},
]


@app.get("/members/{member_id}")
def get_member(member_id: int):
    for member in members:
        if member["id"] == member_id:
            return member
    raise HTTPException(status_code=404, detail="Member not found")
```

`member_id: int`라고 선언하면 FastAPI가 URL의 값을 정수로 변환하고 검증한다. 존재하는 ID를 보내면 회원 JSON을 반환하고, 목록에 없는 ID를 보내면 `404 Not Found`를 반환한다.

### 해보고 느낀 점

Path Parameter는 `/members/1`처럼 특정 자원 한 개를 가리킬 때 사용한다는 것을 이해했다. 단순히 값을 받아오는 것에서 끝나지 않고, 타입이 맞지 않거나 회원이 없을 때 어떤 상태 코드를 줄 것인지도 API Contract의 일부였다.

## 4. Query Parameter로 검색과 필터 구현하기

이름 검색에서는 Query Parameter를 선택값으로 받았다.

```python
@app.get("/members/search/")
def search_members(name: str | None = None):
    if name is None:
        return members

    keyword = name.lower()
    return [
        member
        for member in members
        if keyword in member["name"].lower()
    ]
```

이후 이름과 최소 나이를 함께 받을 수 있는 필터도 구현했다.

```python
@app.get("/members/filter/")
def filter_members(
    name: str | None = None,
    min_age: int | None = None,
):
    result = members

    if name is not None:
        keyword = name.lower()
        result = [
            member
            for member in result
            if keyword in member["name"].lower()
        ]

    if min_age is not None:
        result = [
            member
            for member in result
            if member["age"] >= min_age
        ]

    return result
```

### 잘 안 됐던 부분

`/members/search/` 대신 마지막 슬래시를 빼고 `/members/search`로 요청했을 때 예상과 다른 `422`가 발생했다. 처음에는 검색 함수의 코드가 잘못됐다고 생각했다.

### 원인과 해결 방법

`/members/{member_id}`가 이미 등록되어 있었기 때문에 FastAPI가 `search`를 정수형 `member_id`로 해석하려고 한 경우였다. 즉 검색 로직의 문제가 아니라 경로 매칭과 타입 검증에서 발생한 오류였다.

다음 사항을 확인해 해결했다.

- Swagger가 제시하는 정확한 URL인 `/members/search/`를 사용한다.
- 고정 경로와 동적 경로가 겹치는지 확인한다.
- 필요하면 `/members/search/`, `/members/filter/` 같은 고정 경로를 `/members/{member_id}`보다 먼저 선언한다.
- `422` Response의 `loc`, `type`, `msg`를 보고 어느 값의 검증이 실패했는지 찾는다.

이 문제를 통해 같은 `422`라도 Request Body만의 오류가 아니라 Path나 Query 값의 타입 검증에서도 발생할 수 있다는 것을 배웠다.

## 5. Request Body와 API Contract 작성하기

Chapter 03에서는 회원 등록 데이터를 URL이 아니라 JSON Body로 받았다. 코드를 작성하기 전에 `README.md`에 계약을 먼저 적었다.

```markdown
## POST /members Contract

### Request Body

- name: string, required
- email: string, required
- age: integer, required

### Success

- 201 Created
- created member JSON

### Failure

- invalid body → 422
```

Path Parameter는 특정 자원을 식별하고 Query Parameter는 검색이나 필터 조건을 전달한다. Request Body는 회원 등록처럼 여러 필드로 구성된 새 데이터를 전달할 때 사용한다.

### 해보고 느낀 점

처음에는 코드를 먼저 만들고 결과만 확인하면 된다고 생각했다. 하지만 입력 필드와 타입, 정상 상태 코드, 실패 상태를 먼저 적으니 무엇을 구현하고 무엇을 테스트해야 하는지가 분명해졌다. AI에게 코드를 요청할 때도 계약을 먼저 주면 결과를 검토하기 쉬울 것 같았다.

## 6. Pydantic Model로 입력 구조 정의하기

회원 등록 Body의 구조는 `BaseModel`을 상속한 클래스로 정의했다.

```python
from pydantic import BaseModel


class MemberCreate(BaseModel):
    name: str
    email: str
    age: int
```

이 Model은 다음 규칙을 동시에 표현한다.

- `name`은 필수 문자열이다.
- `email`은 필수 문자열이다.
- `age`는 필수 정수이다.
- 구조나 타입이 맞지 않으면 Endpoint 함수를 실행하기 전에 요청을 막는다.
- Swagger에서 Request Body 입력 Schema를 자동으로 만든다.

### 해보고 느낀 점

Pydantic Model은 데이터를 담는 클래스라고만 생각했는데, 실제로는 API 입력 설계도이자 검증 규칙이었다. Python 타입 힌트가 문서와 Validation에 동시에 사용되는 점이 인상적이었다.

## 7. POST Endpoint 구현하기

`MemberCreate`를 함수 인자 타입으로 지정해 Request Body를 받았다.

```python
@app.post("/members", status_code=201)
def create_member(member: MemberCreate):
    return member
```

FastAPI의 처리 순서는 다음과 같다.

```text
POST /members 요청
→ JSON Body 읽기
→ MemberCreate 규칙으로 검증
→ 검증 성공 시 create_member 실행
→ 201 Created와 JSON Response 반환
```

아직 데이터베이스에 저장하는 단계는 아니므로, 이번 실습에서는 검증을 통과한 데이터를 그대로 반환했다.

## 8. 정상 요청에서 201 확인하기

Swagger의 `POST /members`에서 다음 Body를 전송했다.

```json
{
  "name": "Hong Gil Dong",
  "email": "hong@example.com",
  "age": 30
}
```

확인한 결과는 다음과 같다.

```text
Status Code: 201
Response Body:
{"name":"Hong Gil Dong","email":"hong@example.com","age":30}
```

`200 OK`가 일반적인 성공을 뜻한다면 `201 Created`는 새로운 Resource 생성 요청이 성공했다는 의미로 사용한다.

## 9. 필수값 누락에서 422 확인하기

이번에는 `email`을 제외한 Body를 전송했다.

```json
{
  "name": "Hong Gil Dong",
  "age": 30
}
```

확인한 결과는 다음과 같다.

```text
Status Code: 422
오류 위치: body → email
오류 유형: missing
오류 메시지: Field required
```

실제 Response에는 다음과 같은 핵심 정보가 포함됐다.

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "email"],
      "msg": "Field required"
    }
  ]
}
```

### 해보고 느낀 점

처음에는 `422`가 나오면 서버 코드가 고장난 것으로 생각하기 쉬웠다. 하지만 이번 테스트에서는 서버가 API Contract에 맞지 않는 입력을 정확하게 차단한 것이므로 오히려 정상 동작이었다. 오류 JSON 전체를 외우기보다 `loc`, `type`, `msg`를 먼저 확인하면 원인을 빠르게 찾을 수 있었다.

## 10. Swagger로 API를 검증하는 방법

Swagger에서는 다음 항목을 직접 확인했다.

- HTTP Method와 URL
- Request Body Schema
- `Try it out`에서 실제로 보낸 JSON
- Request URL
- Response Code
- Response Body

브라우저 주소는 다음과 같았다.

```text
http://127.0.0.1:8000/docs
```

코드를 수정했는데 Swagger에 새 Endpoint가 보이지 않을 때는 다음 순서로 확인했다.

1. 파일을 저장했는지 확인한다.
2. Uvicorn이 현재 Chapter의 `main.py`를 실행 중인지 확인한다.
3. 이전 Chapter의 서버가 같은 8000번 포트를 사용 중인지 확인한다.
4. 서버를 종료하고 올바른 Chapter에서 다시 실행한다.
5. Swagger 페이지를 새로고침한다.

## 오늘 느낀 점

오늘은 FastAPI 문법 자체보다 **요청이 들어와 검증되고 응답이 나가는 전체 흐름**을 이해하는 것이 더 중요하다는 것을 느꼈다. 코드는 몇 줄 되지 않지만 폴더, 가상환경, 실행 위치, URL, 상태 코드 중 하나라도 맞지 않으면 예상한 결과가 나오지 않았다.

특히 잘못된 결과가 나왔을 때 코드를 바로 다시 쓰기보다 다음을 차례로 확인하는 습관이 필요했다.

```text
현재 파일 경로
→ 저장 여부
→ 서버 실행 경로
→ 요청 Method와 URL
→ 보낸 Parameter 또는 Body
→ Response Code와 오류 위치
```

또한 실패 응답도 중요한 테스트 결과라는 점을 배웠다. 정상 Body에서 `201`이 나오는 것만 확인하면 API가 입력을 제대로 검증하는지 알 수 없다. 필수값을 일부러 빼서 `422`와 오류 위치까지 확인해야 Pydantic Model이 실제로 동작한다고 말할 수 있었다.

수업 중 폴더를 잘못 만들거나 화면이 많아지고, 이전 서버가 남아 있는 등의 문제가 있었지만 그 과정을 해결하면서 개발 환경과 서버 상태를 확인하는 방법을 함께 익혔다. 다음 실습에서는 코드를 입력하기 전에 현재 경로와 실행 중인 서버부터 확인하면 같은 혼란을 줄일 수 있을 것 같다.

## 오늘 배운 내용을 내 말로 정리

Path Parameter는 특정 회원처럼 자원 하나를 식별할 때 사용하고, Query Parameter는 이름 검색이나 최소 나이처럼 조회 조건을 전달할 때 사용한다. 여러 필드를 묶어 새로운 데이터를 만들거나 수정할 때는 JSON Request Body를 사용한다.

FastAPI에서는 Pydantic Model로 Body의 필드와 타입을 정의할 수 있다. 요청이 들어오면 FastAPI가 먼저 Pydantic으로 데이터를 검증하고, 성공한 경우에만 Endpoint 함수를 실행한다. 정상적인 생성 요청은 `201 Created`를 반환하고, 필수 필드가 없거나 타입이 잘못되면 함수 실행 전에 `422 Validation Error`를 반환한다.

따라서 API를 완성했다는 것은 정상 요청이 성공하는 것만 의미하지 않는다. 계약에 맞지 않는 요청이 정확한 오류로 차단되는지까지 확인해야 한다.

## 오늘의 한 줄 정리

> FastAPI 실습의 핵심은 코드를 작성하는 데서 끝나는 것이 아니라, API Contract에 따라 정상 요청은 201로 처리하고 잘못된 요청은 422로 차단되는 과정을 직접 검증하는 것이다.
