## 1. Google OAuth 콜백에서 발생한 401 문제

Google 인증 자체는 성공했지만 콜백에서 FastAPI JWT를 발급한 직후 프로필을 조회하면 401이 발생하는 문제가 있었다.

원인은 새 JWT를 쿠키에 저장하더라도 같은 서버 요청 안에서는 브라우저가 그 쿠키를 아직 다시 보내지 않는다는 점이었다.

```text
Google 인증 성공
→ FastAPI JWT 발급
→ 응답에 Set-Cookie 추가
→ 같은 요청에서 /accounts/me 호출
→ 새 쿠키는 아직 요청에 없음
→ 401로 잘못 판단
```

이를 해결하기 위해 방금 발급받은 JWT를 프로필 확인 요청의 Authorization 헤더에 직접 전달했다. 프로필 확인이 성공한 뒤 최종 응답에서 HttpOnly 쿠키를 설정하도록 순서를 바꾸었다.

### 배운 점

쿠키를 설정하는 코드가 실행됐다고 해서 그 순간부터 모든 서버 요청에서 쿠키를 읽을 수 있는 것은 아니다. `Set-Cookie`는 브라우저가 응답을 받은 다음 요청부터 적용된다. 인증 콜백처럼 한 요청 안에서 토큰 발급과 후속 검증을 모두 수행한다면 새 토큰을 명시적으로 전달해야 한다.

## 2. 기존 프로필 때문에 Google 로그인이 반복 실패한 문제

이전에 OAuth 콜백이 실패한 계정은 `auth.users`와 `profiles`만 있고 `app_users`가 없는 불완전한 상태가 될 수 있었다. 이 사용자가 다시 로그인하면 OAuth 저장 로직이 `profiles`를 다시 INSERT하면서 기본키 충돌이 발생했다.

```text
기존 상태: auth.users 있음 + profiles 있음 + app_users 없음
재로그인: app_users와 profiles를 모두 생성 시도
결과: profiles.id 중복 → IntegrityError → 500
```

저장소 로직을 수정해 기존 프로필이 있으면 재사용하고, 없는 `app_users`만 동일 UUID로 연결하도록 했다. 계정과 프로필 UUID가 다르거나 같은 이메일이 다른 UUID에 연결된 경우에는 자동으로 합치지 않고 충돌로 처리했다.

### 배운 점

외부 인증은 정상적인 최초 가입만 생각하면 부족하다. 네트워크 오류나 중간 실패 때문에 일부 테이블만 저장된 상태도 복구할 수 있어야 한다. 재시도 가능한 인증 기능을 만들려면 완전한 신규 상태, 완전한 기존 상태, 일부 데이터만 남은 상태를 각각 검증해야 한다.

## 3. 실패한 Supabase 세션이 로그인처럼 보인 문제

FastAPI 계정 연동이 실패해도 Supabase 세션이 브라우저에 남아 있으면 헤더에 회원 닉네임이 표시되거나 마이페이지에서 로그인된 것처럼 보일 수 있었다. 하지만 실제 보호 API에 필요한 FastAPI JWT는 없기 때문에 화면과 서버의 인증 상태가 서로 달랐다.

이를 해결하기 위해 다음 기준을 적용했다.

- 서비스 로그인 여부는 FastAPI JWT 쿠키를 기준으로 판단한다.
- OAuth 콜백 실패 시 Supabase 세션을 정리한다.
- Supabase 세션만으로 빈 프로필을 자동 생성하지 않는다.
- 콜백이 실패하면 사용자에게 다시 시도할 수 있는 오류 화면을 제공한다.

이 작업을 통해 외부 인증 세션과 서비스 인증 세션의 역할을 다시 이해했다.

```text
Supabase 세션: Google이 실제 사용자인지 증명
FastAPI JWT: 서비스 내부의 로그인·권한·소유권 판단
```

## 4. 로그인된 사용자에게 로그인 화면이 다시 나타난 문제

한 번 OAuth에 실패하면 주소에 `error=oauth`가 남았다. 이후 정상 로그인에 성공해도 기존 코드는 오류 파라미터가 있다는 이유로 로그인 폼과 실패 문구를 다시 표시했다.

로그인된 사용자는 과거 오류 파라미터와 관계없이 홈 또는 검증된 `next` 경로로 이동하도록 조건을 수정했다. 같은 문제가 재발하지 않도록 로그인 페이지 소스를 확인하는 OAuth 회귀 테스트도 추가했다.

검증한 내용은 다음과 같다.

- 로그인하지 않은 사용자는 로그인 화면을 본다.
- 정상 로그인 사용자는 `/login`에 다시 접근해도 홈으로 이동한다.
- `error=oauth`가 남아 있어도 로그인된 사용자는 오류 화면을 보지 않는다.
- 외부 주소를 `next`로 전달해도 외부 사이트로 이동하지 않는다.

## 5. Supabase 연결 풀 안정화

팀원들이 백엔드 서버와 테스트를 동시에 실행하면 Supabase DB의 연결 한도 15개가 빠르게 소진됐다. 특히 애플리케이션 연결 풀과 Supabase transaction-mode pooler를 함께 사용하면 연결이 필요 이상으로 오래 유지될 수 있었다.

다음 설정으로 변경했다.

```text
SQLAlchemy: NullPool 사용
asyncpg: statement_cache_size = 0
```

`NullPool`은 요청이 끝난 연결을 애플리케이션이 계속 보관하지 않고 pooler에 바로 반환한다. statement cache를 끄면 PgBouncer가 다른 연결을 재사용할 때 prepared statement 이름이 충돌하는 문제를 피할 수 있다.

변경 후 catalog API를 연속 호출하고 홈의 상품·기획전·레시피·농가 이야기 화면을 확인했다.

### 배운 점

DB 연결 풀은 무조건 크게 잡는 것이 좋은 것이 아니다. 이미 외부 pooler를 사용하는 환경에서는 애플리케이션 풀과 중복될 수 있다. 팀 공용 무료 DB처럼 연결 한도가 작은 환경에서는 서버 한 대의 기본 풀 설정도 전체 한도를 소진할 수 있다.

## 6. 실제 브라우저 통합 검증

고객 사이트 3000과 관리자 사이트 3001을 모두 열어 다음 흐름을 확인했다.

```text
Google 계정 선택
→ Supabase 콜백
→ FastAPI JWT 교환
→ 홈에서 닉네임 표시
→ 마이페이지 조회
→ 장바구니·주문 화면 접근
→ 로그아웃
→ 보호 화면 재접근 차단
```

관리자 화면에서는 일반 사용자 접근이 403으로 차단되고 승인된 관리자만 들어갈 수 있는지 확인했다. QA 전용 상품을 이용해 상품 등록, 이미지 업로드, 고객 화면 노출, 가격·재고 수정, 휴지통 이동, 복원과 영구 삭제도 점검했다.

## 7. Supabase 접속 시간 초과 분석

마지막 재확인 과정에서 Google 계정 선택 화면으로 넘어가기 전에 Supabase 주소가 열리지 않는 현상이 발생했다. 브라우저 오류는 다음과 같았다.

```text
ERR_TIMED_OUT
votponhrnpetlrmttstl.supabase.co의 응답이 너무 오래 걸립니다.
```

이 오류는 OAuth 콜백이나 계정 코드가 실행되기 전 Supabase 서버 접속 단계에서 발생한다. 따라서 Google Client 설정이나 JWT 코드 오류와 구분해야 한다.

원인을 다음처럼 나누어 확인했다.

- 모든 팀원에게 발생: Supabase 프로젝트 중지·복구 중이거나 서비스 장애 가능성
- 특정 팀원에게만 발생: DNS, VPN, 프록시, 방화벽 또는 네트워크 문제 가능성
- 일반 Chrome에서는 되고 인앱 브라우저에서만 발생: 인앱 브라우저 네트워크 제한 가능성

발표 중 외부 인증 장애가 생길 수 있으므로 일반 아이디·이메일 로그인 계정을 예비 수단으로 준비해야 한다는 점도 정리했다.

## 어려웠던 점과 해결 방법

### 오류가 발생한 계층을 구분하기

Google 로그인 실패라는 같은 화면이라도 원인은 여러 곳에 있을 수 있었다.

```text
Supabase 주소도 안 열림 → 네트워크 또는 Supabase 장애
Google 화면에서 거부됨 → OAuth Provider 설정
콜백에서 실패 → 코드 교환·리디렉션 설정
FastAPI에서 실패 → 내부 계정 연결·JWT 발급
로그인 후 화면만 이상함 → 쿠키·상태 갱신·프런트 조건
```

처음에는 모든 실패를 OAuth 설정 문제로 생각하기 쉬웠지만, 요청이 어느 단계까지 도달했는지 확인하면 원인 범위를 빠르게 줄일 수 있었다.

### 자동 테스트와 실제 화면을 함께 확인하기

자동 테스트는 조건 분기와 API 결과를 빠르게 확인할 수 있지만, 로그인 후에도 오류 문구가 남거나 헤더가 잘못 표시되는 문제는 브라우저에서 직접 확인해야 발견할 수 있었다. 앞으로는 인증 작업을 할 때 단위 테스트, API 테스트, 브라우저 시나리오를 함께 수행해야겠다.

## 오늘 느낀 점

오늘은 인증 기능이 단순히 로그인 성공 응답을 받는 작업이 아니라는 것을 다시 느꼈다. 외부 인증 세션, 내부 계정, JWT 쿠키, 프로필 데이터, DB 연결, 화면 상태가 모두 정확한 순서로 이어져야 사용자는 정상 로그인으로 인식한다.

또한 장애가 발생했을 때 코드부터 수정하기보다 브라우저 오류 코드와 요청 단계를 먼저 확인하는 것이 중요했다. `ERR_TIMED_OUT`은 인증 로직이 아니라 서버 접속 문제인데, 이를 구분하지 못하면 정상 코드를 계속 고치게 된다.

작업 기록도 단순히 “로그인 구현”이라고 적는 것보다 설계, 저장, 보안, 예외 처리, 검증으로 나누어야 내가 실제로 무엇을 해결했는지 설명할 수 있다는 점을 배웠다.
