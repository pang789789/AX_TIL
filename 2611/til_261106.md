# 2026-11-06 TIL — CORS와 Frontend·FastAPI 연동 기초

## 오늘 학습한 내용

오늘은 지금까지 만든 FastAPI Member API를 Browser에서 실행되는 Frontend JavaScript와 연결하는 방법을 배웠다. 이전까지는 Swagger와 TestClient를 이용해 Backend 내부에서 API 동작을 확인했다면, 오늘은 HTML에서 `fetch()`를 호출하고 Browser의 CORS 검사를 거쳐 FastAPI와 PostgreSQL까지 요청이 전달되는 전체 흐름을 학습했다.

오늘 수업의 핵심 흐름은 다음과 같다.

```text
Browser
→ Frontend JavaScript
→ fetch()
→ CORS 검사
→ FastAPI Router
→ Service / Repository
→ PostgreSQL
→ JSON Response
→ Browser UI
```

또한 Frontend와 Backend 서버를 동시에 실행하려면 왜 터미널이 두 개 필요한지, Python 가상환경은 어느 터미널에 적용해야 하는지도 정리했다.

## 1. Origin의 의미

Browser는 다음 세 가지 조합으로 Origin을 구분한다.

```text
scheme + host + port
```

예를 들어 다음 두 주소는 host가 같아도 port가 다르기 때문에 서로 다른 Origin이다.

```text
Frontend: http://localhost:5500
Backend : http://localhost:8000
```

처음에는 둘 다 `localhost`이므로 같은 주소라고 생각했다. 하지만 Browser 입장에서는 `5500`과 `8000`이 서로 다른 출처이다. Frontend JavaScript가 다른 Origin의 API를 호출하면 Browser는 Backend 응답을 사용해도 되는지 CORS 정책을 검사한다.

오늘 가장 중요하게 정리한 내용은 다음과 같다.

```text
CORS는 FastAPI가 Browser를 차단하는 기능이 아니다.
Browser가 다른 Origin의 응답 사용을 제한하는 보안 정책이다.
```

따라서 Swagger에서 API가 정상이어도 실제 Frontend Browser에서는 CORS 오류가 발생할 수 있다.

```text
Swagger도 실패
→ Backend 코드, DB 연결, API 자체 문제부터 확인

Swagger는 성공하지만 Browser만 실패
→ CORS, Frontend Origin, API URL부터 확인
```

## 2. FastAPI CORS Middleware

FastAPI에서는 `CORSMiddleware`를 사용해 허용할 Frontend Origin을 지정한다.

```python
from fastapi.middleware.cors import CORSMiddleware


allowed_origins = [
    "http://localhost:5500",
    "http://127.0.0.1:5500",
]

app.add_middleware(
    CORSMiddleware,
    allow_origins=allowed_origins,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

각 설정의 역할은 다음과 같다.

- `allow_origins`: 요청을 허용할 Frontend 주소 목록
- `allow_credentials`: Cookie나 인증정보를 포함한 요청 허용 여부
- `allow_methods`: 허용할 HTTP Method
- `allow_headers`: 허용할 Request Header

개발 중에는 `allow_origins=["*"]`를 사용하면 편해 보이지만, 운영 환경에서는 실제 Frontend 주소를 명시하는 편이 안전하다. 중요한 것은 코드를 단순히 복사하는 것이 아니라 “현재 어떤 Frontend 주소의 요청을 왜 허용했는가?”를 설명할 수 있어야 한다는 점이다.

## 3. Frontend와 Backend 서버를 따로 실행하는 이유

교수님 화면을 따라가면서 터미널을 왜 두 개 열어야 하는지 처음에는 이해되지 않았다. 이유는 Frontend 서버와 Backend 서버가 각각 독립적으로 계속 실행되어야 하기 때문이다.

### Backend 터미널

```powershell
python -m uvicorn app.main:app --reload --port 8000
```

FastAPI 서버가 실행되는 동안 이 터미널은 Uvicorn Process가 사용한다.

### Frontend 터미널

```powershell
python -m http.server 5500
```

HTML과 JavaScript 파일을 Browser에 제공하는 Static Web Server가 이 터미널을 사용한다.

```text
터미널 1 → FastAPI Backend, 8000번 Port
터미널 2 → Frontend Static Server, 5500번 Port
```

서버 명령은 실행한 뒤 바로 종료되는 명령이 아니라 계속 대기하며 요청을 처리한다. 따라서 한 터미널에서 두 서버를 동시에 실행하기 어렵고, 각각의 로그도 구분해서 보기 위해 두 개의 터미널을 사용한다.

## 4. VS Code Python 가상환경 선택

오늘 VS Code에서 사용할 Python Interpreter를 다음 경로의 공용 가상환경으로 지정했다.

```text
C:\dev\fullstack-web-course\practice\phase02\.venv\Scripts\python.exe
```

VS Code 상태 표시줄에서 다음과 같이 선택된 것을 확인했다.

```text
.venv (3.13.15)
```

가상환경은 FastAPI, Uvicorn, SQLAlchemy, psycopg처럼 프로젝트에 설치한 Python Package를 정확하게 사용하기 위해 필요하다. 시스템 Python을 선택하면 Module을 설치했는데도 `ModuleNotFoundError`가 발생할 수 있다.

새 Backend 터미널에서 프롬프트 앞에 다음과 같이 보이면 가상환경이 활성화된 상태이다.

```text
(.venv) PS C:\dev\fullstack-web-course\...
```

Frontend의 `python -m http.server`는 특별한 외부 Package가 필요하지 않지만, 프로젝트에서 어떤 Python을 사용하는지 혼란을 줄이기 위해 VS Code Interpreter는 공용 `.venv`로 통일해 두는 것이 이해하기 쉬웠다.

## 5. Frontend에서 GET /members 호출하기

Frontend JavaScript에서는 API 주소를 한 곳에 정의하고 `fetch()`로 회원 목록을 요청한다.

```javascript
const API_BASE_URL = "http://localhost:8000";

async function loadMembers() {
  try {
    const response = await fetch(`${API_BASE_URL}/members`);

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const members = await response.json();
    console.log(members);
  } catch (error) {
    console.error(error);
  }
}

loadMembers();
```

`fetch()`는 HTTP Status가 404나 500이어도 무조건 JavaScript Exception을 발생시키지는 않는다. 따라서 `response.ok`를 직접 확인하고 실패 응답을 처리해야 한다.

GET 요청을 검증할 때는 화면에 회원이 보이는지만 확인해서는 안 된다. Browser DevTools의 Network에서 다음 정보를 확인해야 한다.

```text
Request URL    → http://localhost:8000/members
Request Method → GET
Status Code    → 200
Response       → 회원 JSON 배열
```

## 6. Frontend에서 POST /members 호출하기

회원 생성 요청은 HTTP Method, Header, JSON Body를 함께 전달해야 한다.

```javascript
async function createMember(member) {
  const response = await fetch(`${API_BASE_URL}/members`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
    },
    body: JSON.stringify(member),
  });

  const body = await response.json();

  if (!response.ok) {
    throw new Error(body.detail ?? `HTTP ${response.status}`);
  }

  return body;
}
```

테스트 데이터 예시는 다음과 같다.

```javascript
createMember({
  name: "Frontend User",
  email: "frontend@example.com",
  age: 28,
});
```

정상적인 POST 요청은 `201 Created`를 반환해야 하며, Browser 응답만 보는 것이 아니라 PostgreSQL에도 실제 Row가 생성됐는지 확인해야 한다.

## 7. CORS 오류를 확인하는 순서

Browser에서 API 호출이 실패했을 때 무작정 전체 코드를 다시 작성하면 원인을 찾기 어렵다. 오늘 배운 확인 순서는 다음과 같다.

```text
1. Browser Console 오류 확인
2. Network에 Request가 생성됐는지 확인
3. 실제 Request URL 확인
4. 현재 Frontend Origin 확인
5. FastAPI allow_origins와 비교
6. HTTP Method, Header, Payload 확인
7. FastAPI/Uvicorn Log 확인
8. SQLAlchemy Log와 Database 확인
```

가장 중요한 질문은 “코드 어디가 틀렸는가?”가 아니라 “요청이 어디까지 정상적으로 도달했는가?”이다.

예를 들어 Network 요청이 FastAPI까지 도달하지 않았다면 Repository나 SQL을 먼저 수정할 이유가 없다. 반대로 FastAPI Log에는 요청이 보이는데 500이 반환된다면 CORS보다 Service, Repository, DB 문제를 확인해야 한다.

## 8. API Base URL과 환경 분리

개발 환경과 운영 환경의 API 주소는 다를 수 있다.

```text
Development → http://localhost:8000
Production  → https://api.example.com
```

코드 여러 곳에 URL을 직접 작성하면 배포 환경이 바뀔 때마다 모든 파일을 수정해야 한다. 따라서 API Base URL은 환경별 설정으로 분리하고, JavaScript 코드에서는 한 곳의 설정만 참조하는 구조가 좋다.

오늘 정리한 원칙은 다음과 같다.

```text
프로그램 로직 ≠ 환경에 따라 달라지는 설정값
```

Backend에서도 다음 값은 코드에 직접 작성하지 않고 환경변수로 관리한다.

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD
CORS_ORIGINS
```

그리고 실제 비밀번호가 포함된 `.env`는 반드시 `.gitignore`에 포함되어야 한다.

## 9. Browser에 노출해도 되는 값과 Secret

Frontend JavaScript는 사용자의 Browser에서 실행된다. 따라서 Frontend Bundle이나 Frontend 환경변수에 들어간 값은 사용자가 볼 수 있다고 가정해야 한다.

### Browser에 있어도 되는 값

- 공개 API Base URL
- 공개 가능한 환경 이름
- UI 설정

### Browser에 절대 넣으면 안 되는 값

- PostgreSQL 비밀번호
- Private API Key
- Server Secret
- JWT Signing Secret

```text
Browser로 전달되는 값은 Secret이 아니다.
```

Frontend에서 DB에 직접 연결하지 않고 FastAPI를 거치는 이유도 여기에 있다. Browser는 필요한 요청만 Backend에 보내고, DB 비밀번호와 중요한 업무 규칙은 Server 내부에 남겨야 한다.

## 어려웠던 부분과 해결 방법

### 1. localhost인데 왜 CORS가 필요한지 헷갈렸다

처음에는 Frontend와 Backend가 모두 내 컴퓨터에서 실행되므로 같은 Origin이라고 생각했다.

해결 방법:

- Origin은 `scheme + host + port` 조합으로 판단한다.
- `localhost:5500`과 `localhost:8000`은 port가 다르므로 다른 Origin이다.
- FastAPI `allow_origins`에는 port까지 정확하게 포함해야 한다.

### 2. 터미널을 왜 두 개 열어야 하는지 이해되지 않았다

서버 명령도 일반 Python 파일처럼 실행 후 끝나는 것으로 생각했다.

해결 방법:

- Uvicorn과 Static Web Server는 요청을 기다리며 계속 실행되는 Process이다.
- Backend와 Frontend가 동시에 실행되어야 Browser 연동을 테스트할 수 있다.
- 두 서버의 로그를 구분하기 위해 터미널도 각각 사용한다.

### 3. 가상환경이 선택됐는지 확신하기 어려웠다

기존 터미널에는 오래된 실행 기록이 남아 있어 현재 환경과 혼동됐다.

해결 방법:

- VS Code의 `Python: Select Interpreter`에서 정확한 `.venv\Scripts\python.exe`를 직접 선택했다.
- 상태 표시줄에 `.venv (3.13.15)`가 표시되는지 확인했다.
- 새 터미널에서는 프롬프트의 `(.venv)` 표시를 확인해야 한다.

### 4. Swagger 성공과 Browser 성공을 같은 것으로 생각했다

Swagger에서 GET이 성공하면 Frontend에서도 당연히 성공할 것이라고 생각할 수 있었다.

해결 방법:

- Swagger는 Backend 자체 동작을 확인하는 Evidence이다.
- 실제 Frontend Browser 호출에는 Origin과 CORS 검사가 추가된다.
- Browser Console과 Network를 별도로 확인해야 한다.

### 5. 화면에 데이터가 보이면 연동이 끝난 것으로 생각했다

UI 결과만 보면 이전 데이터나 잘못된 주소를 사용해도 문제를 놓칠 수 있다.

해결 방법:

```text
Browser UI
= Network Response
= FastAPI Log
= SQLAlchemy Log
= PostgreSQL 실제 데이터
```

여러 Evidence가 서로 일치하는지 확인해야 연동 성공이라고 판단할 수 있다.

## 해보고 느낀 점

오늘은 Backend API가 정상적으로 동작하는 것과 Frontend에서 그 API를 사용할 수 있는 것이 별개의 문제라는 점을 이해했다. Swagger에서는 요청이 바로 FastAPI에서 실행되지만, 실제 Browser에서는 CORS라는 추가 경계를 통과해야 한다. CORS 오류가 발생했을 때 Backend 코드를 전부 고치기 전에 Frontend Origin과 허용 Origin이 정확히 일치하는지 먼저 확인해야 한다.

터미널을 두 개 사용하는 이유도 단순히 교수님 화면을 따라 하는 것이 아니라 Frontend와 Backend가 서로 다른 Process와 Port에서 실행되기 때문이라는 것을 알게 되었다. 각각의 터미널에서 로그를 분리해서 보면 요청이 Frontend에서 Backend까지 전달됐는지 확인하기도 더 쉽다.

가상환경은 Python Package 충돌을 막는 설정이라고만 생각했는데, VS Code Interpreter와 새 터미널의 환경이 일치해야 실제 실행에서도 같은 Package를 사용한다는 점이 중요했다. 화면 아래에 Python 버전이 표시된다고 끝나는 것이 아니라 정확한 `.venv` 경로인지 확인하는 습관이 필요하다.

보안 부분에서는 Frontend 환경변수라는 이름 때문에 안전하게 숨겨질 것이라고 생각하면 안 된다는 점이 기억에 남았다. Browser에 전달되는 값은 결국 사용자가 확인할 수 있으므로 DB 비밀번호나 Private Key는 반드시 Backend에만 있어야 한다.

## 오늘의 핵심 정리

```text
Origin = scheme + host + port

Frontend : localhost:5500
Backend  : localhost:8000
→ 서로 다른 Origin

CORS
→ Browser가 다른 Origin 응답 사용을 제한하는 정책

터미널 1
→ FastAPI Backend Server

터미널 2
→ Frontend Static Server

Frontend 공개 가능
→ API Base URL, UI 설정

Backend에만 보관
→ DB Password, Private Key, Server Secret

검증 Evidence
→ Browser Console
→ Network
→ FastAPI Log
→ SQLAlchemy Log
→ PostgreSQL Data
```

환경별 설정은 코드에서 분리하고, Secret은 Browser 경계를 넘어가지 않도록 해야 한다.
