# 2026-11-19 TIL — Chunking과 검색 품질 평가, 근거 기반 RAG

## 오늘 학습한 내용

오늘은 오전에 Lesson 07의 Chunking과 PostgreSQL + pgvector 검색 구조를 학습하고, 오후에는 Lesson 08의 검색 품질 평가와 근거 기반 RAG를 실습했다.

같은 긴 문서를 Fixed-size, Paragraph, Overlap 방식으로 나누면서 청크 크기와 경계가 어떻게 달라지는지 확인했다. 이후 검색 결과에 정답 문구가 포함됐는지를 Hit@K와 MRR로 평가하고, 근거가 확인된 경우에만 원문과 출처를 표시하며 근거가 없으면 답변을 보류하는 흐름을 실행했다.

오전 DB 실습은 전용 데이터베이스를 생성하고 Preview까지 진행했지만 `.env`의 PostgreSQL 비밀번호가 입력되지 않아 실제 인덱싱부터는 실행하지 못했다. 오후 Lesson 08은 PostgreSQL을 사용하지 않는 Fixture 방식이어서 검색, 평가, 근거 Preview, HOLD 및 전용 자동 테스트까지 실행했다.

```text
긴 문서 확인
→ 세 가지 Chunking 방식 비교
→ 청크 ID와 위치 Metadata 이해
→ 검색 결과의 정답 근거 순위 평가
→ Hit@3·RR·MRR 계산
→ 근거가 있으면 원문 발췌와 출처 표시
→ 근거가 없으면 HOLD
```

## 2. 핵심 개념과 실습 내용

### Chunking

Chunking은 긴 문서를 검색 가능한 작은 단위로 나누는 과정이다. 청크가 너무 크면 여러 주제가 섞이고, 너무 작으면 필요한 문맥이나 정답 문장이 경계에서 끊길 수 있다.

| 방식 | 원리 | 장점 | 주의점 |
|---|---|---|---|
| Fixed-size | 일정한 문자 수로 분할 | 단순하고 크기를 예측하기 쉬움 | 문장 중간에서 잘릴 수 있음 |
| Paragraph | 빈 줄을 기준으로 분할 | 문단 의미 경계를 보존하기 쉬움 | 청크 길이가 일정하지 않음 |
| Overlap | 일정 크기로 자르면서 일부를 중첩 | 경계 주변 문맥을 다음 청크에도 보존 | 중복 저장량과 청크 수가 증가 |

`size=160`, `overlap=30`이면 이동 간격은 130자다.

```text
stride = size - overlap
       = 160 - 30
       = 130

첫 청크:   0:160
둘째 청크: 130:290
공통 범위: 130:160, 총 30자
```

Overlap을 늘린다고 검색 정확도가 반드시 높아지는 것은 아니다. 같은 질문과 Top-K를 유지한 채 실제 결과로 비교해야 한다.

### 청크 ID와 Metadata

각 청크에는 원문뿐 아니라 식별자와 출처 정보를 함께 관리한다.

```text
ID          같은 청크를 구분하는 안정적인 해시
Document    청크의 실제 원문
Metadata    분할 전략, 파일명, 시작·끝 위치, 순번
Embedding   검색에 사용하는 숫자 벡터
```

원문 위치 `start_pos`, `end_pos`를 기록하면 검색 결과가 문서의 어느 부분에서 왔는지 다시 확인할 수 있다. 같은 설정으로 재인덱싱할 때 기존 행을 지우고 다시 저장하면 중복 증가와 사라진 청크의 잔존을 막을 수 있다.

### Hit@K, RR, MRR

Hit@3은 상위 세 결과 안에 사전에 지정한 정답 문구가 하나라도 있는지 검사한다.

```text
정답 문구가 상위 3개 안에 있음 → Hit@3 = 1
정답 문구가 상위 3개 안에 없음 → Hit@3 = 0
```

RR(Reciprocal Rank)은 첫 정답의 순위를 역수로 표현한다.

```text
1위 → 1 / 1 = 1.0
2위 → 1 / 2 = 0.5
3위 → 1 / 3 ≈ 0.333
범위 안에 없음 → 0
```

MRR은 여러 질문의 RR 평균이다. 오늘 평가 데이터에서는 정답 근거가 없는 질문을 Hit@K와 MRR 평균의 분모에서 제외했다.

Hit@3과 MRR은 생성된 답변의 정답률이나 확률이 아니다. 정확한 정답 문자열 포함 여부를 기준으로 한 교육용 검색 지표이며, 최종 답변의 사실 정확성은 별도로 검토해야 한다.

### Fixture와 Live

Fixture는 사람이 정한 규칙 벡터를 사용해 실행 구조를 확인한다. 실제 의미 임베딩 모델의 성능을 나타내지 않는다. Live는 실제 Embeddings API와 대화 모델을 호출할 수 있어 비용과 데이터 전송을 확인해야 한다.

```text
Fixture: 로컬 수동 벡터, API 호출 0회
Live:    실제 임베딩·대화 API, 선택 실행 및 비용 가능
```

## 3. 코드와 실행 흐름

### Lesson 07 실행 흐름

```text
preview → 문서를 분할하여 위치와 길이를 화면에서 확인
```

실제로 실행한 Preview 명령은 다음과 같다.

```powershell
$env:PYTHONIOENCODING='utf-8'
python lesson07_pgvector.py preview --strategy fixed --size 160
python lesson07_pgvector.py preview --strategy paragraph
python lesson07_pgvector.py preview --strategy overlap --size 160 --overlap 30
```

### Lesson 08 실행 흐름

`rag_quality.py`는 Lesson 07의 PostgreSQL 테이블을 읽지 않는다. 실행할 때 원문을 다시 나누고 Fixture 벡터와 코사인 유사도로 메모리에서 순위를 계산한다.

```text
질문 입력
→ chunking.split_chunks()로 원문 분할
→ Fixture 질문·청크 벡터 생성
→ 코사인 유사도 계산 및 내림차순 정렬
→ 정답 문자열의 첫 순위 확인
→ Hit@K·RR·MRR 계산
→ 근거 있음: 원문 발췌 + 출처
→ 근거 없음: NO_EVIDENCE + HOLD
```

주요 함수의 역할은 다음과 같다.

| 함수 | 역할 |
|---|---|
| `rank_chunks()` | 질문과 청크의 유사도를 계산하고 정렬 |
| `gold_rank()` | 정답 문자열이 처음 나타난 순위 확인 |
| `evaluate_cases()` | 질문별 Hit와 RR 계산 |
| `extract_evidence()` | 검색된 원문에서 정확한 근거 발췌 |
| `load_cases()` | JSON 평가 데이터 읽기 |
| `display_rows()` | 순위·유사도·ID·출처·범위 출력 |
| `main()` | search, evaluate, preview, generate 분기 |

실제로 실행한 명령은 다음과 같다.

```powershell
python chunking.py preview --strategy paragraph
python rag_quality.py search "과제 마감일"
python rag_quality.py evaluate
python rag_quality.py preview "과제 마감일" --gold "금요일 오후 6시"
python rag_quality.py preview "과제 마감일" --gold "확인되지 않은 가상의 문구"
python -m unittest tests.test_rag_quality -v
```

### Chunking Preview

| 전략 | 실제 청크 수 | 관찰 내용 |
|---|---:|---|
| Fixed-size 160 | 4 | 마지막 청크는 130자로 짧음 |

| Overlap 160/30 | 5 | 시작 위치가 0, 130, 260, 390, 520으로 중첩됨 |

### Fixture 검색

`과제 마감일` 검색에서 관련 청크 한 개가 반환됐다.

```text
[SEARCH] mode=fixture; strategy=paragraph; chunks=5; retrieved=1
[1] sim=1.000; source=lesson07_long_notice.md; range=31:173
[FIXTURE] 수동 벡터; api_calls=0
```

코사인 유사도 `sim`은 클수록 가깝다. 이전 pgvector의 `<=>` 코사인 거리는 작을수록 가까우므로 방향을 혼동하면 안 된다.

### Hit@3과 MRR

```text
과제 마감일     hit=1, rank=1, rr=1.0
API Key 보안   hit=1, rank=1, rr=1.0
질문 게시판     hit=1, rank=2, rr=0.5
우주선 연료 종류 gold 없음, 평균 계산에서 제외

Hit@3 = 3/3
MRR = (1.0 + 1.0 + 0.5) / 3 = 0.833
```

### 근거 Preview와 HOLD

정답 근거가 검색된 경우 원문 문구와 출처가 표시됐다.

```text
[EVIDENCE] 금요일 오후 6시
[CITATION] lesson07_long_notice.md range=31:173
[PREVIEW] 원문에서 발췌한 문구이며 모델 생성 답변이 아닙니다.
```

존재하지 않는 근거 문자열을 지정했을 때는 답변을 만들지 않았다.

```text
[NO_EVIDENCE] 검증된 정답 문구를 검색 결과에서 찾지 못했습니다.
[HOLD] 근거가 없어 답변을 생성하지 않습니다.
```

HOLD는 검색 결과에서 지정한 문자열을 찾지 못했다는 뜻이다. 원문 전체에 답이 절대 없다는 증명은 아니다.

## 5. 어려웠던 부분과 잘 안됐던 점

### Windows 콘솔 인코딩 오류

처음 Preview를 실행했을 때 문서에 포함된 긴 대시 문자를 CP949 콘솔이 출력하지 못했다.

```text
UnicodeEncodeError: 'cp949' codec can't encode character '\u2014'
```

코드와 원문을 수정하지 않고 실행 환경의 출력 인코딩을 UTF-8로 지정해 해결했다.

```powershell
$env:PYTHONIOENCODING='utf-8'
```

### PostgreSQL 비밀번호 누락

Lesson 07 인덱싱 명령은 다음 오류로 중단됐다.

```text
RuntimeError: 누락된 .env 항목: DB_PASSWORD
```

DB 이름과 사용자를 설정하는 것만으로는 Python이 접속할 수 없다. 실제 비밀번호는 채팅이나 TIL에 남기지 않고 로컬 `.env`에 직접 입력해야 한다.

### 검색 성공과 답변 성공의 혼동

검색 결과가 반환되고 유사도 값이 높아도 정답 근거가 포함됐다는 뜻은 아니다. Hit@K로 정답 문자열을 검사하고, 최종 답변이 근거와 일치하는지는 다시 확인해야 한다.

### 교안과 로컬 테스트 수 차이

처음 로컬 `test_rag_quality.py`는 테스트가 9개였지만 교안은 12개라고 설명했다. 최신 원격 파일과 비교한 결과 전용 테스트 파일만 이전 버전이어서 최신 원본으로 갱신했다. 다시 실행해 12개 모두 통과하는 것을 확인했다.

## 6. 오류의 원인과 해결 방법

### Preview에서 인코딩 오류가 발생할 때

```text
1. 오류 문자와 현재 콘솔 인코딩을 확인한다.
2. 원문을 임의로 삭제하거나 문자를 바꾸지 않는다.
3. PYTHONIOENCODING=utf-8로 출력 인코딩을 지정한다.
4. 같은 Preview 명령을 다시 실행한다.
5. 청크 수와 위치가 정상적으로 출력되는지 확인한다.
```

### DB 인덱싱이 실패할 때

```text
1. .env 파일 존재 여부를 확인한다.
2. DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD를 확인한다.
3. 비밀번호 값은 터미널이나 문서에 출력하지 않는다.
4. DBeaver에서 같은 DB 연결이 되는지 확인한다.
5. 대상 DB에서 vector 확장이 활성화됐는지 확인한다.
6. index와 query에 같은 strategy, size, overlap을 사용한다.
7. count 결과와 Preview 청크 수를 비교한다.
```

### 검색 결과가 예상과 다를 때

```text
1. Fixture인지 Live인지 확인한다.
2. 질문 벡터나 청크 벡터가 0벡터인지 확인한다.
3. 같은 분할 전략과 Top-K로 비교한다.
4. 정답 문자열이 원문에 정확히 존재하는지 확인한다.
5. 정답 문자열이 청크 경계에서 둘로 나뉘지 않았는지 확인한다.
6. 유사도·거리와 정답 확률을 혼동하지 않는다.
7. 검색된 원문을 직접 읽고 근거 충분성을 판단한다.
```

## 7. 해보고 느낀 점

문서를 잘게 나누는 것 자체보다 질문의 답을 보존하는 단위를 선택하는 것이 더 중요하다는 점을 이해했다. Paragraph 방식은 의미 경계를 지키기 쉬웠고, Overlap은 경계 문맥을 보존했지만 중복이 증가했다. 어느 방식도 항상 가장 좋다고 단정할 수 없었다.

Hit@3이 모두 성공해도 MRR은 달라질 수 있다는 점도 흥미로웠다. `질문 게시판`의 정답 근거가 2위에 있어 Hit@3은 1이지만 RR은 0.5였다. 단순히 찾았는지뿐 아니라 얼마나 앞에서 찾았는지를 함께 봐야 했다.

근거를 찾지 못했을 때 그럴듯한 답을 생성하지 않고 HOLD하는 흐름이 신뢰할 수 있는 RAG에서 중요하다고 느꼈다. 다만 정확한 문자열을 미리 알고 있는 교육용 방식이므로 실제 서비스에는 더 복잡한 근거 적합성 평가가 필요하다.

## 오늘의 핵심 정리

1. Chunking은 긴 문서를 검색 가능한 단위로 나누는 과정이다.
2. Fixed-size는 단순하지만 문장 중간을 자를 수 있다.
3. Paragraph는 문단 경계를 보존하지만 청크 길이가 일정하지 않다.
4. Overlap은 경계 문맥을 보존하지만 중복과 저장량을 늘린다.
5. 청크에는 ID, 원문, 출처, 시작·끝 위치와 벡터를 함께 관리해야 한다.
6. 같은 질문과 Top-K를 유지하고 한 번에 하나의 조건만 바꿔 비교한다.
7. Hit@K는 정답 근거가 상위 K개 안에 있는지를 확인한다.
8. RR은 첫 정답 순위의 역수이고 MRR은 여러 RR의 평균이다.
9. MRR은 정답 확률이나 생성 답변 정확도가 아니다.
10. Fixture는 수동 규칙 벡터이며 실제 의미 임베딩 성능이 아니다.
11. 코사인 유사도는 클수록 가깝고 코사인 거리는 작을수록 가깝다.
12. Preview는 모델 생성 답변이 아니라 원문 발췌다.
13. 근거가 없으면 추측하지 않고 HOLD한다.
14. HOLD는 원문 전체에 답이 없다는 증명이 아니라 현재 검색에서 못 찾았다는 뜻이다.
15. API Key와 DB 비밀번호는 로컬 `.env`에만 보관한다.
16. 실행하지 않은 DB 인덱싱과 Live API 결과를 성공했다고 기록하지 않는다.
