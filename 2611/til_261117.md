# 2026-11-17 TIL — Prompt·Context 설계와 문서 기반 RAG 첫걸음

## 오늘 학습한 내용

오늘은 My AI Assistant에 두 가지 기능을 이어서 추가했다. 먼저 Lesson 03에서 같은 질문을 기본 프롬프트와 구조화 프롬프트로 만들어 비교했고, Context가 최종 입력의 어느 위치에 포함되는지 확인했다. 이어서 Lesson 04에서는 Markdown 공지 문서를 읽고 질문과 겹치는 키워드가 있는 문단을 검색해 출처와 함께 보여 주는 간단한 RAG 흐름을 만들었다.

오늘 실습의 전체 흐름은 다음과 같다.

```text
기본 질문 입력
→ 역할·목표·제약·출력 형식을 추가한 구조화 프롬프트 생성
→ Context를 <reference>에 삽입
→ Preview와 형식 검사
→ Markdown 공지 문서 읽기
→ 섹션 분리와 키워드 검색
→ source·section·score가 포함된 근거 표시
→ 근거가 있을 때만 Live 모델 호출 준비
→ 프롬프트 실행 로그 기록
```

실제 OpenAI API Key가 준비되지 않아 Live 답변 생성은 성공으로 확인하지 않았다. Mock·Preview·검색·자동 테스트 결과와 Live 설정 오류를 구분해 기록했다.

## 1. 실습 환경과 폴더 구조

어제 사용한 `main.py`와 `chat_loop.py`를 그대로 유지하고 Lesson 03·04 파일을 추가했다.

```text
my-ai-assistant/

├─ chat_loop.py

├─ document_qa.py
├─ data/
│  └─ lesson04_notice.md

└─ tests/
   ├─ test_main.py
   ├─ test_chat_loop.py
   ├─ test_prompt_compare.py
   └─ test_document_qa.py
```

각 파일의 역할은 다음과 같다.

| 파일 | 역할 |
|---|---|
| `prompt_compare.py` | 기본 프롬프트와 구조화 프롬프트 생성·비교 |
| `document_qa.py` | 문서 읽기, 섹션 분리, 키워드 검색, 근거 기반 프롬프트 생성 |
| `lesson04_notice.md` | 과제 제출·실습 준비·질문 응대 정보가 담긴 예제 문서 |
| `prompt_log.jsonl` | 질문, 검색 근거, 최종 프롬프트와 실행 상태 누적 기록 |
| `test_prompt_compare.py` | Prompt·Context·형식 검사 테스트 |
| `test_document_qa.py` | 문서 검색·근거 없음·점수·Preview 테스트 |

API Key는 소스 코드나 로그에 기록하지 않았다. 로컬 프롬프트 로그도 Git에 올라가지 않도록 `.gitignore`에 `logs/*.jsonl`을 추가했다.

## 2. 핵심 개념과 실습 내용

### Prompt와 Context의 차이

Prompt는 모델에게 전달하는 질문과 지시 전체다. Context는 그 질문에 답할 때 참고할 주변 정보다.

예를 들어 다음 문장은 질문이다.

```text
과제 제출 시간은 언제인가요?
```

다음 문장은 답변에 필요한 Context다.

```text
수업 공지: 과제는 금요일 오후 6시까지 제출합니다.
```

프로그램은 Context를 다음 태그 안에 참고 데이터로 넣었다.

```xml
<reference>
수업 공지: 과제는 금요일 오후 6시까지 제출합니다.
</reference>
```

Context를 전달했다는 것은 자료가 실제 모델 입력에 포함됐다는 뜻이다. 파일이 컴퓨터에 존재하기만 하고 요청에 포함되지 않았다면 모델이 그 내용을 참고했다고 말할 수 없다.

### 구조화 프롬프트의 구성

`build_prompt_pair()`는 질문 하나를 받아 두 프롬프트를 만든다.

- `basic`: 사용자가 입력한 질문 그대로
- `structured`: 역할, 목표, 제약, 출력 형식, Context와 질문을 포함

구조화 프롬프트에는 다음 조건을 넣었다.

```text
역할: 입문자를 위한 친절한 학습 도우미
목표: 정확하고 쉬운 한국어로 설명
제약: 모르는 사실을 추측하지 않음
출력 형식: 핵심 설명, 쉬운 예시, 확인할 점
```

구조화했다고 항상 답변 내용이 정확해지는 것은 아니다. 다만 원하는 역할과 결과 형식을 모델에 더 분명하게 전달할 수 있다.

### RAG의 기본 흐름

RAG는 질문과 관련된 자료를 먼저 검색하고 그 근거를 모델에 전달해 답변을 생성하는 방식이다.

```text
Retrieval: 문서에서 관련 근거 검색
Generation: 검색 근거를 참고해 답변 생성
```

오늘은 임베딩이나 벡터 검색을 사용하지 않았다. 질문과 문서에서 정확히 같은 키워드가 나타나는지를 비교하는 단순 검색부터 시작했다.

### 출처와 검색 점수

검색 결과는 다음 정보를 가진 `Evidence` 객체로 표현했다.

```text
source   파일명
section  Markdown 구역 제목
text     검색된 원문
score    질문 키워드가 구역에 나타난 횟수
```

최신 교안에서는 검색 점수를 겹치는 고유 단어 수가 아니라, 섹션 제목과 본문 안에서 질문 키워드가 나타난 전체 횟수로 계산했다.

```python
def calculate_score(question_words, document_text):
    document_words = tokenize(document_text)
    return sum(1 for word in document_words if word in question_words)
```

점수가 높다고 답변 근거가 충분하다는 뜻은 아니다. 단지 키워드가 더 많이 등장했다는 의미다.

## 3. 코드와 실행 흐름

### prompt_compare.py

실행 흐름은 다음과 같다.

```text
질문과 Context 입력
→ strip()으로 앞뒤 공백 제거
→ 빈 질문과 길이 제한 검사
→ basic·structured PromptPair 생성
→ Preview이면 두 프롬프트만 출력
→ Live이면 기본·구조화 프롬프트를 각각 모델에 전달
```

빈 질문은 다음 조건으로 거절했다.

```python
if not question:
    raise ValueError("비어 있는 질문은 비교할 수 없습니다.")
```

질문이 1,000자를 넘거나 Context가 1,500자를 넘는 경우에도 중단하도록 했다.

### 출력 형식 검사

`validate_format()`은 응답에 세 Markdown 제목이 들어 있는지만 확인한다.

```text
## 핵심 설명
## 쉬운 예시
## 확인할 점
```

세 번째 제목을 생략한 문자열로 STEP 07을 실행한 결과는 다음과 같았다.

```text
{'핵심 설명': True, '쉬운 예시': True, '확인할 점': False}
exit=0
```

이 함수는 제목 순서, 중복, 본문 정확성이나 안전성을 검사하지 않는다. 문자열 포함 여부만 확인한다.

### document_qa.py

문서 검색 실행 흐름은 다음과 같다.

```text
read_document()
→ UTF-8 Markdown 읽기

split_sections()
→ ## 제목 기준으로 구역 분리

tokenize()
→ 비교할 키워드 목록 생성

calculate_score()
→ 섹션 제목·본문에서 키워드 출현 횟수 계산

retrieve()
→ 점수가 높은 문단을 top-k만큼 선택

build_grounded_prompt()
→ 출처와 원문을 포함한 모델용 프롬프트 생성
```

근거가 없으면 `build_grounded_prompt()`나 모델 호출로 넘어가지 않는다.

```text
문서에서 답변 근거를 찾지 못했습니다.
[retrieval=none; api_calls=0]
```

### 프롬프트 로그

교수님 설명에 따라 프롬프트 실행 기록을 JSON Lines 형식으로 남겼다. 한 줄이 실행 한 건이다.

기록 항목은 다음과 같다.

- UTC 실행 시각
- Preview 또는 Live 모드
- 사용자 질문
- 검색된 파일·섹션·원문·점수
- 최종 모델 프롬프트
- 실제 모델 전송 여부
- 성공, Preview, 근거 없음, 설정 오류 상태
- 모델명과 입력·출력·캐시 토큰
- 오류 유형

API Key와 SDK의 상세 오류 문자열은 로그에 기록하지 않았다.

## 4. 실행 및 테스트 결과

### Prompt Preview

다음 명령으로 기본·구조화 프롬프트를 비교했다.

```powershell
python prompt_compare.py "AI Agent와 챗봇의 차이는?"
```

Context를 넣은 Preview도 실행했다.

```powershell
python prompt_compare.py "과제 제출 시간은?" --context "수업 공지: 과제는 금요일 오후 6시까지 제출합니다."
```

두 실행 모두 `[PREVIEW]`가 출력됐으며 실제 모델 API는 호출하지 않았다.

### 제출 기한 검색

```powershell
python document_qa.py "과제 제출 기한은 언제인가요?"
```

`lesson04_notice.md`의 `과제 제출` 섹션에서 금요일 오후 6시라는 근거를 찾았다.

### 다른 질문 검색

```powershell
python document_qa.py "과제 관련 문의"
python document_qa.py "문의 게시판"
python document_qa.py "우주선 연료는 무엇인가요?"
```

`문의 게시판`은 문서의 `문의는`, `게시판에`와 정확히 같은 토큰이 아니어서 검색에 실패했다. 우주선 질문도 관련 키워드가 없어 근거 없음으로 끝났다. 이는 단순 키워드 검색이 조사와 동의어를 처리하지 못하는 한계다.

### top-k 비교

```powershell
python document_qa.py "과제" --top-k 2
```

최신 점수 방식에서 다음 결과를 확인했다.

```text
과제 제출: score=3
질문 응대: score=1
```

두 번째 문단이 항상 질문에 필요한 것은 아니다. `top-k`를 늘리면 모델 입력과 비용이 늘고 관련 없는 내용이 섞일 수도 있다.

### Live 실행 시도

```powershell
python document_qa.py "과제" --top-k 2 --mode live
```

검색 근거 두 개는 정상적으로 선택됐지만 `.env`에 OpenAI Key가 준비되지 않아 다음 오류로 종료됐다.

```text
설정 오류: OPENAI_API_KEY를 설정해야 합니다.
exit=2
```

로그에는 다음 상태가 기록됐다.

```text
mode: live
evidence_count: 2
prompt_saved: True
sent_to_model: False
status: configuration_error
```

따라서 실제 모델 답변, 모델 ID와 토큰 사용량은 `NOT_VERIFIED`다.

### 자동 테스트

Lesson 03 파일을 추가한 뒤에는 28개 테스트가 통과했다. Lesson 04 초기 버전에서는 42개가 통과했다. 최신 출현 횟수 점수 방식과 추가 검증을 반영한 최종 결과는 다음과 같다.

```text
Ran 44 tests in 0.369s
OK
```

## 5. 어려웠던 부분과 잘 안됐던 점

### 블로그에서 복사한 Python 코드가 깨졌다

첨부 코드에는 스마트 따옴표, 사라진 밑줄, 잘못된 들여쓰기가 섞여 있었다.

```text
“”" → """
from future → from __future__
Path(file) → Path(__file__)
if name == “main” → if __name__ == "__main__"
```

문자만 비슷해 보인다고 그대로 붙여 넣지 않고 교수님 공개 코드의 함수 구조와 Python 문법을 대조해 복원했다.

### PowerShell 파이프에서 한글이 손실될 수 있었다

Here-String을 Python에 파이프로 전달할 때 한글이 `?`로 바뀔 수 있어 다음 설정을 적용했다.

```powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
```

그 뒤 STEP 07 형식 검사가 기대 결과와 일치했고 종료 코드 0을 확인했다.

### 검색 점수 변경으로 기존 테스트가 실패했다

최신 교안은 키워드의 전체 출현 횟수를 세도록 변경됐다. 그 결과 `과제 관련 문의` 질문에서 `과제`가 여러 번 등장하는 `과제 제출` 섹션이 먼저 선택되어 이전 테스트 하나가 실패했다.

```text
AssertionError: '과제 제출' != '질문 응대'
```

코드 오류가 아니라 점수 정의가 바뀌면서 테스트의 이전 가정이 틀어진 문제였다. 질문 응대 섹션을 확인하는 테스트 질문을 `관련 문의`로 바꾸고, 반복 키워드 점수와 잘못된 `top-k` 거절 테스트를 추가했다.

### Live 결과를 확인하지 못했다

검색과 최종 프롬프트 생성은 성공했지만 `.env`가 없어 API 요청 전에 중단됐다. Preview 성공을 Live 성공이라고 기록하지 않고 설정 오류와 `sent_to_model=False`를 로그에 남겼다.

## 6. 오류의 원인과 해결 방법

오늘 오류를 확인한 순서는 다음과 같다.

```text
1. 현재 명령이 Preview인지 Live인지 확인한다.
2. 질문과 Context가 비어 있거나 길이 제한을 넘는지 확인한다.
3. Markdown 문서가 UTF-8이고 실제 경로에 있는지 확인한다.
4. 검색 결과의 source, section, score, 원문을 직접 읽는다.
5. 근거 없음과 근거 부족을 구분한다.
6. top-k를 늘렸을 때 관련 없는 문단이 섞이는지 확인한다.
7. Live라면 .env와 모델 권한을 확인하되 Key를 출력하지 않는다.
8. 프롬프트 로그에서 sent_to_model과 status를 확인한다.
9. 코드 변경 후 전체 unittest를 다시 실행한다.
```

검색 점수가 있어도 질문에 답할 충분한 근거라는 뜻은 아니다. 예를 들어 과제 제출 문단이 검색됐더라도 그 문단에 환불 규정이 없다면 환불 가능 여부를 답해서는 안 된다.

## 7. 해보고 느낀 점

Prompt와 Context를 구분하니 모델이 왜 내가 기대한 내용을 모를 수 있는지 이해하기 쉬웠다. 내가 알고 있는 정보나 로컬 파일이 자동으로 모델에게 전달되는 것이 아니며, 필요한 자료를 실제 요청에 포함해야 한다.

RAG도 처음에는 복잡한 벡터 데이터베이스 기능이라고 생각했지만, 오늘 실습에서는 “먼저 자료를 찾고 그 근거로 답한다”는 가장 작은 흐름부터 확인했다. 단순 키워드 검색이라 한계가 명확했지만, 오히려 다음 수업에서 임베딩과 의미 검색이 필요한 이유를 직접 볼 수 있었다.

프롬프트 로그를 남기는 것도 중요했다. 터미널에 답변만 보이면 어떤 질문과 근거가 실제 모델 입력으로 전달됐는지 나중에 확인하기 어렵다. 질문, 검색 근거, 최종 프롬프트, 전송 여부와 토큰을 함께 기록하면 오류와 비용을 분석하기 쉬워진다.

또한 자동 테스트가 실패했을 때 무조건 구현을 이전 방식으로 되돌리는 것이 아니라, 요구사항과 점수 정의가 바뀌었는지 먼저 확인해야 한다는 점을 배웠다.

## 8. 다음 학습 계획

1. `.env`를 안전하게 준비한 뒤 Live 호출을 한 번만 실행한다.
2. 실제 답변에 파일명과 섹션 출처가 표시되는지 확인한다.
3. 모델 ID와 입력·출력 토큰을 프롬프트 로그에서 확인한다.
4. 검색된 문단과 질문의 실제 관련성을 별도로 평가한다.
5. `top-k=1`과 `top-k=2`의 입력 토큰과 답변 차이를 비교한다.
6. 조사와 어미가 달라도 찾을 수 있도록 임베딩 검색을 학습한다.
7. 키워드 검색과 의미 검색의 결과를 같은 질문으로 비교한다.
8. Live 답변이 비거나 중단되면 성공이 아니라 `PARTIAL` 또는 `HOLD`로 기록한다.

## 오늘의 핵심 정리

1. Prompt는 요청과 지시이고 Context는 답변에 필요한 참고 정보다.
2. 구조화 프롬프트는 역할·목표·제약·출력 형식을 분명하게 전달한다.
3. Preview는 모델 응답이 아니라 실제로 보낼 프롬프트를 확인하는 기능이다.
4. `validate_format()`은 Markdown 제목의 문자열 포함 여부만 검사한다.
5. RAG는 관련 근거 검색과 그 근거를 활용한 답변 생성으로 나뉜다.
6. 오늘의 Retrieval은 임베딩이 아닌 단순 키워드 검색이다.
7. `split_sections()`는 Markdown의 `##` 제목을 기준으로 문서를 나눈다.
8. 최신 검색 점수는 섹션 제목과 본문에서 질문 키워드가 등장한 전체 횟수다.
9. 검색 점수는 근거 충분성이나 사실 정확성 점수가 아니다.
10. `top-k`를 늘린다고 항상 답변 품질이 좋아지는 것은 아니다.
11. 근거가 없으면 Live 모드여도 API를 호출하지 않고 종료한다.
12. 질문·근거·최종 프롬프트·전송 상태·토큰을 JSONL 로그로 남겼다.
13. API Key와 상세 오류 문자열은 프롬프트 로그에 기록하지 않았다.
14. Live 실행은 API Key 누락으로 중단되어 실제 모델 답변은 `NOT_VERIFIED`다.
15. 최신 코드 반영 후 전체 자동 테스트 44개가 모두 통과했다.
