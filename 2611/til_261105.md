## 1. 역할과 책임을 분리한 Backend 구조

이번 수업에서 가장 강조된 내용은 역할과 책임을 분리하는 것이었다.

```text
Client
→ Router
→ Service
→ Repository
→ SQLAlchemy Session
→ PostgreSQL
```

각 계층은 다음 책임을 가진다.

- `Router`: HTTP 요청을 받고 Status Code와 Response를 반환한다.
- `Service`: 회원 존재 여부, 이메일 중복 같은 Business Rule을 판단한다.
- `Repository`: SQLAlchemy ORM을 사용해 실제 DB CRUD를 수행한다.
- `Schema`: 요청과 응답 데이터의 형식 및 유효성을 검증한다.
- `Model`: PostgreSQL Table과 Python 객체를 연결한다.
- `DB/Session`: DB 연결과 Transaction 상태를 관리한다.

처음에는 파일이 많아져 오히려 복잡하다고 느꼈다. 하지만 중복 이메일을 `409 Conflict`로 판단하는 코드는 Service에 있고, 실제 회원을 저장하는 코드는 Repository에 있다는 식으로 문제의 위치를 빠르게 찾을 수 있었다. 한 파일이 모든 일을 하는 것보다 수정 범위가 분명했다.

## 3. Request 단위 Session 관리

`db.py`에는 Engine과 Session Factory를 구성하고, FastAPI Dependency로 사용할 `get_db()`를 작성했다.

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

`yield`를 기준으로 요청 처리 전에 Session이 생성되고, 요청이 끝나면 성공 여부와 관계없이 `finally`에서 닫힌다. Session은 단순한 DB 연결 객체가 아니라 ORM 객체의 상태와 Transaction을 함께 관리한다.

처음에는 Router 함수에서 매번 `SessionLocal()`을 직접 호출하면 된다고 생각했다. 하지만 `Depends(get_db)`를 사용하면 Session 생성과 정리 책임을 한곳에 모을 수 있고, 요청이 끝난 뒤 닫는 코드를 빠뜨릴 가능성도 줄어든다.

## 4. ORM Repository CRUD

### 전체 회원과 특정 회원 조회

전체 회원은 `select()`와 `scalars()`를 이용했다.

```python
def find_all(db: Session):
    stmt = select(Member).order_by(Member.member_id)
    return db.scalars(stmt).all()
```

특정 회원은 Primary Key 조회에 적합한 `db.get()`을 사용했다.

```python
def find_by_id(db: Session, member_id: int):
    return db.get(Member, member_id)
```

### 회원 생성

```python
def create_member(db: Session, name: str, email: str, age: int):
    member = Member(name=name, email=email, age=age)

    try:
        db.add(member)
        db.commit()
        db.refresh(member)
        return member
    except Exception:
        db.rollback()
        raise
```

각 메서드의 의미를 다음과 같이 정리했다.

```text
add()      → 새 ORM 객체를 Session의 관리 대상으로 등록
commit()   → Transaction 확정
rollback() → 실패한 Transaction 취소
refresh()  → DB가 생성한 member_id 등 최신 값을 객체에 다시 반영
```

### PUT 전체 수정

ORM에서는 UPDATE SQL 문자열을 직접 작성하는 대신 조회한 객체의 속성을 변경한다.

```python
member.name = payload.name
member.email = str(payload.email)
member.age = payload.age
db.commit()
db.refresh(member)
```

Python에서는 단순한 속성 대입처럼 보이지만 SQLAlchemy Log에서는 실제 `UPDATE`가 실행되는 것을 확인할 수 있다. ORM을 사용해도 내부에서 어떤 SQL이 실행되는지 로그로 확인해야 한다.

## 5. PATCH의 생략과 null 구분

PATCH에서는 전체 필드를 받는 PUT과 달리 실제로 전달된 필드만 수정해야 한다.

```python
changes = payload.model_dump(exclude_unset=True)
```

`exclude_unset=True`를 사용하면 Client가 생략한 필드는 결과에서 제외된다. Repository에서는 전달된 값만 순회하며 ORM 객체에 반영했다.

```python
for field, value in changes.items():
    if field == "email":
        value = str(value)
    setattr(member, field, value)
```

오늘 유지한 PATCH Contract는 다음과 같다.

```text
PATCH {"age": 31}     → 200, age만 변경
PATCH {}              → 400, 변경할 필드 없음
PATCH {"email": null} → 422, 명시적 null 금지
```

가장 헷갈렸던 부분은 필드 생략과 `null`이 둘 다 Python에서는 `None`처럼 보일 수 있다는 점이었다. `model_fields_set`을 확인하는 Validator를 추가해 Client가 값을 아예 보내지 않은 경우와 명시적으로 `null`을 보낸 경우를 구분했다.

ORM은 DB 값을 변경하는 방법을 제공하지만, 어떤 변경을 허용할지는 자동으로 결정하지 않는다. 이 의미는 HTTP Contract, Pydantic Schema, Service Rule에서 정해야 한다.

## 6. DELETE와 Transaction 실패 처리

삭제는 조회된 ORM 객체를 `db.delete()`에 전달하고 Transaction을 확정했다.

```python
def delete_member(db: Session, member: Member):
    try:
        db.delete(member)
        db.commit()
    except Exception:
        db.rollback()
        raise
```

Service에서는 먼저 회원을 조회한다. 결과가 `None`이면 Repository 삭제를 호출하지 않고 `404 Member not found`를 반환한다.

Repository의 Create, PUT, PATCH, DELETE에는 다음 공통 형태를 적용했다.

```python
try:
    ...
    db.commit()
except Exception:
    db.rollback()
    raise
```

처음에는 `rollback()` 후 오류를 처리한 것으로 생각하고 끝낼 수 있다고 생각했다. 하지만 Repository에서 다시 `raise`하지 않으면 Service가 실패 사실을 알 수 없고 성공 응답을 만들 가능성이 있다. 따라서 DB 상태는 rollback으로 되돌리고, 예외는 상위 계층이 HTTP 의미로 변환할 수 있도록 다시 전달해야 한다.

## 7. 오류를 올바른 HTTP Status로 표현하기

오류가 발생했다고 모두 `500 Internal Server Error`가 되는 것은 아니다.

| Status | 의미 | 오늘 실습 예시 |
|---|---|---|
| 400 | 요청의 의미가 부적절함 | 빈 PATCH `{}` |
| 404 | 요청한 자원이 없음 | 존재하지 않는 회원 |
| 409 | 현재 데이터 상태와 충돌 | 중복 이메일 |
| 422 | 입력 Schema 검증 실패 | 잘못된 email, age, explicit null |
| 500 | 예상하지 못한 서버 오류 | 처리하지 못한 DB/코드 오류 |

중복 이메일은 먼저 조회하여 확인하지만, 동시에 같은 이메일이 저장되는 상황에서는 DB의 `UNIQUE` Constraint가 최종 방어선이 된다. Repository의 `IntegrityError`를 Service에서 `409 Conflict`로 변환했다.

```python
try:
    return member_repository.create_member(...)
except IntegrityError as error:
    raise HTTPException(
        status_code=409,
        detail="Email already exists",
    ) from error
```

Database는 데이터 무결성을 지키고, Service는 내부 오류를 Client가 이해할 수 있는 HTTP 의미로 번역한다.

## 8. Swagger 수동 검증

FastAPI 서버를 8080 포트에서 실행하고 Swagger를 확인했다.

```powershell
python -m uvicorn app.main:app --port 8080
```

Swagger에는 다음 API가 표시되었다.

```text
GET    /members
POST   /members
GET    /members/{member_id}
PUT    /members/{member_id}
PATCH  /members/{member_id}
```

처음 `--reload` 옵션으로 실행했을 때 자동 재시작 Process에서 오류가 발생했다. 코드 자체의 문제라기보다 실행 환경에서 Reload Process가 충돌한 것이었고, `--reload`를 제외해 서버가 정상적으로 실행되는 것을 확인했다. 실행 오류가 보이면 코드 오류와 실행 도구 문제를 구분해야 한다는 점을 배웠다.

```python
def test_get_members_returns_200():
```

## 어려웠던 부분과 해결 방법

### 1. 최종 폴더 구조와 현재 수업 단계를 혼동했다

교안에는 최종적으로 Repository, Service, Router, Tests가 모두 있는 구조가 제시되었다. 처음에는 이 구조를 한 번에 만들었지만 교수님 화면에는 현재 단계에서 필요한 파일만 있어서 진도를 비교하기 어려웠다.

해결 방법:

- 최종 목표 구조와 현재 STEP의 완료 구조를 따로 확인했다.
- Chapter 12 원본은 수정하지 않았다.
- Chapter 13에는 기본 파일, Repository, Service, Router 순서로 복사했다.
- 교수님이 안내하기 전에는 다음 단계의 테스트 코드를 미리 작성하지 않았다.

### 2. Repository와 Service의 책임이 헷갈렸다

중복 이메일을 어디에서 처리해야 하는지 처음에는 명확하지 않았다.

해결 방법:

```text
Repository → 같은 이메일이 있는지 조회
Service    → 중복이면 409라고 판단
Database   → UNIQUE Constraint로 최종 무결성 보장
```

조회와 저장 방법은 Repository의 책임이고, 그 결과가 어떤 업무 의미인지 판단하는 것은 Service의 책임으로 구분했다.

### 3. PATCH의 생략과 null이 구분되지 않았다

Optional Field를 사용하면 생략과 `null`이 모두 `None`처럼 보여 Contract를 그대로 구현하기 어려웠다.

해결 방법:

- `model_dump(exclude_unset=True)`로 전달된 필드만 추출했다.
- `model_fields_set`으로 명시적으로 전달된 필드를 확인했다.
- 전달된 값이 `None`이면 Validation Error를 발생시켜 422로 처리했다.

### 4. SQLAlchemy의 ROLLBACK 로그가 계속 보였다

GET 테스트 후에도 `ROLLBACK`이 출력되어 테스트가 실패한 것으로 오해할 수 있었다.

해결 방법:

- 조회 Session도 암시적으로 Transaction을 시작한다는 점을 다시 확인했다.
- 변경 없이 Session이 닫힐 때의 ROLLBACK은 정상적인 정리 동작이다.
- 실제 pytest 결과와 HTTP Status를 함께 확인했다.

### 5. POST 테스트가 실제 DB를 변경했다

`TestClient`라는 이름 때문에 가짜 DB에서만 동작할 것으로 생각했지만, 현재 Application의 `get_db()`를 그대로 사용하므로 실제 학습용 PostgreSQL에 Test User가 추가되었다.

해결 방향:

- 오늘은 `uuid4()`를 사용해 재실행 시 이메일 중복을 피했다.
- 이후에는 `.env.test`, 테스트 전용 Database 또는 Schema를 분리해야 한다.
- 테스트 종료 후 데이터 삭제나 Transaction Rollback 전략도 필요하다.
- 운영 DB를 자동 테스트 대상으로 직접 사용하지 않아야 한다.

## 해보고 느낀 점

오늘은 ORM 문법 자체보다 계층별 책임과 실패 처리의 중요성을 더 크게 느꼈다. Router에서 직접 DB를 조회하면 처음에는 코드가 짧아 보이지만, 이메일 중복 처리나 Transaction Rollback 같은 규칙이 추가되면 한 파일이 금방 복잡해진다. Router, Service, Repository를 나누니 각 코드가 왜 존재하는지 설명하기 쉬웠다.

또한 `commit()`만 중요하다고 생각했지만 실패했을 때 `rollback()`하고 예외를 다시 전달하는 과정이 똑같이 중요했다. 실패한 Session을 그대로 두면 다음 DB 작업에도 문제가 이어질 수 있고, 예외를 숨기면 Client는 잘못된 성공 응답을 받을 수 있다.

자동 테스트는 Swagger를 대체하는 것이 아니라 서로 다른 역할을 한다는 점도 이해했다. Swagger는 요청과 응답을 직접 보면서 흐름을 이해하기 좋고, pytest는 같은 Contract를 짧은 시간에 반복 검증하기 좋았다. 오늘 `3 passed`를 확인하면서 테스트 PASS는 무조건 200을 의미하는 것이 아니라 404처럼 예상한 실패도 계약대로 동작하면 PASS가 된다는 점이 인상적이었다.

다만 현재 POST 테스트가 실제 학습 DB에 Row를 남긴다는 점은 주의해야 한다. 테스트가 반복 가능하려면 고유한 입력값만 만드는 것으로 충분하지 않고, 테스트 환경과 데이터 정리 전략까지 함께 설계해야 한다.

## 오늘의 핵심 정리

```text
Router     → HTTP Request / Response
Service    → Business Rule / HTTP Error Contract
Repository → ORM CRUD
Session    → ORM Object State + Transaction

INSERT → Member(...) + add() + commit()
SELECT → select() / get()
UPDATE → ORM 객체 속성 변경 + commit()
DELETE → delete() + commit()
실패   → rollback() + raise

Swagger    → 수동 Evidence
SQL Log    → ORM이 실행한 SQL Evidence
PostgreSQL → 실제 Row Evidence
pytest     → 자동 Regression Evidence
```

한 번 성공한 기능이 계속 정상이라는 보장은 없다. API Contract를 코드로 테스트하고, 변경 후 반복 실행하는 습관이 필요하다.
