## 2. 핵심 개념과 실습 내용

### 벡터 데이터베이스를 사용하는 이유

지난 시간에는 문장을 벡터로 변환하고 코사인 유사도를 Python에서 계산했다. 문서 벡터를 실행할 때마다 다시 만들면 API 호출과 시간이 반복해서 필요하다. 이번 수업에서는 한 번 만든 문서 벡터를 PostgreSQL에 저장하고 새로운 질문이 들어왔을 때 저장된 벡터와 비교하는 흐름을 배웠다.

```text
문서 등록: 문서 → 임베딩 생성 → PostgreSQL에 저장
질문 검색: 질문 → 질문 임베딩 생성 → 저장된 문서 벡터와 거리 비교
```

문서 내용이 바뀌지 않았다면 저장된 문서 임베딩을 재사용할 수 있다. 반면 새로운 자연어 질문은 검색할 때 질문 임베딩을 새로 만들어야 한다.

### pgvector

pgvector는 별도의 PostgreSQL 제품이 아니라 PostgreSQL에 벡터 자료형과 거리 연산을 추가하는 확장이다. 일반 업무 데이터와 벡터를 같은 테이블에서 다룰 수 있고 SQL, JOIN, 트랜잭션을 함께 사용할 수 있다.

```sql
embedding vector(3)
```

위 선언은 세 개의 숫자를 가진 벡터 열을 의미한다. 실제 `text-embedding-3-small`의 기본 출력은 1536차원이므로 교육용 `vector(3)` 테이블과 실제 임베딩용 `vector(1536)` 테이블을 섞으면 안 된다.

### 코사인 유사도와 코사인 거리

Python 실습의 코사인 유사도는 값이 클수록 가깝다. pgvector의 `<=>` 연산자는 코사인 거리를 반환하며 값이 작을수록 가깝다.

```text
코사인 거리 = 1 - 코사인 유사도
같은 방향: 거리 0
직각 방향: 거리 1
반대 방향: 거리 2
```

검색 거리는 정답 확률이나 신뢰도가 아니다. 가장 가까운 문단이 반환됐더라도 원문에 질문의 답이 실제로 있는지 별도로 확인해야 한다.

### Fixture와 Live 분리

Fixture는 개념 확인을 위해 사람이 정한 3차원 벡터를 사용하고 API 호출이 없다. Live는 OpenAI 임베딩 모델이 만든 1536차원 벡터를 사용하며 API 호출과 비용이 발생할 수 있다.

| 모드 | 차원 | API 호출 | 목적 |
|---|---:|---:|---|
| Fixture | 3 | 없음 | 저장·검색 원리 확인 |
| Live | 1536 | 있음 | 실제 의미 임베딩 검색 |

## 3. 코드와 실행 흐름

### 설치 전 확인 SQL

DBeaver에서 먼저 현재 데이터베이스와 pgvector 설치 여부를 확인한다.

```sql
SELECT current_database(), version();

SELECT name, default_version, installed_version
FROM pg_available_extensions
WHERE name = 'vector';

SELECT extname, extversion
FROM pg_extension
WHERE extname = 'vector';
```

판단 기준은 다음과 같다.

```text
pg_extension에 vector가 있음
→ 현재 DB에서 활성화 완료

pg_available_extensions에만 vector가 있음
→ 서버 파일은 있으므로 CREATE EXTENSION 필요

pg_available_extensions 결과도 없음
→ PostgreSQL 설치 경로에 pgvector 확장 파일 설치 필요
```

내 PC에서는 `pg_available_extensions` 조회 결과가 0행이었다. 따라서 `CREATE EXTENSION vector`만 실행할 수 있는 상태가 아니라 Windows용 pgvector 빌드가 먼저 필요하다.

### 수업에서 진행한 Fixture SQL 흐름

수업에서는 확장 설치 후 다음과 같은 흐름으로 3차원 벡터를 확인했다.

```text
CREATE EXTENSION vector
→ vector(3) 임시 또는 Fixture 테이블 생성
→ [1,0,0], [0,1,0], [0,0,1] 저장
→ count(*)로 3건 확인
→ <=> 연산자로 거리 오름차순 검색
```

중복 저장은 `ON CONFLICT (id) DO UPDATE`로 처리한다. 같은 ID를 다시 저장해도 행이 계속 늘어나지 않고 기존 행이 갱신된다.

### lesson06_pgvector.py의 실행 구조

교수님은 프로젝트 루트에 `lesson06_pgvector.py`를 만들고 다음 명령 구조를 사용했다.

```text
check       DB 연결과 pgvector 버전 확인
index       Fixture 3건 저장
count       Fixture·Live 테이블의 행 수 확인
query       정해진 Fixture 질문 검색
live-index  실제 문서 임베딩 생성 및 저장
live-query  새로운 질문 임베딩 생성 및 검색
```

DB 연결 확인 명령은 다음과 같다.

```powershell
python lesson06_pgvector.py check
```

내 PC에서는 pgvector 확장이 준비되지 않아 이 명령의 정상 성공 결과를 확인하지 못했다.

## 4. 실행 및 테스트 결과

### 임베딩 검색 복습

`embedding_search.py`의 Fixture 검색에서 질문과 일치하는 단어가 없을 때 `일치 단어 없음`이 출력되는 것을 확인했다. Live 모드는 OpenAI 임베딩 API를 사용하는 선택 실습이며, Fixture 결과와 실제 임베딩 결과를 같은 것으로 해석하면 안 된다.

### PostgreSQL 버전 확인

실제 로컬 설치 경로의 `pg_config.exe`를 실행해 다음 버전을 확인했다.

```text
PostgreSQL 18.4
```

기본 설치 경로는 다음과 일치했다.

```text
C:\Program Files\PostgreSQL\18
```

### pgvector 설치 여부

DBeaver에서 다음 쿼리를 실행했다.

```sql
SELECT name, default_version, installed_version
FROM pg_available_extensions
WHERE name = 'vector';
```

결과 그리드에는 열 이름만 표시되고 데이터는 없었다.

```text
결과: 0행
판정: pgvector 확장 파일 없음
```

따라서 확장 활성화, `vector(3)` 임시 테이블, Fixture 3건 저장과 거리 검색은 내 PC에서 아직 실행하지 않았다.

### Visual Studio Build Tools 확인

Visual Studio Build Tools 2022 설치 관리자에서 버전 `17.14.45`가 표시되는 것은 확인했다. 그러나 C++ 빌드 환경의 핵심 파일을 확인한 결과는 다음과 같았다.

```text
VCVARS64_NOT_FOUND
```

확인 대상 경로는 다음과 같다.

```text
C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat
```

따라서 현재 확인된 상태는 Build Tools 관리자는 설치됐지만 `C++를 사용한 데스크톱 개발` 워크로드 설치가 완료됐다고 검증할 수 없는 상태다.

### 오늘 결과 표

| 항목 | 실제 관찰 결과 | 상태 |
|---|---|---|
| PostgreSQL | 18.4 확인 | PASS |
| DBeaver 로컬 연결 | `localhost:5432` 연결 확인 | PASS |

| Live 임베딩 저장·검색 | 실행하지 않음 | NOT_RUN |

## 5. 어려웠던 부분과 잘 안됐던 점

### Visual Studio와 VS Code를 혼동하기 쉬웠다

pgvector Windows 빌드에 필요한 것은 평소 코드를 작성하는 VS Code가 아니라 Visual Studio 2022의 C++ 빌드 도구다. 이름이 비슷하지만 역할이 다르다.

### 설치 관리자에서 필요한 워크로드를 정확히 골라야 했다

Visual Studio Installer가 설치됐다고 C++ 컴파일러까지 자동으로 설치되는 것은 아니었다. 처음에는 약 132MB의 MSBuild 도구만 선택된 상태였고, 이 상태에서는 `vcvars64.bat`과 `nmake`를 사용할 수 없다.

### 교수님 진도와 내 PC 상태가 달랐다

교수님은 pgvector 활성화, Fixture 저장·검색과 Python 파일 생성까지 진행했지만 내 PC에서는 선행 설치가 끝나지 않았다. 화면을 따라 코드만 먼저 실행하면 `extension "vector" is not available` 같은 오류가 발생할 수 있으므로, 실제 상태를 구분해야 했다.

### 실행하지 않은 결과를 성공으로 적을 수 없었다

수업 화면에서 `count=3`과 거리 검색을 확인했더라도 내 PC에서 같은 쿼리를 실행한 것은 아니다. 오늘 TIL에서는 교수님의 예시와 내 실행 결과를 분리하고 미실행 항목을 `NOT_RUN` 또는 `HOLD`로 남겼다.

## 6. 오류의 원인과 해결 방법

### `vector` 조회 결과가 0행인 경우

원인은 현재 연결된 PostgreSQL 18 설치 폴더에 pgvector 확장 라이브러리와 SQL 파일이 없기 때문이다. 이 상태에서는 다음 SQL을 먼저 실행해도 해결되지 않는다.

```sql
CREATE EXTENSION vector;
```

Windows 네이티브 설치를 완료한 후 다시 실행해야 한다.

### C++ 빌드 환경 확인 실패

```text
VCVARS64_NOT_FOUND
```

가능한 원인은 Visual Studio Installer에서 `MSBuild 도구`만 설치하고 `C++를 사용한 데스크톱 개발`을 선택하지 않은 것이다.

다음에 같은 문제가 발생하면 아래 순서로 확인한다.

```text
1. Visual Studio Installer에서 Build Tools 2022의 수정 화면을 연다.
2. C++를 사용한 데스크톱 개발 워크로드가 선택됐는지 확인한다.
3. MSVC x64/x86 빌드 도구와 Windows SDK가 설치 대상인지 확인한다.
4. 설치 완료 후 vcvars64.bat 경로를 다시 확인한다.
5. x64 Native Tools Command Prompt에서 where nmake를 실행한다.
6. pg_config --version과 DBeaver가 연결한 서버 버전이 같은지 확인한다.
7. 그 뒤에만 pgvector를 빌드하고 설치한다.
```

설치 명령이 실패하면 오류를 무시하고 다음 단계로 진행하지 않고 PostgreSQL 버전, `PGROOT`, `where nmake` 결과와 오류 메시지를 함께 기록한다.

## 7. 해보고 느낀 점

벡터 검색은 AI 모델만의 기능이 아니라 저장소, 자료형, 거리 연산과 연결된다는 점이 흥미로웠다. 임베딩을 매번 새로 만드는 대신 데이터베이스에 저장해 재사용하면 비용과 시간을 줄일 수 있다는 흐름이 이해됐다.

이번 실습에서는 코드보다 환경 확인이 더 중요했다. 설치 관리자가 보인다는 이유만으로 필요한 컴파일러가 설치됐다고 판단할 수 없었고, `vcvars64.bat`, `nmake`, `pg_config`처럼 실제 파일과 명령 결과를 확인해야 했다.

수업 진도를 빨리 따라가고 싶었지만 선행 조건이 실패한 상태에서 SQL과 Python을 실행하면 오류가 연속해서 발생한다. 빠르게 진행하는 것과 확인 없이 건너뛰는 것은 다르다는 점을 느꼈다.

## 오늘의 핵심 정리

1. 임베딩은 문장이나 문서를 숫자 벡터로 표현한다.
2. 변하지 않은 문서 벡터는 DB에 저장해 재사용할 수 있다.
3. pgvector는 PostgreSQL에 벡터 자료형과 거리 연산을 추가하는 확장이다.
4. 코사인 유사도는 클수록 가깝고 코사인 거리는 작을수록 가깝다.
5. pgvector의 `<=>`는 코사인 거리를 계산한다.
6. Fixture 3차원 벡터와 실제 1536차원 임베딩은 분리해야 한다.
7. `ON CONFLICT DO UPDATE`는 같은 ID의 중복 행 생성을 막는다.
8. Top-K 결과가 있다는 사실만으로 답변 근거가 충분한 것은 아니다.
9. `pg_available_extensions` 결과가 0행이면 확장 파일 설치가 먼저 필요하다.
10. 내 PC의 PostgreSQL 버전은 18.4로 확인됐다.
