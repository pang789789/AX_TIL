# 2026-11-04 TIL — SQLAlchemy ORM 기초와 PostgreSQL 회원 조회

## 오늘 학습한 내용

오늘은 기존에 psycopg와 SQL로 직접 처리했던 PostgreSQL 조회 작업을 SQLAlchemy ORM 방식으로 다시 구현했다. 오전에는 이전 실습에서 생성된 테이블이 너무 많아 수업에 필요한 구조를 구분하기 어려웠기 때문에 `public` 스키마를 초기화하고, 수업에서 사용할 `members` 테이블과 Seed 데이터를 새로 준비했다. 이후 PostgreSQL의 테이블을 Python의 `Member` 클래스로 매핑하고, `Session`을 이용해 전체 회원, 특정 회원, 존재하지 않는 회원을 조회했다.

오늘 수업에서 가장 중요하게 느낀 점은 ORM이 SQL을 없애는 기술이 아니라는 것이다. Python 코드에서는 `select(Member)`를 사용하지만, `echo=True`로 출력되는 로그를 확인하면 실제 PostgreSQL에는 여전히 `SELECT ... FROM members` SQL이 전달된다.

오늘 실습 흐름은 다음과 같았다.

```text
PostgreSQL public 스키마 정리
→ members 테이블 생성
→ Seed 데이터 5건 입력
→ SQLAlchemy 설치
→ Engine / Session / Base 구성
→ Member ORM Model 정의
→ 전체 회원 조회
→ 특정 회원 조회
→ 없는 회원 조회 및 None 처리
```

## 1. PostgreSQL 실습 환경 초기화

DBeaver에서 `public → Tables`를 펼쳤을 때 이전 Django 실습에서 자동 생성된 테이블이 많이 남아 있었다. 처음에는 `Foreign Tables`, `Views`, `Functions` 같은 항목도 삭제해야 하는 데이터로 생각했지만, 이 항목들은 실제 테이블이 아니라 PostgreSQL 객체를 종류별로 보여 주는 폴더였다.

실제로 정리해야 할 대상은 `account_*`, `auth_*`, `django_*`처럼 `Tables` 아래에 표시되는 기존 테이블들이었다. 오늘 수업에서는 기존 데이터를 사용하지 않고 처음부터 진행하기 때문에 `public` 스키마를 초기화했다.

```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
```

이 명령은 `public` 안의 테이블과 관련 객체를 모두 삭제하므로 실행 전에 대상 스키마가 정확히 `public`인지 확인하는 것이 중요했다. `practice` 스키마는 별개의 공간이므로 건드리지 않았다.

초기화 후에는 다음 구조로 `members` 테이블을 만들었다.

```sql
CREATE TABLE public.members (
    member_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    age INTEGER NOT NULL
);
```

`member_id`는 `SERIAL PRIMARY KEY`이므로 INSERT할 때 직접 값을 입력하지 않아도 PostgreSQL이 순서대로 생성한다.

## 2. Seed 데이터 준비

ORM 조회 결과를 확인하기 위해 회원 5명을 입력했다.

```sql
INSERT INTO public.members (name, email, age)
VALUES
    ('Kim', 'kim@example.com', 30),
    ('Lee', 'lee@example.com', 25),
    ('Park', 'park@example.com', 35),
    ('Choi', 'choi@example.com', 28),
    ('Jung', 'jung@example.com', 40);
```

DBeaver에서 다음 쿼리를 실행해 5건이 정상적으로 저장된 것을 확인했다.

```sql
SELECT *
FROM members
ORDER BY member_id;
```

처음 ORM 코드를 실행했을 때 SQL 오류는 없었지만 회원 정보가 한 줄도 출력되지 않았다. 코드가 잘못된 것으로 생각했지만 원인은 테이블에 Seed 데이터를 입력하지 않은 것이었다. 이 경험을 통해 프로그램의 출력이 비어 있을 때는 코드뿐 아니라 실제 DB Row가 존재하는지도 먼저 확인해야 한다는 것을 배웠다.

## 5. Engine, SessionLocal, Base 구성

`db.py`에서는 `.env`의 DB 접속 정보를 읽어 SQLAlchemy Engine과 Session을 구성했다.

```python
import os

from dotenv import load_dotenv
from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, sessionmaker


load_dotenv()

DATABASE_URL = (
    f"postgresql+psycopg://{os.getenv('DB_USER')}:{os.getenv('DB_PASSWORD')}"
    f"@{os.getenv('DB_HOST')}:{os.getenv('DB_PORT')}/{os.getenv('DB_NAME')}"
)

engine = create_engine(DATABASE_URL, echo=True)

SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    autocommit=False,
)


class Base(DeclarativeBase):
    pass
```

각 객체의 역할은 다음과 같이 이해했다.

- `Engine`: Python과 PostgreSQL 사이의 연결 설정과 연결 풀을 관리한다.
- `SessionLocal`: 실제 ORM 작업에 사용할 Session을 만드는 Factory이다.
- `Base`: ORM Model 클래스가 공통으로 상속하는 부모 클래스이다.
- `echo=True`: ORM 코드가 생성한 실제 SQL을 터미널에 출력한다.

기존 psycopg 방식에서는 Connection과 Cursor를 직접 열고 닫았지만, ORM에서는 Session이 조회된 객체와 Transaction 상태를 함께 관리한다.

## 6. 실제 테이블과 Member Model 매핑

`models.py`에는 실제 PostgreSQL `members` 테이블과 일치하는 ORM Model을 작성했다.

```python
from sqlalchemy import Integer, String
from sqlalchemy.orm import Mapped, mapped_column

from .db import Base


class Member(Base):
    __tablename__ = "members"

    member_id: Mapped[int] = mapped_column(
        Integer, primary_key=True
    )
    name: Mapped[str] = mapped_column(
        String(100), nullable=False
    )
    email: Mapped[str] = mapped_column(
        String(255), nullable=False, unique=True
    )
    age: Mapped[int] = mapped_column(
        Integer, nullable=False
    )
```

Model을 작성할 때 단순히 Python 코드가 실행되는지만 확인하면 안 된다. 실제 DB와 다음 항목이 모두 일치해야 한다.

- 테이블 이름: `members`
- 기본키 컬럼: `member_id`
- 문자열 길이: `VARCHAR(100)`, `VARCHAR(255)`
- `NOT NULL` 여부
- 이메일의 `UNIQUE` 제약
- 정수와 문자열 Type

AI가 습관적으로 기본키 이름을 `id`로 작성할 수 있지만, 오늘 만든 실제 테이블의 기본키는 `member_id`이다. ORM Model은 새로운 구조를 상상해서 만드는 것이 아니라 기존 DB Schema를 정확히 표현하는 코드라는 점을 알게 되었다.

또한 SQLAlchemy Model과 Pydantic Schema의 차이도 다시 정리했다.

```text
SQLAlchemy Model = DB Table 구조와 Row를 표현
Pydantic Schema  = API Request/Response 데이터 계약을 표현
```

## 7. 전체 회원 ORM 조회

전체 회원은 다음 코드로 조회했다.

```python
from sqlalchemy import select

from app.db import SessionLocal
from app.models import Member


with SessionLocal() as session:
    stmt = select(Member).order_by(Member.member_id)
    members = session.scalars(stmt).all()

    for member in members:
        print(
            member.member_id,
            member.name,
            member.email,
            member.age,
        )
```

실행 결과는 다음과 같았다.

```text
1 Kim kim@example.com 30
2 Lee lee@example.com 25
3 Park park@example.com 35
4 Choi choi@example.com 28
5 Jung jung@example.com 40
```

`session.scalars(stmt).all()`의 결과는 튜플이나 딕셔너리가 아니라 `Member` 객체 5개가 들어 있는 리스트이다. 따라서 각 값에 `member.name`, `member.email`처럼 속성으로 접근할 수 있었다.

```text
select(Member)         → Member 전체 조회문 준비
session.scalars(stmt)  → 각 Row를 Member 객체로 변환
.all()                 → 모든 Member 객체를 리스트로 반환
```

## 8. 특정 회원 ORM 조회

한 명만 조회할 때는 `session.scalar()`를 사용했다.

```python
with SessionLocal() as session:
    stmt = select(Member).where(Member.member_id == 1)
    member = session.scalar(stmt)

    if member is not None:
        print("회원 ID:", member.member_id)
        print("이름:", member.name)
        print("이메일:", member.email)
        print("나이:", member.age)
    else:
        print("해당 회원이 존재하지 않습니다.")
```

실행 결과는 다음과 같았다.

```text
회원 ID: 1
이름: Kim
이메일: kim@example.com
나이: 30
```

이때 DBeaver에서 직접 실행한 SQL 결과와 ORM 객체의 값이 같은지도 비교했다.

```sql
SELECT member_id, name, email, age
FROM members
WHERE member_id = 1;
```

Raw SQL 결과와 ORM 객체의 값이 모두 일치했기 때문에 Model 매핑과 조회가 정상이라는 것을 확인할 수 있었다.

## 9. 존재하지 않는 회원과 None 처리

존재하지 않는 ID를 조회하도록 값을 `99999999`로 바꿨다.

```python
stmt = select(Member).where(Member.member_id == 99999999)
member = session.scalar(stmt)

if member is not None:
    print("회원이 존재합니다.")
else:
    print("해당 회원이 존재하지 않습니다.")
```

실행 결과는 다음과 같았다.

```text
해당 회원이 존재하지 않습니다.
```

처음에는 결과가 `None`이면 오류가 발생한 것으로 생각하기 쉬웠다. 하지만 `session.scalar()`는 조건에 맞는 Row가 없으면 정상적으로 `None`을 반환한다. 따라서 조회 후에는 `if member is None` 또는 `if member is not None` 검사가 필요하다.

FastAPI와 연결할 때는 이 `None`을 다음과 같이 HTTP 의미로 변환할 수 있다.

```python
if member is None:
    raise HTTPException(
        status_code=404,
        detail="Member not found",
    )
```

즉 Repository 또는 ORM의 `None` 결과를 API 계층에서 `404 Not Found`로 바꾸는 흐름을 이해할 수 있었다.

## 어려웠던 부분과 해결 방법

### 1. DBeaver에 테이블이 너무 많이 보여 혼란스러웠다

이전 Django 실습 테이블과 PostgreSQL 객체 폴더가 한꺼번에 보여 오늘 사용할 `members`를 찾기 어려웠다.

해결 방법:

- 실제 테이블과 객체 종류 폴더를 구분했다.
- 오늘 사용하지 않는 `public` 스키마의 기존 테이블을 초기화했다.
- `practice` 스키마는 별개이므로 삭제하지 않았다.
- 새로고침 후 `Tables → members` 하나만 존재하는지 확인했다.

### 2. ORM 코드는 정상인데 회원이 출력되지 않았다

SQL 로그에는 오류가 없었지만 출력 결과가 비어 있었다. 처음에는 `select(Member)`나 Session 사용법이 잘못된 것으로 생각했다.

원인:

- 새로 만든 `members` 테이블에 Seed 데이터가 없었다.

해결 방법:

- DBeaver에서 `SELECT * FROM members`를 실행해 실제 Row 수를 확인했다.
- Seed 데이터 5건을 입력했다.
- ORM 코드를 다시 실행해 같은 5명이 출력되는 것을 확인했다.

### 3. `scalar()`와 `scalars()`가 헷갈렸다

이름이 비슷해서 둘의 반환 결과를 구분하기 어려웠다.

해결 방법:

```text
session.scalar(stmt)
→ 첫 번째 컬럼 또는 ORM 객체 하나를 반환
→ 결과가 없으면 None

session.scalars(stmt).all()
→ ORM 객체들을 ScalarResult로 받은 뒤
→ .all()로 전체 목록 반환
```

조회 목적이 한 명인지 여러 명인지 먼저 정한 후 메서드를 선택하는 것이 이해하기 쉬웠다.

### 4. SQLAlchemy 로그의 ROLLBACK이 오류처럼 보였다

단순 SELECT 후에도 마지막에 `ROLLBACK`이 출력되어 조회가 실패한 것으로 오해할 수 있었다.

해결 방법:

- Session이 암시적으로 Transaction을 시작한다는 것을 확인했다.
- 조회만 하고 변경사항을 commit하지 않은 상태에서 Session이 닫히면 정상적으로 rollback 정리가 수행된다.
- SELECT 결과가 정상 출력되었다면 마지막 `ROLLBACK`은 오류가 아니라 Session 종료 과정이다.

### 5. `.env` 위치가 중복되어 헷갈릴 수 있었다

처음에는 각 Chapter 안에 `.env`를 두려고 했지만 수업에서는 `phase02/.env`를 공용으로 사용했다.

해결 방법:

- 공용 `.env` 하나만 유지했다.
- `.gitignore`에서 `.env`와 `.env.*`를 제외했다.
- 실제 비밀번호를 코드에 직접 작성하지 않고 환경변수로 읽었다.

## 해보고 느낀 점

psycopg로 SQL을 직접 실행할 때는 Connection, Cursor, SQL 문자열, `fetchone()`이나 `fetchall()`을 각각 관리해야 했다. SQLAlchemy ORM에서는 `select(Member)`와 Session을 사용해 같은 작업을 Python 객체 중심으로 표현할 수 있어서 코드의 의도가 더 잘 보였다.

하지만 ORM이 더 편해 보인다고 해서 DB 구조를 몰라도 되는 것은 아니었다. `member_id`, 문자열 길이, `nullable`, `unique` 중 하나라도 실제 테이블과 다르면 Model이 잘못된다. DBeaver의 실제 테이블 구조, SQLAlchemy Model, 터미널의 SQL 로그를 함께 비교하는 습관이 필요하다고 느꼈다.

특히 오늘은 결과가 나오지 않을 때 코드만 계속 수정하지 않고 실제 DB 데이터가 존재하는지 확인하는 과정이 중요했다. ORM 코드, 생성된 SQL, PostgreSQL Row를 함께 검증해야 문제의 위치를 빠르게 찾을 수 있었다.

또한 `None`이 단순 오류가 아니라 “조건에 맞는 데이터가 없음”을 표현하는 정상적인 결과라는 점을 이해했다. 이후 FastAPI와 연결하면 이 결과를 `404 Not Found`로 변환하는 방식으로 DB의 결과와 HTTP 응답을 연결할 수 있을 것 같다.

## 오늘의 핵심 정리

```text
PostgreSQL Table  ↔ SQLAlchemy Model Class
PostgreSQL Row    ↔ Python ORM Object
SELECT            ↔ select()
Connection/Cursor ↔ Engine/Session
전체 객체 조회     ↔ session.scalars(stmt).all()
단일 객체 조회     ↔ session.scalar(stmt)
조회 결과 없음     ↔ None
API에서 결과 없음  ↔ 404 Not Found
```

ORM을 사용하더라도 실제 SQL과 Database Schema를 계속 확인해야 한다. 오늘 실습의 핵심은 문법을 외우는 것이 아니라 `Table → Model`, `Row → Object`, `SELECT → select()`의 대응관계를 이해하는 것이었다.
