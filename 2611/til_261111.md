## 1. 프로젝트 목표와 전체 구조

AX2 Classroom Jukebox는 강의실 입실 시간에 맞춰 음악을 자동으로 재생하는 시스템이다.

주요 사용자는 학생과 관리자다.

- 학생은 YouTube URL을 이용해 곡을 신청한다.
- 관리자는 신청곡을 승인하거나 반려한다.
- 승인된 곡은 재생 권한이 확인된 음원 파일을 등록한다.
- 재생 가능한 곡으로 플레이리스트를 구성한다.
- 스케줄에 따라 Ubuntu 서버와 MPD가 실제 음악을 재생한다.

기술 구성은 다음과 같다.

```text
학생·관리자 브라우저
        ↓
FastAPI Web/API
        ↓
PostgreSQL
        ↓
APScheduler / Player Controller
        ↓
MPD
        ↓
Ubuntu 오디오 출력과 강의실 앰프
```

개발 환경에서는 실제 장비 없이도 기능을 검증할 수 있도록 FakePlayer를 사용하고, 실제 Ubuntu 서버에서는 MPD로 전환할 수 있게 구성했다.

## 3. Redmine 중심 작업 절차

튜터님의 안내를 통해 각 일감을 다음 순서로 진행해야 한다는 것을 배웠다.

1. 작업계획을 Redmine에 작성하고 진척도 10%로 설정한다.
2. 작업계획 컨펌을 요청한다.
3. 컨펌된 범위만 개발한다.
4. 진행 중 궁금한 사항은 질문한다.
5. 개발 완료 후 진척도를 90%로 조정한다.
6. PR을 작성해 전체 검수를 요청한다.
7. 별도 승인 담당자가 검토하고 병합한다.
8. 병합을 확인한 뒤 Redmine을 100%, Closed로 처리한다.

여기에서 중요한 점은 **개발 완료와 일감 완료가 다르다**는 것이다.

- 코드 작성 완료: 개발은 끝났지만 아직 90%
- PR 검토 및 병합 완료: 최종 완료 처리 가능
- Redmine 100%와 Closed: 모든 절차가 끝난 상태

따라서 개발자가 임의로 PR을 병합하거나, 승인 전에 다음 단계 구현을 시작하면 정해진 작업 흐름을 건너뛰게 된다.

## 4. STEP 02 관리자 운영 대시보드

처음에는 STEP 02를 “플레이어 자체를 만드는 작업”으로 이해할 수 있었지만, 피드백을 통해 범위를 다시 정리했다.

STEP 02의 목적은 플레이어 엔진을 새로 만드는 것이 아니라 **관리자가 기존 기능을 확인하고 조작할 수 있는 운영 페이지를 만드는 것**이다.

관리자 화면에는 다음 영역을 구성했다.

- 재생 현황 및 제어
- 신청곡 승인
- 플레이리스트 편성
- 자동 재생 스케줄
- 로그아웃
- 상태 새로고침
- 오류 안내

상단 메뉴를 누르면 각 영역으로 이동할 수 있도록 구성하고, 좁은 화면에서는 메뉴를 가로로 스크롤할 수 있게 만들었다.

또한 다음과 같은 불필요하거나 오해하기 쉬운 표시를 제거했다.

- `Demo Player Online`
- 마지막 확인 시각
- 교수님의 피드백이라는 직접적인 표현
- 일반 사용자에게 필요하지 않은 기술 설명

관리 화면은 시스템 내부 용어를 보여주기보다 **관리자가 실제로 해야 할 행동을 이해할 수 있게 만드는 것**이 중요하다는 점을 배웠다.

## 5. 서비스 이름과 로그인 화면 정리

기존 프로젝트에는 개인 이름이 포함된 Jina Jukebox 명칭이 있었다. 이를 프로젝트 성격에 맞춰 **AX2 Classroom Jukebox**로 변경했다.

변경 대상은 다음과 같았다.

- 브라우저 제목
- 로그인 화면 제목
- 관리자 화면 제목과 설명
- 학생 화면 제목
- README와 환경설정 예시
- 애플리케이션 메타데이터
- 자동 테스트의 예상 문자열

로그인 화면에서는 긴 제목이 좁은 화면에서 부자연스럽게 줄바꿈되는 문제가 있었다.

처음에는 카드 너비를 넓히고 줄바꿈 기준을 조정했지만, 한글 `로그인`이 `로그 / 인`처럼 글자 단위로 끊기는 문제가 발생했다.

최종적으로는 다음 방법을 사용했다.

```css
.login-card h1 {
  font-size: clamp(1rem, 5.2vw, 2rem);
  letter-spacing: -0.03em;
  white-space: nowrap;
}
```

`clamp()`를 사용하면 화면 크기에 따라 글자 크기가 자동으로 조절된다.

- 최소 크기: `1rem`
- 화면 너비에 따른 크기: `5.2vw`
- 최대 크기: `2rem`

제목을 억지로 줄바꿈하는 것보다 화면에 맞춰 글자 크기를 조절하는 편이 더 자연스러웠다.

로그인 화면에 있던 다음 문구도 제거했다.

- 등록된 학생 또는 관리자 계정으로 로그인하라는 설명
- Argon2 해시 저장 방식을 설명하는 기술 문구

보안 구현은 중요하지만, 일반 사용자가 로그인할 때 반드시 읽어야 하는 내용은 아니다. 기술 설명은 README나 운영 문서에 두고, 로그인 화면은 입력에 집중하도록 단순화하는 것이 좋다.

## 6. 반응형 UI 문제를 실제 화면에서 찾기

자동 테스트가 통과해도 실제 화면이 자연스럽다는 뜻은 아니다.

내부 서버를 브라우저로 직접 확인하면서 다음 UI 문제를 발견했다.

### 6.1 플레이리스트 추가 버튼 줄바꿈

곡 선택 영역 옆의 `추가` 버튼 너비가 너무 작아 다음처럼 표시됐다.

```text
추
가
```

Flexbox에서 버튼이 줄어들 수 있었기 때문에 최소 너비와 줄바꿈 방지 속성을 추가했다.

```css
#playlist-add-track {
  flex-shrink: 0;
  min-width: 4.5rem;
  white-space: nowrap;
}
```

템플릿에도 Bootstrap 클래스를 추가했다.

```html
class="btn btn-outline-info flex-shrink-0 text-nowrap"
```

이렇게 하면 사용자 브라우저가 이전 사용자 정의 CSS를 캐시하고 있어도 Bootstrap 클래스가 버튼 축소와 줄바꿈을 막는다.

### 6.2 승인 상태 배지가 세로로 늘어난 문제

신청곡 카드 오른쪽의 `승인` 배지가 카드 높이만큼 늘어나 매우 큰 버튼처럼 보였다.

원인은 Flexbox의 기본 교차축 정렬값인 `stretch`였다. 부모 요소에 `align-items-start`를 추가하고 배지가 축소되지 않게 했다.

```javascript
header.className =
  "d-flex flex-wrap justify-content-between align-items-start gap-3";
```

```javascript
const badge = makeText(
  "span",
  `badge flex-shrink-0 request-status-${item.status.toLowerCase()}`,
  label,
);
```

수정 후에는 상태가 카드 오른쪽 위의 작은 라벨로 표시됐다.

## 7. 정적 파일 캐시 문제

서버 파일은 수정됐지만 브라우저에서 계속 이전 UI가 표시되는 문제가 있었다.

HTML은 새로 받아도 CSS와 JavaScript가 같은 URL이면 브라우저가 기존 파일을 재사용할 수 있다.

예를 들어 다음 주소가 계속 같으면 캐시가 남을 수 있다.

```text
/static/styles.css
/static/dashboard.js
```

그래서 버전 쿼리를 붙였다.

```html
<link href=".../styles.css?v=20261106-1" rel="stylesheet">
<script src=".../dashboard.js?v=20261106-1" defer></script>
```

파일 내용이 변경될 때 버전 값도 바꾸면 브라우저는 다른 URL로 판단해 새 파일을 요청한다.

이번 경험으로 다음을 배웠다.

- 서버 코드가 바뀌었다고 브라우저 화면도 바로 바뀌는 것은 아니다.
- 새로고침만으로 해결되지 않으면 정적 파일 캐시를 의심한다.
- 개발 서버에서도 캐시 무효화 전략이 필요하다.

## 8. GitHub PR을 작업 범위별로 분리하기

처음 작성한 PR #15에는 다음 두 작업이 함께 들어 있었다.

1. STEP 02 관리자 운영 대시보드
2. AX2 브랜딩과 로그인 화면 디자인

리뷰어는 PR을 분리해 달라고 요청했다.

PR은 단순히 커밋을 올리는 장소가 아니라 **하나의 목적을 검토하는 단위**다. 관련 없는 변경이 섞이면 리뷰 범위가 넓어지고, 문제가 생겼을 때 어떤 변경 때문인지 찾기 어렵다.

따라서 다음과 같이 분리했다.

- PR #16: STEP 02 관리자 운영 대시보드
- PR #17: AX2 공통 브랜딩과 로그인 화면
- PR #15: 분리 사유를 댓글로 남기고 중복 PR로 종료

분리 과정에서는 기존 브랜치를 바로 강제로 변경하지 않고 백업 브랜치를 만든 뒤 진행했다.

```text
backup/pr-15-before-split-20261106
```

그다음 `main`에서 새 브랜치를 만들고 필요한 커밋만 `cherry-pick`했다.

```text
main
 ├─ feature/1131-step02-admin-dashboard-only
 └─ feature/common-ax2-branding-login
```

두 PR이 같은 파일의 같은 줄을 수정하면 병합 충돌이 발생할 수 있다. 관리자 화면 브랜딩은 PR #16에만 남기고, PR #17에서는 해당 파일 변경을 제거해 중복을 줄였다.

마지막으로 두 브랜치가 충돌 없이 합쳐지는지 확인했다.

PR을 분리할 때는 파일 개수만 나누는 것이 아니라 **변경 목적, 의존 관계, 병합 순서와 충돌 가능성**까지 확인해야 한다.

## 9. PR 리뷰 대응 과정

리뷰어가 플레이리스트 편성 UI가 깨진다고 수정 요청을 남겼다.

리뷰는 PR #17에 남겨졌지만 실제 문제는 관리자 화면인 PR #16 범위였다.

이때 리뷰 위치만 보고 무조건 해당 PR을 수정하면 안 된다. 문제의 실제 소유 범위를 확인해야 한다.

다음 순서로 대응했다.

1. 리뷰 내용을 확인한다.
2. 내부 서버에서 실제 화면을 연다.
3. 플레이리스트 영역에서 문제를 재현한다.
4. 원인이 Flexbox 버튼 축소임을 확인한다.
5. 관리자 UI PR #16에 수정한다.
6. 서버에도 배포한다.
7. 브라우저에서 정상 표시를 다시 확인한다.
8. GitHub Actions와 보안 검사 결과를 확인한다.

리뷰 대응에서 중요한 점은 “수정했습니다”라고 말하는 것이 아니라 **재현 → 원인 → 수정 → 검증 증거**를 남기는 것이다.

## 10. GitHub Actions와 검증

PR #16과 #17에서 다음 검사를 확인했다.

- Backend 자동 테스트
- GitGuardian 보안 검사
- 병합 가능 상태
- 브랜치 간 충돌 여부

로컬에서는 다음 명령도 사용했다.

```bash
python -m pytest
node --check backend/app/static/dashboard.js
python -m compileall -q backend
git diff --check
```

Windows 환경에서 `pytest`가 임시 폴더를 만들지 못해 실패한 경우도 있었다.

이 오류는 애플리케이션 코드 실패가 아니라 테스트 도구가 기본 Temp 경로를 사용할 수 없어서 발생했다.

프로젝트 내부 임시 폴더를 사용하도록 다음 옵션을 줄 수 있다.

```bash
pytest --basetemp=.pytest-tmp
```

다만 로컬 환경에서 장시간 멈추는 경우가 있어 GitHub Actions 결과도 함께 확인했다.

테스트 결과를 볼 때는 실패 메시지만 보고 코드 문제라고 판단하지 말고 다음을 구분해야 한다.

- 테스트 대상 코드 오류
- 데이터베이스 연결 오류
- 권한 또는 임시 폴더 문제
- 환경 차이
- 테스트 자체의 정지 또는 타임아웃

## 11. Ubuntu 내부 서버 배포

내부 Ubuntu 서버에 애플리케이션을 배포하고 다음을 확인했다.

- 프로젝트 코드 배치
- Python 가상환경과 의존성 설치
- PostgreSQL 연결
- systemd 서비스 실행
- 내부망 웹 접속
- 관리자·학생 로그인
- 관리자 화면 접근
- 최신 브랜치 pull과 서비스 재시작

서비스 코드를 갱신할 때는 다음 흐름을 사용했다.

```text
GitHub 브랜치 push
    ↓
Ubuntu 서버에서 git pull --ff-only
    ↓
systemctl restart
    ↓
HTTP 응답과 실제 브라우저 화면 확인
```

단순히 서비스가 실행 중인지만 보는 것이 아니라 로그인 API, 관리자 페이지, 정적 파일 내용과 실제 화면을 함께 확인했다.

내부 서버 계정과 애플리케이션 계정은 서로 다르다.

- SSH 계정: 서버에 접속하기 위한 운영 계정
- 관리자 계정: 웹 관리자 화면에 로그인하는 애플리케이션 계정
- 학생 계정: 학생 화면에 로그인하는 애플리케이션 계정

비밀번호는 GitHub, Redmine, README, TIL에 기록하지 않고 필요한 사람에게만 별도 전달해야 한다.

## 12. 관리자와 학생 권한 구분

관리자와 학생은 같은 로그인 화면을 사용하지만 로그인 후 권한이 다르다.

관리자는 다음 기능을 사용할 수 있다.

- 신청곡 승인·반려
- 권한 확인 음원 등록
- 플레이리스트 생성과 편성
- 스케줄 생성
- 재생·정지·다음 곡·볼륨 제어

학생은 다음 기능을 사용할 수 있다.

- YouTube URL로 신청곡 등록
- 본인 신청 내역 조회
- 승인·반려 상태 확인
- 재생 상태 조회

서버는 화면에서 버튼을 숨기는 것뿐 아니라 API 요청마다 역할을 다시 확인해야 한다. 프론트엔드 제한만으로는 보안을 보장할 수 없다.

## 13. YouTube URL과 실제 음원의 차이

학생이 YouTube URL을 입력한다고 해서 서버가 해당 영상을 바로 MP3로 다운로드하는 것은 아니다.

현재 시스템에서 YouTube URL은 다음 목적으로 사용한다.

- 곡 식별
- 중복 신청 확인
- 제목과 채널 정보 저장
- 관리자의 원본 영상 검토

실제 재생은 권한이 확인된 로컬 음원 파일을 사용한다.

흐름은 다음과 같다.

```text
학생 신청 PENDING
    ↓
관리자 승인 APPROVED
    ↓
음원 확보 대기 PENDING_ACQUISITION
    ↓
권한 확인 파일 등록과 검사
    ↓
재생 가능 READY
    ↓
플레이리스트 편성
```

`APPROVED`와 `READY`는 서로 다른 상태다.

- `APPROVED`: 신청을 받아들였다는 뜻
- `READY`: 실제 재생 가능한 파일 준비까지 끝났다는 뜻

## 14. 디스코드 음악 봇과 우리 프로젝트의 차이

일부 디스코드 음악 봇은 YouTube URL에서 오디오 스트림을 추출해 바로 재생한다.

기술적으로는 가능하지만 다음 문제가 있다.

- YouTube 정책과 충돌할 수 있다.
- 오디오만 분리하거나 다운로드하는 방식은 제한될 수 있다.
- YouTube 구조가 바뀌면 갑자기 작동하지 않을 수 있다.
- 차단이나 서비스 중단 위험이 있다.
- 강의실 재생 권리는 별도로 확인해야 한다.

우리 프로젝트는 안정적인 자동재생이 중요하다. 네트워크가 끊겨도 로컬 음원을 계속 재생할 수 있어야 하므로 로컬 파일과 MPD 구조가 더 적합하다.

음원 확보 방식은 주로 **STEP 07**에 해당한다.

- STEP 05: YouTube URL 신청
- STEP 06: 승인·반려
- STEP 07: 실제 음원을 어떻게 확보하고 READY로 만들지 결정
- STEP 08: READY 곡 플레이리스트 편성
- STEP 10: MPD 실제 재생

MVP에서는 수동 업로드 방식을 유지하고, 권한이 확인된 소스의 자동 다운로드는 별도 개선 일감으로 분리하는 것이 안전하다.

## 15. 작업 중 어려웠던 부분과 해결 방법

### 1. 빠르게 다음 단계로 가고 싶었지만 승인 절차가 남아 있었다

코드는 이미 이후 단계까지 존재해 바로 다음 기능을 개발하고 싶었다.

하지만 공식 진행 기준은 저장소 코드가 아니라 Redmine 일감과 PR 상태였다.

STEP 02는 개발이 끝났더라도 승인과 병합 전까지 완료가 아니다. 현재는 90% 상태로 두고 재검토를 기다리는 것이 맞다.

### 2. PR 하나에 서로 다른 목적의 변경이 섞였다

관리자 대시보드와 로그인 브랜딩을 하나의 PR에 넣어 리뷰 범위가 커졌다.

백업 브랜치를 만든 뒤 `main` 기준으로 두 브랜치를 새로 생성하고 필요한 커밋만 분리했다.

앞으로는 작업을 시작할 때부터 다음 원칙을 지켜야 한다.

```text
일감 하나 → 목적 하나 → 브랜치 하나 → PR 하나
```

### 3. 코드 수정 후에도 화면이 바뀌지 않았다

서버 파일과 서비스는 최신인데 브라우저 화면은 이전 상태였다.

정적 CSS와 JavaScript 캐시가 원인이었다. 파일 URL에 버전 쿼리를 추가해 해결했다.

### 4. 자동 테스트는 성공했지만 UI가 깨졌다

테스트는 API 응답과 필수 HTML 요소를 검증했지만 버튼 글자가 세로로 깨지는 시각적 문제는 찾지 못했다.

따라서 화면 작업에서는 다음 검증이 모두 필요하다.

- 자동 테스트
- JavaScript 문법 검사
- 데스크톱 화면 확인
- 좁은 사이드 패널 또는 모바일 화면 확인
- 실제 서버 배포 후 확인

### 5. 리뷰가 다른 PR에 남겨졌다

리뷰는 브랜딩 PR에 남았지만 문제는 관리자 UI에 있었다.

리뷰가 작성된 위치보다 문제의 실제 코드 소유 범위를 기준으로 수정해야 한다는 것을 배웠다.

## 16. 해보고 느낀 점

처음에는 기능을 많이 구현하면 프로젝트가 빨리 끝난다고 생각했다.

하지만 실제 개발에서는 구현량보다 **작업 범위를 명확히 하고 검증 가능한 상태로 전달하는 과정**이 중요했다.

이번 작업에서는 화면의 작은 줄바꿈 문제 하나를 고치기 위해 다음 과정을 거쳤다.

1. 리뷰 확인
2. 서버 화면 재현
3. CSS와 Flexbox 원인 분석
4. 올바른 PR에 수정
5. 서버 재배포
6. 브라우저 캐시 문제 확인
7. 정적 파일 버전 처리
8. 최종 화면 재검증

작은 UI 수정도 실제 운영 환경에서는 여러 단계가 필요했다.

또한 비밀번호를 문서나 PR에 남기지 않고 DM으로 전달하는 것, 승인 담당자와 튜터의 역할을 구분하는 것, 병합 후에만 Redmine을 완료 처리하는 것도 개발자의 중요한 책임이라는 것을 알게 됐다.

## 오늘의 핵심 정리

1. 개발 완료와 일감 완료는 다르며, PR 병합 후에 Redmine을 종료한다.
2. STEP 02는 플레이어 엔진이 아니라 관리자 운영 페이지 작업이다.
3. 하나의 PR에는 하나의 명확한 목적만 담는 것이 좋다.
4. PR 분리 시 커밋뿐 아니라 파일 중복과 병합 충돌도 확인해야 한다.
5. 자동 테스트가 통과해도 반응형 UI는 실제 브라우저에서 별도로 확인해야 한다.
6. Flexbox의 기본 `stretch`와 요소 축소 때문에 배지와 버튼 모양이 깨질 수 있다.
7. CSS와 JavaScript 변경 후 화면이 그대로라면 브라우저 캐시를 확인한다.
8. 정적 파일 URL에 버전 값을 붙이면 새 파일 로드를 유도할 수 있다.
9. YouTube URL 신청과 실제 재생 음원 준비는 서로 다른 과정이다.
10. 승인된 곡도 음원 파일 검사까지 끝나야 `READY`가 된다.
11. 음원 확보 방식은 STEP 07의 핵심 결정 사항이다.
12. 비밀번호와 서버 비밀정보는 GitHub, Redmine, README, TIL에 기록하지 않는다.
13. 리뷰 대응은 재현, 원인 분석, 수정, 배포, 재검증까지 완료해야 한다.
14. 작업계획과 승인 절차를 지키는 것도 코드 구현만큼 중요한 개발 역량이다.
