# 2026-11-12 TIL — React 미니 팝업 스토어와 Product API 기초

## 오늘 학습한 내용

오늘은 Phase 03의 **미니 팝업 스토어 실습**을 시작했다. 기존 회원관리 프로젝트를 지우거나 구조를 바꾸지 않고, 상품과 주문 기능을 추가하는 별도 Next.js 애플리케이션을 준비했다.

이번 수업에서는 전체 쇼핑몰 기능을 한 번에 구현하지 않고 다음 흐름의 기초를 먼저 만들었다.

```text
PostgreSQL products 테이블
        ↓
Repository
        ↓
Service
        ↓
FastAPI GET /products
        ↓ JSON
Next.js ProductCard
```

Backend에서는 상품 테이블과 조회 API를 만들고, Frontend에서는 상품 한 개를 표현할 `Product` 타입과 `ProductCard` 컴포넌트의 구조를 만들었다. 실제 장바구니 State와 주문 API 연결은 아직 구현하지 않았다.

## 2. 상품 데이터 모델 만들기

상품과 주문 기능을 위해 SQLAlchemy 모델을 추가했다.

### Product

상품 한 개가 가지는 정보는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `id` | 상품 식별자 |
| `name` | 상품명 |
| `price` | 가격 |
| `category` | 카테고리 |
| `stock` | 재고 수량 |

`price`와 `stock`은 음수가 될 수 없도록 제약 조건을 두었다. 이 검증은 화면에서만 처리하는 것이 아니라 데이터베이스에서도 잘못된 값을 막아야 한다.

### Order와 OrderItem

주문은 주문 자체 정보와 주문에 포함된 상품 목록을 나누어 저장한다.

```text
orders 1개
   ↓ 1:N
order_items 여러 개
   ↓ N:1
products 상품 정보
```

`OrderItem`에는 주문 ID, 상품 ID, 수량, 주문 당시 가격을 저장한다. 상품 가격은 나중에 바뀔 수 있으므로 주문 시점의 가격을 주문 상세에 따로 기록해야 한다는 점을 이해했다.

|---|---:|---|---:|
| 초코 쿠키 | 3,000원 | 간식 | 15 |
| 아메리카노 | 2,500원 | 음료 | 20 |
| 딸기 케이크 | 5,500원 | 디저트 | 8 |
| 감자칩 | 2,000원 | 간식 | 12 |
| 탄산수 | 1,500원 | 음료 | 25 |

```text

최종 상품 수: 6
```

Seed 스크립트는 여러 번 실행해도 같은 데이터가 계속 쌓이지 않는 **멱등성**이 중요하다는 것을 배웠다.

## 4. Repository 계층에서 상품 조회하기

Repository는 데이터베이스와 직접 통신하는 계층이다. `product_repository.py`에 전체 상품 조회 함수를 작성했다.

```python
def find_all(db: Session):
    stmt = select(Product).order_by(Product.id)
    return db.scalars(stmt).all()
```

이 코드의 흐름은 다음과 같다.

1. `select(Product)`로 products 테이블 조회 문장을 만든다.
2. `order_by(Product.id)`로 상품 ID 순서대로 정렬한다.
3. `db.scalars(stmt)`로 SQL을 실행하고 ORM 객체만 가져온다.
4. `.all()`로 모든 상품을 리스트 형태로 반환한다.

Repository에서 조회한 상품 수와 PostgreSQL에서 직접 확인한 상품 수가 모두 6개로 일치했다.

## 5. Service 계층의 역할

Service는 Router와 Repository 사이에서 비즈니스 규칙을 담당한다.

오늘 작성한 `get_products()`는 아직 단순히 Repository를 호출하는 형태다.

```python
def get_products(db: Session):
    return product_repository.find_all(db)
```

현재는 로직이 짧지만 Service를 따로 두는 이유는 이후 다음 규칙이 들어갈 수 있기 때문이다.

- 판매 가능한 상품만 반환하기
- 품절 상품 정렬하기
- 카테고리 필터 적용하기
- 주문 수량과 재고 비교하기
- 주문 총액을 서버 가격으로 다시 계산하기

처음에는 한 줄뿐인 함수를 굳이 분리해야 하는지 의문이 들었지만, 계층을 미리 나누면 기능이 커져도 Router와 DB 코드가 섞이지 않는다는 것을 이해했다.

## 6. GET /products API 구현

FastAPI Router에 상품 목록 API를 추가했다.

```python
router = APIRouter(prefix="/products", tags=["products"])

@router.get("", response_model=list[ProductResponse])
def get_products(db: Session = Depends(get_db)):
    return product_service.get_products(db)
```

`Depends(get_db)`는 요청마다 DB Session을 제공하고, 처리가 끝나면 Session을 정리한다. Router는 SQL을 직접 작성하지 않고 Service만 호출한다.

`ProductResponse`에는 다음 다섯 필드를 지정했다.

```text
id, name, price, category, stock
```

`response_model`을 사용하면 응답 형식을 문서로 보여 줄 수 있고, 반환 데이터가 계약과 맞는지도 FastAPI가 검사한다.

`main.py`에서는 상품 Router를 등록했다.

```python
app.include_router(product_router.router)
```

처음에는 `main.py`를 수정하지 않고 진행했지만 Router 파일만 만들어서는 API가 Swagger에 나타나지 않았다. **Router 생성과 애플리케이션 등록은 별개의 작업**이라는 점을 알게 됐다.

## 11. ProductCard 컴포넌트 구조 만들기

상품 한 개를 재사용 가능하게 표시할 `ProductCard`를 만들었다.

Props 계약은 다음과 같다.

```typescript
type ProductCardProps = {
  product: Product;
  onAdd: (product: Product) => void;
};
```

`product`는 카드에 표시할 상품 정보이고, `onAdd`는 부모 컴포넌트가 전달하는 장바구니 담기 이벤트다.

ProductCard의 책임은 다음과 같다.

- 상품명 표시
- 원 단위 가격 표시
- 카테고리 표시
- 재고 표시
- 품절 여부 판단
- 담기 버튼 클릭 시 부모의 콜백 호출

재고가 0이면 다음과 같이 처리했다.

```typescript
const isSoldOut = product.stock === 0;
```

- 재고 대신 품절 문구를 표시한다.
- 담기 버튼을 비활성화한다.
- `onAdd`가 실행되지 않도록 한다.

버튼 클릭 이벤트 때문에 `ProductCard`에는 `"use client"`를 선언했다. Next.js App Router에서 기본 컴포넌트는 Server Component이지만, 클릭 이벤트처럼 브라우저 상호작용이 필요하면 Client Component로 구분해야 한다.

오늘은 STEP 16까지만 진행했기 때문에 ProductCard 파일은 만들었지만 아직 페이지에 카드를 연결하지 않았다. 화면에 카드 한 개를 표시하는 작업은 다음 STEP에서 진행한다.

## 13. 개발 서버 포트 충돌 해결

Frontend 개발 서버를 실행하면서 3000번 포트 충돌을 만났다.

```text
Port 3000 is in use
```

기존 프로세스 정보가 남아 있었고 `.next/dev/lock` 파일도 존재했다. 실제 프로세스는 이미 종료돼 있었기 때문에 stale lock을 정리한 뒤 다른 포트에서 서버를 실행했다.

```text
http://localhost:3002
```

최종적으로 3002번 포트에서 HTTP 200 응답을 확인했다.

포트 번호를 무조건 3000이라고 생각하면 안 되고, 터미널의 `Local` 주소를 실제 접속 주소로 사용해야 한다는 것을 다시 확인했다.

## 14. 작업 중 어려웠던 부분과 해결 방법

### 1. 파일에는 Router가 있는데 `/products`가 404로 나왔다

`main.py`에는 상품 Router가 등록되어 있었지만 실행 중인 서버가 이전 앱을 바라보고 있었다.

실행 프로세스를 정리하고 정확한 `chapter13` 폴더에서 Uvicorn을 다시 시작했다. 이후 Swagger와 `/products`를 재확인해 상품 6개가 반환되는 것을 확인했다.

이 문제를 통해 **코드 파일이 맞는 것과 실행 중인 프로세스가 그 코드를 사용하는 것은 별개**라는 점을 배웠다.

### 2. npm 설치가 너무 오래 걸리고 실패했다

첫 번째 설치는 npm registry의 idle timeout으로 실패했다. 프로젝트 파일을 지우거나 새로 만들지 않고 같은 위치에서 설치를 재실행해 해결했다.

### 3. 새 프로젝트의 TypeScript 검사에서 내 코드와 무관한 오류가 발생했다

개발 서버 실행 전이라 Next.js 생성 타입이 없었다. 서버를 한 번 실행해 `.next` 타입 파일을 만든 다음 다시 검사했다.

### 4. 개발 서버가 Ready라고 했는데 브라우저에서 열리지 않았다

기존 개발 서버 정보와 lock 파일이 남아 있었고, 3000번 포트도 충돌했다. stale lock을 정리하고 3002번 포트에서 새 프로세스를 실행해 HTTP 200을 확인했다.

### 5. 계층을 왜 여러 파일로 나누는지 처음에는 헷갈렸다

Repository, Service, Router가 모두 짧아서 한 파일에 써도 될 것처럼 보였다. 하지만 각 계층의 책임을 구분하니 이후 주문 검증, 재고 차감, 트랜잭션을 추가할 위치가 명확해졌다.

## 15. 해보고 느낀 점

오늘 실습은 단순히 상품 카드를 그리는 수업이 아니라 **데이터가 DB에서 화면까지 이동할 준비를 만드는 과정**이었다.

특히 다음 점이 인상 깊었다.

첫째, Backend API 계약과 Frontend 타입이 연결되어야 한다. PostgreSQL 컬럼, SQLAlchemy 모델, Pydantic 응답 모델, TypeScript 타입 중 하나라도 이름이나 자료형이 다르면 전체 흐름에서 문제가 생긴다.

둘째, 코드 작성보다 실행 환경을 정확히 맞추는 일이 어려웠다. 같은 파일을 보고 있어도 다른 서버 프로세스가 실행 중이면 404가 나오고, Next.js가 Ready라고 표시돼도 포트나 lock 상태 때문에 접속이 안 될 수 있었다.

셋째, 오류를 한꺼번에 고치려고 하기보다 다음처럼 구간별로 확인하는 방법이 효과적이었다.

```text
DB 상품 수 확인
→ Repository 반환 수 확인
→ Service 호출 확인
→ Swagger 200 확인
→ pytest 확인
→ Frontend 타입 검사
→ 개발 서버 HTTP 200 확인
```

각 단계가 통과한 뒤 다음 단계로 넘어가니 문제가 생긴 위치를 찾기 쉬웠다.

마지막으로 ProductCard가 장바구니 전체를 직접 관리하지 않고 `onAdd` 이벤트만 부모에게 전달한다는 점이 중요했다. 컴포넌트마다 장바구니 배열을 따로 가지면 상태가 여러 곳으로 나뉘기 때문이다. 다음 수업에서 부모 컴포넌트가 State를 관리하고 여러 ProductCard에 전달하는 흐름을 직접 확인해 보고 싶다.

## 오늘의 핵심 정리

1. 기존 회원관리 프로젝트를 지우지 않고 상품 실습 구조를 별도로 추가했다.
2. Product, Order, OrderItem은 상품·주문·주문상세의 역할이 다르다.
3. Seed 데이터는 재실행해도 중복되지 않도록 만드는 것이 좋다.
4. Repository는 DB 조회, Service는 비즈니스 규칙, Router는 HTTP 요청·응답을 담당한다.
5. Router 파일을 만들어도 `main.py`에 등록하지 않으면 Swagger에 나타나지 않는다.
6. `GET /products`에서 PostgreSQL 상품 6개와 HTTP 200을 확인했다.
7. 테스트는 실제 DB와 분리해 반복 실행할 수 있도록 구성했다.
8. 전체 pytest 결과는 5 passed였다.
9. Backend 응답 모델과 Frontend Product 타입의 필드가 일치해야 한다.
10. ProductCard는 상품 표시와 `onAdd` 이벤트 전달만 담당한다.
11. 브라우저 이벤트를 사용하는 컴포넌트에는 `"use client"`가 필요하다.
12. 재고가 0이면 품절 표시와 버튼 비활성화를 함께 처리한다.
13. TypeScript와 ESLint 검사를 실제로 실행해 모두 통과했다.
14. npm timeout, stale lock, 포트 충돌은 코드 오류와 구분해 해결해야 한다.
15. 오늘은 STEP 16 구조 준비까지 완료했으며 화면 연결은 다음 STEP에서 진행한다.
