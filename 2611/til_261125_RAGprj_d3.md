## 2. 핵심 개념과 실습 내용

### 모델별 값과 공통 조건을 구분하기

PR #63의 검증기는 답의 숫자가 인용 청크에 있는지 본 다음 모델별 값과 연결한다. 처음에는 서로 다른 모델의 수치를 바꿔 답한 경우를 막는 데 집중했다. 그런데 실제 청크에는 괄호 안 모델 목록, 슬래시, 각주 번호, 수치 뒤에 오는 모델명 등 다양한 표기가 있었다. 단순히 문장을 자르면 맞는 답도 차단됐다.

나경님이 다시 제시한 반례는 `DCP-T830DW` 질문에 다른 모델 전용 행의 전원 Off `0.15W`를 인용하는 경우였다. T830DW의 실제 행은 `0.10W`다. 공통 조건 과차단을 고치려고 만든 단일 값 그룹 fallback이 모델 적용 범위를 먼저 확인하지 않아 `0.15W` 오답을 통과시켰다. 모델 전용 값 행은 다른 모델의 근거로 쓰지 않도록 하고, 모델명이 없는 공통 측정 조건 문장은 별도로 처리했다. 실제 p456의 두 행과 p459의 `ISO/IEC 24712` 조건으로 오답 차단·정답 통과를 함께 고정했다.

PR #63에는 공급자 호출 오류를 조사할 때 필요한 HTTP 상태 코드와 공급자 Request ID를 민감정보 없이 기록하는 변경도 있다. 인증·한도 오류를 근거 부족 보류로 바꾸지 않고, 장애와 문서상 정보 부족을 구별하는 것이 중요하다.

### 숫자에 붙은 한글 단위와 항목명

`400페이지`처럼 숫자와 한글 단위를 붙여 쓰면 기존 정규식이 숫자를 찾지 못하는 경로가 있었다. 별도 PR #80에서 `페이지`를 인식하고 `쪽`과 같은 단위로 비교하도록 수정했다. 올바른 `400페이지`·`400쪽`은 통과하고 `401페이지`·`400개`는 차단하는 테스트를 넣었다. 나경님 승인 후 PR #80은 main에 병합됐다.

또 실제 잉크젯 설명서 p67의 공식 항목명 `스캔 불가능 영역`을 기능 미지원 주장으로 오해해, 근거가 있는 `1mm` 답변까지 차단하는 문제를 재현했다. PR #81은 이 항목명만 좁게 제외한다. `1mm`는 통과하고 `9mm`와 “이 모델은 스캔할 수 없다”는 허위 결론은 계속 차단한다. PR #81은 아직 리뷰·병합·운영 검증 전이다.

### 근거 묶음은 구조 레코드와 실제 청크가 맞아야 한다

나경님 PR #68은 운영 경로에 연결되지 않은 Context Packing 모듈이다. 최신 main과 합쳐 테스트가 통과했지만, 독립 반례 두 건을 재현했다. A 모델만 필요한데 같은 부모 청크를 공유하는 B 전용 각주까지 보호했고, 구조 레코드에는 A 적용이라고 적혀 있으나 현재 청크는 B 전용인 경우에도 `packed`로 반환했다. 오늘 GitHub에 두 코드 위치의 수정 요청 리뷰를 남겼다. **테스트가 모두 통과해도 테스트하지 않은 입력 조합에서 안전 계약이 깨질 수 있다**는 점을 확인했다.

## 5. 어려웠던 부분과 잘 안됐던 점

첫째, 과차단을 줄이는 fallback이 다른 모델 값의 과허용을 만들었다. 한 반례만 고치고 테스트가 통과했다고 끝내면 모델 범위가 다른 실제 표 행에서 새 오답이 생길 수 있었다.

둘째, 저장된 예전 1,823청크를 최신 main 테스트에 그대로 사용하자 데이터 적용 범위 테스트 네 건이 실패했다. 최신 main의 데이터 규칙이 바뀌었는데 청크 파일은 옛 버전이었던 것이 원인이다. PDF에서 1,824청크를 다시 만든 뒤 전체 테스트가 통과했다. 코드 회귀와 오래된 로컬 산출물을 구분해야 했다.

셋째, `uv`가 샌드박스 임시 캐시에 쓰지 못해 `액세스가 거부되었습니다. (os error 5)`를 냈고, 새 패키지 다운로드도 DNS 오류로 실패했다. 이미 설치된 가상환경의 Python을 사용했다. 로컬 HTTP 소켓이 필요한 전체 테스트는 소켓 접근이 허용된 환경에서 다시 실행해 결과를 확인했다.

## 6. 오류의 원인과 해결 방법

수치 검증 오류를 다시 만나면 다음 순서로 확인한다.

1. `/health` 커밋과 청크 fingerprint가 검사하려는 코드·데이터 버전과 같은지 확인한다.
2. 질문 모델, 답변 숫자·단위, 인용한 청크의 `applicable_models`를 나란히 본다.
3. 해당 숫자가 **그 모델의 사양 행**에 있는지, 공통 조건·각주 번호인지 구분한다.
4. 정답 통과와 타 모델 값 차용·수치 교환 오답 차단을 한 쌍의 테스트로 만든다.
5. 저장 답변 재판정으로 새 과차단을 확인하고, 최신 PDF로 청크를 다시 만든 뒤 전체 회귀를 돌린다.
6. 병합 후 서버의 실행 커밋과 실제 API 응답·로그를 확인한다. 그 전에는 점수 향상을 확정하지 않는다.
7. 호출 한도·인증 오류는 정상 보류와 구분하고, 비밀값을 제외한 상태 코드·요청 ID를 확인한다.

## 7. 해보고 느낀 점

RAG 답변 검증은 숫자를 엄격하게 찾는 것만으로 정확해지지 않는다. 같은 청크에 여러 모델의 값과 공통 각주가 함께 있을 때는 **누구의 값인지**가 더 중요했다. 맞는 답을 살리는 수정과 틀린 답을 막는 수정은 같이 검증해야 한다. 또한 팀원이 보고한 색인 검사, 내가 직접 실행한 코드 테스트, 운영 서버 상태, 공식 점수는 각각 다른 수준의 증거라는 점을 분명히 기록해야 혼동이 줄어든다.

## 오늘의 핵심 정리

**인용 청크에 숫자가 있다는 것과 그 숫자가 질문한 모델의 값이라는 것은 다르다.** 오늘은 실제 표 행·공통 조건·한글 단위·공식 항목명 반례를 각각 분리해 검증했다. PR 병합, 데이터 동결, 운영 서버 배포, 공식 점수는 같은 완료 상태가 아니다.
