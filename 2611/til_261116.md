# 2026-11-16 TIL — OpenAI·Gemini 모델 연결과 나만의 AI 비서 실습

## 오늘 학습한 내용

오늘은 지난 수업에서 만든 My AI Assistant의 Mock 실행을 바탕으로, OpenAI와 Gemini 모델을 선택해 호출할 수 있는 구조를 살펴봤다. `.env`에 API Key와 모델 이름을 분리하고, 현재 OpenAI Key에서 조회되는 모델을 확인하는 `model_info.py`도 작성했다.

또한 한 번 질문하는 `main.py`와 여러 번 질문하는 `chat_loop.py`의 차이를 이해하고, 실제 API를 사용하지 않는 자동 테스트 19개를 실행했다. 마지막에는 내가 만들 학습 도우미의 질문 세 가지와 고정 답변 형식을 작성해 기본 질문과 구체적인 질문의 차이를 비교할 준비를 했다.

오늘의 전체 흐름은 다음과 같다.

```text
.env와 모델 설정 확인
→ OpenAI 모델 목록 조회 코드 작성
→ Mock / Live 클라이언트 구조 이해
→ 한 번 질문하기와 반복 질문하기 비교
→ 빈 입력과 오류 처리 보완
→ unittest 19개 실행
→ 나만의 질문 3개와 고정 답변 형식 작성
```

## 1. 실습 환경과 폴더 구조

수업에서 사용한 기준 프로젝트는 `practice/my-ai-assistant`였다. 오늘 작업한 주요 파일의 역할은 다음과 같다.

```text
my-ai-assistant/
├─ .env.example              # 필요한 환경변수 이름과 예시
├─ .gitignore                # .env와 개인 실습 파일 제외
├─ requirements.txt          # OpenAI·Gemini SDK 의존성
├─ main.py                   # 질문 한 번을 처리하는 공통 프로그램
├─ chat_loop.py              # 여러 질문을 반복해서 받는 콘솔 프로그램
├─ model_info.py             # OpenAI Key에 보이는 모델 목록 확인
├─ MY_ASSISTANT_GOAL.md      # 개인 AI 비서 목표와 질문
├─ MY_ASSISTANT_PROMPTS.txt  # 기본·고정 형식 질문 모음
└─ tests/
   ├─ test_main.py
   └─ test_chat_loop.py
```

`.env.example`에는 실제 키가 아니라 어떤 설정이 필요한지만 기록했다.

```dotenv
OPENAI_API_KEY=본인의_OPENAI_API_KEY
OPENAI_MODEL=gpt-4o-mini
OPENAI_EMBEDDING_MODEL=text-embedding-3-small
OPENAI_MAX_OUTPUT_TOKENS=128

GEMINI_API_KEY=본인의_GEMINI_API_KEY
GEMINI_MODEL_NAME=gemini-flash-lite-latest
GEMINI_MAX_OUTPUT_TOKENS=128
```

실제 API Key 값은 문서나 코드에 기록하지 않았다. `.env`는 로컬에서만 사용하고 Git에 포함하지 않아야 한다.

## 2. 핵심 개념과 실습 내용

### Mock 모드와 Live 모드

Mock 모드는 실제 모델 API를 호출하지 않는다. 입력 문자열이 프로그램 안에서 정상적으로 전달되고 출력되는지 확인하는 용도다. API Key가 없어도 실행할 수 있고 사용 요금도 발생하지 않는다.

Live 모드는 OpenAI 또는 Gemini SDK를 이용해 실제 모델을 호출한다. API Key, 정확한 모델 ID, 계정 권한과 사용 한도 등이 모두 준비되어야 한다.

```text
Mock
→ 정해진 예시 응답
→ 입력·분기·출력·오류 처리 확인

Live
→ 실제 Provider API 요청
→ 모델 답변과 토큰 사용량 확인
```

Mock 테스트가 성공했다고 해서 Live 호출까지 성공했다고 기록하면 안 된다. 오늘 자동 테스트와 Mock 실행은 확인했지만 개인 API Key를 이용한 Live 호출은 직접 검증하지 않았으므로 `NOT_VERIFIED`로 구분했다.

### API와 SDK의 차이

API는 프로그램이 외부 서비스와 통신할 때 지켜야 하는 요청과 응답의 규칙이다. SDK는 이 API를 Python 코드에서 더 편하게 사용할 수 있도록 제공되는 도구 모음이다.

OpenAI SDK를 사용하면 직접 HTTP 헤더와 JSON 요청을 모두 작성하지 않고 다음처럼 모델 요청을 만들 수 있다.

```python
response = client.responses.create(
    model=self.model,
    input=question,
    max_output_tokens=self.max_output_tokens,
)
```

### 대화 모델과 임베딩 모델

대화 모델은 질문을 받아 자연어 답변을 만든다. 임베딩 모델은 문장을 숫자 벡터로 바꿔 의미가 비슷한 문서를 찾을 때 사용한다. 역할이 다르기 때문에 `.env`에서도 모델 이름을 분리했다.

`model_info.py`에서는 `client.models.list()`로 현재 OpenAI Key에 표시되는 모델 ID를 조회하도록 했다. 그중 공식 임베딩 모델 ID와 일치하는 항목을 별도로 출력한다.

다만 모델 목록에 보인다는 사실만으로 모든 호출이 반드시 성공하는 것은 아니다. 실제 호출에는 엔드포인트 지원 여부, 결제 상태, 사용 한도와 프로젝트 권한도 영향을 줄 수 있다.

### 출력 토큰 상한을 환경변수로 이동

처음 코드에는 출력 토큰 상한 `128`이 직접 적혀 있었다. 이를 다음 환경변수로 옮겼다.

```text
OPENAI_MAX_OUTPUT_TOKENS
GEMINI_MAX_OUTPUT_TOKENS
```

프로그램은 값을 정수로 바꾸고 1 이상의 값인지 검사한다. 값이 없으면 기본값 128을 사용한다. 숫자가 아닌 값이나 0 이하의 값은 `ValueError`로 처리한다.

## 3. 코드와 실행 흐름

### main.py 실행 흐름

`main.py`는 명령행에서 질문과 실행 모드를 받은 뒤 알맞은 클라이언트를 선택한다.

```text
main()
  ↓
argparse로 질문, mode, provider 읽기
  ↓
질문이 비어 있는지 검사
  ↓
Live이면 load_local_env()로 .env 읽기
  ↓
make_client()로 Mock/OpenAI/Gemini 선택
  ↓
run(question, client)
  ↓
client.ask(question)
  ↓
Reply 객체에 답변과 사용량 저장
  ↓
답변·모델·토큰 사용량 출력
```

`MockClient`는 예시 응답을 반환한다. `OpenAIClient.ask()`는 Responses API를 호출하고, `GeminiClient.ask()`는 Gemini의 `generate_content()`를 호출한다.

`Reply`에는 다음 값을 보관한다.

| 필드 | 의미 |
|---|---|
| `text` | 모델 또는 Mock 답변 |
| `model` | 사용한 모델 ID |
| `input_tokens` | 입력 토큰 수 |
| `output_tokens` | 출력 토큰 수 |
| `cached_input_tokens` | 캐시로 처리된 입력 토큰 수 |
| `measurement_mode` | `mock` 또는 `live` |

### 빈 질문 처리

처음에는 명령행 질문의 기본값과 중복된 `add_argument()` 때문에 질문을 생략한 경우의 동작이 헷갈렸다. 다음처럼 질문을 정리해 검사하도록 수정했다.

```python
question = (args.question or "").strip()
if not question:
    raise ValueError("질문을 입력해야 합니다.")
```

이제 다음 세 입력은 모두 같은 오류로 처리된다.

```powershell
python main.py --mode live
python main.py --mode live ""
python main.py --mode live "   "
```

예상한 오류와 종료 코드를 실제로 확인했다.

```text
ERROR: 질문을 입력해야 합니다.
exit=2
```

PowerShell에서는 블로그에서 복사된 둥근 따옴표 `“”`가 빈 문자열 구분자로 동작하지 않을 수 있다. 일반 따옴표 `""` 또는 `''`를 사용해야 한다.

### chat_loop.py 실행 흐름

`chat_loop.py`는 `main.py`의 클라이언트를 재사용하고 입력만 반복해서 받는다.

```text
콘솔 입력
→ 빈 질문인지 확인
→ help / 도움말 처리
→ exit / quit 처리
→ client.ask(question)
→ 답변과 Live 사용량 출력
→ 다음 질문 대기
```

여러 번 질문할 수 있지만 이전 질문과 답변을 다음 요청에 전달하지 않는다. 반복 입력과 대화 기억은 서로 다른 기능이라는 점을 이해했다.

## 4. 실행 및 테스트 결과

### Mock 실행

다음과 같이 실제 API 없이 질문 처리 흐름을 확인했다.

```powershell
python main.py "안녕하세요"
```

결과에는 `mode=mock`, `model=mock-fixture`가 표시됐고 입력한 질문이 Mock 응답에 포함됐다.

질문 세 개와 고정 답변 형식을 붙인 질문도 Mock 모드로 실행했다. Mock은 실제 지능형 답변을 생성하지 않으므로 답변 형식의 차이까지 비교할 수는 없었지만, 긴 질문과 형식 지시문이 하나의 입력으로 정상 처리되는 것은 확인했다.

### model_info.py 확인

실제 키가 없는 상태에서 실행했을 때 다음 안내와 종료 코드 2를 확인했다.

```text
ERROR: .env에 실제 OPENAI_API_KEY를 입력해 주세요.
```

따라서 모델 목록을 실제로 가져오는 Live 결과는 확인하지 않았다.

### 자동 테스트

수업과 같은 명령으로 테스트를 실행했다.

```powershell
python -m unittest discover -s tests -v
```

결과는 다음과 같았다.

```text
Ran 19 tests in 0.156s

OK
```

테스트에서 확인한 내용은 다음과 같다.

- Mock 응답과 빈 질문 거절
- Mock 모드에서 API Key가 필요하지 않은지 확인
- OpenAI·Gemini Key와 모델 누락 처리
- 지원하지 않는 mode 거절
- 폴백 성공·실패와 설정 오류 처리
- 대화형 콘솔의 여러 질문, 빈 입력, help, exit, quit
- 테스트용 가짜 Live 사용량 출력
- 오류 상세 내용과 비밀 문자열을 화면에 노출하지 않는지 확인

테스트는 가짜 클라이언트를 사용했으며 실제 API를 호출하지 않았다.

## 5. 어려웠던 부분과 잘 안됐던 점

### 교수님 화면과 첨부 코드의 형식이 달랐다

블로그에서 복사한 코드에는 들여쓰기와 따옴표가 깨져 있었고 `__init__`, `__file__`, `__name__`의 밑줄도 사라져 있었다. 그대로 복사하면 Python 문법 오류가 발생할 수 있는 상태였다.

교수님 VS Code 화면과 공개 저장소의 실제 파일을 비교해 `.py` 파일, 4칸 들여쓰기, 함수 이름과 환경변수 이름을 다시 맞췄다.

### 환경변수 이름이 서로 달랐다

처음 요청 예시에는 `OPENAI_MODEL_NAME`이 있었지만 교수님 자료와 저장소 코드는 `OPENAI_MODEL`을 사용했다. 수업 기준은 `OPENAI_MODEL`로 통일하고, 이전 이름도 보조로 읽을 수 있게 했다.

### 빈 문자열이 if문에 걸리지 않는 것처럼 보였다

문제는 `if not question` 자체가 아니었다. 질문 인자의 기본값, 중복 정의, PowerShell에서 사용한 둥근 따옴표 때문에 실제로 빈 문자열이 전달되지 않는 경우를 구분해야 했다.

`None`, 빈 문자열, 공백 문자열을 먼저 `.strip()`으로 정리한 뒤 검사해 해결했다.

### Windows 콘솔에서 UnicodeEncodeError가 발생했다

`chat_loop.py`를 자동 실행했을 때 Windows CP949 콘솔이 긴 대시 문자 `—`를 출력하지 못해 다음 오류가 발생했다.

```text
UnicodeEncodeError: 'cp949' codec can't encode character '\u2014'
```

출력 제목의 긴 대시를 일반 하이픈 `-`으로 바꾼 뒤 같은 대화형 입력을 다시 실행했고 종료 코드 0을 확인했다. 자동 테스트에서는 `PYTHONIOENCODING=utf-8`을 사용해 한글 출력을 안정적으로 검증했다.

## 6. 오류의 원인과 해결 방법

오늘 문제를 해결하면서 다음 확인 순서가 효과적이었다.

```text
1. 오류가 문법, 입력값, 환경설정, 콘솔 인코딩 중 어디에서 발생했는지 확인한다.
2. 실제 전달된 question 값을 None / 빈 문자열 / 공백으로 구분한다.
3. .env의 변수명이 코드에서 읽는 이름과 같은지 확인한다.
4. 블로그의 둥근 따옴표가 아니라 일반 ASCII 따옴표인지 확인한다.
5. 실제 API 없이 재현할 수 있으면 먼저 Mock과 unittest로 확인한다.
6. Windows 출력 문제라면 코드 로직과 콘솔 인코딩 문제를 구분한다.
7. 수정 후 같은 명령을 다시 실행하고 종료 코드와 테스트의 OK를 확인한다.
```

특히 API 관련 오류가 나더라도 Key나 SDK의 상세 오류 메시지를 그대로 출력하지 않도록 했다. 예외 종류만 보여 주면 민감정보 노출 위험을 줄이면서도 어떤 종류의 문제인지 확인할 수 있다.

## 7. 해보고 느낀 점

처음에는 AI 모델에 질문을 보내는 코드만 중요하다고 생각했다. 실제로 실습해 보니 모델 호출 전후의 입력 검증, 환경변수, 오류 처리, 테스트 구조가 훨씬 많은 부분을 차지했다.

Mock 모드는 실제 답변을 주지 않아 단순해 보였지만 매우 유용했다. API Key나 요금 문제와 분리해 Python 코드의 흐름부터 확인할 수 있었고, 자동 테스트도 실제 외부 API 없이 반복 실행할 수 있었다.

또한 “여러 번 질문할 수 있음”과 “이전 대화를 기억함”이 다르다는 점이 인상 깊었다. `chat_loop.py`는 반복문이 있지만 현재 질문 하나만 `ask()`에 전달한다. 앞으로 Context와 Memory를 배우면 이전 대화를 어떤 형식으로 저장하고 다시 전달하는지 확인하고 싶다.

나만의 질문을 작성하면서 질문이 구체적일수록 원하는 답변에 가까워질 가능성이 높다는 것도 느꼈다. 단순히 “학습 계획을 만들어 줘”라고 요청하는 것보다 대상, 기간, 핵심 개념, 실습 과제, 답변 형식을 함께 지정하면 결과를 평가하기 쉬워진다.

4. 역할, 대상 독자, 답변 길이와 출력 형식을 프롬프트에 명확히 넣어 본다.
5. 여러 질문 사이의 맥락을 유지하려면 어떤 Context 구조가 필요한지 학습한다.
6. 다음 Prompt & Context Engineering 수업에서 같은 질문의 프롬프트별 결과를 비교한다.
7. 이후 문서 검색과 RAG에서 임베딩 모델이 어떤 역할을 하는지 확인한다.

## 오늘의 핵심 정리

1. Mock은 실제 API 없이 입력·분기·출력과 오류 처리를 검증하는 방식이다.
2. Live 모드는 실제 Key, 모델 권한, 사용 한도와 결제 상태의 영향을 받는다.
3. API는 통신 규칙이고 SDK는 API를 Python에서 편하게 쓰도록 돕는 도구다.
4. 대화 모델과 임베딩 모델은 목적이 다르므로 설정도 분리한다.
5. `model_info.py`는 현재 OpenAI Key에 표시되는 모델 목록을 확인하기 위한 파일이다.
6. 출력 토큰 상한은 코드에 고정하지 않고 `.env`에서 읽도록 변경했다.
7. `main.py`는 한 번 질문하고 `chat_loop.py`는 질문을 반복해서 받는다.
8. 반복 질문 프로그램이 자동으로 이전 대화를 기억하는 것은 아니다.
9. 빈 질문은 `None`, 빈 문자열, 공백을 정리한 뒤 검사해야 한다.
10. PowerShell에서는 블로그의 둥근 따옴표 대신 일반 따옴표를 사용해야 한다.
11. Windows CP949 환경의 긴 대시 출력 문제를 일반 하이픈으로 바꿔 해결했다.
12. 자동 테스트 19개를 실제로 실행했고 모두 통과했다.
13. 자동 테스트는 실제 API를 호출하지 않아 별도 API 비용이 발생하지 않았다.
14. 개인 Live API와 실제 모델 목록 조회는 실행하지 않아 `NOT_VERIFIED`로 기록했다.
15. 나만의 학습 도우미 질문 세 개와 고정 답변 형식을 구체적으로 작성했다.
