## 1. 선행 일감과 작업 가능 범위 확인

T35~T40은 독립된 기능처럼 보이지만 기존 DB, 인증, 검색 API, 공통 UI에 의존한다. 따라서 구현 전에 각 작업지시서와 선행 일감 상태를 확인했다.

```text
T35 → T05, T06, T14, T15, T17
T36 → T20, T21, T23, T35
T37 → T05, T06, T14, T15, T16
T38 → T20, T21, T22, T37
T39 → T05, T06, T14, T15, T18
T40 → T20, T21, T24, T39
```

작업 관리 도구의 상태만 보고 선행 기능이 실제로 사용할 수 있다고 단정하면 안 된다. Redmine 상태, GitHub PR 병합 여부, 코드에 존재하는 API와 Schema를 함께 확인해야 한다.

선행 작업이 완전히 준비되지 않은 부분은 승인 없이 공용 Staging DB를 변경하지 않고 Mock 계약과 격리 환경을 사용했다. 이를 통해 가능한 범위는 먼저 구현하면서도 다른 작업자의 데이터나 공용 환경에는 영향을 주지 않았다.

오늘 정리한 원칙은 다음과 같다.

```text
담당 신청 ≠ 담당 확정
코드 작성 완료 ≠ 기능 검증 완료
PR 생성 ≠ PR 병합
Mock 통과 ≠ 실제 DB 연동 통과
```

## 2. T35 목표 직무 관리 API

사용자가 목표 직무를 추가하고 우선순위를 변경하거나 제거할 수 있는 API를 구현했다.

핵심 검증 항목은 다음과 같다.

- 존재하는 직무만 목표로 등록할 수 있는지
- 동일한 목표 직무의 중복 등록을 방지하는지
- 우선순위 변경 결과가 다시 조회했을 때 유지되는지
- 다른 사용자의 목표 직무를 수정하거나 삭제할 수 없는지
- 같은 요청을 반복했을 때 데이터가 비정상적으로 중복되지 않는지

Backend는 Router, Service, Repository의 책임을 분리하고 SQLAlchemy를 통해 PostgreSQL과 연결했다. Request와 Response 데이터는 Pydantic Schema로 검증했다.

```text
Router     → HTTP 요청·응답과 Status Code
Service    → 목표 개수, 중복, 우선순위, 소유권 규칙
Repository → SQLAlchemy Query와 CRUD
Pydantic   → 입력값과 응답 형식 검증
```

## 3. T36 목표 직무 선택 UI

Frontend에서는 목표 직무를 선택하고 저장 결과를 확인할 수 있는 화면을 구현했다. 초기에는 Mock 데이터로 화면과 상태 전환을 검증하고, Backend API가 준비된 뒤 실제 API Client와 연결했다.

화면에서만 값이 바뀌는 것으로 성공을 판단하지 않았다. 다음 순서로 확인했다.

```text
목표 직무 선택
→ 저장 요청
→ Backend API 처리
→ PostgreSQL 반영
→ 다시 조회
→ Browser 새로고침
→ 동일한 목표 직무가 표시되는지 확인
```

새로고침 후에도 값이 유지돼야 Client의 임시 State가 아니라 Server와 Database에 실제로 저장된 것으로 판단할 수 있다.

## 4. T37·T38 경력과 프로젝트 CRUD

개인 경력과 프로젝트의 생성·조회·수정·삭제 기능을 Backend API와 Frontend UI로 구현했다.

경력과 프로젝트 데이터는 사용자의 개인 정보이므로 소유권 검증이 중요하다. URL이나 ID를 변경해 다른 사용자의 데이터를 수정할 수 없어야 한다.

주요 검증 항목은 다음과 같다.

- 시작일과 종료일의 순서가 올바른지
- 필수값과 문자열 길이를 검증하는지
- 존재하지 않는 데이터에 적절한 오류를 반환하는지
- 본인 데이터만 수정·삭제할 수 있는지
- 생성 후 목록에 즉시 반영되는지
- Browser 새로고침 후에도 저장 결과가 유지되는지

Browser에서는 경력과 프로젝트를 각각 생성한 뒤 목록과 새로고침 결과를 확인했다. Backend Repository 테스트와 실제 화면 검증을 함께 수행하니 오류가 API 계층인지 UI State 처리인지 구분하기 쉬웠다.

## 5. T39·T40 채용공고 북마크

채용공고 북마크 API와 저장한 공고 화면을 구현했다.

북마크는 단순한 Create·Delete처럼 보이지만 동일한 저장 요청이 반복될 수 있으므로 멱등성이 중요하다.

```text
첫 번째 저장 요청 → 북마크 생성
동일한 저장 요청 → 중복 Row를 만들지 않음
목록 조회       → 현재 사용자의 북마크만 반환
해제 요청       → 해당 북마크 삭제
재조회          → 해제된 항목이 표시되지 않음
```

Frontend에서는 저장한 공고 목록이 표시되는지 확인하고, 북마크를 해제한 뒤 목록과 새로고침 결과가 일치하는지 검증했다.

## 6. Mock Test와 실제 PostgreSQL Test의 차이

초기 구현에서는 Mock Repository와 Mock API를 사용해 업무 규칙과 UI 동작을 빠르게 검증했다. Mock은 기능을 병렬로 개발할 수 있다는 장점이 있지만 실제 SQL, Transaction, Constraint, DB Driver 문제까지 보장하지는 않는다.

```text
Mock Test
→ Service 규칙과 Frontend 흐름을 빠르게 확인

Repository Test
→ SQLAlchemy Query와 Transaction 확인

PostgreSQL E2E
→ 실제 Table, Constraint, Commit, 재조회 확인

Browser E2E
→ 사용자 입력부터 DB 저장과 화면 재표시까지 확인
```

따라서 Mock만 통과한 상태는 `PARTIAL`이고, 실제 PostgreSQL과 Browser에서 전체 흐름을 확인한 뒤 `PASS`로 판단해야 한다.

## 7. 격리 PostgreSQL CRUD E2E

공용 Staging 데이터와 Schema를 변경하지 않기 위해 격리된 PostgreSQL 환경에서 CRUD E2E를 실행했다.

검증한 기능은 다음과 같다.

- 목표 직무 추가·순위 변경·삭제·재조회
- 경력 생성·조회·수정·삭제
- 프로젝트 생성·조회·수정·삭제
- 북마크 추가·중복 요청·목록 조회·해제

테스트가 끝난 뒤 임시 Server와 Test Data를 정리했다. 자동 테스트는 성공 여부뿐 아니라 반복 실행 가능성과 테스트 종료 후 정리까지 포함해야 한다.

실제 DB 검증에서 중요하게 본 Evidence는 다음과 같다.

```text
HTTP Status
→ Response JSON
→ SQLAlchemy Repository 결과
→ PostgreSQL 실제 Row
→ 재조회 결과
```

## 8. Browser 기능 테스트

실제 Browser에서 로그인한 뒤 다음 시나리오를 실행했다.

```text
1. 목표 직무 저장
2. 새로고침 후 저장값 유지 확인
3. 경력 생성
4. 새로고침 후 목록 유지 확인
5. 프로젝트 생성
6. 새로고침 후 목록 유지 확인
7. 저장한 채용공고 표시 확인
8. 북마크 삭제
9. 새로고침 후 삭제 상태 유지 확인
```

이 과정을 통해 API 단위 테스트만으로 확인하기 어려운 Frontend API Base URL, 인증 전달, 상태 갱신, 새로고침 후 재조회 문제까지 검증할 수 있었다.

|---|---|---|

리뷰 요청은 Reviewer를 반드시 GitHub에서 지정해야만 가능한 것은 아니다. Reviewer 지정 없이 PR을 만든 뒤 별도로 링크와 검토 요청을 전달할 수도 있다. 다만 PR 설명에 검증 방법과 결과를 충분히 남겨야 Reviewer가 빠르게 확인할 수 있다.

## 10. Redmine과 Spreadsheet 작업 관리

## 어려웠던 부분과 해결 방법

### 1. 선행 일감 상태와 실제 코드 상태가 달랐다

Redmine에는 일부 선행 일감이 `New` 또는 `In Progress`로 남아 있었지만 Spreadsheet와 GitHub에서는 완료 또는 병합된 작업도 있었다.

해결 방법:

- Redmine 상태 하나만 기준으로 삼지 않았다.
- GitHub PR 병합 여부와 `main`의 실제 코드를 확인했다.
- 준비되지 않은 부분은 Mock 계약과 격리 환경을 사용했다.
- 확인한 상태와 추정한 상태를 구분해 기록했다.

### 2. Mock 테스트 성공을 전체 기능 성공으로 판단하기 쉬웠다

Mock 환경에서는 정상이어도 실제 PostgreSQL의 Constraint나 Transaction에서 실패할 수 있다.

해결 방법:

- Mock Test, Repository Test, PostgreSQL E2E, Browser E2E를 구분했다.
- 실제 저장 후 재조회와 새로고침까지 확인했다.
- 공용 Staging 대신 격리 PostgreSQL을 사용했다.

### 3. Backend와 Frontend 여섯 개 일감의 증빙이 섞였다

여러 기능을 같은 PR에서 구현하면서 어떤 테스트가 어느 일감의 완료 기준을 증명하는지 구분하기 어려웠다.

해결 방법:

- T35~T40별로 목적과 완료 기준을 다시 확인했다.
- Backend는 API·Repository·PostgreSQL Evidence를 연결했다.
- Frontend는 실제 API 연동·Browser·새로고침 Evidence를 연결했다.
- Redmine 댓글도 일감별 검증 결과를 따로 작성했다.

### 4. 작업 완료 후 관리 도구 갱신이 남았다

코드가 병합되어도 Redmine과 Spreadsheet가 갱신되지 않으면 팀에서는 작업이 미완료로 보일 수 있다.

해결 방법:

- PR 병합과 테스트 결과를 최종 확인했다.
- Redmine 상태, 진척도, 댓글을 일감별로 갱신했다.
- Spreadsheet의 계정 정보, PR URL, Redmine URL, 비고를 함께 정리했다.
- 확인할 수 없는 작업시간은 기록하지 않았다.

## 해보고 느낀 점

오늘은 기능을 구현하는 것만큼 검증 범위를 단계적으로 넓히는 과정이 중요하다는 것을 느꼈다. Mock 테스트는 빠르고 편리하지만 실제 Database와 Browser까지 연결했을 때 생기는 문제를 모두 보여주지는 않는다. 단위 테스트에서 시작해 Repository, PostgreSQL, Browser 순으로 Evidence를 쌓으니 어디까지 확인됐는지 설명하기 쉬웠다.

SQLAlchemy와 Pydantic을 사용하는 이유도 더 분명해졌다. SQLAlchemy는 DB 접근과 Transaction을 구조화하고, Pydantic은 API 경계에서 입력과 응답의 Contract를 검증한다. 두 도구를 사용했다고 자동으로 안전한 API가 되는 것은 아니며 소유권, 중복, 멱등성 같은 업무 규칙은 Service에서 명확하게 처리해야 한다.

또한 개발 작업은 PR 병합으로 끝나지 않는다는 점을 배웠다. Reviewer가 확인할 수 있는 테스트 Evidence를 남기고, Redmine과 Spreadsheet의 상태까지 실제 결과와 일치시켜야 팀 전체가 다음 작업을 안전하게 시작할 수 있다.

무엇보다 공용 Staging 환경을 임의로 변경하지 않고 격리된 PostgreSQL에서 실제 CRUD를 검증한 점이 중요했다. 테스트의 신뢰성과 다른 작업자의 안전을 함께 지킬 수 있었다.
