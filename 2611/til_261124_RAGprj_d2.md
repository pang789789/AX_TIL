오늘은 Brother 공식 문서 4종을 사용하는 RAG 프로젝트의 Day-2 평가를 준비하고, 생성·API 담당자로서 답변의 근거 검증과 보류 판단을 다시 살펴봤다. 공개 DEV 10문항에서 좋은 결과가 나와도 공식 평가 문항에서는 비교 질문, 메뉴 경로, 모델별 사양 연결에서 다른 실패가 나타날 수 있다는 것을 배웠다.

운영 서버의 제출 기준 코드는 `8a5fac6`이고, 팀이 공유한 색인은 1,829청크, fingerprint `07cce650c928`이다. 현재 API는 단일 모델 질문에 C 재정렬을 쓰고, 비교·모델 미지정 질문에는 B Hybrid 순서를 유지한다. 오늘 공식 1차 결과는 Composite 82.24점이었다. 2차는 다른 Hidden Variant이므로 1차 문항을 다시 맞히는 것만으로 2차 점수를 예측할 수 없다.

내가 직접 확인한 것은 생성 코드의 과차단 경로, PR #47·#53의 코드와 테스트, 공식 설명서의 근거 문장이다. 팀원이 격리 서버에서 측정한 성능 수치는 별도로 구분했다. 비공개 평가 문항 원문이나 응답 전문은 이 TIL에 적지 않았다.

## 2. 핵심 개념과 실습 내용

### 검색 적중과 완전한 답변은 다르다

비교 질문에서 정답 **페이지**가 Top5에 있어도 두 모델에 필요한 메뉴 경로의 모든 청크가 생성기에 들어왔다고 볼 수 없다. 실제 1,829개 청크를 확인하니 한 모델의 메뉴 경로가 같은 PDF 쪽의 두 청크로 나뉘어 있고, 다른 모델의 경로는 별도 청크에 있었다. 따라서 단순 Hit@5 외에 질문한 모델과 항목의 근거가 모두 들어왔는지를 확인해야 한다.

PR #53은 비교 질문에 전달하는 청크 상한을 5개에서 8개로 넓히고, 본문과 적용 모델이 같은 중복 청크를 건너뛴다. 단일 모델의 상한은 5개 그대로다. PR 작성자가 공유한 격리 서버 재실행에서는 1차 30문항의 정답 추정이 22~23개에서 26~27개로 늘었지만, 한 비교 메뉴 질문은 여전히 보류됐다. 이 숫자는 공식 점수가 아니며 내가 독립적으로 E2E를 재현한 결과도 아니다.

### 과차단과 허위 답변을 함께 봐야 한다

`answer.py`는 답변의 모델, 수치, 인용 청크가 맞는지 검증한다. 오늘 코드에서 공식 항목명인 `스캔 불가능 영역`의 `불가능`을 기능 미지원 주장으로 해석할 수 있는 경로를 확인했다. 그러면 근거와 맞는 수치 답변도 검증에서 막혀 보류될 수 있다. PR #47 초안은 이 표현만 좁게 제외한다.

반대로 검증을 무턱대고 느슨하게 만들면 다른 모델의 사양을 빌려 쓴 허위 답변이 통과한다. 그래서 PR #47에는 `유선 Ethernet/이더넷` 주장도 해당 모델의 직접적인 유선 LAN 사양 근거가 있는지 확인하는 검사가 들어 있다. 그러나 PR #47은 아직 Draft이며 운영 서버에 배포되지 않았다. 단위 테스트 통과와 실제 점수 개선은 구분해야 한다.

### 공식 문서의 명시적 조건을 우선한다

팀의 1차 평가 분석에 ‘여러 팩스 수신 옵션을 함께 사용할 수 있다’는 취지의 답변이 있었다. 공식 설명서의 해당 절을 직접 확인하니 **메모리 수신 옵션은 한 번에 하나만 사용할 수 있다**고 명시되어 있었다. 다른 쪽의 PC-FAX 수신 중 메모리 저장·전송·백업 인쇄 설명은 여러 메모리 수신 옵션을 동시에 켤 수 있다는 근거가 아니다. 메뉴의 공존 여부를 판단할 때 관련 기능 설명만 모아 읽으면 조건을 놓칠 수 있다.

## 3. 코드와 실행 흐름

```text
/agent/invoke 질문
→ 질문의 모델 코드 추출
→ B Hybrid 또는 단일 모델 C 재정렬로 후보 최대 20개 검색
→ 생성 컨텍스트 청크 선택
→ gpt-6-luna가 답변 또는 INSUFFICIENT_EVIDENCE 생성
→ 인용 ID·적용 모델·수치와 항목·조건 검증
→ 필요하면 근거 검증 교정 재시도
→ answer/evidence/abstained/usage 형식으로 응답
```

현재 운영 버전에서 비교 질문도 생성기에 넘기는 근거는 기본 5개다. PR #53의 8개 확대는 **아직 제출 버전에 반영된 사실로 기록하지 않는다**. 근거 검증에 실패한 답은 200 보류로 바뀔 수 있지만, 이를 검색 실패, 처음부터 모델이 정보 부족으로 판단한 경우, 맞는 답을 검증기가 막은 경우와 구분해야 한다.

## 5. 어려웠던 부분과 잘 안됐던 점

첫째, 보류 결과만 보면 검색이 실패했는지 생성 모델이 처음부터 답을 포기했는지, 답을 만든 뒤 검증기가 막았는지 알 수 없었다. 팀의 요약 기록에는 문항별 최초 생성 문장과 교정 문장이 모두 남아 있지 않아 일부 원인은 확정하지 못했다.

둘째, 1차 문항을 재실행해서 좋아진 결과와 2차 공식 점수를 구분하기 어려웠다. 공식 공지는 1·2차에 다른 Hidden Variant가 배정된다고 한다. 1차 재실행은 회귀 검사에는 유용하지만, 거기에 맞춰 만든 수정이 다른 문항에서도 안전한지는 독립 문항으로 확인해야 한다.

셋째, 로컬 셸에서 `uv`를 바로 실행했을 때 `The term 'uv' is not recognized` 오류가 났다. 시스템 Python에서도 `No module named pytest`가 나왔다. 이미 설치된 별도 프로젝트 가상환경의 Python을 명시해 테스트를 실행했다.

## 6. 오류의 원인과 해결 방법

전체 테스트를 처음 실행했을 때 9개가 실패했다. 로컬 HTTP 테스트가 소켓을 열려다 `PermissionError: [WinError 10013]`을 받은 것이 원인이었다. 같은 PR #53 테스트를 로컬 소켓이 허용되는 환경에서 다시 실행하니 `674 passed, 45 skipped`였다. 이 실패를 애플리케이션 회귀로 기록하지 않았다.

스캔 여백 사례는 공식 항목명 `스캔 불가능 영역`과 기능 미지원 표현을 구분하도록 수정한 반례 테스트가 통과했다. 다만 운영 서버에서 같은 유형이 실제로 정답으로 바뀌었는지는 아직 확인하지 못했다.

다음에 같은 문제가 생기면 이 순서로 확인하겠다.

1. `/health`의 실행 커밋과 색인 fingerprint를 확인한다.
2. 검색 Top20 중 **각 모델·각 항목의 필수 청크**가 생성 컨텍스트에 들어갔는지 확인한다.
3. 최초 답이 정보 부족 표식인지, 근거 검증에서 거부된 답인지 로그로 구분한다.
4. 인용 청크의 적용 모델, 문장 안 조건, 수치·단위를 공식 PDF 행과 대조한다.
5. 수정 전후에 정답 통과와 틀린 모델·값 차단 반례를 함께 돌린다.
6. 전체 E2E, API 계약, 최대 지연, Preflight까지 확인한 뒤 제출 후보로 판단한다.

## 7. 해보고 느낀 점

높은 점수는 프롬프트 한 줄을 바꾸거나 검색 결과를 많이 넣는 것만으로 얻을 수 없었다. 정답이 검색됐는지, 필요한 근거가 모두 전달됐는지, 모델이 답을 썼는지, 검증이 그 답을 정확하게 판정했는지를 단계별로 나눠 봐야 했다. 특히 맞는 답을 살리려다 근거 없는 답을 통과시키면 더 큰 손실이 생기므로 두 방향의 반례가 함께 필요하다.
