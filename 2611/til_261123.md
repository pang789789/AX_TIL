## 1. 실습 환경과 폴더 구조

오늘 작업한 Brother RAG 프로젝트의 주요 구조는 다음과 같다.

```text
rag_project/
├─ data/
│  ├─ raw/                         # 공식 PDF 원본, Git에 올리지 않음
│  ├─ processed/
│  │  └─ chunks.jsonl             # 파싱·청킹 결과, Git에 올리지 않음

├─ src/
│  ├─ agent/
│  │  └─ answer.py                # 검색 결과 검증과 최종 답변 생성
│  ├─ retrieval/
│  │  ├─ base.py                  # retrieve(), get_chunks() 인터페이스
│  │  └─ runtime.py               # 색인 로딩과 warmup
│  ├─ api.py                      # /health, /agent/invoke Endpoint
```

내 담당은 생성·API 영역이다. 검색 모듈이 반환한 후보 중 상위 청크를 가져와 답변을 생성하고, 답변이 인용한 근거가 실제 검색 결과에 존재하는지 확인한 뒤 Runner 형식으로 반환한다.

## 2. 핵심 개념과 실습 내용

### 검색 성공과 답변 성공은 다르다

RAG는 검색 결과가 있다는 이유만으로 정답을 만들 수 없다. 검색 상위 5개 안에 정답 근거가 없으면 생성 모델이 다른 청크의 비슷한 표현을 이용해 틀린 답을 만들 수 있다.

```text
검색 성공: 질문과 비슷한 청크를 반환함
근거 성공: 정답을 직접 뒷받침하는 청크가 Top-K에 포함됨
생성 성공: 답변의 주장·수치·조건이 근거와 정확히 연결됨
```

실서버 평가에서 DEV-06은 관련 청크가 검색됐지만 정답 사양표가 10위에 있어 생성에 전달되지 않았다. 대신 `(유선 네트워크 모델의 경우)`라는 조건부 메뉴 설명을 보고 특정 모델이 유선 LAN을 지원한다고 잘못 판단했다. 이 사례로 검색의 유사성과 사실을 증명하는 근거는 다르다는 점을 확인했다.

### 정확한 출처 ID 검증

초기 구현에서는 답변 문자열에 청크 ID가 부분 문자열로 포함되어도 유효한 인용으로 처리될 위험이 있었다. 답변에서 `[chunk_id]` 형식을 정확히 추출한 뒤, 실제로 전달한 청크 ID 목록과 완전히 일치하는지 대조하도록 보완했다.

```text
허용: [MAN-LASER-CVL2508#p622#02]
차단: ID의 일부만 작성한 인용
차단: 검색 결과에 없던 청크 ID
차단: 정상 인용 한 줄 뒤에 근거 없는 결론을 추가한 답변
```

채점에는 앞 5개의 evidence가 사용되므로, 핵심 결론을 직접 뒷받침하는 근거부터 배치해야 한다.

### 모델 적용 범위와 비교 질문

여러 모델을 비교하는 질문은 한 모델의 근거만 확인해서는 안 된다. 각 답변 항목이 어떤 모델에 해당하는지와 인용 청크의 `applicable_models`를 함께 확인해야 한다.

```text
질문의 모델 추출
→ 각 모델에 대한 주장 분리
→ 인용 청크의 applicable_models 확인
→ 모델별 수치·조건과 근거 연결
```

다만 `applicable_models`는 문서의 모든 의미 조건을 완전히 표현하지 못한다. 오늘 확인한 `(유선 네트워크 모델의 경우)`처럼 본문 안에 글로 적힌 조건은 메타데이터에 반영되지 않을 수 있으므로 생성 프롬프트와 데이터 처리 양쪽에서 보완해야 한다.

### 정보 부족과 시스템 오류의 구분

검색 결과가 없거나 근거가 충분하지 않은 경우와 검색 시스템 자체가 실패한 경우를 같은 상태로 처리하면 안 된다.

| 상황 | 처리 원칙 |
|---|---|
| 정상 검색 후 근거 부족 | `abstained=true`, `evidence=[]` |
| 검색 모듈 실패 | `RetrievalError`, 검색 오류 상태 |
| 생성 호출 실패 | 생성 오류 상태 |
| 전체 요청 제한 초과 | 타임아웃 상태 |

정보 부족 응답은 `INSUFFICIENT_EVIDENCE` 계약으로 통일했다. 근거 부족은 정상적인 거부이고, 검색·생성 오류는 시스템 장애이므로 평가와 로그에서도 분리해야 한다.

### Usage 합산

최종 API 응답에는 생성 모델과 임베딩 모델, 입력·출력·전체 토큰을 포함해야 한다.

```text
total_tokens = input_tokens + output_tokens
```

C Re-ranking을 사용하면 재정렬 단계에서도 LLM을 호출하므로 재정렬 토큰과 최종 답변 생성 토큰을 합산해야 한다. 오늘 안정 제출은 B Hybrid를 사용해 추가 재정렬 호출을 제외했다.

## 3. 코드와 실행 흐름

### 서버 시작 흐름

서버를 시작할 때 색인이 없거나 청크 fingerprint가 다르면 요청을 받은 뒤 늦게 실패할 수 있다. 이를 방지하기 위해 시작 시 검색 runtime을 미리 준비한다.

```text
서버 시작
→ retrieval.runtime.warmup()
→ 색인과 manifest 검증
→ BM25·Chroma 로딩
→ /health 준비
→ /agent/invoke 요청 수신
```

색인이 없거나 손상됐으면 서버 시작 단계에서 실패하도록 구성했다.

### `/agent/invoke` 실행 흐름

```text
질문 수신
→ 질문에 포함된 모델 코드와 범위 확인
→ retrieve(question)로 B Hybrid 후보 검색
→ candidates의 ID 최대 20개 보존
→ get_chunks(ids[:5])로 상위 5개 원문 조회
→ gpt-6-luna에 질문과 근거 전달
→ [chunk_id] 인용 추출
→ 인용 ID·모델 범위·수치와 항목 연결 검증
→ answer, evidence, abstained, retrieved_chunk_ids, usage 반환
```

검색 오류가 발생하면 LLM을 호출하지 않고 검색 오류로 반환한다. 후보가 0개인 것은 시스템 오류가 아니라 근거 부족 가능성이므로 정상 보류 흐름으로 처리한다.

### 모델 호출 시 확인한 설정

`gpt-6-luna` 호출에는 `temperature=0`을 넣지 않았다. 실제 호출에서 다음 오류가 확인됐기 때문이다.

```text
400: Only the default (1) value is supported
```

따라서 `temperature` 인자를 생략하고 모델 기본값을 사용했다.

### 오늘 확인한 주요 명령

데이터와 색인을 준비할 때 팀 서버에서 사용한 흐름은 다음과 같다.

```powershell
python -m src.data.verify_sources
python -m src.data.parse_pdf
python -m src.data.chunk
python -m src.data.build_index
python -m src.data.build_index --check
```

Endpoint 상태 확인과 DEV 평가에는 다음 형태의 명령을 사용했다.

```powershell
python -m src.ops.check_endpoint <SERVER_URL>
python -m src.evaluation.run --endpoint <SERVER_URL>
```

실제 서버 DEV 결과는 Runner와 같은 60초 제한과 5xx 1회 재시도 규칙을 브라우저에서 재현해 수집했다. Python 평가 명령으로 수집한 결과라고 잘못 기록하지 않았다.

## 5. 어려웠던 부분과 잘 안됐던 점

### 검증기를 강화할수록 정상 답변도 차단될 수 있었다

근거 없는 숫자를 막기 위해 숫자 검증을 추가했지만, 단위가 숫자에 붙는 표기를 제대로 처리하지 못하면 올바른 답을 생성 오류로 바꿀 수 있었다.

```text
10.1kg  → 10만 검사할 위험
207.4mm → 207만 검사할 위험
920W    → 숫자를 찾지 못할 위험
```

또 `re.finditer()`의 부분 일치 때문에 근거가 `207.4 mm`인데 답변이 `20 mm`여도 숫자 `20`이 포함됐다고 잘못 통과할 가능성이 있었다. 보안 검증은 강할수록 무조건 좋은 것이 아니라 정상 답변과 오답을 모두 반례 테스트로 확인해야 했다.

### 청크 메타데이터만으로 본문 조건을 모두 표현할 수 없었다

DEV-06에서 사용된 설정표 청크에 HL-L2464DW가 붙은 것은 원문 모델 범위상 잘못된 태깅이 아니었다. 실제 문제는 `(유선 네트워크 모델의 경우)`라는 문장 내부 조건이었다. `applicable_models`가 맞더라도 해당 청크의 모든 기능이 그 모델에 지원된다고 해석할 수 없었다.

### 검색 실패와 생성 실패의 경계가 연결되어 있었다

DEV-01·02는 생성 모델이 답을 못한 것처럼 보였지만 먼저 정답 청크가 Top 5에 들어오지 않았다. DEV-06도 생성 검증 문제가 있었지만 정답 근거가 10위에 머문 검색 문제가 함께 있었다. 한 단계만 고치기보다 검색 로그와 API 응답을 함께 봐야 원인을 분리할 수 있었다.

### 제출 직전 수정의 위험

공개 DEV 세 문항을 바로 고치고 싶었지만 오늘은 첫 제출만 일별 점수에 반영된다. 이미 성공률 100%, 타임아웃 0, 계약 위반 0인 버전을 검증한 상태에서 검색·검증 코드를 바꾸면 재색인, 전체 테스트, 서버 재배포와 사전 테스트를 다시 해야 했다. 그래서 개선보다 안정적인 첫 제출을 우선했다.

## 6. 오류의 원인과 해결 방법

### `temperature=0` 호출 오류

```text
오류: 400, Only the default (1) value is supported
원인: gpt-6-luna가 temperature=0 설정을 지원하지 않음
해결: temperature 인자를 제거하고 기본값 사용
```

다음에 같은 모델 호출 오류가 발생하면 모델명, 허용 파라미터, 실제 응답 메시지를 먼저 확인하고 다른 모델의 설정을 그대로 복사하지 않는다.

### 숫자와 단위 검증 오류

원인은 숫자 정규식이 소수 전체와 붙여 쓴 단위를 하나의 값으로 처리하지 못하고 부분 문자열을 허용한 것이다.

다음 개선 PR에서는 아래 순서로 검증한다.

```text
1. 정수와 소수의 전체 범위를 추출한다.
2. 숫자 뒤에 붙은 단위를 허용한다.
3. 숫자 일부만 일치하는 경우를 차단한다.
4. 10.1kg와 10.1 kg를 같은 값으로 정규화한다.
5. 207.4mm 근거에 20mm 답변이 통과하지 않는지 확인한다.
6. 920W·280W·20mm 같은 정수+단위도 검사한다.
7. 정상 답변이 ANSWERED로 유지되는 회귀 테스트를 함께 실행한다.
```

이 보완은 다음 제출용 별도 PR에서 진행했고 오늘 안정 서버에는 적용하지 않았다.

### DEV-06 유선 LAN 오답

```text
표면 원인: 조건부 메뉴 문장을 모델 지원 근거로 사용
검색 원인: 정답 사양표 청크가 10위로 Top 5 밖
데이터 한계: 본문의 글로 적힌 조건이 모델 Metadata에 반영되지 않음
검증 한계: 인용 ID와 모델 범위는 맞지만 주장 의미까지 증명하지 못함
```

개선 방향은 지원 여부 질문에서 사양표를 우선하고, `~모델의 경우` 같은 조건부 문장을 직접적인 기능 지원 근거로 사용하지 않도록 프롬프트 규칙을 추가하는 것이다. 검색 쪽에서는 모델 코드를 제거한 질의와 재순위화를 별도 실험으로 비교해야 한다.

### Windows 로컬 포트 오류

```text
PermissionError: [WinError 10013]
```

다음에 같은 오류가 발생하면 아래 순서로 확인한다.

```text
1. 실패한 테스트가 로컬 HTTP 서버를 여는 테스트인지 확인한다.
2. 포트가 이미 사용 중인지 확인한다.
3. 방화벽·보안 정책·샌드박스의 포트 차단 여부를 확인한다.
4. 애플리케이션 로직 테스트와 네트워크 의존 테스트를 분리한다.
5. 네트워크 의존 테스트를 제외한 결과를 별도로 기록한다.
6. 실제 외부 Endpoint에서 같은 계약 검사를 다시 실행한다.
```

로컬 환경 제한을 코드 성공으로 바꾸어 기록하지 않고, 제외한 테스트 수와 실서버 검사 결과를 함께 남겼다.

## 7. 해보고 느낀 점

오늘은 RAG에서 가장 어려운 부분이 답변 문장을 자연스럽게 만드는 것이 아니라 근거가 정말 그 답을 증명하는지 확인하는 일이라는 점을 느꼈다. 청크 ID가 존재하고 모델 태그가 맞으며 숫자가 원문에 포함되어 있어도, 항목과 숫자의 관계나 조건부 표현을 잘못 읽으면 오답이 통과할 수 있었다.

자동 채점 결과도 그대로 믿을 수 없었다. DEV-06은 모델명만 포함돼 자동으로 정답 처리됐지만 실제 의미는 반대였다. Hit@5, Evidence Accuracy, Answer Accuracy를 따로 보고 마지막에는 사람이 답변과 원문을 읽어야 했다.

팀 작업에서는 데이터·검색·생성·평가를 병렬로 구현하더라도 최종적으로 하나의 질문이 전체 흐름을 통과하는지 확인해야 했다. 검색 담당의 순위 로그와 평가 담당의 문항별 결과가 있어야 생성 오류의 실제 원인을 찾을 수 있었다.

제출 직전에는 더 많은 기능보다 검증된 버전을 고정하는 판단도 중요했다. 오늘은 세 문항을 바로 고치지 못한 것이 아쉽지만, 첫 제출의 안정성을 지키고 다음 실험을 별도 PR로 분리한 것이 더 안전한 선택이었다.

## 오늘의 핵심 정리

1. RAG의 검색 성공, 근거 성공과 생성 성공은 서로 다른 단계다.
2. 검색 상위 5개에 정답 근거가 없으면 생성 모델은 정확히 답하기 어렵다.
3. 인용은 `[chunk_id]` 형식으로 정확히 추출하고 실제 검색 결과와 완전 일치시켜야 한다.
4. 여러 모델 비교 질문은 모델별 주장과 근거를 각각 검증해야 한다.
5. `applicable_models`가 맞아도 본문 속 조건까지 자동으로 보장하지는 않는다.
6. 정보 부족은 정상 거부이고 검색·생성 오류는 시스템 실패다.
7. 근거 부족 응답은 `abstained=true`, `evidence=[]`로 반환한다.
8. C Re-ranking을 사용하면 재정렬과 생성의 LLM 토큰을 합산해야 한다.
9. `gpt-6-luna`에는 `temperature=0`을 전달하지 않는다.
10. 숫자 검증은 소수, 붙여 쓴 단위와 부분 일치 반례를 함께 다뤄야 한다.
11. 자동 채점이 통과해도 답변 의미가 맞는지 사람이 확인해야 한다.
12. DEV-01·02·06 실패는 검색 순위와 생성 의미 검증이 함께 얽힌 문제였다.
13. 오늘 실서버는 10/10 HTTP 200, 타임아웃 0, 계약 위반 0이었다.
14. 사람 판정 Answer Accuracy는 70%, Evidence Accuracy는 71.4%, Hit@5는 5/8이었다.
15. 제출 직전에는 새 기능보다 검증된 코드·색인·서버 버전을 고정하는 것이 중요하다.
16. 확인하지 않은 개선 결과나 미배포 PR을 오늘 운영 성공으로 기록하면 안 된다.
