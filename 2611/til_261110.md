```text
→ Browser에서 화면 확인
```

아직 4강의 실제 `GET /members` 연동은 진행하지 않았다. 현재 회원 목록은 PostgreSQL 데이터가 아니라 Frontend 코드에 작성한 샘플 데이터다.

## 1. Phase 03에서 만들 서비스 이해하기

이번 과정의 최종 목표는 회원 목록, 검색, 등록, 수정, 삭제 기능이 있는 회원관리 웹서비스를 완성하는 것이다.

전체 구조는 다음과 같다.

```text
사용자 Browser
  ↓
React + Next.js + TypeScript
  ↓ HTTP 요청 / JSON 응답
FastAPI
  ↓ SQLAlchemy / SQL
PostgreSQL
```

이전에는 Swagger에서 API를 직접 실행했지만, 이제는 사용자가 버튼과 입력 폼을 이용해 같은 기능을 사용할 수 있도록 화면을 만든다.

오늘 이해한 역할은 다음과 같다.

| 기술 | 역할 |
|---|---|
| React | 화면을 Component 단위로 구성하고 변경된 부분을 갱신한다. |
| Next.js | React 프로젝트의 페이지와 실행 환경을 구성한다. |
| TypeScript | 회원 데이터의 필드와 타입을 미리 정해 실수를 줄인다. |
| FastAPI | Frontend 요청을 받고 회원 관련 로직을 처리한다. |
| PostgreSQL | 회원 데이터를 영구적으로 저장한다. |

## 2. Node.js와 Python 가상환경의 차이

수업을 시작하며 Phase 03 폴더에 Python `.venv`를 먼저 만들었다. 그러나 React와 Next.js 프로젝트는 Python 가상환경이 아니라 Node.js와 npm을 사용한다는 점을 알게 됐다.

```text
FastAPI Backend → Python, pip, .venv
Next.js Frontend → Node.js, npm, package.json, node_modules
```

터미널에 `(.venv)`가 표시된 상태에서도 `npm run dev`는 실행할 수 있지만, `.venv`가 Next.js를 실행해 주는 것은 아니다. 두 환경이 같은 프로젝트 안에 존재할 수는 있어도 담당하는 역할은 서로 다르다.

설치 상태는 다음 명령으로 확인했다.

```powershell
node -v
npm -v
git --version
```

버전 숫자가 강의안과 정확히 같을 필요는 없고, 각각의 명령이 정상적인 버전 문자열을 출력하는지가 중요하다.

## 3. Next.js 프로젝트 생성과 주요 파일

Phase 03 실습 폴더 아래에 `member-next-app`을 만들었다.

```text
practice/
└─ phase03/
   ├─ backend/
   └─ member-next-app/
```

Next.js 프로젝트에서 먼저 기억할 파일은 다음 세 가지다.

| 파일 | 역할 |
|---|---|
| `app/page.tsx` | `/` 주소에 표시되는 첫 화면 |
| `app/layout.tsx` | 여러 페이지에 공통으로 적용되는 바깥 구조 |

또한 `node_modules`에는 npm으로 설치된 수많은 라이브러리가 들어간다. 파일 수가 많아 보여도 정상이며 Git에 직접 올리는 폴더가 아니라는 점도 확인했다.

## 4. 첫 회원관리 화면 실행

`app/page.tsx`를 강의 코드로 교체하고 개발 서버를 실행했다.

```powershell
npm run dev
```

터미널에 표시된 주소로 접속해 다음 내용을 확인했다.

- `Phase 03 · Full-stack 실습`
- `회원관리 시스템`
- React + Next.js + TypeScript 안내 문구
- 앞으로 만들 기능 4개
- 현재 단계가 1강이라는 문구

터미널의 `GET / 200`은 Browser가 첫 페이지를 요청했고 Next.js가 정상적으로 응답했다는 뜻이다.

화면이 강의안과 다르게 어두운 배경으로 보였는데, 이는 브라우저나 운영체제의 다크 모드 설정 영향이었다. 내용과 기능이 같다면 오류가 아니다.

이 과정에서 가장 중요하게 느낀 점은 다음과 같다.

```text
page.tsx 수정
→ Ctrl+S 저장
→ 개발 서버가 변경 감지
→ Browser 화면 자동 반영
```

Backend 수업에서는 서버 로그와 Swagger를 주로 봤다면, Frontend에서는 코드 변경이 바로 시각적인 결과로 나타나는 점이 인상적이었다.

## 5. Phase 03용 Backend 준비

4강에서 Frontend와 API를 연결하기 위해 Phase 02의 Backend 코드를 `phase03/backend`로 복사했다.

```text
phase03/
├─ backend/
│  ├─ repositories/
│  ├─ routers/
│  ├─ services/
│  ├─ db.py
│  ├─ main.py
│  ├─ models.py
│  └─ schemas.py
├─ member-next-app/
└─ .env
```

복사 후에는 기존 폴더 구조를 전제로 작성된 경로가 새 위치와 맞는지 확인해야 했다.

### `.env` 경로 문제

`backend/db.py`에서 `.env` 위치를 계산할 때 `parents[n]`의 숫자가 실제 폴더 구조와 맞아야 한다.

```python
ENV_PATH = Path(__file__).resolve().parents[1] / ".env"
```

`db.py`가 `phase03/backend/db.py`에 있고 `.env`가 `phase03/.env`에 있으므로 한 단계 위인 `parents[1]`이 맞다.

```text
parents[0] → backend
parents[1] → phase03
parents[2] → practice
```

처음에는 기존 주석과 경로를 그대로 가져와 어느 `.env`를 읽는지 헷갈렸다. 파일 위치를 눈으로 따라가며 경로를 계산하니 문제를 이해할 수 있었다.

### `ModuleNotFoundError: No module named 'app'`

Backend를 실행했을 때 다음 오류가 발생했다.

```text
ModuleNotFoundError: No module named 'app'
```

원인은 기존 코드가 `app` 패키지 구조를 기준으로 import하고 있었는데, 새 폴더 이름은 `backend`였기 때문이다. 패키지 이름, import 경로, 서버를 실행하는 현재 위치가 서로 일치해야 한다.

정리한 원칙은 다음과 같다.

```text
폴더 이름: backend
import 시작점: backend
실행 위치: phase03
실행 대상: backend.main:app
```

경로를 맞춘 후 FastAPI가 `http://127.0.0.1:8000`에서 정상 실행되는 것을 확인했다. `/docs`와 `/openapi.json`은 `200 OK`였고, 별도로 만들지 않은 `/`와 `/favicon.ico`가 `404`인 것은 정상이다.

이번 오류를 통해 패키지를 설치했다고 해서 모든 import 오류가 해결되는 것은 아니라는 점을 배웠다. 폴더 구조와 Python 모듈 경로가 다르면 설치 상태가 정상이어도 `ModuleNotFoundError`가 발생한다.

## 6. Component로 화면 나누기

2강에서는 한 파일에 모든 화면을 작성하지 않고 회원 화면을 작은 Component로 분리했다.

```text
page.tsx
  └─ MemberList
       └─ MemberCard
```

각 Component의 책임은 다음과 같다.

| Component | 책임 |
|---|---|
| `page.tsx` | 샘플 회원 데이터를 준비하고 전체 페이지를 구성한다. |
| `MemberList` | 회원 배열을 받아 목록 전체와 회원 수를 표시한다. |
| `MemberCard` | 회원 한 명의 이름, 이메일, 나이, ID를 표시한다. |

`MemberList`에서는 `map()`으로 회원 배열을 반복한다.

```tsx
{members.map((member) => (
  <MemberCard
    key={member.member_id}
    member={member}
  />
))}
```

처음에는 파일을 여러 개로 나누면 오히려 더 복잡해 보였다. 하지만 회원 카드의 디자인을 수정할 때 `MemberCard`만 변경하면 되고, 목록 반복은 `MemberList`가 담당하므로 각 파일의 역할이 명확해진다는 장점이 있었다.

## 7. TypeScript로 Member 타입 정의하기

회원 데이터가 어떤 필드를 가지는지 `types/member.ts`에 정의했다.

```ts
export type Member = {
  member_id: number;
  name: string;
  email: string;
  age: number;
};
```

이 타입은 Frontend 코드끼리의 약속이면서, 앞으로 FastAPI가 반환할 JSON 구조와도 맞아야 한다.

```text
member_id → number
name      → string
email     → string
age       → number
```

TypeScript를 사용하면 `age`에 문자열을 넣거나 필수 필드를 빠뜨렸을 때 실행 전에 오류를 발견할 수 있다. 처음에는 Python의 타입 힌트와 비슷해 보였지만, 화면 Component가 받는 Props에도 같은 타입을 사용할 수 있다는 점이 새로웠다.

`import type`은 실행 시 필요한 값이 아니라 TypeScript 검사에만 사용하는 타입을 가져온다는 의미다.

```ts
import type { Member } from "../types/member";
```

## 8. Props로 데이터 전달하기

`MemberList`와 `MemberCard`는 필요한 데이터를 Props로 받는다.

```text
page.tsx의 sampleMembers
→ MemberList의 members
→ MemberCard의 member
```

Props는 부모 Component가 자식 Component에게 전달하는 값이다. 자식은 전달받은 데이터를 화면에 표시하며, 현재 단계에서는 직접 데이터를 수정하지 않는다.

`MemberListProps`는 `members`가 `Member[]` 형태여야 한다는 약속이다.

```ts
type MemberListProps = {
  members: Member[];
};
```

`MemberCard`의 `key`에는 배열에서 각 회원을 구분할 수 있는 `member_id`를 사용했다. `key`는 React가 어떤 항목이 추가되거나 변경됐는지 효율적으로 판단하는 데 사용한다.

## 9. 샘플 데이터와 실제 API 데이터 구분하기

오늘 화면에 표시할 회원은 `page.tsx`에 직접 작성한 샘플 데이터다.

```text
현재: sampleMembers → MemberList → MemberCard
4강: GET /members → React State → MemberList → MemberCard
```

샘플 회원 카드가 화면에 보이더라도 PostgreSQL 조회가 성공했다는 의미는 아니다. 실제 API 연결 여부를 확인하려면 4강에서 Browser Network의 요청 URL, 상태 코드, Response JSON을 확인해야 한다.

이 구분이 중요한 이유는 화면이 그럴듯하게 보인다고 전체 서비스가 연결된 것은 아니기 때문이다.

```text
샘플 화면 표시 성공 ≠ FastAPI 연결 성공
FastAPI 실행 성공 ≠ Frontend GET 요청 성공
API 응답 성공 ≠ PostgreSQL 데이터 저장 검증 완료
```

## 10. 어려웠던 부분과 해결 방법

### 1) Python `.venv`와 Node.js 환경이 혼동됐다

Phase 03 폴더에 `.venv`를 만들었기 때문에 React도 Python 가상환경에서 실행되는 것처럼 느껴졌다.

**해결 방법:** Backend와 Frontend의 실행 도구를 분리해서 정리했다.

```text
Backend  → python, pip, uvicorn
Frontend → node, npm, next
```

### 2) 강의가 4강 설명부터 시작되어 현재 진도를 헷갈렸다

처음에는 Network와 `GET /members` 흐름을 먼저 보았지만, 실제 진행은 1강부터였다.

**해결 방법:** 4강 이미지는 전체 흐름을 설명하는 예시로만 이해하고, 실제 작업은 1강 개발환경과 첫 화면부터 다시 순서대로 진행했다.

### 3) Backend를 복사한 뒤 import 오류가 발생했다

기존 `app` 구조를 `backend`로 옮겼지만 import 경로가 그대로 남아 `ModuleNotFoundError`가 발생했다.

**해결 방법:** 폴더 이름과 import 시작점, 실행 위치, Uvicorn 대상 경로를 하나의 기준으로 맞췄다.

### 4) 터미널의 404 로그가 오류처럼 보였다

FastAPI 실행 후 `/`와 `/favicon.ico` 요청이 `404`로 표시됐다.

**해결 방법:** 구현하지 않은 경로의 404는 정상이라는 것을 확인했다. 실제 확인 대상인 `/docs`와 `/openapi.json`의 `200 OK`를 기준으로 서버 상태를 판단했다.

### 5) Component와 Props가 처음에는 추상적으로 느껴졌다

한 화면을 여러 파일로 나누고 데이터를 계속 전달하는 이유가 바로 이해되지 않았다.

**해결 방법:** 식당이나 조립 부품처럼 역할을 나눠 생각하지 않고, 실제 데이터 흐름을 화살표로 적어 보았다.

```text
page.tsx → MemberList → MemberCard
```

이렇게 보니 부모가 데이터를 준비하고 자식이 표시한다는 구조가 조금 더 명확해졌다.

## 11. 오늘 느낀 점

React를 처음 배우기 전에는 Frontend가 HTML과 CSS를 작성하는 정도라고 생각했다. 오늘 실습을 통해 React 화면도 데이터 구조와 파일별 책임을 명확하게 나누는 작업이라는 것을 알게 됐다.

특히 Backend에서 Router, Service, Repository로 역할을 나눴던 것처럼 Frontend도 `page`, `MemberList`, `MemberCard`로 역할을 분리한다는 점이 연결되어 보였다. 사용하는 언어와 파일 형식은 달라도 복잡한 코드를 책임별로 나누는 원리는 비슷했다.

아직 `map`, Props, TypeScript 문법이 자연스럽지는 않다. 하지만 첫날부터 모든 문법을 외우려고 하기보다는 다음 질문에 답할 수 있는 정도를 목표로 삼는 것이 좋다고 느꼈다.

- 이 파일은 무엇을 담당하는가?
- 데이터는 어느 Component에서 어느 Component로 이동하는가?
- 화면의 데이터는 샘플인가, 실제 API 응답인가?
- 오류가 나면 Browser, Next.js, FastAPI 중 어디부터 확인해야 하는가?

오늘은 Next.js 첫 화면과 Component 구조를 만들고, Phase 03 Backend를 실행할 준비까지 마쳤다. 다음에는 샘플 회원 3명이 실제로 화면에 표시되는지 확인하고, 검색과 입력 Form에서 State와 Event가 어떻게 동작하는지 이어서 학습할 예정이다.

## 핵심 정리

```text
React       = 화면을 Component 단위로 구성하는 도구
Next.js     = React 프로젝트의 페이지와 실행 환경
TypeScript  = 데이터 타입과 코드 간 약속
Component   = 역할별로 분리한 재사용 가능한 화면 부품
Props       = 부모가 자식에게 전달하는 데이터
Member      = 회원 JSON 구조를 나타내는 TypeScript 타입
```

오늘의 데이터 흐름:

```text
sampleMembers
→ MemberList
→ MemberCard
```
