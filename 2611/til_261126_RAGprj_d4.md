## 오늘 학습한 내용

오늘은 Brother RAG 프로젝트 Day-4에서 답변 생성·검증을 개선했다. 목표는 정답과 인용을 유지하면서 불필요한 교정 호출과 입력 토큰을 줄이는 것이었다. 청크 ID로 복원할 수 있는 출처 정보의 중복을 줄이고, 동치 수치 표현과 원문에 근거한 계산을 검증하는 작업부터 시작했다.

실제 평가에서는 답과 근거를 올바르게 생성하고도 검증기가 정답 문장을 버리는 문제가 남았다. 원인은 크게 두 가지였다. **질문이 제공한 입력값까지 PDF에 있어야 한다고 검사한 것**, 그리고 **숫자와 단위의 띄어쓰기에 따라 검증 여부가 달라진 것**이다. 저장 응답 재생과 새 LLM 호출 평가를 구분하면서 수정했고, 최종적으로 PR #94를 통해 main `125b697`에 반영했다. 서버 재배포와 공식 점수 확인은 아직 완료한 일이 아니다.

## 2. 핵심 개념과 실습 내용

### 숫자의 출처를 먼저 구분하기

ADF 문서 길이를 계산할 때 PDF에는 최대 길이 `355.6mm`가 있지만, 사용하려는 문서의 길이 `300mm`는 질문이 준 조건이다. 답의 여유 `55.6mm`는 두 값의 차이다. 세 숫자가 모두 PDF에 있어야 한다는 규칙은 정답도 막는다.

그래서 문서의 사양값, 질문의 입력값, 둘로 계산한 결과를 구분했다. 단일 요청 모델과 명시적인 길이 입력을 확인하고, 인용된 ADF 길이 행의 모델 범위와 상한을 연결했다. `355.6 mm − 300 mm`뿐 아니라 단위를 일부 생략한 `355.6 − 300`도 피연산자가 맞는지 검사했다. 질문의 입력값을 제조사 상한이라고 바꾸거나, 다른 모델 행을 빌리거나, 계산 순서를 뒤집는 답은 허용하지 않았다.

급지 장수는 별도 각주에서 나온다. 문서가 특정 길이보다 길면 한 번에 한 페이지만 급지하라는 조건을 확인해 `1장` 표현을 처리했다. 사양 행과 각주를 함께 인용하면 문서·쪽·절·각주 번호를 대조하고, 각주를 직접 인용한 문장은 해당 모델의 명시적인 조건을 확인했다. 전체 원본 장수와 한 번에 넣을 수 있는 장수도 구분했다.

### 띄어쓰기로 숫자 검사가 달라지면 안 된다

USB 케이블 사례에서는 `1.5 m`는 숫자 검사에 걸려 차단되지만, `1.5m`는 미터 단위를 인식하지 못해 검사가 생략됐다. 붙여 쓴 답이 통과했다고 검증이 개선된 것으로 볼 수 없었다.

`m`을 수치·단위 인식 대상에 추가하고, 단일 요청 모델의 질문 입력 길이를 인용된 USB 케이블 상한과 비교했다. 두 표기를 동일하게 검사하며 잘못된 모델, 관계없는 케이블 근거, 바뀐 상한, 서로 충돌하는 상한, 상한을 넘는 케이블의 승인은 인증하지 않는다. 이번 경로는 상한을 넘는 케이블의 올바른 거절까지 새로 처리하는 일반 판정기는 아니며, 불확실한 경우에는 보수적으로 기존 검증에 맡기거나 차단한다.

### 계산은 맞아도 모델과 항목이 틀리면 오답이다

앞선 PR #89에서는 원문의 수량 곱셈을 모델별 값과 연결했다. 각 모델의 계산 결과와 두 값의 차이를 인정하면서도 모델별 값을 바꿔 쓴 답, 다른 항목의 숫자를 섞은 계산, 틀린 차이는 막았다. 팀의 #90 단회 평가에서 해당 자체 문항은 교정 없이 첫 답의 계산과 인용을 유지했다. 다만 #90에는 여러 담당자의 변경이 함께 들어 있으므로 전체 점수 상승을 내 수정 하나의 효과로 돌리지 않았다.

### API 장애와 정상 보류를 구분하기

선택적인 보류 재확인 호출에 429 또는 타임아웃을 주입했을 때, 장애가 정상적인 근거 부족 보류로 바뀌는 경로도 보완했다. 생성 장애와 타임아웃 상태를 보존하도록 했으며, 이는 실제 공급자 장애를 새로 겪었다는 뜻이 아니라 모의 오류로 확인한 결과다.

## 3. 코드와 실행 흐름


## 5. 어려웠던 부분과 잘 안됐던 점

처음 작성한 예문에는 질문 입력이라는 표현과 사양 행·각주 인용을 한 줄에 같이 넣었다. 실제 답변은 모델명을 생략하거나, 뺄셈 괄호 안에 입력값을 쓰거나, 급지 문장에 각주만 인용했다. 직접 만든 예문의 성공만으로 실제 응답도 해결됐다고 판단하기에는 범위가 좁았다.

첫 #91 실측에서도 계산·장수의 정답을 생성했는데 보류하거나 일부 문장만 남았다. 그 뒤 실제 초안을 받아 두 표현을 각각 테스트로 추가하고 수정했다. 또한 085는 이전 회차에서 답이 회복됐어도 붙여 쓴 단위의 검증 생략으로 통과한 경우가 있어, 점수만 보고 원인을 판단하면 안 됐다.

병합 과정에서도 실수가 있었다. #91의 base가 main이 아니라 #90 작업 브랜치인 상태로 병합했고, #90은 이미 main에 반영된 뒤였다. 그래서 #91이 merged라고 표시돼도 최신 수정은 main에 없었다. 최신 main에서 수정 커밋 세 개만 다시 적용하고, 파일 내용이 실측한 버전과 같은지 및 전체 회귀를 확인한 뒤 #94로 main 반영을 완료했다. 최종 main은 `125b697`이다.

전체 테스트는 처음 샌드박스의 로컬 소켓 제한 때문에 `PermissionError: [WinError 10013]`으로 멈췄다. 소켓 접근이 허용된 환경에서 다시 실행해 실패 0개를 확인했다. 이 환경 오류를 코드 실패로 확정하거나, 반대로 첫 시도를 전체 통과라고 기록하지 않았다.

## 6. 오류의 원인과 해결 방법

다음에 비슷한 문제가 생기면 아래 순서로 확인한다.

1. 평가 커밋, 실제 실행 커밋, Corpus fingerprint, 활성 옵션을 먼저 맞춘다.
2. 실제 생성 입력·최초 초안·교정문·최종 답변을 나란히 본다.
3. 답변이 틀린 것인지, 맞는 문장을 검증기가 버린 것인지 구분한다.
4. 숫자를 문서의 사양값·질문의 입력값·계산값·각주 번호로 분류한다.
5. 정답 통과와 잘못된 모델·숫자·단위·부등호 차단을 함께 테스트한다.
6. 저장 응답을 재생한 뒤 새 LLM 호출의 동일 조건 2회 결과를 확인한다.
7. Answer·Evidence·정상/부당 보류·교정 호출·API와 SDK 토큰을 함께 비교한다.
8. PR의 대상 브랜치와 병합 후 main의 실제 파일·커밋을 확인한다.
9. 서버 재배포 후 실행 커밋·Endpoint·Preflight를 확인하고 제출 여부를 결정한다.

검증 기준을 느슨하게 하기보다 숫자와 조건의 출처를 정확히 연결해야 한다. 교정 호출은 무조건 줄이는 대상이 아니라, 이미 맞는 최초 답변을 불필요하게 다시 생성하는 경로부터 줄이는 대상이다.

## 7. 해보고 느낀 점

오늘은 테스트 개수보다 **어떤 실패 표현을 실제로 포함했는지**가 중요하다는 것을 느꼈다. 같은 뜻의 문장이라도 입력값을 수식 안에 넣거나 인용을 문장마다 나누면 다른 검증 경로를 탄다. 정규식 하나를 바꿨을 때 정답 복구뿐 아니라 새 우회가 생기지 않는지도 봐야 했다.

또한 코드 수정, 저장 응답 재생, 새 LLM 평가, PR 병합, main 반영, 서버 배포를 같은 완료 상태로 말하면 혼란이 생긴다. 오늘 내 작업은 main 반영까지 완료했고, 운영 서버 재배포는 별도 담당 작업으로 남아 있다. 결과를 공유할 때 완료한 범위를 정확하게 말해야 한다.
